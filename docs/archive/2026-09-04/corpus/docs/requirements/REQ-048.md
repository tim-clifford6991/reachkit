# REQ-048 — Every opportunity states up front the test that would make it a success

- Priority: Must

## User story
As a paying customer, I want to be told before a page is written what would
count as it having worked, so that the verdict I get later is measured against a
promise made in advance rather than one written to fit the result.

## Rationale
A verdict is only trustworthy if its test predates the outcome, so every
opportunity carries, from the moment it is created, a success test the customer
can read in advance and that nothing may rewrite afterwards. Source: `BUILD.md`
§7 (every opportunity carries an acceptance test, in the forms "top 20 for Q",
"named on question P" or "gate passes").

## Acceptance criteria
1. Given an opportunity is created, when it is stored, then it carries an
   acceptance test in exactly one of three forms: the target reaching the top 20
   for a named search, the customer being named in the answer to a named
   question, or a named access barrier being cleared.
2. Given a page in the calendar, when the customer inspects it, then that test is
   shown as part of why the page exists.
3. Given a published page is later judged, when its verdict is produced, then it
   is judged against the test recorded when its opportunity was created, and that
   recorded test is never rewritten — including where it can no longer be
   evaluated.

## Non-goals
- A success test written or reworded by a language model after publication.
- Guaranteeing the test will pass.
- The verdict vocabulary and how a verdict is reported — REQ-063's.
- Per-customer tuning of what the tests may say.
