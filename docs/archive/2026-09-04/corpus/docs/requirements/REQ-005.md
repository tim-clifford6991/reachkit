# REQ-005 — What could not be measured says so; a measured zero stays a zero

> Superseded by REQ-004, which absorbed this requirement's acceptance criteria
> verbatim as its criteria 6–12 (2026-08-30; see
> `requirements/history/REQ-004-2026-08-30-requirement-cleanup.md`). Retired in
> place; cite REQ-004, not this file. The four-way partition — could-not-determine
> (criterion 6), read-and-found-none (criterion 7), storage (throughout), and
> never-attempted (criterion 9) — is intact and unreworded on the survivor.

- Priority: Must

## User story
As a founder reading a verdict about my own site, I want a failed measurement to
be admitted rather than shown as a bad result, so that I can trust every number
that is shown.

## Rationale
Every number a founder reads about their own site — and every number the product
stores about it — must trace to something we actually measured: an input whose
existence we could not determine has to be admitted as unmeasured, an input we
read that contained none of what we counted has to stay a zero wherever it is
shown or recorded, work the scan never got to has to say it was never taken, and
the three must never be shown as the same thing, because rendering an outage as
0 invents a customer fact and makes a false public accusation about someone's
site. This requirement is the single home for that rule, for display and for
storage alike. Source: `BUILD.md` §5 ("Empty denominators read 0, never null"; a
driver that could not be measured is null; "generic noindex on the home document
⇒ 0, and score ⇒ 0"), §4.1 States (degraded) and §2.5 (designed empty states).

## Acceptance criteria
1. Given an input whose existence the scan could not determine — it could not
   tell whether a gate or an input is there at all, because nothing was
   returned, the answer was unreadable, or a data source did not answer — when
   the report renders and the result is stored, then every driver depending on
   it is shown and recorded as "—", one written line names which driver was
   missing or, where no driver depended on that input, names what could not be
   measured, and the score is shown as "—" only where a driver it is composed of
   depended on that input. An input no driver depends on never withholds the
   score.
2. Given an input the scan did read that contained none of what was counted —
   including a site's access rules, read successfully, that gate nothing — when
   the report renders and the result is stored, then the value is shown as 0 with
   its denominator and recorded as a measured zero, never as "—", "unknown", a
   missing section, or a measurement that could not be taken. Access rules read
   successfully that do gate are a measured result too and are likewise never
   "—"; which count and which score each of the two cases produces is REQ-009
   criterion 3's and REQ-004's, not this requirement's. Reading is what divides
   this criterion from criterion 1.
3. Given a domain the scan measured successfully that appears in none of the
   searches measured and is cited in none of the AI answers that appeared, when
   its numbers are stored, then that absence is recorded as a measured zero,
   never as a measurement that could not be taken.
4. Given a measurement the scan never attempted because it stopped early — at
   the 90-second ceiling (REQ-003 criterion 5) or the free path's spend ceiling
   (REQ-015 criteria 6 and 8) — when the report renders and the result is
   stored, then everything depending
   on it is shown and recorded as "—", one written line states it was not
   measured because the scan stopped early, and it is never shown or recorded as
   0; the score is shown as "—" only where a driver it is composed of was among
   the work that was cut off.
5. Given a section whose data could not be retrieved, when the report renders,
   then that section is absent and one written line names the missing section
   and states that it could not be measured — never an empty card, a persistent
   spinner, or placeholder content.
6. Given a partially failed scan, when the report renders, then every part that
   was measured is shown in full and the report is otherwise usable.
7. Given a measurement this scan could not take — an input whose existence it
   could not determine (criterion 1) or work it never attempted (criterion 4) —
   when the report renders and the result is stored, then nothing stands in its
   place: no estimate, no interpolated value, no default, and no value carried
   over from an earlier scan of that domain. Every number the report shows and
   the product stores comes from the scan whose measurement date the report
   carries.

## Non-goals
- No estimated, interpolated, or last-known-good value substituted for a failed
  measurement — stated as criterion 7, not left to this list.
- Whether any of these written lines may be model-written rather than written by
  us: REQ-093 is the single home for that rule and it holds here unchanged.
- No hiding of the whole report because one part failed.
- What a read access rule makes of the blocked-readers count and of the score —
  REQ-009 and REQ-004 hold those; this requirement holds only whether the result
  is a measured value or a "—".
- The exhaustive classification of every scan outcome into one of these cases,
  and which driver each input feeds: the blueprint's, derived from this
  requirement's promise that an unmeasured input is never shown as a zero and a
  measured zero is never shown as unmeasured.
