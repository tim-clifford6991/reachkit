# BP-005 — Configuration and pinned constants

- Parent: BP-001 (executed inside every container)
- Kind: **component** — the single home for every number and every environment
  binding the product reads.

## Responsibility
Define once, and assert once, every pinned number in the specification and every
environment variable the product reads, so no coefficient, cap, floor,
denominator or threshold is ever written twice. Research on the DataForSEO
endpoints and pricing is in `registry/evidence/RESEARCH-dataforseo-endpoints.md`.

## Module / boundary
`src/lib/config/constants.ts` (values), `src/lib/config/env.ts` (bindings, parsed
and validated at boot), `tests/pins.test.ts` (assertions). Imported by every
other module; imports nothing.

## Error & edge behavior
- `env` throws at boot on a missing or malformed binding, so a deployment cannot
  start half-configured. **Decision 6 carries the only two qualifications, and
  neither is a default for a value:** `NANO_API_KEY` absent resolves to
  `ANTHROPIC_API_KEY` — another required member of this same schema, a
  credential the deployment has already supplied and this file has already
  validated, never a fabricated or hard-coded one — and `DATABASE_URL` is not in
  the schema at all, so its absence is not a boot condition there is anything to
  fail on. Every other binding keeps the no-default, no-fallback rule.
- Every constant is `as const` and frozen; nothing mutates a pin at runtime and
  no setting anywhere in the product overrides one (REQ-070 criterion 3).
- `tests/pins.test.ts` asserts each value against the source clause it was pinned
  from, by quotation, not by line number (rule 5.3).

## NFR budget
- Zero runtime cost; the module is data.
- The pins test runs in under a second and is the first check in CI, so a drifted
  constant fails before anything expensive runs.

## Decisions
1. **Grouped frozen objects, not loose exports** — Status: accepted
   - Context: `BUILD.md` §6.1 pins a price book and a dozen other numbers appear
     across §5 to §9; loose exports make "is this pinned?" unanswerable.
   - Decision: one named group per source section, each frozen, each with a
     matching assertion block in `tests/pins.test.ts` that quotes its source.
   - Alternatives considered: a JSON file read at boot — rejected, it loses the
     type and lets a value change without a test failing.
   - Consequences: adding a spend site means adding a price-book row before it
     ships, which is what the charter's cost envelope asks for.
2. **Band boundaries live here; band words do not** — Status: accepted
   - Context: REQ-047 criterion 10 and REQ-096 criterion 2 each state two counts
     and three bands. The counts are parameters (rule 1.1 — the system's); the
     words are customer-visible strings (the owner's).
   - Decision: `WINNABILITY` and `RIVAL_SIZE_BANDS` hold the counts here; the six
     words live in BP-019's `BAND_LABELS`, and `tests/pins.test.ts` asserts their
     disjointness. The reasoning spans four nodes and is **ADR-001**.
   - Alternatives considered: keeping the words here too — rejected, it would put

6. **The boot environment binds to the existing Vercel project `reachkit`, whose secrets are write-only** — Status: accepted (owner ruling relayed 2026-09-04; the three bindings below are parameters under rule 1.1, taken here and not escalated — internal names and a credential default, no promise moves)
   - **The standing fact.** The deployment target is the existing Vercel project
     `reachkit`. Its environment variables are **write-only**: they can be set
     and they cannot be read back. The corpus can therefore verify that a
     binding *name* is expected, never that a *value* is correct — and it cannot
     confirm that a rename it asked for actually landed on the platform. Two
     names the corpus already declares exist there today: `KILL_SWITCH` (false)
     and `HOSTED_EDGE_CNAME_TARGET` (`edge.reachkit.app`). This fact is the
     reason 6a resolves toward the platform's name rather than this corpus's,
     and it is why this node's only `rests-on` row is about a **name** being
     present — a claim a deploy settles — and never about a value, which nothing
     downstream could ever discharge by reading (rule 2.3b: a row nothing can
     observe is a row that stays `open` forever).
   - **6a. `SUPABASE_SERVICE_ROLE` is retired; the binding is `SUPABASE_SERVICE_ROLE_KEY`.**
     - Derivation: the Vercel project already holds the secret under
       `SUPABASE_SERVICE_ROLE_KEY`. Renaming it there is the one operation the
       write-only property makes unverifiable — a rename that silently did not
       land looks identical, from this corpus, to one that did, until a
       deployment fails to reach the database. Renaming *here* is verifiable by
       grep. So the corpus adapts to the deployment.
     - **One name end to end, not an alias** (rule 1.1 — the member name is
       internal, and this node chose it). The process-env key and the `Env`
       member are both `SUPABASE_SERVICE_ROLE_KEY`; every reader
       (`dbAdmin()`'s, and the server-only key set in this same file) moves with
       it. The alternative considered was keeping the member
       `SUPABASE_SERVICE_ROLE` and reading it from the platform's key — rejected
       because it is two names for one secret, one appearing nowhere on the
       platform and the other nowhere in the code, which is exactly the second
       copy this node exists to prevent (`structure.md` rule 5) and exactly the
       divergence the write-only property makes uncheckable. With one name,
       "does the deployment hold this?" is a comparison of two lists of strings.
     - Cost of reversing: a symbol rename — this file's schema row and its
       server-only key set, `dbAdmin()`'s one read, and the binding fixtures in
       the env, client and RLS tests. No value moves, no promise moves, and the
