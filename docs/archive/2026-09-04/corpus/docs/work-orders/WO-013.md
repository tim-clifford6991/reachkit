# WO-013 — Job platform choice, the job registry and serve()

- Branch: wo/WO-013-job-registry
- Estimate: ≤1 day

## Goal
Take BP-003's open platform question, then ship the closed registry and the one
`serve()` handler set BP-001's `/api/jobs` adapter mounts.

## Provenance of this file plan
**This repository holds no `src/`.** Every path is NEW, anchored to
`structure.md`'s row for `src/jobs/**` and to BP-003's `code:` globs.

## File plan
| File | New/Modify | Change |
|---|---|---|
| `src/jobs/client.ts` | NEW | The Inngest client, constructed from `env`. The one place the platform is named, so the reversal in `rests-on` stays one file. |
| `src/jobs/index.ts` | NEW | `serve()` and the `jobs` array — the registry. Imports each job definition and nothing else. An unregistered job cannot be triggered. The registry is closed over BP-003's **seven** `JobId`s — `BUILD.md` §11's six plus `account/maintenance` (BP-003 decision 1) — and WO-014 declares the union. |
| `src/jobs/observability.ts` | NEW | The one log line per invocation: job id, subject id, outcome, duration. A `degraded` outcome carries which step degraded and never a vendor payload. |
| `tests/jobs/registry.test.ts` | NEW | The tests below. |

## Steps
1. Write `client.ts` constructing the Inngest client from `env`, naming the
   platform in this one file (BP-003 decision 4: "the platform is named in
   exactly one file (`src/jobs/client.ts`) so the reversal stays one file and
   one route"). The choice is no longer this work order's to take — it is
   recorded — so nothing here re-derives it.
2. Write `observability.ts` with a field allow-list.
3. Write `index.ts` with an empty `jobs` array and `serve()` over it; WO-015 to
   WO-017 append their definitions, seven in total including
   `account/maintenance` (WO-017).
4. Write the tests; watch the "an unregistered job cannot be triggered" test fail
   first by serving a handler not in `jobs`.
