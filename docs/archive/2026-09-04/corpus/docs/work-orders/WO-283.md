# WO-283 — npm test is flaky again — the live-scratch-schema file set outgrew the db project's include list; make the two lists one

- Branch: wo/WO-283-live-db-project-membership
- Estimate: ≤1 day (one file, one list)

## Goal
Make `npm test` repeatably green by enumerating every test file that resets
the one live scratch schema in a single declared list that `vitest.config.ts`'s
`db` project includes and its `node` project excludes, so the membership of
the serialized boundary WO-275 established can no longer drift as new live-DB
test files are added.

**Risk: normal.** Test configuration only — one declared file list that `vitest.config.ts`'s `db` project includes and its `node` project excludes. It changes no product behaviour, ships nothing to a customer and touches no seam the charter names (doctrine 0.13.2, rule 2b).

## Why this runs first in W3
Three of W3's orders are unvalidated and two more are mid-build. A validation
report, a regression record and a `done` verdict all rest on `npm test`'s
result, and `npm test` is red on a varying set of files today — so every
verdict taken while it stays flaky is a verdict whose evidence cannot be
distinguished from noise. TST-025 has already spent one pass chasing a
transient `db` failure. This order is one file and no product behaviour; it
goes ahead of the orders still to be validated so their evidence means
something.

## Provenance of this file plan
`vitest.config.ts` exists and is BP-001's (`code:` glob `vitest.config.ts`;
`structure.md`'s root-toolchain row, BP-001 decision 2). The file is MODIFY,
not NEW. The defect and its confirmation are WO-276's implementer's, recorded
on that order's `## Log` under constitution rule 4.2 and quoted in
`## Test plan` below — it is not re-derived here. Read directly on
`doctrine-0.11.0` at cut time: `db.include` names four files
(`tests/db/baseline.test.ts`, `tests/db/rls.test.ts`,
`tests/db/clients.test.ts`, `tests/scan/free/admission-claim.test.ts`) and
`node.exclude` names the same four; `tests/scan/free/schema.test.ts` and
`tests/account/columns.test.ts` each run
`"drop schema public cascade; create schema public; …"` and are in neither
list, so they race each other and the four under `node`'s default
concurrency. `tests/scan/free/admission-check.test.ts` was checked and stays
in `node`: it mocks `@/lib/db` (`vi.mock("@/lib/db", …)`) and opens no
connection.

established on the `db` project.

list already names every project this order touches.

## Steps
1. Watch it fail first (constitution §8): run `npm test` ten times against the
   config as it stands and record the pass/fail counts and the differing
   failure sets.
2. Make the change in `vitest.config.ts`.
3. Run `npm test` ten consecutive times; record every run's counts.
4. Attribution probe: show that only the files on the declared list serialize
   and that `ui`, `layout` and the rest of `node` still schedule concurrently
   — a fix whose evidence is only "green now" is indistinguishable from
   blanket serialization.
5. Revert the change alone, reproduce the varying-failure pattern, restore it,
   return to green.

## Out of scope
- Any test file's own contents. No test is rewritten, skipped or deleted; the
  coupling being fixed is which project a file runs in, not what it asserts.
- The scratch substrate itself, and any change to how a test acquires it.
- WO-276's two `tests/costs/*.test.ts` files. They are named on the declared
  list so the boundary is right the moment they land, but they arrive with
  WO-276 and this order neither waits for them nor creates them; a listed
  path that matches no file is not an error, and the ten runs of step 3 are
  measured against whatever `doctrine-0.11.0` holds at implementation time.
- Making the list derive itself from the test files (a marker, a glob, a
  naming convention). Considered and not taken: the set is eight explicit
  paths and a convention would be a second thing to get wrong. Reversal cost
  if it grows past that: this one file.

`db` project and `npm test` returns to being flaky — no product behaviour and
no test assertion moves either way.
