# WO-278 — The presentation boundary for a measured value — handles become terms, values become a dash or a number, and a number reaches a sentence only with its scan date

- Branch: wo/WO-278-presentation-boundary
- Estimate: ≤1 day

## Goal
Ship the one door every measurement passes through on its way to a person: the three total handle→`CopyKey` maps, `renderMeasured()` in which rendering an unmeasured value as a number does not type-check and dashing a measured zero cannot be written as a local edit, and `explain()` in which a number reaches a product sentence only as a `Measured<T>` whose scan date travels with it.

**Risk: normal.** This order touches no seam the charter names: it renders WO-277's arms and moves no money, reads no session, calls no vendor and publishes nothing. Its own fabrication guard is discharged by the typechecker rather than by a runtime mutation (TST-027 measured `expectTypeOf` as a runtime no-op under `vitest run`), and the arms it renders are mutation-tested upstream at `risk: high` on WO-277. Plain criterion tests (doctrine 0.13.2, rule 2b).

## Consolidation (rule 2.6)
Three one-file orders inside one module, all three the same claim at three
levels — a handle becomes a term, a value becomes a dash or a number, a sentence
carries the date of the numbers in it. WO-042's goal is stated over
`renderMeasured` (WO-249's) and WO-249's `## Out of scope` hands `explain()` back
to WO-042; WO-248's `SCORE_BANDS` and WO-249's `renderMeasured` are read by the
same call site in the same line of the same strip. Cut along files inside one
directory is the horizontal cut rule 2.6 forbids. One order: the presentation
boundary for a measured value.

**Direction of the score-band edge, corrected here (rule 1.1).** WO-054 (now
WO-277) carried `depends-on: WO-248` (now this order) while WO-248's
`SCORE_BANDS` is `Record<BandHandle, CopyKey>` over WO-054's own `BandHandle` —
a cycle between the two merged orders. The engine declares the handles and the presentation
boundary maps them, so the edge runs WO-277 → WO-278 and not back. Cost of
reversing: one line of `depends-on`.

13. Implement the function as **exactly two branches** — this shape, and not a
   three-arm switch:

   ```ts
   if (m.kind === 'unmeasured') {
     return { text: copy(DASH_KEY), isDash: true, line: copy(o.unmeasuredLine) }
   }
   return { text: o.format(m.value), isDash: false }
   ```

   The two branches are the whole mechanism, and each closes one of the two
   collapses REQ-004 exists to prevent:

   **(a) An unmeasured value cannot become a number.** Inside the guard, `m`
   narrows to the `unmeasured` arm, which carries **no `value` field**. `o.format`
   is the only path from a `T` to a string, `T` is unconstrained, has no default
   and no witness anywhere in scope, and the arm supplies none. So there is no
   expression an implementer could write on that branch that produces `format`'s
   output — "render an outage as 0" is uninhabited, not merely wrong. The
   `@ts-expect-error` fixture in the test plan is the proof, and it is the reason
   this WO does not add a runtime assertion for the same thing: a runtime check
   would be a weaker copy of a compile error (rule 2.4).

   **(b) A measured zero cannot be dashed by a local edit.** The fall-through is
   **one** branch covering `measured` and `zero` together, reached by narrowing
   *by exclusion* — the literal `'zero'` never appears in the file. There is
   therefore no `zero` branch to edit. The only mutation that dashes a zero is
   moving `'zero'` into the guard, which dashes every measured value in the
   product at the same time and fails every case in every consuming suite at
   once. A three-arm `switch (m.kind)` would put a one-line `zero` case in the
   file that a hurried edit could turn into a dash and that nothing but a test
   would catch — which is exactly the "tested for" that BP-019's `## Error & edge
   behavior` says this must not be.
14. Declare `DASH_KEY` as a module-private `const DASH_KEY = 'unmeasured.dash'
   satisfies CopyKey`. It is not exported: a second reader of the dash key is a
   second place a dash can be produced.
15. Set `line` on the unmeasured branch only, and never on the other. `isDash` is
   computed by neither argument nor option — it is the branch. No parameter of
   any kind can set it, which is what makes `isDash === (m.kind ===
   'unmeasured')` a property rather than a convention.
16. Call `o.format` exactly once, with `m.value` and no second argument, no
   fallback and no coercion. `m.at` is read nowhere: the scan date travels with
   the sentence through WO-042's `explain()`, not through this return, and
   reading it here would mint a second date path (rule 2.4).
17. Export `renderMeasured` and nothing else.

`ScoreFactorName` and needs no fourth entry. Cost of reversing: one exported
constant, three key declarations, and the one call site in WO-282.

**No copy is asked for and none is invented.** The three keys ship empty and
owner-owed; `copy()` throws naming the key rather than rendering a blank
(WO-041's chosen representation), and every test below asserts the key reached,
