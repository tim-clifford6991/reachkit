# WO-276 — The fetch ledger and the cost context — one insert-only row, cache-first, cap-degrades

- Branch: wo/WO-276-cost-context
- Estimate: ≤1 day

## Goal
Ship BP-007's spend seam whole: the one insert-only `fetches` row that is at once ledger, cache and raw store, and the per-scan context that reads it cache-first, ledgers every call that reached a vendor, and returns a value at the cap instead of throwing.

> **Read `decisions/ADR-094.md` before writing a line of this WO.** The
> reserve/settle split and the second-spender mechanics are that decision's and
> BP-028's, not this order's to re-derive.

**Risk: high — seam: money.** This order is the cost seam itself: reserve, settle, clamp and cap-degrade against the spend envelope the charter pins (`00-project.md` § Cost envelope, "Enforced in the seam, not assumed. Caps are hard") and the lean-data law's "every call goes through the cost seam, reads cache first". A cap test that survives deletion of the cap costs real money and shows nothing on any screen, so this order's criteria are mutation-tested (doctrine 0.13.2, rule 2b).

## Consolidation (rule 2.6)
WO-021 created the `fetches` table; WO-022 created the only reader and the only
writer of it. Neither could state its stop condition without the other — WO-022's
goal is "reads cache first, ledgers what was spent", which is a claim about
WO-021's row, and WO-021's own `## Provenance` already folded `reserved_cents`
across the seam under rule 2.6 on 2026-09-03 with the note that "both files sit
under the same `*_fetches*.sql` glob, so no module boundary is crossed". They are
one capability from schema to test: what a call costs, where that is written
down, and what happens at the cap.

### From WO-022

Exposes (verbatim from BP-007 `## Public interface`):
```ts
export type CapName = 'FREE' | 'DEEP' | 'WEEKLY' | 'DRAFT'

export function withCostContext<T>(
  ctx: { scanId: string; cap: CapName; policyVersion: number },
  body: (cost: CostContext) => Promise<T>
): Promise<T>

export interface CostContext {
  /** Cache-first, ledger-always. `fresh` false means the payload came from cache
   *  and cost nothing. An empty payload is always a miss; there is no negative
   *  cache. */
  recordFetch<P>(call: {
    source: string           // vendor endpoint or model id
    cacheKey: string
    freshnessDays: number
    /** The **reservation**: the most this call can cost, known before it runs.
     *  The cap is checked against this, so no call is made against money the
     *  context has not got. */
    costCents: number
    /** Optional **settlement** (ADR-094 decision 3a). Where a vendor's own
     *  documented rule makes the final charge a function of the response, the
     *  call site supplies it and the ledger records the settled figure instead
     *  of the reservation. `settled <= reserved` is enforced here, not trusted:
     *  a closure returning more is clamped to the reservation and logged, since
     *  the excess would be money the cap never authorised. One call site uses
     *  it today — BP-008's flagged `serpOrganic`. Omitting it is the ordinary
     *  case and behaves exactly as before this argument existed. */
    settleCents?: (payload: P) => number
    run: () => Promise<P>
  }): Promise<{ payload: P; fresh: boolean; costCents: number } | { skipped: 'cap' }>
  // The returned `costCents` is the settled figure where one was supplied, the
  // reservation otherwise — one number, and it is the one the row carries.

  capHit(): boolean          // re-checked between calls in any multi-call step
  spentCents(): number
  degraded(): boolean
}
```
Consumes: `db()`/`dbAdmin()` (BP-002), `CAPS` and `CACHE_WINDOWS_D` (BP-005).

  BP-012/BP-023's admission control, which decides not to open a context. This
  work order opens the context it is given.

  supplies; BP-008's flagged `serpOrganic` is the one that supplies it today (ADR-094

  carries no endpoint-specific branch.

  writes and reads rows; it declares no column.
