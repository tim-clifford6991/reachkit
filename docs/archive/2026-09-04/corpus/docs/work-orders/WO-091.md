# WO-091 — pendingChanges, effectiveOn and generationHold — pending is a computation, not a state

- Branch: wo/WO-091-pending
- Estimate: ≤1 day

## Goal
Implement `src/lib/market/changes/pending.ts` so a pending change is computed as the difference
between the declared and measured answers, the effective date is the first weekly
re-measurement that begins after the save in the customer's own time zone, and generation is
held by a domain or category change and by nothing else.

## Context an implementer needs
No source code exists on disk; both paths below are NEW.

**Read `sdlc-factory/docs/decisions/ADR-030.md` before writing a line of this file.** It is the
decision this module *is*: "There is no pending-change record. A save writes the declared answer
immediately, and a pending change is computed as the difference between the declared answers on
`sites` and the measured answers on the current scan." Consequently: "The moment the pass
completes, the new scan is current, `measured` equals `declared`, and `pendingChanges` returns
`[]`. The pending state clears itself with no transition to run and no row to delete." Pending
is not a state, so it cannot get stuck, be applied twice, or survive the pass that resolves it.

**Nothing between save and pass moves** (BP-056's `## Error & edge behavior`): every number on
screen comes from the last completed scan and carries its date, so criterion 10 holds without a
freeze mechanism — there is nothing to freeze, and this WO builds no freeze.

## Interfaces
**Consumes**: `ChangeKind`, `DeclaredAnswers`, `MeasuredAnswers` from `./declared` (WO-089), and
the weekly schedule constants BP-005 holds for REQ-065 (`WEEKLY_DUE_HOUR_LOCAL`).

**Exposes** — copied exactly from BP-056's `## Public interface`, comments included because they
are the specification:

```ts
// src/lib/market/changes/pending.ts
export interface PendingChange { kind: ChangeKind; declared: string; measured: string; effectiveOn: Date }
export function pendingChanges(a: {
  declared: DeclaredAnswers; measured: MeasuredAnswers | null; now: Date; timezone: string
}): PendingChange[]
/** The first weekly re-measurement that begins after `savedAt` (REQ-065 criterion 1:
 *  Monday, in the customer's own stated time zone). */
export function effectiveOn(a: { savedAt: Date; timezone: string }): Date
export function generationHold(pending: PendingChange[]):
  | { held: false }
  | { held: true; because: 'domain' | 'category'; resumesOn: Date }
```

## Steps
1. `effectiveOn({ savedAt, timezone })` returns the next weekly re-measurement boundary strictly
   after `savedAt`, computed in `timezone` — Monday at the pinned local hour. It reads the
   schedule from BP-005/REQ-065 rather than restating it; the hour is not a literal here.
2. `pendingChanges`: `measured === null` ⇒ return `[]`. A customer who has changed something
   before their first pass is not shown a change marker against a measurement that does not
   exist. Otherwise emit one entry per differing answer:
   - `domain`: `declared.domain !== measured.domain`.
   - `category`: `declared.category !== measured.category`.
   - `rivals`: the set of `declared.rivals.map(r => r.domain)` differs from `measured.rivals`
     as a set — order is not a change. `declared` and `measured` on the entry are rendered as
     stable, sorted, comma-joined domain strings, since `PendingChange` types both as `string`.
   Each entry carries `effectiveOn({ savedAt: now, timezone })` — the next pass boundary.
3. `generationHold(pending)`: held when a `domain` or a `category` entry is present, `because`
   naming which (`domain` takes precedence when both are pending, since the domain change
   re-keys the category's own measurement), `resumesOn` that entry's `effectiveOn`. A `rivals`
   change **never** holds generation. Returning the reason is what lets the surface avoid
   showing the empty-pipeline line in its place.
4. Every function is pure: no db, no clock read, no I/O. `now` and `timezone` are arguments.
5. Emit no state of its own; BP-056's observability for saves is WO-090's.
6. Write the tests; watch each fail first.

First-pass path: `pending/null-measured-returns-empty` — `measured: null` returns `[]` for any
declared answers, and `generationHold([])` is `{ held: false }`.

No-pending-record guard, from **ADR-030**: `pending/is-a-computation` — the module exports no
function that writes, resolves no import into `src/lib/db/`, and this WO's diff adds no file
under `supabase/migrations/` and no column matching `/pending/i`.

Discrimination: letting a `rivals` change hold generation, treating a reordered rival set as a
change, returning the current boundary for a save at the boundary instant, or computing
`effectiveOn` in UTC rather than the supplied zone, must each fail a named test above.
