# WO-084 — The setup card's state machine — which market renders, what a domain change clears, what must be true to submit

- Branch: wo/WO-084-setup-state
- Estimate: ≤1 day

## Goal
Implement the pure half of `src/lib/market/setup/index.ts` — the market card's three states,
the domain-change rule that re-keys everything derived and keeps everything typed, and the
one condition that blocks submit.

## Context an implementer needs
No source code exists on disk; both paths below are NEW.

**The current report is supplied to this node, never fetched by it** (BP-034 decision 4):
`ReportFacts` is deliberately not BP-012's `StoredReport`, because importing it — even
type-only — would close a `src/lib/market ↔ src/lib/scan` cycle that `structure.md` rule 6
makes a build failure. The `/setup` route adapter reads the report through BP-012 and hands
it in.

**This is a cycle decision, not a shape one, and it is now unambiguous.** `StoredReport` is
declared: BP-012 decision 3 (accepted 2026-08-31) puts its full shape in that node's
`## Public interface`, so an implementer who reaches for it will find a real, sufficient type
carrying `scanId`, `category` and every other field this node's three could be projected from.
The refusal is unchanged and is not about the type being unavailable or the wrong shape — it
is about the **import edge**. BP-034 decision 4, verbatim: "Calling `readCurrentReport()` from
here would close that cycle; so would a type-only import of `StoredReport`." So:

- `src/lib/market/setup/index.ts` declares its own three-field `ReportFacts` and imports
  nothing from `src/lib/scan/`, type-only imports included. `state/no-scan-import` below is
  the assertion, and it is now the *only* thing standing between this module and a compiling
  shortcut that reads as a tidy-up.
- The three fields are a deliberate **projection** of `StoredReport`, not a rival definition
  of it: `scanId` and `category` are the same facts under the same names, and `rivals` is the
  domain list. Widening `ReportFacts` toward `StoredReport` field by field is the same
  mistake taken slowly; if this node ever needs a fourth fact, the adapter passes a fourth
  field, and BP-034 is where that is decided.
- BP-028's `src/lib/market/coherence/offer.ts` declares a **different** interface, also named
  `ReportFacts`, for the same reason and with different fields. The two are separate modules
  and neither imports the other; do not merge them into one shared type, which would create
  the cross-leaf coupling both decisions exist to avoid.

**What decides confirm-versus-state is whether a completed report exists for the address the
account will use**, never how the purchase was made (BP-034's `## Error & edge behavior`,
the same key REQ-021 criterion 11 turns on).

**This WO creates `src/lib/market/setup/index.ts`; WO-085 modifies the same file.** The two
are sequenced by `depends-on` and must never run in parallel.

```ts
// src/lib/market/setup/index.ts
export type MarketCard =
  | { state: 'inferred'; category: string; fromScanId: string }
  | { state: 'empty' }
  | { state: 'stated'; category: string }
export type SuggestionState = 'awaiting_market' | 'seeking' | 'none_found' | 'offered'

/** What this node needs from the current stored report, supplied by the caller.
 *  Deliberately not `StoredReport`: importing BP-012's type would close a
 *  src/lib/market ↔ src/lib/scan cycle (Decisions 4). */
export interface ReportFacts { scanId: string; category: string | null; rivals: readonly string[] }

export interface SetupState {
  siteDomain: string | null
  market: MarketCard
  suggestions: { state: SuggestionState; candidates: readonly string[] }
  rivals: RivalSet
}

export function marketCardFor(a: { siteDomain: string; report: ReportFacts | null }): MarketCard
export function onDomainChanged(s: SetupState, a: { domain: string; report: ReportFacts | null }): SetupState
export function onMarketStated(s: SetupState, category: string): SetupState
export function validateSetup(s: SetupState): { ok: true } | { ok: false; because: 'market_missing' }
```

## Steps
1. `marketCardFor`: a non-null `report` whose `category` is non-null ⇒
   `{ state: 'inferred', category, fromScanId: report.scanId }`. A null report, or a report
   whose `category` is null, ⇒ `{ state: 'empty' }`. Nothing is pre-filled and nothing is
   labelled inferred or measured on the empty arm.
2. `onMarketStated(s, category)` ⇒ `{ ...s, market: { state: 'stated', category } }` and sets
   `suggestions.state` to `'seeking'` with `candidates: []` — the transition out of
   `'awaiting_market'`. Fetching the candidates is WO-085's; this function performs no I/O.
3. `onDomainChanged(s, { domain, report })`:
   - `siteDomain` becomes `domain`.
   - an `inferred` market is **cleared and re-derived** by calling `marketCardFor` for the new
     address; a `stated` market is **kept exactly as left**; an `empty` one re-runs
     `marketCardFor` too.
   - `rivals` becomes `clearSuggested(s.rivals)` — every `'suggested'` entry dropped, every
     `'typed'` entry kept (WO-083 owns that rule; it is not re-implemented here).
   - `suggestions` resets to `{ state: <'awaiting_market' if the new market is 'empty', else 'seeking'>, candidates: [] }`.
   - No rival found for the replaced domain survives into the new state.
   The function is pure and returns a new `SetupState`; it mutates nothing.
4. Refusing the newly given address as a rival is `addRival`'s `'own_domain'` arm (WO-083),
   reached because the caller passes the new `siteDomain` as `ownDomain`. Assert it here from
   this module's side rather than re-implementing the check.
5. `validateSetup` has **exactly one** failure arm: `market` is `{ state: 'empty' }` ⇒
   `{ ok: false, because: 'market_missing' }`; otherwise `{ ok: true }`. An empty `rivals` set
   is `{ ok: true }`. No future field may quietly become a second thing that blocks the founder
   — the single-arm return type is the guarantee.
6. Emit the observability field BP-034 names: which market-card state rendered.
7. Write the tests; watch each fail first.
