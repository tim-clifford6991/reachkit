# WO-105 — The one Resend request, carrying both bodies, that never throws

- Branch: wo/WO-105-mail-vendor-resend

- Estimate: ≤1 day

## Goal
Make one Resend request per send carrying both bodies, map every vendor outcome to
a value rather than an exception, and log the send without ever logging an address
or a body.

## Provisional against an empty repo
**No `src/` exists.** All files NEW, inside BP-053's `src/lib/mail/vendor/**`
glob (ADR-040 point 3).

Reuse check (rule 7.2): no vendor mail adapter is indexed. `src/lib/vendors/**`
is BP-008's and is the **DataForSEO** closed endpoint list (`structure.md`), not a
general vendor directory — Resend does not belong there and this WO does not put
it there. `src/lib/egress/` (BP-006, `safeFetch()`) guards fetches of URLs a
customer or dataset supplied; the Resend API is neither, so this adapter calls the
vendor SDK/endpoint directly and does not route through the SSRF guard. Recorded
here so the next reader does not "fix" it.

The `rests-on` row above is BP-053's own, restated as this WO's because this WO is
where it is discharged: if one request cannot carry both bodies, criterion 5 needs
a different mechanism and this WO stops and says so (rule 4.2).

## File plan
| File | New/Modify | Change |
|---|---|---|
| `src/lib/mail/vendor/types.ts` | NEW | `VendorSend` (the request this module accepts: `to`, `subject` as a rendered string, `html`, `text`, `kind`) and `VendorResult` (`{ ok: true; id: string }` \| `{ ok: false; retriable: boolean; retryUntil?: Date }`). `retriable: false` is the permanent-rejection signal BP-029's retry window reads to end early. |

| `tests/mail/vendor/vendor.test.ts` | NEW | Both bodies present in the request; every failure shape returns rather than throws; the log line carries no address and no body. |

## Interfaces
**Exposes** (chosen under rule 1.1 — BP-053 declares `vendor/**` as a directory
and does not name its function; the name is an internal one, constitution §1's
"Internal names, type members, module boundaries" row):
```ts
export type VendorResult =
  | { ok: true; id: string }
  | { ok: false; retriable: boolean; retryUntil?: Date }
export function sendViaVendor(v: VendorSend): Promise<VendorResult>
```
Derivation: `sendEmail`'s public result union (`{ sent: false; reason: 'vendor';
retryUntil?: Date }`) is BP-053's and is built by WO-106 from this value; keeping
`retriable` separate from `reason` is what lets BP-029's 24-hour window "end
early rather than spending six attempts on an address that will never accept
mail" (BP-029 `## Error & edge behavior`). Cost of reversing: one mapping
function in `send.ts`.

**Consumes**: `env` (BP-005, `src/lib/config/env.ts`) — the Resend key and the
from-address, which BP-053's diagram names as its BP-005 dependency.

## Steps
1. Write `vendor.test.ts` against a fake transport first and watch it fail.
2. `types.ts`, then `resend.ts`.
3. Assert by construction that no code path throws: the whole body is inside one
   try/catch whose catch returns a value.
4. Mutation check: remove `text` from the request and confirm the both-bodies
   test fails; log an address and confirm the redaction test fails.
