# WO-246 — `POST /api/stripe/webhook` — the raw-body adapter that verifies nothing itself

- Branch: wo/WO-246-stripe-webhook
- Estimate: ≤1 day

## Goal
Deliver Stripe's request body **unparsed** and its signature header to
`handleStripeWebhook`, and map the two arms it returns — the one adapter in the
corpus whose whole correctness is that it does nothing.

## Provenance of this file plan
**This repository holds no `src/`.** Both paths are NEW. This route is the one
BP-001 lists under "Adapters (transport only)" by name —
`POST /api/stripe/webhook -> account.handleStripeWebhook(rawBody, signature)` —
and decision 1 states the reason it is here and not in BP-017: "Globs cannot
express 'everything under `src/app/api/` except two paths' … Signature
verification stays inside BP-017 (`handleStripeWebhook` takes the raw body and
the signature header), so no security check lives in an adapter." WO-004 named
this file in its out-of-scope: "its one call is
`account.handleStripeWebhook(rawBody, signature)` (BP-017), which does not exist
in this block. Named here so it is not written without it." This is that work
order.

## File plan
| File | New/Modify | Change |
|---|---|---|
| `src/app/api/stripe/webhook/route.ts` | NEW | The `POST` adapter. Reads the request body as a `Buffer` **before anything else touches it** — no JSON parse, no schema, no body reuse — and the `stripe-signature` header; calls `handleStripeWebhook(rawBody, signature)`; returns 200 on `{ handled: true }` and 400 on `{ handled: false, reason }`, with no body beyond the outcome. Declares whatever the runtime needs to keep the body raw (`export const runtime = 'nodejs'`, and no body parser). Imports `src/lib/account/billing` and nothing else. Holds no secret, no `constructEvent`, no event-type switch, no provisioning and no mail. |
| `tests/app/stripe/webhook.test.ts` | NEW | The suites below. |

## Interfaces

Consumes (verbatim from BP-017 `## Public interface`):
```ts
export function handleStripeWebhook(rawBody: Buffer, signature: string):
  Promise<{ handled: true; event: string } | { handled: false; reason: 'signature' | 'unknown_event' }>
```
Exposes (verbatim from BP-001 `## Public interface`):
```
Adapters (transport only)
  POST /api/stripe/webhook   -> account.handleStripeWebhook(rawBody, signature)
```
This route is on WO-003's middleware allow-list already ("permits only a path
matching the exported `PUBLIC_PATHS` allow-list, `/api/jobs/*`,
`/api/stripe/webhook`, and Next.js internals"); this work order does not touch
`src/middleware.ts`.

## Steps
1. Write the failing suites first, the byte-identity case first of all.
2. Read the raw body once, as bytes. Do not parse, do not re-encode, do not
   normalise line endings: a signature is over bytes, and any of those three
   turns a valid webhook into an invalid one in a way no local test catches
   unless it compares bytes.
3. Read the `stripe-signature` header; where it is absent, pass an empty string
   and let `handleStripeWebhook` refuse it — the route makes no judgement about
   a signature, including the judgement that a missing one is invalid.
4. Map the arms: `{ handled: true }` → 200; `{ handled: false }` → 400. Neither
   response carries the event, the reason's vendor text or any payload (BP-001:
   "a vendor error payload never reaches a response body"; BP-017 NFR: "No card
   data, no Stripe secret and no session token ever reaches a log").
5. Confirm the log line carries route id, status and duration and no event id,
   no customer id and no signature.

## Test plan

> Criteria are copied verbatim from `requirements/REQ-024.md`; line breaks are
> normalised to fit the table and no word is changed. Criteria 1, 3, 4, 5 and 6
> are BP-017's and BP-032's — provisioning, the sign-in mail, the 15-minute
> chase and the 24-hour backstop — and are not inherited by a route that
> forwards bytes. Criterion 2 is the one this adapter can break on its own.

| Acceptance criterion (verbatim from REQ) | Test |
|---|---|
| REQ-024 c2 — "Given a payment that did not complete — abandoned, declined, or a claimed payment we cannot verify as ours — when anything acts on it, then no account, no site and no sign-in email results." | `stripe-webhook/verification · this route verifies nothing and decides nothing` — a source assertion that `route.ts` names no signing secret, contains no `constructEvent`, no `stripe.` call and no event-type comparison, and resolves exactly one import into `src/lib/account/**`; plus a runtime assertion that a request with a forged signature reaches `handleStripeWebhook` unchanged and that the route itself creates nothing — no write, no mail, no provisioning call — on any path. The mutation this catches is the natural one: a route that checks the signature "as well", which makes the real check optional-looking and moves a security decision into an adapter. |
| REQ-024 c2, the byte-level half | `stripe-webhook/body · the bytes handed over are the bytes received` — a body containing a multi-byte character, a CRLF sequence and trailing whitespace is asserted byte-identical between the request and the `rawBody` argument, and `typeof rawBody` is `Buffer`, never `string` and never a parsed object. A JSON round-trip anywhere in the route fails it. This is the defect that would make every live webhook fail signature verification while every unit test that stubs the verifier passes. |
