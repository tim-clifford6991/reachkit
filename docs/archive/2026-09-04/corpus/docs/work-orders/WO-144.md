# WO-144 — The 30-day purge — the only deleter in the schema

- Branch: wo/WO-144-purge
- Estimate: ≤1 day

## Goal
Remove, thirty days after the tombstone, everything REQ-079 c7 enumerates —
idempotently, resumably, in dependency order — as the one code path in this
product that deletes a customer's rows.

## File plan
> **Every path below is NEW.** No `src/` exists. Anchored to
> `registry/structure.md` and BP-063's `code:` glob
> `src/lib/account/lifecycle/**`. Provisional against a repo with no code.
>
> **This work order writes no file under `src/jobs/**`.** BP-003's
> `account/maintenance` tick calls these two functions; its own `JobId`
> documentation names `REQ-079 c7 BP-063.accountsDueForPurge -> purgeAccount`.
> This node owns the rule; BP-003 owns the schedule, and since 2026-08-31
> BP-003 also names the platform (Inngest, decision 4) — which changes nothing
> here, because every function below takes an explicit `now` and no test needs a
> scheduler.
>
> **The two blueprints state the cadence differently, and the difference is
> safe in one direction only.** BP-063 decision 3 fixes the purge at **hourly**
> ("so the bound is 30 days + 1 h"); BP-003's `account/maintenance` runs **every
> 15 minutes**. Fifteen minutes is strictly tighter than an hour, so REQ-079 c7's
> promise holds either way and no test below depends on which is configured — the
> boundary cases are asserted against a fixed clock and `purge_due_at`, never
> against a tick. Reported to the architect: two artifacts state one cadence
> (rule 2.4). Do not "reconcile" it by loosening BP-003's tick to hourly from
> inside this work order — a schedule is `src/jobs/**` and neither this file's
> nor this planner's.
>
> **ADR-051 point 6: "The purge is the only deleter."** Nothing else in this
> corpus issues a `DELETE` against a customer's rows, and WO-140's schema test
> asserts no cascade exists to do it accidentally.

| File | New/Modify | Change |
|---|---|---|
| `src/lib/account/lifecycle/purge.ts` | NEW | Exports `accountsDueForPurge(now)` and `purgeAccount(userId)` with BP-063's signatures verbatim. The query is one indexed scan on `purge_due_at <= now()` where `deleted_at is not null`. `purgeAccount` deletes **in dependency order within one transaction per site**, through `dbAdmin()` (the tombstoned rows are hidden from `db()`): the `danger_tickets` rows, `auth_links`, publications, drafts — **including `drafts.grounded_fact`, whose retention under REQ-050 c1 ends here** — measurements, destination credentials, the site, and finally the account and its sign-in address. Idempotent and resumable: re-running it on a purged account is a no-op. Emits one event per purge; **a purge that finds rows it cannot delete is an alert, not a warning** (BP-063's NFR budget) — it means data promised gone at 30 days is still present. |
| `tests/account/lifecycle/purge-due.test.ts` | NEW | Fixed-clock boundaries: at 29 days 23:59 not due, at 30 days 00:01 due; an account with `deleted_at` but no `purge_due_at` is never due (and raises); a live account is never due; the query uses the index. |
| `tests/account/lifecycle/purge.test.ts` | NEW | The enumerated sweep, one case per named class: the account, its sign-in address, the site, its pages, drafts, measurements, destination credentials, and every copy of the customer's own page content, **with `drafts.grounded_fact` its own case**; running twice purges once and the second run is a no-op; a purge interrupted mid-way is resumable and completes on the next run; a whole-database sweep afterwards finds no row referencing the purged `user_id`; a purge that cannot delete a row raises an alert rather than reporting success. |
| `tests/account/lifecycle/purge-410.test.ts` | NEW | ADR-051 point 7's pair, in one file: while tombstoned, a hosted address answers through `hostedServingState` with `account_deleted` (which BP-004 renders as 410); **after** the purge, the site row is gone and the address resolves to no site at all. The two states are asserted as a sequence, because the value of the thirty-day gap is exactly that they differ. |

## Interfaces
Exposes (verbatim from BP-063's `## Public interface`):
```ts
export function accountsDueForPurge(now: Date): Promise<string[]>
export function purgeAccount(userId: string): Promise<{ purged: true }>
```
Consumes: `dbAdmin()` (BP-002) — "the only way BP-063's own mail composition and
BP-003's purge reach a tombstoned account" (ADR-051 point 3);
`hostedServingState(siteId)` (WO-130) for the 410-then-404 sequence.

## Steps
1. Write `tests/account/lifecycle/purge-due.test.ts` with a fixed clock; watch the
   boundaries fail.
2. Write the due-work query.
3. Write `tests/account/lifecycle/purge.test.ts`'s enumerated cases — one per class
   REQ-079 c7 names — and watch them fail.
4. Write `purge.ts` in dependency order, one transaction per site.
5. Add the resumability case and the alert case.
6. Write `purge-410.test.ts` last: it is the test that proves the gap did its job.

## Out of scope
- The `account/maintenance` job, its hourly tick and its cron expression —
  `src/jobs/**` is BP-003's; decision 3's schedule is implemented there.
- The RLS condition that hides a tombstoned account — BP-002's, per ADR-051
  point 3.
- Answering 410 or 404 at the edge — BP-004's.
- Backup, encryption and access control over rows inside the window. ADR-051:
  "Nothing here weakens that; the point is that they are unreachable through the
  product, not that they are unimportant."
- Erasing earlier than 30 days. ADR-051 alternative 4 rejects a shorter window;
  the number is a pin, and changing it is the owner's, not this work order's.

## Rollback
Delete one source file and three test files. Nothing is un-purged by a rollback —
purged rows are gone, which is the promise. Removing the purge while tombstones
exist leaves data past the date REQ-079 c7 promised, so a rollback must be paired
with a plan to run the purge by other means.
