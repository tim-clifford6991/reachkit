# WO-248 — The band-label registry: BAND_LABELS, SCORE_BANDS and SEVERITY — handles to CopyKeys, no word written here

- Branch: wo/WO-248-band-labels
- Estimate: ≤1 day

## Goal
Create `src/lib/presentation/bands.ts` — the one place an internal band handle
becomes a customer-facing term, as three total maps from handles to `CopyKey`s
and not one string a person reads.

## Interfaces

**Consumes:** the `CopyKey` type and `copy()` from
`src/lib/presentation/copy/` (BP-020, WO-041). Nothing else — no config, no
clock, no network, no engine.

**Exposes** (verbatim from BP-019 `## Public interface`):
```ts
/** The band-label registry. Two sets, six words, asserted disjoint (ADR-001).
 *  The six words were ruled by the owner on 2026-08-31 and are transcribed
 *  below; the keys are this node's, the strings are the owner's. */
export const BAND_LABELS: {
  winnability: Record<'winnable' | 'reach' | 'not-yet', CopyKey>
  rivalSize:   Record<'near' | 'middle' | 'far', CopyKey>
}
// winnability (REQ-047 c10)   winnable → band.winnability.winnable → "Winnable"
//                             reach    → band.winnability.reach    → "Reach"
//                             not-yet  → band.winnability.notYet   → "Not yet"
// rivalSize (REQ-096 c2, c9)  near     → band.rivalSize.near       → "Similar size"
//                             middle   → band.rivalSize.middle     → "Larger"
//                             far      → band.rivalSize.far        → "Much larger"

export const SCORE_BANDS: Record<'invisible'|'hard-to-find'|'findable'|'dominant', CopyKey>
// invisible → "Invisible" · hard-to-find → "Hard to find" · findable → "Findable"
// · dominant → "Dominant" — REQ-004 c1's own words, transcribed, never chosen.

/** REQ-009 c8's three levels, **ascending in the count**: index 0 is the level a
 *  problem measured at 0 carries and index 2 the most severe, so "of any two
 *  reports the one with the larger count never carries the lower severity" is a
 *  property of the tuple's order. BP-027's handles `low | mid | high` index it
 *  in that order. Ruled by the owner on 2026-08-31. */
export const SEVERITY: readonly [CopyKey, CopyKey, CopyKey]
// low  → severity.low  → "Minor"
// mid  → severity.mid  → "Worth fixing"
// high → severity.high → "Critical"
```

The thirteen `CopyKey` values this file names, and nothing else:
`band.winnability.winnable` · `band.winnability.reach` · `band.winnability.notYet` ·
`band.rivalSize.near` · `band.rivalSize.middle` · `band.rivalSize.far` ·
`band.score.invisible` · `band.score.hard-to-find` · `band.score.findable` ·
`band.score.dominant` · `severity.low` · `severity.mid` · `severity.high`.

## Steps
1. Write `tests/presentation/bands.test.ts` first and watch every case fail —
   there is no module to import (constitution §8, "watch it fail first").
2. Create `src/lib/presentation/bands.ts`. Import `type { CopyKey }` from
   `./copy` — a **type-only** import, so this module contributes no runtime edge
   into the registry and cannot be the reason a surface pulls the whole copy
   table in.
3. Declare `BAND_LABELS` with the type annotation exactly as BP-019 writes it —
   an annotation, not `satisfies`, because totality over the two handle unions is
   the property that matters here and there is no literal type downstream needs.
   A missing handle and a fourth handle are both compile errors at the
   `Record<>`; that is the whole mechanism.
   **Note the deliberate asymmetry, and do not smooth it:** the *handle* is
   `'not-yet'`, hyphenated (BP-040's `Winnability`, REQ-047 criterion 10's own
   spelling); the *`CopyKey`* is `band.winnability.notYet`, camel-cased; and the
   *rendered term* is `Not yet`, unhyphenated. All three are correct in their own
   place and none is a typo for the others (BP-019 decision 6, "One transcription
   note, deliberately not smoothed").
4. Declare `SCORE_BANDS` over the four `BandHandle` values in `BUILD.md` §5's
   order — `invisible`, `hard-to-find`, `findable`, `dominant` — mapping to the
   four `band.score.*` keys. Import no boundary and no number: BP-005's
   `SCORE_BAND_BOUNDS` holds the four boundaries (0/25/50/75) and this map holds
   the four words. The names are similar and the things are not; the test in step
   8 is what keeps them apart.
5. Declare `SEVERITY` as `readonly [CopyKey, CopyKey, CopyKey]` — a tuple, in
   ascending order, `['severity.low', 'severity.mid', 'severity.high'] as const`.
   Write the ordering fact in a comment on the declaration: index 0 is the level
   a problem measured at 0 carries, index 2 the most severe. It is **not** keyed
   by the handle; consumers index it by ordinal through BP-027's handle→index map
   (`low: 0, mid: 1, high: 2`, WO-064 Steps 7), and `SEVERITY['low']` is a
   compile error by design.
6. Export nothing else. In particular, export **no** flattened array of the six
   band terms and no `BAND_TERMS` constant: ADR-001 point 4 makes the disjointness
   assertion strong precisely because it iterates the two sets
   (`Object.values(BAND_LABELS.winnability)` and `.rivalSize`), so a fourth term
   is caught the moment it is added. A hand-written six-element array is the
   seventh copy that would let a fourth term pass, and is the failure the ADR
   exists to prevent.
7. Add the two `@ts-expect-error` fixtures the test plan names — a fourth
   winnability handle, and `SEVERITY['low']`.
8. Add the separation assertion: read `bands.ts` from disk and assert its import
   list contains no path under `src/lib/config/`, and that no numeric literal
   appears in the file.

| **REQ-004 c1** — "Given a completed report whose score could be computed, when it opens, then the first module shows a single score on a 0–100 scale, its band as one of the four written words — Invisible, Hard to find, Findable, Dominant — the domain measured, and the date it was measured." | `bands · SCORE_BANDS is the closed four-word set and its only source` — `SCORE_BANDS` has exactly the four keys `invisible`, `hard-to-find`, `findable`, `dominant`; each resolves through `copy()` to REQ-004 criterion 1's own word, quoted in the test body (rule 5.3); the four resolved words are distinct; and a `@ts-expect-error` fixture adding a fifth handle fails to compile. **This WO discharges the four-words half only**; the single-score, domain and date half is WO-068's `ReportView`. Discriminates: rewording any of the four in `keys/bands.ts` fails it, and so does adding a fifth band at BP-010 without a word here. |
| **REQ-009 c8** — "Given the severity of any of the three problems, when it renders, then it is one of exactly three written levels drawn from one closed set — the same three words on every report the product renders, never wording chosen per report or per problem — and it follows that problem's own count and nothing else: a problem measured at 0 always carries the lowest of the three and states in writing that there is nothing to fix, and of any two reports the one with the larger count for the same problem never carries the lower severity." | `bands · SEVERITY is one closed ordered triple` — `SEVERITY.length === 3` and a fourth element is a compile error by the tuple type; the three resolve to `Minor`, `Worth fixing`, `Critical` in index order, quoted from BP-019 decision 6 in the test body; the three are distinct; and `SEVERITY['low']` is a `@ts-expect-error` fixture, so the triple can only be read by ordinal. **This WO discharges the one-closed-set and the ordering halves**: because the words are a tuple in ascending order and the only handle→index map is WO-064's, "the larger count never carries the lower severity" reduces to `severityOf` being monotone, which is WO-064's property test. Discriminates: reordering the triple to put `severity.high` at index 0 fails it, which is exactly the mutation that would make a zero count read `Critical`. |
| **REQ-047 c10** — "Given an assessed target, when its winnability is recorded, then it carries exactly one of three bands: Winnable, where a domain in its top ten ranks for no more than the greater of 100 searches and twice the customer's own measured count — a site roughly their size already ranks there; Reach, where it passes criterion 9 but no domain that small is present; and Not-yet, where it fails criterion 9. A Not-yet target is never queued for a page." | `bands · BAND_LABELS.winnability is total over the three handles and renders the ruled terms` — the map has exactly `winnable`, `reach`, `not-yet`; each resolves through `copy()` to `Winnable`, `Reach`, `Not yet`; the three are distinct; and `band.winnability.notYet` resolves to `Not yet` and never `Not-yet` — the transcription note BP-019 decision 6 declines to smooth, asserted here as well as in WO-041 because this is the map that decides which key a handle reaches. **This WO discharges the three-terms half only**; the banding rule (the counts, the "greater of 100 and twice") is BP-040's and the never-queued clause is BP-013's. Discriminates: a `@ts-expect-error` fixture adding a fourth winnability handle fails to compile; pointing `not-yet` at any other key fails the resolution. |
| **REQ-096 c9** — "Given a rival's band is rendered anywhere in the product, when the customer reads it, then `near`, `middle` and `far` each render as their own distinct term, the same term for that band on every surface; and no term rendered for a rival's band is a term rendered for a target's winnability band (REQ-047 criterion 10), so no single word names both how big a rival is and how winnable a target is." | `bands · BAND_LABELS.rivalSize is total, distinct, and the only source of a rival's term` — the map has exactly `near`, `middle`, `far`; each resolves to `Similar size`, `Larger`, `Much larger`; the three are distinct. The **"same term on every surface"** clause is discharged structurally: this is the only declaration of a rival-size term in the corpus, so every surface reaching a term reaches this map — asserted by a source sweep over `src/lib/` and `src/app/` for any other mapping of `near`/`middle`/`far` to a `CopyKey`, which finds none. **The disjointness clause is NOT tested here.** It is ADR-001 point 3's single assertion in `tests/pins.test.ts` (BP-005, WO-007), asserted over the sets so a fourth term fails immediately; a second copy in this file is the drift ADR-001 point 4 exists to prevent. |

Additional tests this WO owns, not inherited from a criterion:
- `bands · no word a person reads is written in this file` — read
  `src/lib/presentation/bands.ts` from disk and assert every string literal in it
  is one of the thirteen key names above and that none of the thirteen *terms*
  (`Winnable`, `Reach`, `Not yet`, `Similar size`, `Larger`, `Much larger`,
  `Invisible`, `Hard to find`, `Findable`, `Dominant`, `Minor`, `Worth fixing`,
  `Critical`) appears anywhere in the source. Discriminates: inlining a word
  instead of a key fails it, which is the one way this file could become a second
  home for the owner's strings (rule 2.4).
- `bands · the words and the boundaries stay apart` — `bands.ts` imports nothing
  under `src/lib/config/`, and contains no numeric literal. BP-005 owns
  `SCORE_BAND_BOUNDS` (the four boundaries 0/25/50/75, `BUILD.md` §5) and this
  file owns the four words; the two are separate things with similar names and
  this is the assertion that keeps them separate. WO-006's mirror assertion —
  that no band word appears in `constants.ts` — is the same seam from the other
  side.
- `bands · every key resolves and none is owner-owed` — all thirteen `CopyKey`s
  are present in `COPY`, `copy()` on each returns a non-empty string, and none is
  in `OWNER_OWED`. Count assertion: the test states the number of keys checked
  (13) rather than passing silently over an empty map (rule 5.5). Discriminates: a
  key deleted from `keys/bands.ts` fails to compile; a key emptied there fails
  this test with the key named.
- `bands · the three maps export no flattened set` — the module's exports are
  exactly `BAND_LABELS`, `SCORE_BANDS` and `SEVERITY`. A seventh copy of the six
  band terms as an array would let a fourth term slip past ADR-001 point 4's
  assertion; this test is why it cannot appear.
