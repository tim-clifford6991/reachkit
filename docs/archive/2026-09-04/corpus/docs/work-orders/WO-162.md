# WO-162 — Alerts, the overflow count, and the one supply statement Overview may make

- Branch: wo/WO-162-overview-alerts
- Estimate: ≤1 day

## Goal
Select at most two alerts with the count of any remainder, and resolve the
supply statement and the stopped-work statement into exactly one key each.

## File plan
> Every path below is **NEW** (no `src/` on disk, checked 2026-08-31). Placement
> follows `structure.md` and BP-038's `code:` globs; provisional.

| File | New/Modify | Change |
|---|---|---|
| `src/app/(account)/app/overview/alerts.ts` | NEW | `Alert` selection: the pages awaiting review and the items that cannot proceed without the customer, ranked, capped at two, each with the `href` that navigates straight to the item; plus `overflow` carrying how many remain and where to see them. An empty list is a success state carrying BP-019's line, never a blank. |
| `src/app/(account)/app/overview/supply.ts` | NEW | The supply statement resolver — one key, resolved in the order exhausted → short → first-arrival-shortfall — and the stopped-work statement for a day ReachKit stopped its own work, which stops being stated when the work resumes. Overview **shares BP-039's empty-account resolver** and defines no second one (ADR-061). |

## Interfaces
Consumes (verbatim from BP-038 `## Public interface`):
```ts
  supply?: { key: CopyKey; vars: Record<string, string> } // REQ-095 criteria 3, 5, 6 — one statement, never two
  alerts: readonly Alert[]                                // at most two (criterion 5)
  overflow?: { remaining: number; whereKey: CopyKey }
export interface Alert { key: CopyKey; vars: Record<string, string>; href: string }
```
and `supplyDepth()` / `supplyNotice()` (BP-013/BP-041), `accountFor()`
(BP-039, WO-165 — the shared empty-account resolver), `stoppedWorkStatement`
(BP-019/BP-054), the draft counts (BP-015).

Exposes: `readAlerts()` and `readSupplyStatement()` inside the overview module;
no new cross-node interface.

## Steps
1. Write the failing tests first (§8).
2. Select alerts from pages awaiting review and items blocked on the customer;
   cap at two; emit `overflow` with the remaining count and the where-to-see-it
   key when more exist.
3. Give every alert exactly one control — the `href` that navigates straight to
   the item.
4. Resolve the supply statement in the order exhausted → short →
   first-arrival-shortfall and return **one** key even where all three
   conditions hold at once.
5. Call BP-039's `accountFor` for the stopped-work fact; do **not** write a
   second resolver here (ADR-061 alternative 5).
6. Mutation check: return two supply keys and confirm the one-statement test
   fails; raise the cap to three and confirm the at-most-two test fails.
