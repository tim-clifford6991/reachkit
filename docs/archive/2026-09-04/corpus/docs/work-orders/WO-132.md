# WO-132 — billingSummary, portalLink and PORTAL_FEATURES — the portal is the only surface for four things

- Branch: wo/WO-132-billing-summary-portal
- Estimate: ≤1 day

## Goal
Assemble what the billing card reads, open one portal session that returns the
customer to Settings still signed in, and export the portal's feature set so a
test can assert that all four customer-owned changes are enabled there and offered
nowhere else.

## File plan
> **Every path below is NEW.** No `src/` exists. Anchored to
> `registry/structure.md` and BP-060's `code:` glob `src/lib/account/billing/**`.
> Provisional against a repo with no code.

| File | New/Modify | Change |
|---|---|---|
| `src/lib/account/billing/summary.ts` | NEW | Exports `billingSummary(userId)` with BP-060's signature verbatim. Every value is read from Stripe at request time except `paidThrough`, which is read from `users`. Returns instants, never formatted dates — "the customer's time zone is applied at render (BP-019), never here". `planKey` is `'plan.single'` and `priceKeys` is BP-030's `PRICE_COPY_KEYS`, imported. Cached 60 s per user. `nextInvoice.amountCents` is asserted equal to the pinned price. |
| `src/lib/account/billing/portal.ts` | NEW | Exports `PORTAL_FEATURES` (verbatim from BP-060) and `portalLink(userId, returnTo)` with BP-060's signature verbatim. `returnTo` is same-origin-checked against `env.NEXT_PUBLIC_APP_URL` by URL parse, not prefix match. The portal configuration is created or updated from `PORTAL_FEATURES` rather than being left to the dashboard. |
| `tests/account/billing/summary.test.ts` | NEW | Each field of the summary; `paidThrough` comes from the database and not from Stripe (a stub whose Stripe period end disagrees with the column still returns the column); `nextInvoice.amountCents` equals the pin and `currency` is `'eur'`; the summary returns instants and contains no formatted date string; `plan_status` may be surfaced for display and is not used in any conditional in this file. |
| `tests/account/billing/portal.test.ts` | NEW | `PORTAL_FEATURES` field by field, each its own case, including `subscription_update: { enabled: false }` and `allowed_updates` containing exactly `address`, `tax_id` and `email`; `returnTo` refusals; **the discriminating test for c2's exclusivity**: a source-level assertion that no route or function under `src/lib/account/**` accepts a card, invoice address, VAT number or invoice-history parameter — the four changes exist on the portal and nowhere in the product. |

## Interfaces
Exposes (verbatim from BP-060's `## Public interface`):
```ts
export function billingSummary(userId: string): Promise<{
  planKey: 'plan.single'                   // one plan; the words are BP-019's
  priceKeys: typeof PRICE_COPY_KEYS        // BP-030
  nextInvoice: { at: Date; amountCents: number; currency: 'eur' } | null
  card: { brand: string; last4: string; expMonth: number; expYear: number } | null
  paidThrough: Date
  cancelledAt: Date | null
  invoicesVia: 'portal'
}>

export function portalLink(userId: string, returnTo: string):
  Promise<{ url: string } | { ok: false; reason: 'no_customer' | 'vendor' }>

export const PORTAL_FEATURES: {
  payment_method_update: { enabled: true }
  customer_update: { enabled: true; allowed_updates: ['address', 'tax_id', 'email'] }
  invoice_history: { enabled: true }
  subscription_cancel: { enabled: true; mode: 'at_period_end' }
  subscription_update: { enabled: false }
}
```

## Out of scope
- The Settings billing card — BP-001's surface; its sentences are BP-019's.
- Cancelling and resuming — WO-133.
- Recording the VAT number at checkout — WO-119.
- Anything that calculates, charges or displays a tax amount. ADR-052 point 5: no
  surface displays, calculates or implies one.

order updates it in place.
