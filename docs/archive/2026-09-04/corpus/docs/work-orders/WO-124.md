# WO-124 — users provisioning columns — one account per address, and what the chase reads

- Branch: wo/WO-124-users-provisioning-migration
- Estimate: ≤1 day

## Goal
Add the second idempotency key — a unique index on the lowercased sign-in
address — and the one column the 15-minute chase reads, under the
`users_provisioning` sub-token.

## File plan
> **Every path below is NEW.** No `supabase/` exists. Anchored to
> `registry/structure.md` rule 3a and BP-032's `code:` globs. Provisional against
> a repo with no code.

| File | New/Modify | Change |
|---|---|---|
| `supabase/migrations/<ts>_users_provisioning_keys.sql` | NEW | `create unique index users_email_lower_key on users (lower(email))` — BP-032 decision 1's second idempotency key, "the second-purchase key (REQ-024 c3)". `alter table users add column first_signed_in_at timestamptz null` — "what the 15-minute chase reads". An index on `(checkout_session_id) where first_signed_in_at is null` supporting `paymentsAwaitingSignIn`. No `payments` table and no `provisioning_attempts` table are created here: BP-032's data-model delta rules both out. No cascade (ADR-051 point 2). |
| `tests/account/provisioning/schema.test.ts` | NEW | Asserts the functional unique index exists and that two rows differing only in the case of their address are refused; asserts `first_signed_in_at` exists and is nullable; asserts no table named `payments` or `provisioning_attempts` exists (the absence BP-032 decided, made enforceable). |

## Interfaces
Consumes: `db()` · `dbAdmin()` (BP-002).
Exposes: no TypeScript surface. This is the substrate for WO-126 and WO-128.

## Steps
1. Write the migration.
2. Write the schema test and watch it fail.

## Test plan
| Acceptance criterion (verbatim from REQ) | Test |
|---|---|
| REQ-024 c3 — "Given the address that paid already has an open account, when a further completed payment from it is processed — the same payment reported to us again, or a second purchase — then once that processing ends the address still has exactly one account, one site and one running subscription, no further sign-in email and no further deep pass result from it, and a founder whose second purchase was charged is told that it bought no second subscription in an `account` mail to the address that paid (REQ-064 criterion 6) naming one way to reach a person." (the database-level half of the guarantee: one account per address, enforced by the index; the handler's branches are WO-126) | `tests/account/provisioning/schema.test.ts › a second users row for the same address in a different case is refused by the unique index` |
| REQ-024 c5 — "Given a payment that completed, when 15 minutes have passed since the charge and no one has signed in at the address that paid, then that address is written to again with an `account` mail (REQ-064 criterion 6): it says the payment succeeded, carries a working sign-in link where the account is open or says it is not open yet where it is not, names one way to reach a person, and never asks for payment again." (the storage half: the column the query reads exists and is indexed) | `tests/account/provisioning/schema.test.ts › first_signed_in_at exists and the partial index supports the awaiting-sign-in query` |

## Out of scope
- Setting `first_signed_in_at` — BP-061's session creation writes it (WO-136).
- The `checkout_session_id` unique constraint — WO-116, BP-030's column.
- Every handler and query that reads these keys — WO-125 to WO-128.

## Rollback
Drop the index and the column in a follow-up migration. Dropping the unique index
in an environment that has run WO-126 removes the guarantee behind REQ-024 c3 and
lets a second account for one address exist — the rollback is safe only before
that work order lands.
