# WO-275 — npm test's default file parallelism races tests/db/**'s shared scratch database — scope the fileParallelism boundary to a dedicated vitest project

- Branch: wo/WO-275-npm-test-file-parallelism
- Estimate: ≤1 day (two files, one existing project boundary extended by one)

## Goal
Make `npm test` — the documented gate command (`structure.md`'s root-toolchain
row, BP-001 decision 2) — pass reliably by scoping vitest's file-parallelism
serialization to exactly the three `tests/db/**` files that share the one
live scratch database, instead of leaving the root `test` script racing them
by default or serializing the whole suite to paper over a coupling that
belongs to one directory.

## Provenance

**The defect, as measured (quoted verbatim, not rounded — rule 1.2).**
`package.json`'s `test` script reads `"vitest run --project node --project
ui"` — no `--no-file-parallelism`. On `doctrine-0.11.0` at `a5219d8`, same
tree, same moment: `npx vitest run --project node --project ui
--no-file-parallelism` → **288/288 pass**; `npm test` run 1 → **13 failed /
267 passed / 8 skipped**; run 2 → **17 failed / 263 passed / 8 skipped**;
run 3 → **17 failed / 263 passed / 8 skipped** — "It fails every run, and
*which* tests fail varies between runs — the signature of a shared-resource
race, not a logic bug. Every failure is in `tests/db/**`." Cause, per the
dispatch and confirmed by reading the files themselves: `tests/db/
baseline.test.ts`, `tests/db/rls.test.ts` and `tests/db/clients.test.ts`
each reset and rebuild the same physical `public` schema on the one native
Postgres scratch database (`reachkit_scratch`) WO-267 stood up in place of
`supabase db reset` (Docker unavailable). Each of the three files' own
header comment already states this and already names the fix's future
location: *"`vitest.config.ts` is outside this work order's file plan (rule
2), so the flag is stated here rather than forced in config."* This WO is
that deferred fix landing.

**Why (b) — a dedicated vitest project — over (a) — a root
`--no-file-parallelism` flag.**

- **§8 / rule 3.1 (a gate must discriminate).** (a) also turns `npm test`
  green, but it does so by serializing every file in every project — `node`,
  `ui` and `layout` alongside the three `tests/db/**` files that actually
  need it. A green run under (a) is indistinguishable from a green run
  under a correct, narrow fix; it cannot tell an auditor *where* the
  coupling lives, and it would stay green even if a future, unrelated file
  introduced its own shared-state race elsewhere in the suite, because
  everything is already serial. (b) names the coupling at the one project
  boundary that has it, so the fix itself is the record of which capability
  needed it — exactly the property §8 asks a gate to have.
- **Rule 7.1 (single owner per capability).** The coupling — three files
  sharing one live scratch database — is `tests/db/**`'s, i.e. BP-002's, by
  `structure.md` rule 4 ("tests live beside the module they exercise") and
  by the files' own header comments. The *mechanism* that enforces it does
  not have to live in a BP-002 file to respect that ownership: BP-001's
  root toolchain row already is, per `structure.md`, *"the one place a
  cross-module lint invariant can be enforced"* — `vitest.config.ts` is
  named there for exactly this kind of cross-file scheduling concern.
  Scoping the fix to a `vitest.config.ts` project (plus the one-line
  `package.json` script update to invoke it) keeps the entire diff inside
  BP-001's own `code:` globs and touches zero BP-002 files — one order,
  one BP, no split needed, and no second owner minted for the
  `tests/db/**` capability itself (unlike (a), which would also have kept
  the diff inside BP-001's files, so this point is not what decided
  between them — §8 and rule 2.5 below are).
- **Rule 2.5 (a document does not say what the code will say).** (a) is one
  flag; there is nothing to over-specify. (b) is a project boundary, and
  this WO's `## File plan` states *what* changes (a fourth project scoped
  to the three named files, `fileParallelism: false` on it, the `node`
  project's selection narrowed so the same three files are not double-run,
  `package.json` invoking the new project) without prescribing the exact
  glob syntax or project ordering the implementer writes — that is the
  implementer's "how."
- **Reversal cost, both options.** Near-identical and cheap: (a) is a
  one-line revert; (b) is a two-file revert (drop the fourth project block,
  drop `--project db`). Cost was not the deciding factor; discrimination
  and ownership were.

**Reuse check (rule 7.2).** `vitest.config.ts` already defines the
project-splitting mechanism this WO extends (three existing projects:
`node`, `ui`, `layout`) — no new config file, no second test runner
introduced. `grep -rn "tests/db" sdlc-factory/docs/registry/capabilities.md`
returns nothing: no product capability row governs test-execution
scheduling, so there is no capability to duplicate.

**No other order claims these two files for this change.** `grep -rln
"vitest.config.ts\|package.json" sdlc-factory/docs/work-orders/*.md`
returns WO-001 (created both, `done`) and a number of later, unrelated,
`done`/merged orders that touched one or the other for different reasons;
none states or reserves this fix.

## File plan
| File | New/Modify | Change |
|---|---|---|
| `package.json` | MODIFY | The `test` script gains a fourth `--project` naming the new project `vitest.config.ts` adds (next row), alongside the existing `--project node --project ui`, so `npm test` — unchanged in name and in the arguments an external caller passes it — actually executes `tests/db/**`'s three live-database files (today they run under the `node` project; after this change they must run under the new one, not nowhere). |
| `vitest.config.ts` | MODIFY | Add a fourth project (name it `db`) whose file selection is exactly the three files that share the live scratch database per their own header comments — `tests/db/baseline.test.ts`, `tests/db/rls.test.ts`, `tests/db/clients.test.ts` — with `test.fileParallelism: false` set on that project only, so those three serialize against each other while every other project keeps its current concurrency. Narrow the existing `node` project's file selection so it no longer also matches those same three files (they must run under exactly one project, not two). `tests/db/migration-naming.test.ts` — which "touches no live database and is unaffected" per `tests/db/rls.test.ts`'s own header — is untouched and keeps running under `node`, in parallel with everything else. |

## Interfaces
Consumes: vitest 4.1.11's own `projects` / `test.fileParallelism`
configuration surface (`ProjectConfig`, `node_modules/vitest/dist/chunks/
reporters.d.DtoKVV2s.d.ts`) — `fileParallelism` is not excluded from
per-project config (it is absent from the `NonProjectOptions` union that
`ProjectConfig` omits from `InlineConfig`), so it is a supported,
project-scoped setting, not a root-only one. Exposes: nothing new —
`npm test` keeps its existing name and existing zero-argument invocation
for every external caller (CI, a validator, a developer); only its internal
project composition changes.

### 4. The `rests-on` row, at runtime — independently observed, partially refuted

The row claims per-project `fileParallelism: false` "scopes serialization
to the files of the one project it is set on, while files in the other
three projects (`node`, `ui`, `layout`) keep scheduling concurrently with
each other **and with that project**."

**Confirmed half:** the `db` project's three files never overlap with
each other. Using the vitest JSON reporter's per-file `startTime`/`endTime`
(one full `npm test` invocation, no probes needed for this half):
`baseline.test.ts` (3853–5917ms), `clients.test.ts` (6435–6941ms),
`rls.test.ts` (8248–9360ms) — zero pairwise overlap, strictly sequential.
**Also confirmed:** `node` and `ui` files overlap with each other in the
same run (e.g. `tests/app/lint-rules.test.ts` 632–2902ms overlaps
`tests/app/toolchain.test.ts` 713–947ms by 234ms, and four other pairs) —
the fix does not accidentally serialize the rest of the suite.

**Refuted half — "and with that project."** The implementer's own log
cites the same kind of evidence (no overlap observed between `db` files
and everything else) as *confirming* concurrency, but a default `npm
test` run cannot discriminate "runs concurrently with `db` but the fast
`node`/`ui` files just happen to finish first" from "is scheduled to run
only after `node`/`ui`/`layout` fully drain" — both produce zero observed
overlap when the non-`db` files are all sub-second. I built a run that
can tell them apart: added a temporary `it()` to one `node`-project file
(`tests/app/toolchain.test.ts`) and one `ui`-project file
(`tests/ui/surface.test.tsx`) that each `await`s a 9-second timer (test
timeout raised to 12s for just that case), keeping both projects
genuinely in flight for 9+ seconds — long enough to span where the `db`
