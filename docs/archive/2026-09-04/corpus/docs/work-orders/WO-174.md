# WO-174 — The site-local week: weekStartFor, weekKey, and the date the next measurement is due

- Branch: wo/WO-174-weekly-week
- Estimate: ≤1 day

## Goal
Compute the site-local Monday as a calendar date that survives a time-zone
change, the job's idempotency key, and the date the shell and Overview both
state when nothing has been measured.

> `00-project.md`: "Greenfield. No source code on disk yet"). Placement follows

> code.

| File | New/Modify | Change |
|---|---|---|
| `src/lib/scan/weekly/week.ts` | NEW | `weekStartFor()` returning `'YYYY-MM-DD'` — Monday 00:00 in the site's stored zone, returned as a **calendar date, never an instant**; `weekKey()`, BP-003's stated idempotency key made concrete; and `nextDueOn()`, the one date the shell and Overview both read so they cannot state two different dates. |

## Interfaces
Consumes: `sites.time_zone` (REQ-073's delta on the `sites` topic),
`WEEKLY_DUE_HOUR_LOCAL` (BP-005's pin, value **6** — ADR-060 point 4).

Exposes (verbatim from BP-050 `## Public interface`):
```ts
/** The site-local week. Monday 00:00 in the site's stored zone (REQ-073 c1).
 *  Returned as a calendar date, never an instant, so it survives a zone change. */
export function weekStartFor(a: { at: Date; zone: string }): string   // 'YYYY-MM-DD'

/** BP-003's stated idempotency key for this job, made concrete here. */
export function weekKey(a: { siteId: string; weekStart: string }): string

/** The date the shell and Overview both state when nothing has been measured. */
export function nextDueOn(a: { siteId: string; now: Date }): Promise<Date>

export const WEEKLY_DUE_HOUR_LOCAL: 6      // 06:00 in the site's zone (BUILD.md §11's hour, its zone)
```

## Steps
1. **Read ADR-060 before writing this file.** `BUILD.md` §11's `Mon 06:00 UTC`
   is not the trigger; the hour is kept and its **zone** is corrected. A site
   west of UTC−6 is in its previous week at 06:00 UTC on Monday.
2. Write the failing tests first (§8, "Watch it fail first").
3. Implement `weekStartFor` as local-calendar arithmetic in the site's zone,
   returning a date string. Never return or store an instant — an instant
   re-invites recomputation at every render (BP-050 decision 2).
4. Implement `weekKey` as `(siteId, weekStart)` — the same key BP-003 already
   states for this job.
5. Implement `nextDueOn` from the site's zone and `WEEKLY_DUE_HOUR_LOCAL`; it is
   the single source the shell (WO-154) and Overview (WO-157) both read.
6. Mutation check: compute the week from UTC instead of the site's zone and
   confirm the UTC−8 test fails.
