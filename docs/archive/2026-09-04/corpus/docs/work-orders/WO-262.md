# WO-262 — A site's condition — recorded only from an answer that site gave, and never a suppression on a non-answer

- Branch: wo/WO-262-verify-site-condition
- Estimate: ≤1 day

## Goal
Ship `src/lib/publish/verify/site.ts`: the condition of a site a page sits in — named, dated, stored on the check that learned it and read back for later pages — recorded **only from an answer the site gave**, so no page is ever marked as having failed a check for a condition of its site and no non-answer suppresses anything.

## Interfaces

**Consumes**

- `db()` under RLS — BP-002, WO-011.
- `publications.verify jsonb` — WO-208 and `BUILD.md` §10. The `siteCondition` field lives **inside** that jsonb; no new column and nothing on BP-058's `destinations` row.
- Nothing from `verify.ts` or `answer.ts`. This module is read-side and has no dependency on the fetch.

**Exposes** — copied exactly from BP-049's `## Public interface`:

```ts
// src/lib/publish/verify/site.ts
/** REQ-062 criterion 6, narrowed by the 2026-09-01 fold to the sitemap and the
 *  robots policy alone — reachability moved into criterion 4's third outcome and
 *  is **not** a site condition. Recorded only from an answer the site gave. */
export type SiteConditionKind = 'publishes_no_sitemap' | 'robots_blocks_site'
export interface SiteCondition { kind: SiteConditionKind; foundAt: Date }

/** The site's condition as of the last check that got an answer from it. Derived
 *  from the most recent `publications.verify.siteCondition` for that
 *  destination — one indexed read, not a second column and not a second fetch
 *  (decision 5). `null` where no check has ever had an answer to record one
 *  from, which is not the same as "the site is fine" and is never rendered as
 *  one. */
export function siteConditionFor(destinationId: string): Promise<SiteCondition | null>
```

**"Only from an answer the site gave" is the whole of this module, and the wrong
version is the natural one — ADR-085 Decision 6.** Criterion 6 used to cover
reachability; the 2026-09-01 fold moved that case into criterion 4's third
outcome and added the sentence that a condition is recorded *only from an answer*.
So **any suppression keyed on "the site could not be reached" is wrong twice
over**: the case has moved, and criterion 6 may not fire on a non-answer at all.

The failure mode is worth stating because it is silent and durable. A sitemap
fetch that times out looks, to a naive implementation, exactly like a site that
publishes no sitemap — and recording `publishes_no_sitemap` from it does two
things at once: it tells the customer something about their site that ReachKit
never observed, and, because the condition is read back for **every later page on
that destination**, it **suppresses the sitemap check for every page published
there afterwards**. The site then silently stops being checked, with every screen
still correct. The six non-answer rows in the file plan are what stop that, and
nothing else in the corpus would notice.

**Where the answer did not come, the cost falls on one page and stops there.**
BP-049: that one check is `unmeasured` **for this page alone**, with its reason;
no `SiteCondition` is written; nothing about the site is stated as the customer's
to act on; and **no later page's check is suppressed**. `unmeasured`, never
`false` — nothing anywhere defaults a `Measured<boolean>` to `false` (BP-010).

**`null` is not a clean bill of health.** It means no check has ever had an answer
to record a condition from. The type is `SiteCondition | null` precisely so there
is no third value a surface could read as "we looked and the site is fine" — a
distinction that matters because ReachKit's only look at this site is whatever
the last page's check happened to fetch, and the requirement bounds the condition
to exactly that freshness.

**Stored on the check that found it, not on the destination row.** BP-049
decision 5 rejects a column on `destinations`: it puts a fact this node observes
in a row BP-058 owns, and that node's health check would then read like its
writer. It also rejects a fresh probe when a later page is checked — that page's
own check already fetches the sitemap, and a second probe is a second look at a
site for a purpose REQ-062's non-goal closes ("Going back to a site to see
whether a condition … has been put right").

## Steps
1. Read **ADR-085** Decision 6 and BP-049 decision 5 before writing a line. The wrong implementation of this module is the one a competent engineer writes first.
2. Create `site.ts` with the block above verbatim. **Two kinds and no third** — reachability is not one of them.
3. Implement `siteConditionFor` as one query for the most recent non-null `verify.siteCondition` on that destination. Make **no outbound request** — assert its absence in test.
4. Expose the recordability predicate this module owns — an observation is recordable **only where the document answered and could be read** — and write the six non-answer fixtures against it before implementing it.
5. Return `null` where nothing was ever recorded. Add no third value and no boolean.
6. Write the "an unparseable sitemap records nothing and suppresses nothing for a later page" test first and watch it fail against an implementation that treats a non-answer as `publishes_no_sitemap` (constitution §8). That is the mutation that matters here: it passes every happy-path row and silently disables a check for every later page on the site.
7. Choose the index that makes the read one query, and **report it to the architect for WO-208's migration** rather than writing it — `supabase/migrations/*_publications*.sql` is BP-045's glob under structure.md rule 3 and is not this work order's file.

## Out of scope
- **Recording a condition.** The write happens on the check that learned it — WO-234's `verifyLive`. This module supplies the type, the recordability predicate and the read-back.
- Fetching a sitemap or a robots document — WO-234. **And fetching one on this module's own account is forbidden**, not merely out of scope: a fresh probe when a later page is checked is a second look at a site for a purpose REQ-062's non-goal closes.
- The `publications.verify` column and any index over it — WO-208, on BP-045's migration glob. Step 7 reports the index rather than writing it.
- Any column on `destinations` — BP-058's topic, and BP-049 decision 5 rejects putting this fact there.
- Classifying the page's own answer — WO-261. Reachability is **not** a site condition and this module has no arm for it.
- The four `Measured<boolean>` checks and the `unmeasured` writes that carry a condition's reason — WO-234.
- Every customer-visible string. ADR-085's Open questions record that what criterion 6's site-condition line says, and what a surface says where one check alone could not be confirmed while the other three were measured, are **owner-owed**. This module names two kinds and a date.
- Going back to a site to see whether a recorded condition has been put right — REQ-062's non-goal in terms. A condition is only ever as fresh as the last page checked there, which is exactly what the requirement bounds it to.

## Rollback
Delete both files. WO-234 imports `SiteCondition` and the recordability predicate and WO-235 imports the type; revert this only before either lands, or verification records a condition nothing can read back. Nothing is stored by this module and no migration is involved — the field it reads lives in a jsonb WO-208 already creates, so a revert leaves that field simply unread.
