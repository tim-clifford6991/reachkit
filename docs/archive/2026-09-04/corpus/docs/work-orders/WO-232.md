# WO-232 — When a check is due, and the two ways it never will be

- Branch: wo/WO-232-verify-disposition
- Estimate: ≤1 day

## Goal
Ship `dispositionFor` and `dueNow`: the dispositions of a publication's 24-hour check, decided from the row and never from the destination kind, and never due again once an outcome is recorded — whichever of the three outcomes it was.

A publication with `unpublished_at` set before `verify_due_at` is `never: 'taken_down_first'` — **no fetch is made and the row is not deleted**, because deleting it would break BP-045's idempotency guard (ADR-080). `never: 'no_live_address'` is decided from `live_url is null`, **not** from `destination.kind`. **Since ADR-084 that arm is reached only by a delivery that never completed** — every destination now serves publicly and every delivered row carries an address — and it stays written against the address, which is the seam that let WordPress join the verified population with no second rule anywhere. `dueNow` selects only rows with `verify is null`, oldest due first. **A recorded `could_not_confirm` is a recorded outcome and the row is not due again** — no backoff, no reschedule, no "pending" render, no second look for any reason (ADR-085 Decision 3). |

The `could_not_confirm` row is the discriminating one — ADR-085's warning block leads with the retry, which is the single most likely wrong change anyone will make to this node, reads as a bug fix, and passes every other test in this file. |

## Interfaces

**Consumes**

- `publications.verify`, `publications.verify_due_at`, `publications.published_at`, `publications.unpublished_at`, `publications.live_url` — WO-208 (created) and WO-213 (`verify_due_at` written). Since ADR-084 `verify_due_at` is set on every delivery at both destinations, because the rule that sets it reads the address.
- `VerifyDisposition` and `VerifyOutcome` — `src/lib/publish/types.ts` (WO-206). **Declared in BP-045's leaf, not here** (BP-045 decision 9): `record/` must name the recorded outcome for REQ-062 criterion 7, and declaring the union in `verify/` would make `record/ → verify/` a node-level cycle between BP-045 and BP-049 that structure.md rule 6 forbids. This file re-exports it, so every caller's spelling is unchanged.
- `db()` under RLS — BP-002.

**Exposes** — copied exactly from BP-049's `## Public interface`:

```ts
// src/lib/publish/verify/due.ts — the union below is BP-045's leaf's, re-exported
export type { VerifyDisposition, VerifyOutcome } from '../types'

// the shape this file implements, quoted from BP-049's `## Public interface`:
export type VerifyDisposition =
  | { kind: 'not_yet';     dueAt: Date }                       // REQ-062 c3, the 24 hours before
  | { kind: 'due' }
  | { kind: 'done';        result: VerifyOutcome }             // all three of c4's outcomes live here
  | { kind: 'never';       because: 'taken_down_first' }       // REQ-062 c4, first sentence
  | { kind: 'never';       because: 'no_live_address' }        // a delivery that never reached an address

export function dispositionFor(publicationId: string): Promise<VerifyDisposition>
export function dueNow(limit: number): Promise<string[]>       // publication ids, oldest due first
```

**`done` carries a `VerifyOutcome`, not four booleans.** All three of REQ-062
criterion 4's outcomes — the page was found and measured, no page was found, the
check could not be confirmed — live in that one arm, so a surface that wants to
render "no verdict this week" must destructure (ADR-085 Decision 1). There is no
fourth arm and no "pending": a check that has not run yet is a disposition, not
an outcome.

**Exclusion is decided by a null live address, not by destination kind** (BP-049
decision 2 — **and this is the seam that held**). The rule was written against
the address because that was the stated reason; the kind was only that day's
instance of it. When the owner ruled on 2026-09-01 that every destination
publishes live, WordPress rows gained a `live_url` and joined the verified
population with **no edit to this rule and no second destination rule anywhere**
(ADR-084 Decision 2). What broke was the fixtures written against the old
constant, not the shape. `if (kind === 'wordpress')` would now silently exclude
every WordPress page from a check REQ-062 criterion 1 promises it — write the
stated rule, and assert it against a WordPress row that has an address.

**A recorded outcome is never due again, and `could_not_confirm` is a recorded
outcome — ADR-085 (landmine).** A transport failure at 24 hours *is* a flake, and
retrying flakes is what good code does; it is forbidden here because there is no
second look. REQ-062's non-goal states it in terms: the check "is not retried,
rescheduled or repeated; 'not confirmed' is a final outcome for that page, not a
pending one". A retry that succeeds an hour later records a **different day's
fact under the check's own date**. `dueNow` selects on `verify is null` and on
nothing else, which is what makes that true by construction rather than by a
rule somebody has to keep.

## Steps
1. Create `verify/due.ts` with the block above verbatim, re-exporting `VerifyDisposition` and `VerifyOutcome` from `../types` rather than declaring them (BP-045 decision 9).
2. Decide `no_live_address` from `live_url is null`. Do not read `destination.kind` anywhere in this file — assert its absence in test.
3. Decide `taken_down_first` from `unpublished_at < verify_due_at`. Make no fetch and delete no row.
4. Implement `dueNow` on the partial index `(verify_due_at) where verify is null`, oldest first. **Add no backoff, no reschedule and no second selection predicate.** Read ADR-085's warning block first: the retry it forbids is the change that looks most like a bug fix.
5. Write the "a null live address is excluded whatever the kind, and a WordPress row with an address is not excluded" pair first, with a hypothetical third kind, and watch it fail against a kind check (constitution §8).
6. Write the three not-due-again rows first as well, and mutate: add a retry for `could_not_confirm` and confirm that row — and only that row — fails.

| **REQ-062 c3** — Given a check the page itself did not pass, when the outcome is shown, then the failure is stated plainly rather than omitted or shown as pending; and in the 24 hours before the check runs, the four outcomes state that they have not been checked yet and when they will be, never that they passed or failed. | `tests/publish/verify/due.test.ts` › "in the 24 hours before the check runs, the outcomes state that they have not been checked yet and when they will be" — `not_yet` carries `dueAt` and carries no outcome; the rendering of "not checked yet" is BP-019's `renderMeasured` and the four `Measured` values are WO-234's. |
| **REQ-062 c4** — Given a page ReachKit's own record shows was unpublished or taken down before its check was due, when the customer inspects it, then no check is run and it states that the page was taken down before it could be verified. Given instead the check runs and the address answers, unambiguously, that there is no such page — a 404 or a 410, and no other answer — then this criterion governs the outcome and not criterion 3: it states that no page was found at that address when the check ran, carrying the date it was looked for; it names no cause and never says who removed the page or that the customer did; it is never stated as a failure of publishing or of any of the four checks; and no further check is run for that page. Given any other answer — the site could not be reached, the address returned a server error, it redirected away from the page, or what came back was not the page ReachKit published — then neither the four outcomes nor the page's absence is asserted: it states that the check could not be confirmed, carrying the date it was tried, the page is not recorded as no longer there, nothing is stated as a failure of this page, and no further check is run for it. | `tests/publish/verify/due.test.ts` › "a page unpublished or taken down before its check was due runs no check and states that it was taken down before it could be verified" — no fetch, `verify` stays null, the row is not deleted. › **"no further check is run, for either outcome"** — a row recording `page_not_found` and a row recording `could_not_confirm` are each absent from `dueNow` and stay absent at every later tick. This work order carries **only the "no further check" limb** of the criterion; which answers land in which arm is WO-261's, and what the arms produce is WO-234's. |
| **REQ-062 c7** — Given criterion 4 recorded that no page was found at a page's address, or that its check could not be confirmed, when any product surface states that page's state, then that surface carries the recorded outcome and its date alongside, so no surface presents the page as live without also carrying what ReachKit saw when it looked; and no surface states as a fact about the page today anything beyond what that one check recorded on that date. | `tests/publish/verify/due.test.ts` › "the disposition carries the whole recorded outcome, checkedAt included" — the `done` arm returns the stored `VerifyOutcome` entire and never a projection of it, which is what lets BP-045's page record hand state and outcome to a surface as one value (WO-263, ADR-085 Decision 5). This row is the supply half only; the promise itself is WO-263's. |
