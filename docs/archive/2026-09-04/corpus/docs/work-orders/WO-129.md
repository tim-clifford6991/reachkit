# WO-129 — users subscription columns — the paid-through gate, and plan_status as an inert record

- Branch: wo/WO-129-users-subscription-migration
- Estimate: ≤1 day

## Goal
Add the paid-through date that is the product's whole access gate, the
subscription id and the cancellation stamp, under the `users_subscription`
sub-token — and record in the schema that `plan_status` is a record, not an input.

## File plan
> **Every path below is NEW.** No `supabase/` exists. Anchored to
> `registry/structure.md` rule 3a and BP-060's `code:` globs. Provisional against
> a repo with no code.
>
> **Read ADR-050 before writing this file.** The columns below sit next to each
> other on purpose and only one of them decides anything.

| File | New/Modify | Change |
|---|---|---|
| `supabase/migrations/<ts>_users_subscription_columns.sql` | NEW | `alter table users add column stripe_subscription_id text null`, `paid_through timestamptz not null` (BP-060: "the gate … Set at provisioning to the first period end and advanced by `onSubscriptionEvent`; never computed at read time" — added with a backfill default for existing rows and the default then dropped), `cancelled_at timestamptz null`. An index on `paid_through` supporting `hasActiveAccess`'s read through `sites.user_id`. A `comment on column users.plan_status` carrying, verbatim, ADR-050's ruling — "the record of what Stripe says; read by no gate" — so a reader of the schema meets the landmine where they meet the column. No cascade (ADR-051 point 2). |
| `tests/account/billing/schema.test.ts` | NEW | The three columns exist with the stated types and nullability; `paid_through` is `not null`; the index exists; the `plan_status` comment is present and non-empty (the one place the schema itself carries ADR-050's warning). |

## Interfaces
Consumes: `db()` · `dbAdmin()` (BP-002). `plan_status` itself is `BUILD.md` §10's
column on the baseline table and is not created here.
Exposes: no TypeScript surface.

## Steps
1. Write the migration, with the backfill for `paid_through` on existing rows.
2. Write the schema test and watch it fail.
3. Apply and re-run.

## Test plan
| Acceptance criterion (verbatim from REQ) | Test |
|---|---|
| REQ-076 c8 — "Given any site, when the weekly re-measurement and the daily generation and publishing loops ask whether it has active access (REQ-065 criterion 1), then it has active access while its paid-through date has not passed and none once that date has passed, whether or not the subscription was cancelled and whether or not its latest renewal was paid." (the storage half: one non-null date column, indexed, with the landmine recorded beside `plan_status`; the gate itself is WO-131) | `tests/account/billing/schema.test.ts › users.paid_through is not null and indexed` and `› plan_status carries the comment recording that no gate reads it` |
| REQ-076 c3 — "Given the customer cancels, when the cancellation is confirmed, then the screen states the exact date their access ends, and measurement, generation and publishing continue unchanged until that date, except that no page is generated whose publish moment — the moment REQ-057 criterion 2 actually publishes it, not the date it was planned for — would fall after that date." (the storage half: the cancellation stamp exists and is separate from the date access ends; the behaviour is WO-133) | `tests/account/billing/schema.test.ts › users.cancelled_at exists, is nullable, and is a different column from paid_through` |

## Out of scope
- Writing any of the three columns — WO-133 and WO-126.
- The `sites_hosting` columns — WO-130.
- `hasActiveAccess` — WO-131.

## Rollback
Drop the index and the three columns in a follow-up migration. Dropping
`paid_through` removes the access gate's only input; every scheduled loop that
reads it must be stopped first.
