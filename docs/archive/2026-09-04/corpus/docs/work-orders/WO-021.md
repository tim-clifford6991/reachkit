# WO-021 — fetches — ledger, cache and raw store in one table

- Branch: wo/WO-021-fetches
- Estimate: ≤1 day

## Goal
Create the one row that is at once the spend ledger, the cache and the raw
store: insert-only, with the index the cache read uses and the index the ledger
read uses.

## Provenance of this file plan
`supabase/` now exists and carries six applied migrations through
`00000000000006_scans_freepath_claim.sql`; the `…004` slot this order planned
before WO-267 landed is taken by `00000000000004_sites_timezone_column.sql`.
The filename below follows the corpus's newer timestamped convention
(`20260901090000_opportunities_core.sql`), which sorts after every `0000…`
file. Path anchored to BP-007's `code:` glob `supabase/migrations/*_fetches*.sql`.
`tests/costs/` is still new.

**`reserved_cents` ships in this create-table, not in WO-022's additive
migration** (ruling 2026-09-03, rule 1.1). Derivation: BP-007's `## Data model
delta` names the column in `fetches`' own column list; both orders are unbuilt
and no `fetches` row exists anywhere, so an additive migration would alter a
table created moments earlier in the same unapplied set — ceremony against an
empty schema, and a second statement of one column (rule 2.4). Both files sit
under the same `*_fetches*.sql` glob, so no module boundary is crossed, and
WO-022's `depends-on: WO-021` already fixes the order of application. Rule 2.6
is unaffected: this order's stop condition stays the applied schema, WO-022's
stays the seam's behaviour — a column moving into the create-table moves no
behaviour, and WO-022 still asserts the column from the seam's side.
Reversal cost: if ADR-094 decision 3a is reversed before this ships, one column
is deleted from one unapplied statement (zero cost today); after it ships, a
`drop column` migration under this same glob — the same cost the separate
migration would have had.

   `spend_ledger` fixture table, and the re-buy test fail first by adding the
   unique constraint decision 3 dropped.

## Out of scope
- `withCostContext()`, `recordFetch()`, `capHit()` — WO-022.
- The cache read predicate — "the newest row on that key inserted within
  `freshnessDays`, excluding a row whose payload is the vendor's own
  zero-result shape" (BP-007 decision 3). It is a read, not a write: this order
  adds no flag, no column and no constraint for it.
- The retention policy BP-007 notes `fetches` will need; the purge of a deleted
  account's payloads is BP-063's.
- `scans.cost_cents` and `scans.status` — written at context close by WO-022,
  columns owned by BP-012's `*_scans*.sql`.
