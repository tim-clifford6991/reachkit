# WO-253 — `measureDomain` and `readMeasuredText`

- Branch: wo/WO-253-measure-domain
- Estimate: ≤1 day

## Goal
Read a domain end to end — home document, detected pricing page, access rules
and the customer's own ranked rows — turn it into BP-010's four measured
quantities and its on-page facts, and expose the one re-read of that measured
text the generation engine's comparison set needs without a second fetch.

## Provenance of this file plan
**This repository holds no `src/`.** All four paths are NEW. `src/lib/measure/`
is BP-010's row in `structure.md`; its `code:` globs are `src/lib/measure/**`
and `tests/measure/**`, and BP-024's `code:` enumerates five other files and
`tests/measure/verdict/**`, so `index.ts`, `text.ts` and `tests/measure/domain/**`
are the component's under `structure.md` rule 2.

**`index.ts` is the declared home of `Drivers`.** WO-054's `## Interfaces`
already consumes "BP-010's `Drivers` (`src/lib/measure/index.ts`, another node's
file — the four measured quantities …)". This work order creates the file that
import resolves to. No existing file plan row names `src/lib/measure/index.ts`,
so this is a creation, not a modification.

**Reuse check (rule 7.2).** `capabilities.md`'s row "Deterministic HTML parse and
on-page facts · `src/lib/measure/` · BP-010 · `measureDomain()` · consumers
BP-012, BP-013, BP-014" names this seam and **no work order authors it**: a grep
of the corpus finds `measureDomain` in WO-018, WO-023 and WO-055 only, each as a
consumer or an out-of-scope note, and in WO-046's stage table as an entry point
it calls but does not create. This work order creates the indexed capability.
`readMeasuredText` is the same case: named by WO-185 and WO-199 as consumers,
authored nowhere. Neither is duplicated — every fetch goes through BP-006's
`safeFetch`, every vendor row through BP-008, every ledgered call through
BP-007, and the text extractor is WO-251's `visibleText`, imported and not
re-written.

**Status.** Left `status: draft` — written and not self-certified in the same
pass. A later audit sets the status against §3's gate list.

## File plan
| File | New/Modify | Change |
|---|---|---|
| `src/lib/measure/index.ts` | **NEW** | `Drivers` and `measureDomain`, both verbatim from BP-010's `## Public interface` (below), plus this module's re-export surface. `measureDomain` runs, in order: `safeFetch` the home document; detect a pricing page from the home document's own links and `safeFetch` it; `readRobots` at the origin; `rankedKeywords(c, { domain, rows })` at the tier's row count; then `parseOnPage` per document and the four driver functions. Every outbound call is made **inside** the caller's `CostContext` through `recordFetch`, so a re-run inside one scan resolves from cache at zero cost and every byte lands in `fetches`. Each `FetchOutcome` with `ok: false` becomes an `unmeasured` with `'undeterminable'`; a `capHit()` or an exhausted deadline observed before a call becomes `'not_attempted'` and the call is not made — never a 0, never an estimate (BP-010 `## Error & edge behavior`). `aiPresence` is returned `{ kind: 'unmeasured', reason: 'not_attempted' }` and the reason is stated in a comment naming the second `rests-on` row. `tier` changes **parameters only** — the ranked-row count and how many pages `pages?` may carry, capped at BP-005's `BATTERY.MEASURED_PAGES_MAX` — and no `if (tier === …)` selects a different formula, a different parser or a different driver. **Exposes** (verbatim from BP-010's `## Public interface`):
```ts
/** The four **measured quantities** the parsers and vendor rows produce. These
 *  are not the three drivers a customer is shown. `BUILD.md` §5 composes the
 *  score as Foundations x Answerability x Presence, where Presence is itself
 *  `max(1, sqrt(SearchPresence x AIPresence))`; REQ-004 criterion 2 says "the
 *  three drivers it is composed of" and `BUILD.md` §4.1 says "three driver
 *  mini-bars". So `searchPresence` and `aiPresence` are sub-measures and never
 *  a shown factor. The shown triple is BP-024's `ScoreFactors`, derived from
 *  this by `factorsOf`. Four fields are kept here because collapsing them at
 *  measurement would lose which of the two failed (BP-024 decision 1). */
export interface Drivers {
  foundations:    Measured<number>   // 0-100; a read generic noindex on the home doc is a measured 0
  answerability:  Measured<number>   // 0-100, floored at 1
  searchPresence: Measured<number>   // sub-measure of Presence, never shown alone
  aiPresence:     Measured<number>   // sub-measure of Presence, never shown alone
}
export function measureDomain(c: CostContext, a: {
  domain: string; tier: 'free' | 'deep' | 'weekly'; pages?: string[]
}): Promise<{ drivers: Drivers; onPage: OnPageFacts; robots: Measured<RobotsPolicy> }>

/** REQ-050 criterion 9's comparison set, without a fresh fetch at generation
 *  time: the rendered text of every page this engine measured for a site, read
 *  back from BP-007's `fetches` row — which is ledger, cache and raw store in
 *  one, so the bytes are already there and cost nothing to re-read. BP-042
 *  rests on this; decision 4 is why it is an export here and not a re-fetch
 *  there. */
export function readMeasuredText(a: { siteId: string; scanId?: string }):
  Promise<Array<{ url: string; text: string; measuredAt: Date }>>
```

> **What `measureDomain` returns for `aiPresence`, and why.** Always
> `{ kind: 'unmeasured', reason: 'not_attempted' }`. The second `rests-on` row
> above states the derivation: the AI rates are over the twelve SERPs, the
> twelve are BP-011's, and BP-010 does not depend on BP-011. The pipeline
> (WO-256) computes the field with WO-252's `aiPresenceOf` at the `scoring`
> stage, from SERPs stage 5 already bought, and hands the completed `Drivers`
> to BP-024's `verdictOf`. The implementer of this work order does **not** buy a
> SERP here — that would spend the free path's ceiling twice on the same rows
> and is on `BUILD.md` §6.4's redundancy ground — and does **not** widen
> BP-010's declared signature.

## Steps
1. Write both test files first and run them; every case must fail on a missing
   module (constitution §8, "Watch it fail first").
2. Implement `measureDomain`'s read half: `safeFetch` the home document under
   `recordFetch`; detect the pricing page from the home document's own links;
   `safeFetch` it under `recordFetch`; `readRobots` at the origin. Re-check
   `capHit()` between calls, exactly as BP-007 requires of any multi-call step.
3. Buy the ranked rows: `rankedKeywords(c, { domain, rows })` where `rows` is
   `PRICE_BOOK.RANKED_FREE_ROWS` on the free tier and `RANKED_PAID_ROWS`
   otherwise. This is the only vendor call in the file.
4. Parse each document read with `parseOnPage` and compose the four drivers.
   `onPage` in the return is the **home** document's facts; the pricing page and
   any `pages?` feed `answerabilityOf`'s array and nothing else.
5. Map outcomes to the trichotomy once, in one helper, so no call site invents a
   second mapping: `ok: false` → `undeterminable`; a cap or deadline observed
   before the call → `not_attempted` and the call is not made; anything read →
   `measured` or `zero` by what it contained.
6. Implement `readMeasuredText` as one query plus `visibleText` per row. Import
   the extractor from WO-251; do not write a second one.
7. Mutate to prove the suite discriminates: (a) return a 0 instead of an
   `unmeasured` for an unreadable home document and confirm the trichotomy row
   fails; (b) branch a formula on `tier` and confirm the tier row fails;
   (c) replace `visibleText` with a local extractor and confirm the
   same-extractor row fails.
