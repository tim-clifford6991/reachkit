# WO-238 — Yoast and RankMath — detected, never assumed, and neither present is a success

- Branch: wo/WO-238-wordpress-seo
- Estimate: ≤1 day

## Goal
Ship `detectSeoPlugins()` and the title/description write into whichever of Yoast and RankMath is present — with neither present a successful delivery and a written line, not a failure.

## File plan

> This repository carries no `src/`, no `tests/`, no `supabase/` and no
> `package.json` (verified 2026-08-31). **Every path below is NEW** — none was
> verified to exist, because none can. Placement is anchored to
> `sdlc-factory/docs/registry/structure.md` and to this work order's blueprint
> `code:` globs, and is provisional against a repo with no code: if the
> implementer finds a file already present at one of these paths, they stop and
> log `failed` naming the drift rather than merging into it.

| File | New/Modify | Change |
|---|---|---|
| `src/lib/publish/destinations/wordpress/seo.ts` | NEW | `SeoPlugin`, `detectSeoPlugins`, and the title/description contribution. Detection inspects the REST index of the customer's site **once per delivery, before the create call** — plugins are detected, never assumed. **The SEO fields are contributed to the one create request, not written by a call of their own** (ADR-084 Decision 1: the create carries `status: 'publish'`, the SEO fields and the stamp in the same request). This module therefore exposes the fields to include and, where a plugin needs a separate namespaced write that cannot ride the create, **that write happens after the post is already live** and its failure is a not-written outcome, never a failed publish. Both present means both contributed; one present means one; **neither present is not a failure**. Names the copy key `publish.wordpress.noSeoPlugin` for criterion 4's line and writes no sentence. |
| `tests/publish/destinations/wordpress/seo.test.ts` | NEW | Both plugins present → both contributed and `seoWritten` has two members; one present → one; neither present → the delivery still succeeds, `seoWritten` is empty and the copy key is carried; a write to one plugin failing leaves the delivery successful and that plugin absent from `seoWritten`; detection makes exactly one REST index read per delivery and never assumes from a version string. **The ordering rows, against a one-call create:** detection happens **before** the create request, so the fields can ride it; the recorded request log shows the SEO fields **inside the create body** wherever the plugin permits it; and where a plugin requires its own request, that request is recorded **after** a create that already carried `status: 'publish'` — asserted as an ordering over the recorded log, so **no implementation can create a draft, write SEO, then publish**. That last assertion is the one the old ordering permitted and the ruling of 2026-09-01 forbids. |

## Interfaces

**Consumes**

- The REST calls and the error mapping — `wordpress/client.ts` and `wordpress/errors.ts` (WO-236).
- `WordPressConfig` — declared in `adapter.ts` (WO-237); received as a parameter.
- `copy()` — BP-019, for the key `publish.wordpress.noSeoPlugin`. The sentence is the owner's.

**Exposes** — copied exactly from BP-048's `## Public interface`:

```ts
export type SeoPlugin = 'yoast' | 'rankmath'
export function detectSeoPlugins(cfg: WordPressConfig): Promise<readonly SeoPlugin[]>
```

**Neither SEO plugin present is a success, not a degradation** (BP-048 decision
2). `seoWritten: []` sits on a successful `DeliveryResult`; the state machine
reaches `published` and the line is a copy key on the page's record.
`needs_attention` would be wrong — the page is in their site and nothing needs
the customer. A silent success would also be wrong — criterion 4 requires the
telling.

**The ordering is fixed by the one-call create, and the obvious alternative is
now forbidden — ADR-084 Decision 1.** The natural way to write SEO metadata into
a WordPress post is: create it as a draft, write the plugin fields, then publish.
That sequence is **forbidden**, not merely dispreferred: it opens a window in
which a post exists in the customer's site as a draft ReachKit meant to publish,
and a crash inside that window re-creates by accident exactly the population the
owner's ruling removes. So detection runs **before** the create, the fields ride
the create request wherever the plugin permits it, and any write that genuinely
cannot ride it happens **after the post is already live** — where its failure
costs the page's metadata and never the page's liveness. The three ordering
assertions in the file plan are what hold that; a two-step would otherwise pass
every functional row in this file.

**A page that went live with no SEO metadata is still a delivered page.** The
page is publicly readable on the customer's own site from the moment the create
returns; reporting a metadata write failure as a failed publish would be a false
statement about content that is on the web in the customer's name.

`seoWritten` must survive into the publication record for the line to be rendered
later; BP-048 stores it in the publication row's existing `verify` jsonb sibling
field rather than a new column.

**The writable path is unverified in this corpus** — see `rests-on`. The
implementer discovers it against a real site with each plugin installed and
records what they found; if no writable path exists for one of them,
`seoWritten` simply omits it and criterion 4's line covers the case, which is why
that outcome is not a failure.

## Steps
1. Create `wordpress/seo.ts` with the block above verbatim.
2. Detect by inspecting the REST index once per delivery, **before the create call**. Do not assume from a version string and do not cache across deliveries.
3. Contribute the title and description to the **create request** wherever the plugin's fields can ride it. **Do not create a draft, write SEO, and then publish** — read ADR-084 Decision 1 before writing this step; the two-step is forbidden and its failure mode is a crash window, not a slow path.
4. Where a plugin genuinely requires its own namespaced request, make it **after** the create that already carried `status: 'publish'`. A failure of that write is a not-written outcome on `seoWritten`, never a failed publish.
5. Return `seoWritten` and name `publish.wordpress.noSeoPlugin` where it is empty. Write no sentence.
6. Discharge the `rests-on` by testing against a real site with each plugin installed and record what was found in the work order log — **including whether each plugin's fields can ride the create request or need one of their own**, which is the fact step 3 turns on. If no writable path exists for one, omit it from `seoWritten` and say so in the log — do not invent one.
7. Write the "neither plugin present still delivers" test first and watch it fail against an implementation that treats it as an error (constitution §8).
8. Write the three ordering assertions before the implementation and watch the last one fail against a create-draft-then-write-then-publish implementation, which is the sequence a WordPress developer will reach for first.

## Out of scope
- SEO plugins other than Yoast and RankMath — REQ-060's non-goal.
- Installing or configuring plugins on the customer's site — REQ-060's non-goal.
- Creating the post, and asserting the status it came back with — WO-237. This module contributes fields to that one request; it makes no create of its own and no publish call of any kind.
- Rendering the written line — the page record (WO-263) and BP-001, on the page's own record and on no other surface.

## Rollback
Delete both files. WO-237 imports this; revert together, or the adapter delivers with no SEO write — which is criterion 4's already-supported case and therefore a safe degraded state.
