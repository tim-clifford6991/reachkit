# WO-223 — The destinations migration — a reason, a breakage clock, one live destination per site, and no cascade

- Branch: wo/WO-223-destinations-migration
- Estimate: ≤1 day

## Goal
Add the `destinations` columns REQ-074 criteria 1 and 6 need, the partial unique index that makes "one live destination per site" a database invariant, and no `on delete cascade` reaching `publications`.

## Interfaces

**Consumes**

- The baseline `destinations` table — `id, site_id, kind, config jsonb, health, created_at` (`BUILD.md` §10, BP-002).
- The migration runner and `db()` / `dbAdmin()` — BP-002.

**Exposes** — copied exactly from BP-058's `## Public interface`:

```ts
-- BP-058 "## Data model delta", on the `destinations` topic:
--   health_reason text null              selects the copy key and the action; the three
--                                        states stay BUILD.md §10's enum (decision 2)
--   health_changed_at timestamptz not null   REQ-074 c6 counts 24 hours from when it broke
--   broken_mail_sent_at timestamptz null     the once-per-breakage guard; cleared on every
--                                        transition back to `ok`
--   config is ciphertext                 encrypted at rest with a key from BP-005's env
--   partial unique index (site_id) where deleted_at is null
--                                        ONE LIVE DESTINATION PER SITE — what makes
--                                        REQ-028 c5's "nothing is published to any other
--                                        destination" true by construction
--   deleted_at timestamptz null          disconnect destroys the credential and keeps the
--                                        row, because published pages stay live and their
--                                        publications point at it (REQ-074 c4)
```

**Do not widen `health`.** BP-058 decision 2: the three states are what REQ-074
criterion 1 shows the customer, and the reason is a separate column that selects
the copy key and the action. Widening the enum to six would change a specified
column and make criterion 1's three states a mapping every surface has to know.

**Do not add a cascade.** ADR-080 decision 3 forbids `on delete cascade` into
`publications` from `destinations`: a disconnect-and-reconnect cycle — which
REQ-074 criteria 3 and 4 make an ordinary customer action — would otherwise start
every page over as a first attempt against a site that already holds the posts.

## Steps
1. Read ADR-080 before writing the foreign keys. The cascade this file must not add is the default a schema reviewer asks for.
2. Write the migration with the columns and the partial unique index above.
3. Constrain `health_reason` to exactly the seven `HealthReason` members and `health` to exactly `BUILD.md` §10's three.
4. Add SQL comments on the partial unique index (naming REQ-028 criterion 5 and BP-035 decision 2) and on each foreign key (naming ADR-080).
5. Write the schema test and watch "a second live destination for one site is refused" fail before the partial index exists (constitution §8).

## Rollback
A down migration dropping the added columns and the partial index. Dropping the partial unique index re-opens REQ-028 criterion 5's failure — a page published to a destination the founder did not choose — so revert only while no publish path exists.
