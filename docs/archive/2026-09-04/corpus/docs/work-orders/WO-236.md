# WO-236 — The WordPress REST client and the one place a vendor payload stops

- Branch: wo/WO-236-wordpress-client
- Estimate: ≤1 day

## Goal
Ship the authenticated REST calls to a customer's WordPress — every one through BP-006's `safeFetch` — and the error mapping that turns every vendor response into a `FailureReason` and discards the payload.

| File | New/Modify | Change |
|---|---|---|
| `src/lib/publish/destinations/wordpress/client.ts` | NEW | The REST calls, **every one through BP-006's `safeFetch`** with a 2 MB response cap and DNS pinning: the REST index read, the post search, **the one post create that carries `status: 'publish'`** (ADR-084 Decision 1 — there is no create-then-publish two-step and this file exposes no call that could make one), the post-meta writes, and the status write `unpublish` uses. The REST root is derived from `baseUrl`, never stored twice. Robots checking is **off** for this adapter — these are authenticated API calls to a site the customer connected and gave us a credential for; `robots.txt` governs crawling, not an API the site's own administrator authorised (BP-048's stated rule 1.1 choice). The application password is present only in memory, only inside one call: never logged, never returned by any read path a surface uses, never echoed back to anyone. |
| `src/lib/publish/destinations/wordpress/errors.ts` | NEW | Vendor response → BP-045's `FailureReason`. **The one place a vendor payload stops.** 401/403 → `credentials_expired` (not retryable). **A create that succeeds but comes back with a post whose status is not `publish` → `credentials_invalid`, not retryable** (**ADR-086** Decision 5): the credential is valid and will never do what is needed, BP-058's probe reads the same site as `failing`/`cannot_publish`, and the page comes to rest needing the customer. It is deliberately **not** `credentials_expired`, which would put the destination in the wrong one of REQ-074 criterion 1's three states and offer the customer the ordinary Reconnect — the one remedy REQ-060 criterion 7 says is never offered here. 404 on the REST root, or a root that is not a WordPress REST index → `destination_rejected` (not retryable). 429 → `rate_limited` (retryable). 5xx, connection reset, DNS failure, timeout → the retryable members. **A response we cannot classify is not retryable** (BP-048 decision 3): an unrecognised outcome at a destination we do not own must not be hammered three times. **A `404` for a post id we hold is `already_gone` and a DNS failure, reset, timeout or 5xx at the site is `unreachable`** (ADR-082, carried forward by ADR-084 Decision 4) — the separation WO-239's two arms read. The payload is discarded — no vendor string reaches a screen, a mail or an export. |
| `tests/publish/destinations/wordpress/client.test.ts` | NEW | Every call goes through `safeFetch` (a module-graph assertion plus a stubbed seam that throws if bypassed); the 2 MB cap and DNS pinning are in force; a seeded application password appears in **no** log line, error message, thrown stack or returned value anywhere in either file; robots checking is off and a customer `Disallow: /` does not stop a call. |
| `tests/publish/destinations/wordpress/errors.test.ts` | NEW | Each stated status maps to its stated `FailureReason` with its stated retryability; an unrecognised status and an unrecognised body each map to a non-retryable reason; no mapped result carries any part of the vendor payload; a payload containing a credential-shaped string is discarded rather than propagated. **The non-publish-status row:** a `201` whose body carries `status: 'draft'` (and one carrying `status: 'pending'`) maps to **`credentials_invalid`, not retryable — and specifically not to `credentials_expired`**, asserted as a negative. That negative is the whole of ADR-086 Decision 5: mapping it to `credentials_expired` reads as more accurate, passes every other row here, and silently moves the destination into the state that offers the customer the one remedy that cannot work. **The two-mapping row:** a `404` for a post id maps to `already_gone` and a transport failure at the site maps to `unreachable`, and the fixtures assert the two are distinct — collapsing them makes one of REQ-056 criterion 16's four outcomes unreachable, which is a change to the requirement. |

## Interfaces

**Consumes**

- `safeFetch()` — BP-006, `src/lib/egress/`. SSRF-guarded, DNS-pinned, size-capped.
- `FailureReason` — `src/lib/publish/types.ts` (WO-206), re-exported by BP-045's `attempt/index.ts`.
- `WordPressConfig` — declared in `adapter.ts` (WO-237); this client receives it as a parameter and holds nothing.

**Exposes** — copied exactly from BP-048's `## Public interface`:

```ts
export interface WordPressConfig {          // the shape stored in destinations.config, sealed by BP-058
  baseUrl: string                           // the customer's site root; the REST root is derived, never stored twice
  username: string
  applicationPassword: string               // present only in memory, only inside one call
}
```

`WordPressConfig` is declared by BP-048 alongside the adapter and is created in
`adapter.ts` by WO-237; this work order's client takes it as a parameter.
Credential *storage*, encryption and disconnect-time destruction are **BP-058's**
(WO-224): this adapter receives a decrypted config for the duration of one call
and holds nothing.

**Robots checking off is a deliberate, recorded choice** (BP-048, rule 1.1).
Reversal is one flag, and reversing it would make a customer's own `Disallow: /`
stop their paid publishing.

**A create that came back not-published is `credentials_invalid` — ADR-086
Decision 5, and the alternative is the trap.** WordPress's default role map gives
`edit_posts` to Contributor and `publish_posts` only from Author upward, so an
application password from a Contributor-level user can create a post and have
WordPress quietly hold it at `draft` whatever the request asked for. That is the
one route by which the owner's ruling of 2026-09-01 could produce, unnoticed,
exactly the outcome it abolishes: a page ReachKit reports as published sitting
invisible in a drafts folder. `credentials_invalid` is already in BP-045's
non-retryable set and already means "this credential will not do what we need
and no repetition will change that", which is exactly true here.
`credentials_expired` is **rejected**: 401/403 already routes to it and BP-058
marks the destination `expired` from it, which would put this occasion in the
wrong one of REQ-074 criterion 1's three states and hand the customer the
ordinary Reconnect that ADR-086 Decision 2 exists to withhold. The negative
assertion in the test row is what holds that, and nothing else in the corpus
would.

**This mapping and BP-049's are two mappings and must not be merged.** BP-048's
`errors.ts` maps answers to the **REST API about a post id ReachKit holds**;
BP-049's `classify` (WO-261) maps an answer to the **page's own public address**
that a reader went to. They look alike, run against the same host, and mean
different things — `already_gone` is a fact about a post ReachKit is trying to
write to, `page_not_found` is a fact about a page a reader went to. They share
one unverified assumption (that a 404 can be told from an unreachable site) and
nothing else. BP-048 says it in terms: **do not merge them.**

## Steps
1. Create `wordpress/client.ts` with the four call shapes, every one through `safeFetch`.
2. Derive the REST root from `baseUrl`. Store it nowhere.
3. Create `wordpress/errors.ts` with the mapping exactly as BP-048 states it, and make the default arm **non-retryable**.
4. Map a create that came back with a status other than `publish` to `credentials_invalid`, non-retryable. Read ADR-086 Decision 5 before choosing any other reason.
5. Keep the `already_gone` / `unreachable` separation. Collapsing them makes one of REQ-056 criterion 16's four outcomes unreachable.
6. Discard every vendor payload at the mapping boundary. Log at most a classified reason, never a body.
7. Write the seeded-credential sweep first — seed a recognisable application password, exercise every path including every error path, and assert it appears in no emitted string. Watch it fail against a client that logs the request (constitution §8).
8. Write the `credentials_expired` negative assertion before the mapping, and watch it fail against the natural implementation that routes every credential-shaped problem to one reason.
