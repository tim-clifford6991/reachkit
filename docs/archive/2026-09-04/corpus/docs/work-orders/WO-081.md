# WO-081 — The correction state machine and CORRECTION_SCOPE

- Branch: wo/WO-081-correction-state
- Estimate: ≤1 day

## Goal
Implement `src/lib/market/coherence/state.ts` — the correction states, a transition function
total over states × events with one refusal that costs nothing, and the named scope constant
that says what a correction re-measures and what it carries forward.

**Risk: high — seam: a state machine that publishes.** `correction_state` is stored on the scan row and read back into the report's one notice, and this machine's refusals — `already_used`, `already_running` — are what a customer is told when a correction is declined; REQ-094 binds each outcome to a different written line. A totality or refusal test that survives deletion lets one submission be accepted twice, or a decline be reported under the wrong line. Mutation-tested (doctrine 0.13.2, rule 2b).

## The block is cleared: six members, and the table is written down
This WO carried `blocked-by: [BP-028]` because the five-member union as approved required one
(state, event) pair — `running + produced_no_report` — to yield `failed_once` on a first
attempt and `exhausted` on a retry, which a total function cannot do. **BP-028 decision 2a
(accepted 2026-08-31) split the running state**: `running` is the first attempt in flight,
`running_retry` is the second, entered by `failed_once + submitted`. The edge is discharged
and the plan below is cut against the six-member machine.

Decision 2a also records why the two alternatives this WO offered are not taken, and an
implementer must not reintroduce either:

- an `attempts` field on `ReportFacts` with one `running` state is **rejected** — it puts the
  machine's own memory outside the machine and is the integer `attempts` counter decision 2
  already rejected, arriving by a side door;
- redefining which state `produced_no_report` applies to (letting the retry run while the
  state stays `failed_once`) is **rejected** — it makes the retry run indistinguishable from a
  report sitting idle after one failure, so a second submission during the retry would be
  refused `already_used` when criterion 5 binds that outcome to a different written line. This
  node's `already_running` clause depends on the retry being a running state.

`scans.correction_state` admits one more string value and needs **no migration**: the column is
text and its value domain is this node's (BP-028's `## Data model delta`). `CORRECTION.retries:
1` still bounds the machine — a seventh state would mean a second retry, which is a pin change
and a requirement question, not something implemented here.

```ts
// src/lib/market/coherence/state.ts
/** Six members, not five. `running` and `running_retry` are both *running*
 *  states and differ only in which attempt is in flight, because
 *  `(running, produced_no_report)` must yield `failed_once` on a first attempt
 *  and `exhausted` on the retry — one pair, two results, which a total function
 *  cannot produce. Decision 2 records why the attempt count is in the state
 *  rather than in `ReportFacts`. */
export type CorrectionState =
  | 'none' | 'running' | 'failed_once' | 'running_retry' | 'used' | 'exhausted'
export type CorrectionEvent =
  | 'submitted' | 'refused_before_run' | 'produced_report' | 'produced_no_report'
export function nextCorrectionState(a: { current: CorrectionState; event: CorrectionEvent }):
  { next: CorrectionState } | { refused: 'already_running' | 'already_used' }
// The whole table, and the exhaustive switch is over exactly these pairs:
//   none         + submitted          -> running
//   running      + produced_report    -> used
//   running      + produced_no_report -> failed_once
//   failed_once  + submitted          -> running_retry
//   running_retry+ produced_report    -> used
//   running_retry+ produced_no_report -> exhausted
//   any          + refused_before_run -> current, unchanged (costs no attempt)
//   running | running_retry + submitted        -> refused 'already_running'
//   used | exhausted        + submitted        -> refused 'already_used'
//   used | exhausted | none | failed_once + produced_(no_)report -> unreachable,
//     and a compile error rather than a fall-through arm.

/** What a correction re-measures and what it carries forward. BP-012 reads this
 *  constant rather than deciding the scope itself, so no correction can re-read
 *  the domain's own pages by accident (REQ-094 criterion 3). */
export const CORRECTION_SCOPE: {
  reDerive:     readonly ['market', 'questions', 'ai_answers', 'google_presence', 'rivals', 'score']
  carryForward: readonly ['foundations', 'answerability', 'on_page', 'robots']
}
```

## Steps
1. Declare the two unions and the constant, `as const`, with the two tuples exactly as quoted.
   `CorrectionState` has **six** members in the order BP-028 writes them.
2. Implement `nextCorrectionState` as an exhaustive switch over every (state, event) pair,
   transcribed from BP-028's table. An unhandled pair must be a **compile error** (a
   `never`-typed exhaustiveness check), not a fall-through (BP-028 decision 2).
3. The nine named rows, exactly as the table states them — sixteen of the twenty-four pairs
   between them:
   - `none + submitted → running`.
   - `running + produced_report → used`.
   - `running + produced_no_report → failed_once`.
   - `failed_once + submitted → running_retry`.
   - `running_retry + produced_report → used`.
   - `running_retry + produced_no_report → exhausted`.
   - `<any state> + refused_before_run → { next: <that same state> }` — a refusal before the
     correction ran consumes neither attempt: nothing was measured and nothing was spent.
   - `running + submitted` and `running_retry + submitted` → `{ refused: 'already_running' }`.
     Both running members refuse the same way: a submission during the retry is
     `already_running`, **not** `already_used`, because the retry has not been spent until it
     returns (BP-028's `## Error & edge behavior`), and criterion 5 binds the two outcomes to
     different written lines.
   - `used + submitted` and `exhausted + submitted` → `{ refused: 'already_used' }`.
4. `produced_report` from either running member returns `used` **including where that report
   stopped early**: a correction whose re-measurement stopped early did produce a report
   (criterion 7's last sentence).
5. The pairs unreachable from a correct caller — `none`, `failed_once`, `used` and `exhausted`
   each with `produced_report` or `produced_no_report`, eight pairs in all — are enumerated in
   the switch, not caught by a `default`, and each returns `{ next: current }`.
   **Placement choice (rule 1.1).** BP-028's table marks these pairs "unreachable, and a
   compile error rather than a fall-through arm" but states no return value for them, while
   decision 2 requires the function to be **total** over states × events. `{ next: current }`
   is the only return that satisfies totality without inventing a transition: it advances
   nothing and spends nothing, so a caller that reached it by mistake loses no attempt.
   Reversing this is one arm-set of the switch and one test row; no stored value and no
   customer-visible consequence. Reported to the architect as a gap in the table, not asked.
6. Emit the observability field BP-028 names: each state transition with its event.
7. Write the tests; watch each fail first.
