# WO-116 — users billing columns — the migration checkout writes into

- Branch: wo/WO-116-users-billing-migration
- Estimate: ≤1 day

## Goal
Add the four additive `users` columns BP-030's data-model delta names, under the
`users_billing` migration sub-token, with the two uniqueness constraints the
provisioning replay key depends on.

## File plan
> **Every path below is NEW.** This repository carries no `src/` and no
> `supabase/` — nothing here was verified against an existing file. Placement is
> anchored to `registry/structure.md` (`supabase/**` · `src/lib/db/**` row, and
> rule 3a's sub-token list, which names `*_users_billing_*` inside BP-017's
> `*_users*`) and to BP-030's own `code:` globs. It is provisional against a repo
> with no code.

| File | New/Modify | Change |
|---|---|---|
| `supabase/migrations/<ts>_users_billing_columns.sql` | NEW | `alter table users add column stripe_customer_id text`, `billing_country text null`, `vat_number text null`, `checkout_session_id text null`. Add `unique (stripe_customer_id)` and `unique (checkout_session_id)` as named constraints (`users_stripe_customer_id_key`, `users_checkout_session_id_key`). No `not null` on any of the four: a `users` row exists before `recordCheckoutFacts` fills them. No default. No `on delete cascade` anywhere in this file (ADR-051 point 2). `<ts>` is the implementer's `YYYYMMDDHHMMSS` at creation; the filename carries exactly one sub-token (`users_billing`) — two is a lint failure under `structure.md` rule 3a. |
| `tests/account/checkout/schema.test.ts` | NEW | Asserts the applied schema: the four columns exist with the stated types and nullability; both unique constraints exist; `vat_number` carries no check constraint, no trigger and no normalisation default (REQ-022 c7's "whatever any registry would say" must not be defeated in the schema); no foreign key introduced by this file carries `on delete cascade`. |

Consumes: `db()` · `dbAdmin()` (BP-002, verbatim: `export function db(): SupabaseClient<Database>` / `export function dbAdmin(): SupabaseClient<Database>`).

  BP-002's.

## Rollback
Drop the two constraints and the four columns in a follow-up migration. No data is
written by this WO, so a rollback before WO-119 lands loses nothing. After WO-119
has run in an environment, a rollback discards recorded billing countries and VAT
numbers — REQ-022's rationale ("a record that was never captured cannot be
reconstructed later") makes that a data-loss event, not a clean revert.
