# WO-019 — resolvesInDns — the one meaning of reachable

- Branch: wo/WO-019-resolves-in-dns
- Estimate: ≤1 day

## Goal
Answer exactly one question about a domain — does this name resolve — in one
place, so three requirements that define "reachable" the same way cannot define
it three times.

## Provenance of this file plan
**This repository holds no `src/`.** Both paths are NEW under BP-006's `code:`
glob `src/lib/egress/**`. This work order shares no file with WO-018 and may run
beside it.

## File plan
| File | New/Modify | Change |
|---|---|---|
| `src/lib/egress/dns.ts` | NEW | `resolvesInDns(host)`. Resolves A/AAAA/CNAME; returns true when the name resolves at all, false when it does not. Bounded timeout. It answers nothing about whether the site responded, and exposes no other verdict, so "reachable" cannot be widened at a call site. |
| `tests/egress/dns.test.ts` | NEW | The tests below. |

## Interfaces
Exposes (verbatim from BP-006 `## Public interface`):
```ts
export function resolvesInDns(host: string): Promise<boolean>
```
Consumes: nothing beyond Node's resolver.

## Steps
1. Write the resolver wrapper with its timeout.
2. Write the tests, including the four acceptance cases BP-006 names — new, thin,
   unbuilt, and blocking our fetcher — each of which resolves and is therefore
   accepted.
3. Watch the "a site that refuses our fetcher still resolves" test fail first by
   implementing `resolvesInDns` as a HEAD request.
