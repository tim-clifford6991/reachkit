# WO-266 — cannot_publish — a fourth occasion inside three states, and an action that leads to a different account

- Branch: wo/WO-266-destination-cannot-publish
- Estimate: ≤1 day

## Goal
Ship the `cannot_publish` health reason, the `reconnect_other_account` action and `publishCapability()`: a WordPress credential that can create but not publish reads as failing, holds its queue, carries a line of its own, and is never offered the one remedy that cannot work.

**A union member, not a copy key — and that is the entire mechanism** (ADR-086
Decision 2). REQ-060 criterion 7 promises that "re-entering the same credential
is never offered as the remedy". If the difference lived only in a sentence, the
promise would be enforced by nobody: the control is the same control, and a
surface renders it from `action === 'reconnect'` **without ever reading the
line**. As a union member the promise is a property of the type — a surface that
offers the ordinary Reconnect in this state **fails to typecheck rather than
failing a copy review**. ADR-086 rejects "one `reconnect` action with a different
sentence" in those terms, and the `@ts-expect-error` fixture in the file plan is
that argument made executable.

The cost of getting it wrong is the customer's time, not a rendering nit. **The
credential is valid.** Re-entering it is the one action guaranteed to change
nothing, and it is the action a customer offered "Reconnect" will take first. The
capability comes from a different WordPress user, or from a role change in a
screen ReachKit does not own.

**Three prohibitions, and the ordinary `expired` path would do all three by
default** (BP-058's Error & edge behavior, in terms — "none of which fails a
test"):

1. **It never says pages are being held and nothing has been lost.** That is
   REQ-074 criterion 2's line, and it is false here twice over: the credential is
   valid, and the page has already **failed** rather than been held — ADR-084
   Decision 3 puts it at rest in `needs_attention`, which BP-045 makes a *state*,
   not a hold (holding is the absence of an edge). Telling a customer "nothing
   has been lost" over a page in `needs_attention` is a false statement about
   their own content.
2. **It never offers the ordinary Reconnect** — the union member above.
3. **It never writes its line from `heldPages`.** The count stays on the view
   because it is a true count; it is not this occasion's sentence (ADR-086
   Decision 3). The identical-line-at-0-and-at-7 fixture is what holds it.

**No new state, and the enum assertion is not ceremonial.** ADR-086 Decision 1
and BP-058 decision 2 both reject a fourth `DestinationHealth` member: it changes
a column `BUILD.md` §10 specifies and makes REQ-074 criterion 1's three
customer-read states a mapping every surface has to know. This is decision 2's
existing mechanism applied to a **fourth occasion** — a reason, a copy key and an
action — and REQ-060 criterion 7's own non-goal says it "supplies one further
occasion for the failing state, adds no state". What it *did* cost that decision
2 did not anticipate is the **action union member**, which is why ADR-086 exists.

**A probe that could not be asked is not a probe that answered no.** A read that
fails maps through `errors.ts`; writing it as `false` would hold a working
customer's queue on a network blip and tell them their account lacks a permission
it has. WO-264 holds the same distinction on its own side; this file must not
undo it by coercing.

**This occasion's own ancestor is silent, and that is recorded rather than
glossed.** REQ-074 — BP-058's `satisfies` requirement — has **no criterion for
this state**, because REQ-060 criterion 7 narrowed its own non-goal to REQ-074
criterion 1 alone precisely when criterion 2 stopped covering it. So the promise
this file renders lives in a neighbouring requirement's criterion 7. It is enough
to build and **not enough for the destinations list to own the promise** (rule
5.7). First `rests-on`, `open`.

## Steps
1. Read **ADR-086** in full, then ADR-084 Decision 3, then BP-058 decision 2's "fourth occasion" note.
2. Add `cannot_publish` to `HealthReason` in `destinations/index.ts`. **Do not touch `DestinationHealth`** — assert its three members at type level in test.
3. Add `reconnect_other_account` to `DestinationView.action` **as its own member**. Do not implement it as `reconnect` with a different key, and do not let any code path map one to the other.
4. In `checkHealth`, call `canPublish` for a `wordpress` destination inside `withConfig`, write the answer to `publish_capable`, and derive `error`/`cannot_publish` from a `false`. Leave `null` selecting no reason.
5. **Do not coerce a failed read into `false`.** Map it through `errors.ts` as WO-264 returns it.
6. Export `publishCapability` from `health/index.ts` beside `stampCapability`. Keep the two separate: one is a health input and the other is not, and BP-058's data-model delta says which.
7. Name the occasion's copy key and write **no string**. The sentence is owner-owed (second `rests-on`) and **may not be written from `heldPages`**.
8. Write the three prohibition assertions first and watch each fail against an implementation that reuses the `expired` path — which is the implementation a developer writes when the state is "another kind of broken credential" (constitution §8).
9. Mutate, and confirm each fails: map `reconnect_other_account` to `reconnect` (the negative assertion and the `@ts-expect-error` fixture fail); write the line from `heldPages` (the 0-versus-7 fixture fails); reuse REQ-074 criterion 2's held-pages line key (prohibition 1 fails); add `cannot_publish` to `DestinationHealth` (the enum row fails).

ADR-086 adds that the label "must not read as 'Reconnect'": a label that reads like the ordinary one re-offers the forbidden remedy in effect. This file names the key, the reason and the action.
