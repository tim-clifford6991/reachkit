# WO-090 — saveDomain, saveCategory, saveRivals — the save is immediate, its effect is not

- Branch: wo/WO-090-saves
- Estimate: ≤1 day

## Goal
Complete `src/lib/market/changes/declared.ts` with the three saves: each writes the declared
answer at once and returns the date the change becomes effective, recomputed **after** the
write so the customer is never shown one date and given another.

## Context an implementer needs
No source code exists on disk; `declared.ts` exists only as WO-089 leaves it. **This WO
modifies that file — it must never run in parallel with WO-089.**

**Read `sdlc-factory/docs/decisions/ADR-030.md` first.** A save writes the declared answer and
**nothing else**: no `pending_*` column, no `site_changes` row, no queue. "A pass reads the
declared answers at the moment it begins — which is precisely REQ-071's 'the first weekly
re-measurement that begins after the moment of the save', with no scheduling arithmetic and no
queue to drain."

**A save during a running pass is resolved by the database, not by us**: the pass reads the row,
so the write that lands first wins, and the effective date is recomputed after the write rather
than before it (BP-056's `## Error & edge behavior`).

## Interfaces
**Consumes**: `db()` (BP-002), `resolvesInDns()` (BP-006, quoted below), `effectiveOn` from
`./pending` (WO-091), `RivalSet` and the add/remove invariant from
`src/lib/market/rivalset/` (WO-083), and `DeclaredAnswers` from this same file (WO-089).

```ts

export function resolvesInDns(host: string): Promise<boolean>
```

**Exposes** — copied exactly from BP-056's `## Public interface`, the trailing comment included
because it is the ownership rule:

```ts
export function saveDomain(a: { siteId: string; domain: string }):
  Promise<{ ok: true; effectiveOn: Date } | { ok: false; because: 'unreachable' }>
export function saveCategory(a: { siteId: string; category: string }): Promise<{ ok: true; effectiveOn: Date }>
export function saveRivals(a: { siteId: string; rivals: RivalSet }): Promise<{ ok: true; effectiveOn: Date }>
//  add/remove themselves are BP-034's addRival / removeRival; these persist the result.
```

## Steps
1. `saveDomain`: `resolvesInDns(domain)` first — the same test a rival meets. False ⇒
   `{ ok: false, because: 'unreachable' }` with **no write**. True ⇒ write `sites.domain`, then
   compute `effectiveOn({ savedAt: <the moment the write landed>, timezone })` and return it.
   No measurement of the new domain runs here.
2. `saveCategory`: write `sites.category` at once, then compute and return `effectiveOn`. No
   re-measurement and no question-set re-derivation runs before that date — re-derivation
   happens only inside a pass, and a pass reads the declared answers when it begins.
3. `saveRivals`: write `sites.competitors jsonb` with the supplied `RivalSet` verbatim, entries
   carrying their `origin`, then compute and return `effectiveOn`. **This function does not
   validate, add or remove**: `addRival`/`removeRival` (WO-083) are the invariant, and
   re-implementing any part of them here is the rule 7.1 conflict BP-034 decision 1 forbids.
   `rivals: []` is a legal value and is written as an empty array — never an error state.
4. All three compute `effectiveOn` **after** the write, from the same clock and time zone the
   Settings card renders with, so a save at 05:59 for a 06:00 pass returns the date the pass
   will actually honour.
5. The time zone is the customer's own stated preference (REQ-073 criterion 3, the `rests-on`
   row REQ-071 already carries as `confirmed`). Read it alongside the site row; do not default
   to UTC and do not read the server's zone.
6. Write **only** the one column each. No second write, no audit row, no `pending_*` anything.
7. Emit the observability BP-056 names: every save with its kind, its effective date, and the
   declared and measured values at that moment.
8. Write the tests; watch each fail first.

No-pending-record guard, from **ADR-030**: `saves/write-exactly-one-column-each` — each save
issues exactly one update statement touching exactly one column; the module references no
column matching `/pending/i`, adds no `supabase/migrations/` file, and writes no change-log row.

Time-zone correctness, from BP-056's `## NFR budget` ("a fixture suite covers DST boundaries, a
save during a running pass, and a save in the same minute as the schedule"): the DST and
same-minute fixtures live with `effectiveOn` in WO-091; this WO asserts only that the three
saves pass the customer's stored zone through unchanged —
`saves/passes-the-customers-timezone` — and never substitute UTC.

Discrimination: writing `sites.domain` before the DNS check, computing `effectiveOn` before the
write, or having `saveRivals` re-validate a domain, must each fail a named test above.
