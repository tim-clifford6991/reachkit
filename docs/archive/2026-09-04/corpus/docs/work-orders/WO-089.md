# WO-089 — declaredAnswers and measuredAnswers — the two facts a pending change is the difference between

- Branch: wo/WO-089-declared-measured
- Estimate: ≤1 day

## Goal
Implement the read half of `src/lib/market/changes/declared.ts` — the declared answers from
`sites` and the measured answers from the scan that produced the current report — as two
separate reads, because a pending change is their difference and nothing else.

## Context an implementer needs
No source code exists on disk; both paths below are NEW.

**Read `sdlc-factory/docs/decisions/ADR-030.md` before touching this module.** It is a landmine
ADR: *"Read this before adding `sites.pending_category`, a `site_changes` table, or any 'apply
this change later' queue."* There is no pending-change record in this product. The declared
answer lives on `sites`; the measured answer lives on the scan that produced the current
report. This WO ships those two reads and **adds no column and no table**. If you find yourself
wanting `pending_*`, the answer is in that file, and it is deliberate, not an oversight.

**This module never imports `src/lib/scan/`** (BP-056 decision 4). BP-012 already depends on
this module's parent, so the import would close a cycle `structure.md` rule 6 makes a build
failure. The measured answers are read from `scans` rows through BP-002's `db()` — the
`src/lib/` → `src/lib/db/` direction rule 6 permits — projecting only the four fields this node
needs.

**This WO creates `declared.ts`; WO-090 modifies the same file.** Sequenced, never parallel.

## Interfaces
**Consumes**: `db()` from `src/lib/db/` (BP-002 — "request-scoped, RLS") and `RivalSet` from
`src/lib/market/rivalset/` (WO-083).

**Exposes** — copied exactly from BP-056's `## Public interface`, the comment included because
it is the specification:

```ts
// src/lib/market/changes/declared.ts
export type ChangeKind = 'domain' | 'category' | 'rivals'
export interface DeclaredAnswers { domain: string; category: string; rivals: RivalSet }
export interface MeasuredAnswers {
  domain: string; category: string; rivals: readonly string[]; at: Date; scanId: string
}
export function declaredAnswers(siteId: string): Promise<DeclaredAnswers>
/** Reads the `scans` rows through BP-002's `db()`. It never imports
 *  `src/lib/scan/`: BP-012 already depends on this module's parent, and the
 *  import would close a cycle `structure.md` rule 6 makes a build failure
 *  (Decisions 4). */
export function measuredAnswers(siteId: string): Promise<MeasuredAnswers | null>
```

## Steps
1. `declaredAnswers(siteId)` reads `sites.domain`, `sites.category` and `sites.competitors
   jsonb` through `db()`, returning the `competitors` payload as a `RivalSet` of
   `{ domain, origin }` entries — the shape BP-034 decision 3 writes.
2. `measuredAnswers(siteId)` reads the **current** scan's row and projects exactly four fields
   plus the id: `scans.domain`, `report.market.category`, `report.rivals` and the scan's
   measurement date (BP-056's `## Data model delta`). It projects nothing else, and it selects
   the current scan by the `is_current` pointer BP-012 maintains — via a `db()` query, not via
   `readCurrentReport()`.
3. Where no scan has completed for the site, `measuredAnswers` returns `null`. Do not
   substitute the declared answers, do not throw, and do not return a partially filled object.
4. Note the deliberate type asymmetry: `DeclaredAnswers.rivals` is a `RivalSet` (entries carry
   `origin`, because the customer chose them) while `MeasuredAnswers.rivals` is
   `readonly string[]` (a measurement has no origin). Do not "harmonise" the two — the
   comparison in `pendingChanges` (WO-091) is over domains, and BP-056's interface fixes both.
5. Emit no state of its own. These are reads.
6. Write the tests; watch each fail first.
