# WO-109 — The leads sequence columns, the criterion-13 unique index, and email_suppressions

- Branch: wo/WO-109-leads-suppressions-migrations

- Estimate: ≤1 day

## Goal
Give `leads` the columns and the three indexes that make REQ-010's follow-up
bound a schema fact rather than an application check, and land
`email_suppressions` as the address-keyed store.

## Provisional against an empty repo
**No `src/` and no `supabase/` exist.** Both migration files are NEW. Timestamps
are the implementer's at authoring time; the **token** in each filename is fixed
here and is not the implementer's to choose (`structure.md` rule 3, closed topic
list): one file carrying `leads`, one carrying `suppressions`. BP-029 owns both
globs — `structure.md`'s `## Scope conflicts` records that BP-016 withdrew them
under rule 2a — so no sibling planner may write either.

Reuse check (rule 7.2): `registry/capabilities.md` names BP-002 as the owner of
"Postgres access, RLS default-deny" and the baseline; the two topic tokens here
belong to BP-029 alone. No migration exists on disk to extend.

## Read ADR-041 before touching the index
`unique (lower(email), domain) where sequence_state is not null` **is** criterion
13. It is not a performance index and it is not a belt-and-braces check on top of
application logic — it is the enforcement, and the branch it replaces was rejected
("a check is a race and this is a uniqueness claim, which the database can hold
and application code cannot", BP-029 decision 1). A second `leads` row for a
domain an address already has a sequence for will carry a **null**
`sequence_state` forever; that reads as a lost enqueue and is not one.

## File plan
| File | New/Modify | Change |
|---|---|---|
| `supabase/migrations/<timestamp>_leads_sequence.sql` | NEW | Adds to `leads`: `domain text not null` (lowercased, written once at capture, thereafter read-only), `sequence_state` as a check-constrained text or enum over `waiting \| running \| finished \| dropped \| stopped` (nullable; set once, every later value terminal, never returns to null), `sequence_started_at`, `next_touch_at`, `touch_count`, `dropped_at`, `page_delivered_at`, `first_page_state` over `pending \| written \| sent \| notice_sent \| abandoned`, `first_page_first_attempt_at`, `first_page_attempts`, `first_page_failure`. Indexes: `unique (lower(email), domain) where sequence_state is not null`; `(sequence_state, next_touch_at)`; `(lower(email), page_delivered_at)`. RLS stays default-deny (BP-002); no policy grants a request-scoped client access to `leads`. |
| `supabase/migrations/<timestamp>_suppressions_email.sql` | NEW | `email_suppressions` as BP-029's data model states: `email` lowercased as the primary key, `cause`, `at`. Insert is idempotent on the primary key. RLS default-deny. |
| `tests/mail/leads/schema.test.ts` | NEW | The three indexes exist with those exact predicates; the unique index rejects a second sequence row; the suppression insert is idempotent. |

## Interfaces
**Exposes**: no TypeScript. The schema is the contract. The columns and their
meanings are BP-029's `## Data model delta` and are transcribed above without
addition — no column is invented here, and the four `first_page_*` columns exist
because "the 24-hour window is measured from the first attempt (criterion 8), so
the first attempt's time is a stored fact".

**Consumes**: BP-002's baseline `leads` and `email_suppressions` tables and its
RLS default-deny posture; `dbAdmin()` for the schema test's fixture setup.

## Steps
1. Write `schema.test.ts` first, against a migrated test database, and watch it
   fail — there is no migration.
2. Write the `leads` migration; run it; confirm the unique index's partial
   predicate is exactly `where sequence_state is not null` (a full unique index
   would forbid the second `leads` row criterion 13 requires to exist).
3. Write the `suppressions` migration.
4. Mutation check: drop the `where` clause from the unique index and confirm the
   second-delivery fixture in `schema.test.ts` fails; drop `domain` and confirm
   the index cannot be created at all.

## Test plan
| Acceptance criterion (verbatim from REQ) | Test |
|---|---|
| REQ-010 c13 — "Given an address that has a sequence for a domain — running, waiting to begin, or already finished — when that domain's page is delivered to that address again, for any reason, then no second sequence for that domain is started and that domain's touches to that address stay capped at the three of criterion 9." | `tests/mail/leads/schema.test.ts` → `a second leads row for the same (lower(email), domain) may be inserted with a null sequence_state and may never be given one` — three cases, one per surviving state (`running`, `finished`, and `stopped`/`dropped` as the terminal others), asserting the insert of a second non-null `sequence_state` raises a unique violation. The scheduling half is WO-114's. |
| REQ-010 c12 — "Given a domain's page has been delivered to an address, when that domain's sequence begins, then it begins no earlier than the delivery of that page and never while another sequence to that address is running or still waiting to run: at most one sequence to an address is ever running, and sequences to one address run in the order their pages were delivered, however many domains that address has. A sequence that has not begun within 7 days of its own page's delivery is dropped and never sent, so no follow-up about a domain ever reaches an address more than 14 days after that domain's page was delivered to it. A sequence ended by a subscribe (criterion 10) or an opt-out (criterion 11) releases nothing — those end the waiting sequences too, and no waiting sequence ever begins after either." | `tests/mail/leads/schema.test.ts` → `the release-ordering index (lower(email), page_delivered_at) and the due-work index (sequence_state, next_touch_at) exist` — the storage half only: `page_delivered_at` is the anchor the 7-day deadline is measured from, and the ordering index is what makes "in the order their pages were delivered" a query rather than a sort in memory. The behaviour is WO-114's. |

## Rollback
A down migration dropping the added columns and the three indexes, and dropping
`email_suppressions`. Safe while no row exists; once leads are captured, dropping
the unique index silently un-enforces criterion 13 (ADR-041) — a rollback after
capture is a behaviour change and needs the ADR superseded.
