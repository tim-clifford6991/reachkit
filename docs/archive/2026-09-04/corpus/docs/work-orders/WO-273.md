# WO-273 — The first-sign-in time zone post — the account shell reports the browser's zone once, through one adapter over adoptBrowserTimezone

- Branch: wo/WO-273-timezone-post
- Estimate: ≤1 day

## Goal
Make BP-057's first-sign-in write happen: the account shell posts the browser's
resolved time zone once per session to one transport-only adapter that calls
`adoptBrowserTimezone`, so every customer has a stated zone from their first
authenticated request onward and a zone they chose is never overwritten.

## Provenance of this file plan
**This repository holds no `src/`.** Three paths are NEW and one is a MODIFY of
a file WO-002 creates. Placement is anchored to BP-001's `code:` globs
(`src/app/(account)/**`, `src/app/api/**`, `tests/app/**`) and to `structure.md`
rule 1: the adapter is transport only, and the writing is BP-057's.

Reuse check (rule 7.2): `adoptBrowserTimezone` is BP-057's (WO-218) and is
**consumed**, not re-implemented; `currentSession()` is BP-061's (WO-136);
`adapter()` is WO-004's. This order mints no function and reads no column.

**Three placements chosen here (rule 1.1), each with its reversal.**

1. **A new order, not WO-003.** WO-003's stop condition — default-deny at the
   edge, one allow-list — and this order's — a null zone written from the
   browser once — each state themselves without citing the other, so rule 2.6
   makes them two orders, not one. WO-003 "reads no database", consumes
   "nothing outside Next.js", and precedes every account surface; giving it
   `depends-on: WO-218` would put the middleware behind the publishing block.
   The client effect's file is the account layout, which is WO-002's, not the
   middleware. Reversal: none needed; the two never share a file.
2. **`src/app/api/account/timezone/route.ts`, not `src/app/api/settings/**`.**
   `src/app/api/settings/**` is BP-055's by the more specific glob
   (`structure.md` rule 2), and BP-055 names `POST /api/settings` "the only
   write path" behind its closed `SETTABLE` list — a second route there is a
   second write path, rule 7.1's conflict. No node globs `src/app/api/account/**`,
   so it is BP-001's by the container glob; and `/api/account/*` is on BP-033's
   `SETUP_INCOMPLETE_ALLOWLIST`, so the post is not redirected to `/setup` for
   the founder BP-057 names (`rests-on` row). Reversal: a path rename and one
   allow-list entry.
3. **Once per session, guarded on the server.** The shell posts once per
   session without first asking whether the site has a zone; the null guard is
   `adoptBrowserTimezone`'s. Derivation: BP-057 makes `settings.ts` the column's
   only writer and WO-218's `readPublishingSettings` treats a null zone as an
   error, so a client-side "has no zone" flag would need a second reader of one
   column; a once-per-session request answered `already_set` is one adapter
   call at BP-057's ≤ 10 ms read budget. The behaviour BP-057 states holds
   identically — the zone is written on the first authenticated request of a
   session whose site has no zone, and never otherwise. Reversal: a
   server-provided flag on the layout; one prop.

`ui: no`: the client component renders no element, no string and no token; the
layout edit adds nothing a person sees.

## File plan
| File | New/Modify | Change |
|---|---|---|
| `src/app/(account)/adopt-timezone.tsx` | NEW | A client component that renders nothing. On first mount in a session it posts `Intl.DateTimeFormat().resolvedOptions().timeZone` to `POST /api/account/timezone` and records that it has, so a second mount in the same session posts nothing. No string, no element, no import from `src/lib/**`. |
| `src/app/(account)/layout.tsx` | MODIFY (WO-002's) | Mounts the component above beside `{children}`. The layout still holds no chrome and no string; WO-002's tests stand unchanged. |
| `src/app/api/account/timezone/route.ts` | NEW | `POST`, wrapped in WO-004's `adapter()`. Resolves `siteId` from `currentSession()` — never from the body; a body naming a site is ignored. Calls `adoptBrowserTimezone(siteId, reported)` and maps its result to a response: `adopted: true` and `already_set` are both success, `invalid` is a refusal naming no zone. Imports `adoptBrowserTimezone` and nothing else from an engine module (BP-001 decision 1). |
| `tests/app/adopt-timezone.test.ts` | NEW | The discriminating tests below: the post is made once per session with the browser's resolved zone; the adapter passes the session's `siteId` and the posted value to `adoptBrowserTimezone` and nothing else; a body-supplied site id is ignored; `already_set` is not an error; a signed-out request is denied by WO-003's middleware; a session whose setup is incomplete still reaches the route. |

## Interfaces
**Consumes** (verbatim from BP-057 `## Public interface`):
```ts
// src/lib/publish/settings/settings.ts
/** REQ-073 criterion 1: the zone the browser reported at first sign-in. Writes
 *  `sites.timezone` only while it is null — a zone the customer set is never
 *  overwritten — and validates `reported` with the same IANA check as a patch. */
export function adoptBrowserTimezone(siteId: string, reported: string):
  Promise<{ adopted: true } | { adopted: false; reason: 'already_set' | 'invalid' }>
```
and (verbatim from BP-061 `## Public interface`):
```ts
export function currentSession(): Promise<{ userId: string; siteId: string } | null>
```
and WO-004's `adapter<T>(h)`; BP-033's `SETUP_INCOMPLETE_ALLOWLIST` as data.

**Exposes**: `POST /api/account/timezone` — a transport-only adapter under
BP-001's `src/app/api/**`; BP-001's interface lists it by the container glob
(decision 1) and no leaf names it.
