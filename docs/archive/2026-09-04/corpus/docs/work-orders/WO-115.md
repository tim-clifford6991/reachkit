# WO-115 — deliverFirstPage — one page, once, or a written message saying why not

- Branch: wo/WO-115-deliver-first-page

- Estimate: ≤1 day

## Goal
Write the page once for a captured lead and deliver it to that one address, or
deliver one written message naming why it is not coming — retrying whichever
exists for 24 hours from the first attempt and then recording neither as
delivered.

## Provisional against an empty repo
**No `src/` exists.** Both files NEW, inside BP-029's `src/lib/mail/leads/**`
glob.

Reuse check (rule 7.2): `generateDraft()` is BP-014's / BP-042's in
`registry/capabilities.md` ("The five-step draft pipeline"), and `runHardRules()`
and `claimCheck()` are the same nodes'. This WO **calls** `generateDraft()` once
per lead and implements no writing, no hard rule and no claim check of its own —
BP-029 is explicit that the writing of the page is not this node's. `sendEmail()`
is WO-106's; `buildFirstPage()` / `buildFirstPageUnavailable()` are WO-113's.

**Pins are BP-005's and imported, never redeclared** (`structure.md` rule 5):
`FIRST_PAGE_RETRY_WINDOW_HOURS = 24`, `FIRST_PAGE_RETRY_MINUTES = [5, 30, 120,
360, 720, 1440]`. Asserted in `tests/pins.test.ts`, which this WO does not touch.
A literal retry interval in this module is a defect.

The `rests-on` row is BP-029's own, restated because this WO is where it is
discharged: `sendViaVendor` (WO-105) returns `retriable: boolean`, and this module
ends the window early on `retriable: false`. If the vendor cannot distinguish the
two, the row is `refuted` and the window simply runs its full six attempts —
say so rather than inventing a distinction (rule 1.2).

## Read ADR-041 before adding a suppression check to this send
`first-page` and `first-page-unavailable` are `stoppable: false`, so WO-106's seam
does not consult `email_suppressions` for them. **A suppressed address that
submitted the control for a different domain still receives that domain's page.**
It reads as the one thing no mail system may ever do and it is REQ-010 c3: "a mail
the founder cannot stop: it is the thing they asked for, sent once, in answer to
their own submission". The opt-out in that same mail (WO-113) stops the follow-up,
not the page.

## Interfaces
**Exposes** (verbatim from BP-029 `## Public interface`):
```ts
// src/lib/mail/leads/giveaway.ts — one lead, one page, once
export type FirstPageFailure =
  | 'no-page-to-write'      // the current report no longer offers one (see rests-on 1)
  | 'writing-failed'        // BP-014 could not produce a page
  | 'writing-refused'       // hard rules or claim check refused it (BP-014)
  | 'delivery-failed'       // the 24-hour window closed on the page itself

export function deliverFirstPage(leadId: string): Promise<
  | { delivered: 'page' }
  | { delivered: 'unavailable-notice'; cause: FirstPageFailure }
  | { delivered: 'none'; cause: FirstPageFailure }>   // c8's window closed on both
```
Plus, under rule 1.1, `export const FIRST_PAGE_UNAVAILABLE_COPY: Record<FirstPageFailure, CopyKey>`.
Derivation: BP-029 states "one `FirstPageFailure` member per cause, each mapped to
one `CopyKey` in BP-019's registry (`mail.firstPageUnavailable.<cause>`)" and that
"Where the founder is still on the report, the same key renders in place" — so the
map must be exported from where the union is declared, and read by both BP-001's
surface and WO-113's template. Cost of reversing: two copies of a nine-row map,
which is rule 2.4's second copy.

**Consumes**: `firstPageOffer()` (WO-110); `captureLead`'s `leads` row (WO-111);
`sendEmail()` (WO-106); `buildFirstPage()` / `buildFirstPageUnavailable()`
(WO-113); `scheduleSequence()` (WO-114); `generateDraft()` (BP-014 / BP-042);
`FIRST_PAGE_RETRY_WINDOW_HOURS`, `FIRST_PAGE_RETRY_MINUTES` (BP-005);
`dbAdmin()` (BP-002).

## Steps
1. Write both test files first and watch them fail.
2. Implement the happy path: read lead → re-read offer → `generateDraft()` →
   `sendEmail('first-page')` → `scheduleSequence()`.
3. Implement the four `FirstPageFailure` causes and the `FIRST_PAGE_UNAVAILABLE_COPY`
   map. Do not add a fifth cause: the union is BP-029's.
4. Implement the retry window on top, driven by the stored
   `first_page_first_attempt_at` and `first_page_attempts` — never by an in-memory
   counter, because the job is re-entrant.
5. Assert as a dependency property that `generateDraft` is called from exactly one
   place in this module and is guarded by `first_page_state !== 'pending'` —
   BP-029's NFR budget: "One `generateDraft()` call per lead, ever."
6. Log the `FirstPageFailure` cause, retry count and state transition; never an
   address in clear text, never a page body.
7. Mutation checks: (a) let a retry re-call `generateDraft` and confirm the
   one-generation test fails; (b) mark a lead delivered on a vendor failure and
   confirm the c8 "nothing shown or recorded as delivered" test fails; (c) add an
   `isSuppressed` check before the `first-page` send and confirm the ADR-041
   dependency assertion fails.
