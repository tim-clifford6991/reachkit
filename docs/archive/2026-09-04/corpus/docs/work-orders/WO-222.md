# WO-222 — applySetupChoice() — two writes, one transaction, zero network calls, and never a fallback destination

- Branch: wo/WO-222-setup-apply
- Estimate: ≤1 day

## Goal
Ship `applySetupChoice()`: record the mode through BP-057's single writer and create the deferred destination row through BP-058's `connect`, in one transaction and without a single network call.

| File | New/Modify | Change |
|---|---|---|
| `src/lib/publish/setup/apply.ts` | NEW | `applySetupChoice`. Two writes in one transaction: the mode through BP-057's `savePublishingSettings` (the single writer of `sites.mode`), and the destination through BP-058's `connect` with `config: null` — a **deferred connection**, created `health='expired'`, `reason='never_connected'`, `last_checked_at` set at creation. It resolves no DNS, reaches no WordPress site and checks no health. Returns `connected: false` unconditionally and by design: nothing is connected at setup, so the type has no branch for it and no caller can be written that waits on one. **This module stores no setting of its own and contains no fallback logic.** |
| `tests/publish/setup/apply.test.ts` | NEW | Submit performs exactly two writes in one transaction — a founder never ends setup with a mode recorded and no destination, or the reverse; **zero outbound network calls**, asserted with the egress seam stubbed to throw, so a future edit adding a DNS check to setup fails rather than slowing it; the destination row is created deferred; choosing WordPress completes setup; no `veto_hours`, `publish_time`, brand voice or do-not-claim value is written. |

## Interfaces

**Consumes**

- `Actor` — WO-206.
- `savePublishingSettings(siteId, patch, by)` — BP-057, `src/lib/publish/settings/settings.ts` (WO-220). The one writer of `sites.mode` (rule 7.1).
- `connect({siteId, kind, config, by})` — BP-058, `src/lib/publish/destinations/index.ts` (WO-225). `config: null` is the deferred connection.
- The partial unique index `(site_id) where deleted_at is null` — **one live destination per site** — declared in BP-035 decision 2 and landing in BP-058's `destinations` migration (WO-223). This work order does not create it.

**Exposes** — copied exactly from BP-035's `## Public interface`:

```ts
// src/lib/publish/setup/apply.ts
export function applySetupChoice(a: {
  siteId: string
  mode: 'autopilot' | 'copilot'
  destinationKind: 'hosted' | 'wordpress'
  by: Actor
}): Promise<{ ok: true; destinationId: string; connected: false }>
```

**Held, and never redirected.** With one live destination per site, REQ-028
criterion 5's "nothing is published to any other destination" is true because no
other destination exists to publish to. BP-045's `destination_working` guard then
holds the page (WO-209, WO-212) and BP-058's view says which action is missing.
**This node contains no fallback logic, because a fallback would be the bug**:
the one thing a founder must be able to trust at setup is that their pages do not
appear somewhere they did not choose.

**A deferred connection is a normal broken destination, not a fourth state**
(BP-035 decision 3): `health='expired'`, `reason='never_connected'`, and the same
Reconnect action, the same line and the same held-queue mechanism as any other
broken destination.

## Steps
1. Create `setup/apply.ts` with the block above verbatim.
2. Perform both writes in one transaction. Call `savePublishingSettings` for the mode; call `connect` with `config: null` for the destination.
3. Make no network call of any kind. Assert it by stubbing BP-006's egress seam to throw — this is the budget REQ-028's whole rationale rests on.
4. Return `connected: false` unconditionally. Do not add a branch for a connected setup.
5. Write no fallback: if the chosen destination is not connected, the page is held by BP-045's guard and nothing else happens here.
6. Write the zero-egress test first and watch it fail against an implementation that resolves DNS at submit (constitution §8).
