## Goal
Run the five steps, assemble the comparison set, put the finished text through the battery, and return one of three outcomes — never queueing a draft that failed a rule, and never spending the one automatic regeneration on a step that did not run.

## File plan

## Steps
1. Write `generate.test.ts` first and run it; it must fail on a missing module.
2. Implement `comparison.ts`, then `index.ts`.
3. This function performs no state transition. It returns an outcome; BP-015 moves the item, and ADR-070 point 3 is why no job in this repository may take `needs_attention -> generating`. Do not add a retry loop, a sweep, or a scheduler hook here — ADR-070's cost-of-reversing paragraph is about exactly this file.
4. `hard_rule_attempts` counts automatic attempts only (ADR-070 point 2). A customer-started regeneration resets it to 0, and that reset is BP-015's edge, not this module's.
5. A step failure returns before `failed` exists. Assert in the test that `hard_rule_attempts` is unchanged after one — the counter is the observable ADR-070 point 5 protects.
6. Run the tests. Then mutate: increment `hard_rule_attempts` on a step failure and confirm the step-failure case fails; add a loop that regenerates twice and confirm the `attempt: 2` case returns `rest` and the loop's third pass is unreachable.

**Discriminates (mutation check, constitution §8).**
- Incrementing `hard_rule_attempts` on a step failure passes every rule test and fails the step-failure assertion — the exact one-character mutation ADR-070 point 5 names.
- Queueing a draft that failed a rule makes the c10 test fail; the test asserts both the absence of a queued item and the absence of a destination hand-off.
- Wiring a retry sweep over `needs_attention` leaves this WO's tests green — which is why the ban is written into the steps and into ADR-070, and why the reviewer of this file should read it before adding one.
