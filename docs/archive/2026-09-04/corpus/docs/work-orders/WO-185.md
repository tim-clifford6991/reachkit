## Goal
Derive the three Improve candidates from a shortfall measured on the customer's own page, and the one Fix candidate from a barrier measured on it — the Fix one inert by construction.

## File plan
| File | New/Modify | Change |
|---|---|---|
| `src/lib/opportunities/derive/improve.ts` | NEW | `improveCandidates(a: { siteId; scanId; report; ownRanked }): DerivationResult`. `expand_page` where the named page's measured word count is the shortfall (`{ kind: 'thin', words }`); `refresh_page` where its content's last change is (`{ kind: 'stale', lastSeenChanged }`); `answerable_page` where the page ranks for a question's search but the answer does not name the customer (`{ kind: 'position', position }`). Evidence is `family: 'improve'` — the search, its `Measured` volume, the page of theirs it names, and the shortfall — with no rival required. Acceptance is `top20` for `expand_page` and `refresh_page`, `named_on` for `answerable_page`. Banding is WO-182's, over the same top ten as the Write family. |

One `unblock` candidate per measured barrier, evidence `{ family: 'fix', barrier, foundOnUrl }`, acceptance `{ form: 'gate_cleared', gate }`, `targetQuery: null`, `fitBand: null`, `volume: null`, and no `effort` term used by anything (it is unranked). The five barriers are the closed `Barrier` union and no sixth is produced. |
| `tests/opportunities/derive/improve.test.ts` | NEW | Fixtures for each shortfall kind; a site with no measured page of its own yields no Improve candidate at all (cold start) rather than a page invented to improve; a shortfall whose measurement is `unmeasured` yields no candidate. |
| `tests/opportunities/derive/fix.test.ts` | NEW | One fixture per barrier; an `unblock` carries null query, null band and null volume; a sixth barrier value cannot be constructed (compile-time) and a report carrying an unknown barrier string yields no candidate. |

## Steps
1. Write both test files first and run them; both must fail on a missing module.
2. Rule 1.1 parameter record — the shortfall-to-type mapping. `thin → expand_page`, `stale → refresh_page`, `position on a question the customer is not named on → answerable_page`. Derivation: REQ-047 c1 names the three Improve types as "expand it, make it answerable, refresh it" and c2 names the three shortfalls as "its own position, its thinness, or its staleness"; the pairing above is the only one that matches each type to the measurement that describes it. Cost of reversing: a branch here plus fixtures; nothing stored changes, because the type is recorded per row at creation.
3. Implement `improve.ts`. A shortfall whose `Measured` kind is `unmeasured` produces nothing — not a candidate with a guessed shortfall.
4. Implement `fix.ts`. The `unblock` candidate is constructed with `targetQuery: null` and `fitBand: null`; that is the shape WO-181's schema enforces, so a regression here is refused by the database as well as by the test.
5. Run the tests. Then mutate: give an `unblock` a `targetQuery` and confirm both the fix test and WO-181's schema constraint fail.

| **REQ-047 c2** Given an opportunity, when it is stored, then it carries the measured evidence that produced it: for the four that propose writing a new page, the search, its volume, and the rival page or position that shows the gap; for the three that propose improving a page the customer already has, the search, its volume, the page of theirs it names, and the measurement on that page that shows the shortfall — its own position, its thinness, or its staleness — with no rival required; for the one that asks the customer to remove an access barrier, the barrier found and the page of theirs it was found on. Every one of those values is one the product measured and stored, never one it composed (REQ-093 criterion 4). | `improve.test.ts › evidence carries the search, its volume, the page named and the shortfall, with no rival`; `fix.test.ts › evidence carries the barrier and the page it was found on` |
| **REQ-047 c5** Given an opportunity that asks the customer to remove an access barrier, when it is presented, then it is presented as an instruction for them to carry out: no page is generated for it, it takes no publishing day and consumes no supply, and it is never actioned automatically in either publishing mode. | `fix.test.ts › an unblock carries null target_query, null fit_band and null volume` — the no-page and no-day halves are WO-183's, WO-188's and BP-014's |
| **REQ-047 c6** Given an opportunity is created, when it is stored, then it carries an acceptance test in exactly one of three forms: the target reaching the top 20 for a named search, the customer being named in the answer to a named question, or a named access barrier being cleared. | `improve.test.ts › acceptance is top20 for expand and refresh and named_on for answerable`; `fix.test.ts › acceptance is gate_cleared naming the barrier` |

**Discriminates (mutation check, constitution §8).**
- Removing the `unmeasured` guard on a shortfall produces an `expand_page` for a page whose word count was never read — the fixture asserts zero.
- Giving `unblock` a non-null `targetQuery` makes it eligible for ranking and generation; the test asserts null, and WO-181's check constraint refuses the row.
- Falling back to a default barrier for an unknown string makes `fix.test.ts › an unknown barrier yields no candidate` fail.
