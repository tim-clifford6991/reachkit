# WO-143 — deleteAccount — signed out, subscription ended, tombstone stamped, and one mail about what is still live

- Branch: wo/WO-143-delete-account
- Estimate: ≤1 day

## Goal
Run the deletion arm in the fixed order — take the pages down, end the
subscription at once, stamp the tombstone and the promised purge date, sign the
customer out — and write once to the address being deleted about any pages a
destination would not let go of.

## File plan
> **Every path below is NEW except `confirm.ts`.** No `src/` exists; `confirm.ts`
> is created by WO-142 and modified here, which is why the two are sequential.
> Anchored to `registry/structure.md` and BP-063's `code:` glob
> `src/lib/account/lifecycle/**`. Provisional against a repo with no code.
>
> **Read ADR-051 before writing this file.** `deleteAccount` "sets
> `users.deleted_at = now()` and `users.purge_due_at = now() + ERASURE_DAYS`. It
> issues no `DELETE` of any kind." Finishing the delete path is the mistake the
> ADR exists to prevent.

## Interfaces
Exposes (verbatim from BP-063's `## Public interface`):
```ts
export interface DeleteAccountResult {
  signedOut: true
  subscriptionEndedAt: Date
  stillLive: UnpublishAllResult['stillLive']   // c6 — named in one `account` mail to the deleted address
  /** c6's WordPress half. **Four sentences, one per REQ-056 c16 outcome, each
   *  with its own count** (the 2026-09-01 round-two fold; earlier it was one
   *  count and one place, and before that a list). The outcome set has one home
   *  and it is REQ-056 c16's (rule 2.4), so this is keyed by
   *  `UnpublishResult`'s four WordPress arms and never by a set of its own.
   *
   *  - `returned_to_draft` — made live by ReachKit and now back to draft. Has a
   *    place. **This is the populous arm since ADR-084**, and it was the empty
   *    one when this interface was written.
   *  - `named_for_removal` — created and never made live, "which nobody
   *    published, which were never public, and into which nothing has been
   *    written". Has a place. **Empty in production since ADR-084**, kept
   *    renderable for the reason ADR-084 Decision 4 keeps the arm.
   *  - `already_gone` — no longer in that site when ReachKit went to return
   *    them. **`place: null` by construction, not by stamp capability**: c6 says
   *    this sentence names no place "because there is nothing there to find". A
   *    non-null place here would send the customer to look for posts that cannot
   *    be in the list.
   *  - `unreachable` — standing in a site ReachKit could not reach, may still be
   *    live, nothing written. Has a place.
   *
   *  "An outcome holding no posts is not named at all rather than named with a
   *  count of none", so an entry with `count === 0` is absent from the map and
   *  the mail cannot render a zero. `place` is REQ-060 c6's list, which exists
   *  only where the stamp was applied (ADR-083): `null` where the site would not
   *  take it, and that sentence then says so and still carries its count — an
   *  owner-owed sentence, not one this node mints. */
  leftInWordPress: Partial<Record<
    'returned_to_draft' | 'named_for_removal' | 'already_gone' | 'unreachable',
    { count: number; place: WordPressListPlace | null }
  >>
  purgeDueAt: Date                              // c7 — deleted_at + 30 days
}
/** The one place, from BP-058's `stamp_capable` row and BP-005's pin. This node
 *  renders no sentence and builds no URL text — it hands the values to the
 *  `account` mail's blocks (BP-053) and the copy key is BP-019/BP-020's. */
export interface WordPressListPlace { siteBaseUrl: string; stampSlug: string }
```

**Discriminates (mutation check, constitution §8).**
- **Writing `count: 0` for an outcome with no posts** — the total-record
  implementation, which is the natural one — fails the absent-key case and the
  compile-time `Partial` assertion. In production it puts a sentence in front of
  a customer saying nothing happened to nothing, on the last mail they will ever
  get from ReachKit; the criterion says the outcome "is not named at all".
- **Giving `already_gone` a place because the site is stamp-capable** passes
  every capability-driven reading and fails its own case. It sends the customer
  to a list to look for posts that cannot be in it — the failure the 2026-09-01
  fold corrected, and the one a reviewer reading only the code will call a
  missing `if`.
- **Summing two arms into one count** — most plausibly `already_gone` with
  `unreachable`, which both mean "not returned to draft" — fails the distinct-primes
  fixture. The criterion says "no sentence carries two outcomes or one count for
  both", and one number for both tells the customer a different thing about their
  own site than two numbers do.
- **Suppressing the mail when `stillLive` is empty** fails the either-kind case.
  It is the previous cut of this work order's behaviour, and its effect is that a
  customer whose destinations all answered gets no mail at all while posts stand
  live under their own name on their own domain, with no product left to tell
  them where.
- Replacing the tombstone with a `DELETE` fails both the no-row-deleted case and
  the compose-after-tombstone case — the discriminating case for ADR-051's first
  consequence.
