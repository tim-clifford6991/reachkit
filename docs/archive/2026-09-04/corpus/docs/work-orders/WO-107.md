# WO-107 — The three notification toggles, stored on the user, read at send

- Branch: wo/WO-107-notify-prefs

- Estimate: ≤1 day

## Goal
Hold each customer's choice for `draft-ready`, `published` and `weekly`
independently on their own user row, and answer the send seam's question of
whether this kind is switched off for this customer.

## Provisional against an empty repo
**No `src/` exists.** All files NEW, inside BP-059's
`src/lib/mail/notifications/**` glob (ADR-040 point 4: "Everything true of *some*
leads or *some* customers — sequencing, capture, suppression, preferences — is a
named subdirectory of the owning node").

Reuse check (rule 7.2): `registry/capabilities.md` row "Notification toggles for
the three recurring mails — `src/lib/mail/notifications/` — BP-059 —
`TOGGLABLE_KINDS` · `readNotifyPrefs()` · `stoppedByPreference()` ·
`applyUnsubscribeToken()`". No implementation exists. `db()` (BP-002) is the
request-scoped RLS client this WO consumes and does not re-mint.

**No migration.** BP-059 decision 4: `users.notify jsonb` ships in BP-002's
baseline and this node claims no `supabase/migrations/**` glob. This WO writes no
SQL. If the baseline lands without the column, stop and say so (rule 4.2) — do
not mint a `*_notify*.sql` token, which `structure.md` rule 3's closed list does
not carry.

## Read ADR-042 before touching this file
This store is keyed by **user** and reaches exactly three kinds. It never writes
`email_suppressions` and never reads it. The obvious unification — one
suppressions table with a nullable kind — is what removes a paying customer's
magic-link sign-in mail.

## Interfaces
**Exposes** (verbatim from BP-059 `## Public interface`):
```ts
// src/lib/mail/notifications/index.ts
export type NotifyKind = 'draft-ready' | 'published' | 'weekly'
export const TOGGLABLE_KINDS: readonly NotifyKind[]        // exactly these three
export type NotifyPrefs = Readonly<Record<NotifyKind, boolean>>

/** A key absent from users.notify reads as on: never toggled is not the same
 *  fact as switched off, and the customer bought a product that mails them. */
export function readNotifyPrefs(userId: string): Promise<NotifyPrefs>

/** Writes one key. Never enqueues anything: criterion 4's mails missed while a
 *  toggle was off are not sent afterwards, and the way to guarantee that is to
 *  have no code path that could. */
export function setNotifyPref(a: {
  userId: string; kind: NotifyKind; on: boolean
}): Promise<NotifyPrefs>

/** The question BP-053 asks immediately before the vendor call. 'unreadable' is
 *  its own answer, not a false: decision 2 states why it stops the send. */
export function stoppedByPreference(a: {
  userId: string; kind: MailKind          // type-only import from the register
}): Promise<'send' | 'stopped' | 'unreadable'>
```
**Consumes**: `MailKind` (WO-104, type-only); `db()` (BP-002, `src/lib/db/`);
`env`'s signing secret is WO-108's, not this WO's.

## Steps
1. Write the four test files first and watch them fail.
2. `index.ts` with `TOGGLABLE_KINDS` as the literal triple.
3. `store.ts`: read, single-key write, and a read path that distinguishes
   "no keys" from "could not read".
4. `stoppedByPreference`: a kind not in `TOGGLABLE_KINDS` returns `'send'`
   **without touching the store** — assert the store was not called.
5. Mutation check: make an unreadable store return `'send'` and confirm
   `outage.test.ts` fails; make a missing key read as off and confirm
   `prefs.test.ts` fails.
