## Goal
Derive whether a draft's claim check is outstanding from the list as it stands right now, expose the entry it matched, and sweep a bounded number of stale drafts for timeliness only.

## File plan
| File | New/Modify | Change |
|---|---|---|
| `src/lib/generate/claims/outstanding.ts` | NEW | `claimRecheckOutstanding(draftId)` — true while the draft's recorded `claim_check.listHash` differs from `listHash(sites.do_not_claim)`, or there is no passing check. One row read plus a hash of a jsonb array: no model call, no vendor call, no stored flag, no job output. `outstandingMatch(draftId)` returns `{ matchedEntry }` from a `failed` verdict and null otherwise — the customer's own recorded string. |
| `src/lib/generate/claims/sweep.ts` | NEW | `sweepOutstandingRechecks(c, siteId)` — runs `claimCheck` for that site's drafts short of hand-off whose recorded hash is stale, at most `CLAIM_RECHECK_SWEEP_MAX` per invocation, reporting the rest as `deferred`. Served off WO-200's partial index. A deferred draft is still held by the guard, so truncating the sweep delays a telling and can never release a page. |
| `tests/generate/claims/outstanding.test.ts` | NEW | A draft whose verdict was reached against the previous list is outstanding the instant the customer saves a change, with no job run in between; a draft with no verdict at all is outstanding; a draft whose passing verdict carries the current hash is not; a `failed` verdict yields its `matchedEntry` and a `passed` one yields null; the guard makes no model call and issues one read. |
| `tests/generate/claims/sweep.test.ts` | NEW | A site with 30 stale drafts checks 25 and defers 5; every deferred draft is still outstanding afterwards; the sweep never marks a draft as passing without running a check; drafts already handed to a destination or live are not in the sweep's set at all. |

**Exposes** (verbatim from the blueprint):
```ts
/** True while this draft's last passing check was against a different list than
 *  the site holds now, or there is no passing check. Derived — never a stored
 *  flag, never a job's output (decision 2). */
export function claimRecheckOutstanding(draftId: string): Promise<boolean>

/** What the customer is told when a re-check fails: the entry it matched, which
 *  is a string they wrote (REQ-053 c5). Not model output. */
export function outstandingMatch(draftId: string): Promise<{ matchedEntry: string } | null>

/** Runs the check for this site's drafts short of hand-off whose recorded hash
 *  is stale. For timeliness only; the guard above is what makes it safe. */
export function sweepOutstandingRechecks(c: CostContext, siteId: string):
  Promise<{ checked: number; failed: number; deferred: number }>
```

## Steps
1. Write both test files first and run them; both must fail on a missing module.
2. Implement `outstanding.ts` as a derivation, never a lookup of a stored flag. BP-043 decision 2: the failure mode of the obvious build — a job that marks the affected drafts — is a page publishing a forbidden claim because a job did not run.
3. Assert in the test that no job, sweep or write runs between the customer's save and the draft being held: the test changes `sites.do_not_claim` and immediately asserts the guard.
4. Implement `sweep.ts`. The bound is BP-005's pin; the sweep reports `deferred` rather than looping, and a deferred draft's safety is the guard, not the sweep.
5. This module never regenerates anything and never transitions a page. ADR-070 point 4: a draft that has entered review is never regenerated, whatever stopped it — it leaves review only by `in_review -> approved` (once a re-check passes) or `in_review -> skipped`, both BP-015's edges.
6. Run the tests. Then mutate: cache the guard's answer per draft and confirm the immediate-hold test fails.

| **REQ-053 c5** Given a page carrying an outstanding claim re-check against the changed list, when it would otherwise go to its destination — its veto window expiring, the customer approving it, its publish time arriving, an automatic retry falling due, or the customer starting one — then it is not handed over, whatever stage it sits in; no approval, schedule or retry can put a page carrying a forbidden claim on the customer's site. The re-check stands outstanding until one passes against the text as it then stands (REQ-057 criterion 2); the entry it matched is named to the customer; it is never regenerated — criterion 3's path reaches only a draft stopped before it entered review — and it goes to its destination only if a re-check later passes, or never, if the customer stops it. | `outstanding.test.ts › a draft with an outstanding re-check reports outstanding to the hand-off gate, whatever stage it sits in` and `… the entry it matched is the customer's own string`; `sweep.test.ts › a deferred draft is still outstanding` — the hand-off refusal itself is BP-015's `becomesPublishable`, whose call of this guard is BP-043's first `rests-on` |

**Discriminates (mutation check, constitution §8).**
- Storing the outstanding state as a flag makes `… outstanding the instant the list changes, with no job run in between` fail — and in production reintroduces the gap between the list changing and the drafts being marked, which is the whole reason for the hash.
- Raising the sweep's bound so it never defers leaves every test but `a site with 30 stale drafts checks 25 and defers 5` green; that test is the one holding the bound.
- Marking a deferred draft as checked would release it: `sweep.test.ts › every deferred draft is still outstanding afterwards` fails.
- Regenerating a held draft here would destroy customer text with no undo (ADR-070 point 4); no test can catch a successful-looking regeneration, which is why this module holds no write path to a draft's body at all.
