# WO-226 — Health as a state — checked in-line on read, never more than 24 hours old

- Branch: wo/WO-226-destination-health
- Estimate: ≤1 day

## Goal
Ship `checkHealth` and `ensureFreshHealth`: the seven-reason taxonomy, the DNS answer for hosted, the authenticated read for WordPress, and the in-line refresh that keeps the date the customer reads never more than 24 hours old.

## File plan

> This repository carries no `src/`, no `tests/`, no `supabase/` and no
> `package.json` (verified 2026-08-31). **Every path below is NEW** — none was
> verified to exist, because none can. Placement is anchored to
> `sdlc-factory/docs/registry/structure.md` and to this work order's blueprint
> `code:` globs, and is provisional against a repo with no code: if the
> implementer finds a file already present at one of these paths, they stop and
> log `failed` naming the drift rather than merging into it.

| File | New/Modify | Change |
|---|---|---|
| `src/lib/publish/destinations/health/check.ts` | NEW | `checkHealth(destinationId)`. For `hosted`, resolve `content.{sites.domain}` through BP-006's `resolvesInDns()`: unset → `expired`/`dns_unset`; resolving somewhere that is not our edge → `expired`/`dns_elsewhere`; resolving to us → `ok`. For any other kind, call `adapterFor(kind).health(cfg)` inside `withConfig`. Writes `health`, `health_reason`, `last_checked_at`, and `health_changed_at` **only when the health actually changed**; reaching `ok` clears `broken_mail_sent_at`. **Makes no write to a customer's site**, so a health check during a delivery cannot interfere with it. |
| `src/lib/publish/destinations/health/index.ts` | NEW | `ensureFreshHealth(destinationId)` — re-checks in-line when `last_checked_at` is older than `DESTINATION_HEALTH_MAX_AGE_H` (BP-005, 24), then returns the `DestinationView`. Debounced to at most one check per destination per 60 s, so a burst of page loads makes one check. Re-exports `checkHealth`. |
| `src/lib/publish/destinations/index.ts` | MODIFY | `listDestinations` now calls `ensureFreshHealth` for each of the site's destinations before returning, so the date the customer reads is fresh whether or not a publish was attempted. At most two destinations exist per site, so the read path does not fan out. |
| `tests/publish/destinations/health/health.test.ts` | NEW | Each of the three hosted DNS answers maps to its stated state and reason; an expired WordPress credential maps to `expired`/`credentials_expired`; `last_checked_at` after a `listDestinations` read is never older than 24 hours, on a fixture where no publish was ever attempted; the debounce collapses a burst of ten reads into one check; `health_changed_at` moves only on an actual change; reaching `ok` clears `broken_mail_sent_at`; a health check performs no write to the customer's site. |

- `withConfig` — WO-224.
- `DESTINATION_HEALTH_MAX_AGE_H: 24` — BP-005, `src/lib/config/constants.ts`, asserted in `tests/pins.test.ts`. Taken directly from REQ-074 criterion 1 and pinned rather than written in this module.
- `heldPages(siteId)` — BP-045, WO-210, for the view's count.

**Exposes** — copied exactly from BP-058's `## Public interface`:

```ts
// src/lib/publish/destinations/health/
export function checkHealth(destinationId: string): Promise<{ health: DestinationHealth; reason: HealthReason | null; checkedAt: Date }>
/** REQ-074 c1: re-checks in-line when `last_checked_at` is older than 24 h, then returns. */
export function ensureFreshHealth(destinationId: string): Promise<DestinationView>
```

**The freshness guarantee is on the read path, not on a job** (BP-058 decision
1). REQ-074 criterion 1's promise is about the date the customer reads, so it is
kept where the customer reads it — and it therefore cannot be stopped out of by
BP-003's kill switch, which stops `publish/execute` and `draft/generate`.

BP-058 decision 1 also **reports rather than makes** a change it judged cleaner:
a seventh job id, `destination/health`, is "not rejected on the merits" but is an
edit to BP-003, another node's file. This work order does not make that edit
either.

## Steps
1. Create `health/check.ts` with the seven-reason taxonomy and the two kinds' checks.
2. Write `health_changed_at` only on an actual change of `health`, and clear `broken_mail_sent_at` on every transition back to `ok` — that clearing is how "until it is reconnected and breaks again" is expressed as data.
3. Create `health/index.ts` with `ensureFreshHealth` and the 60 s debounce.
4. Modify `listDestinations` in `destinations/index.ts` to call `ensureFreshHealth` per destination before returning.
5. Assert the health check makes no write to a customer's site — the WordPress health call is a read of the REST index and nothing else.
6. Write the "last checked is never more than 24 hours old whether or not a publish was attempted" test first, on a fixture with zero publish attempts, and watch it fail against an implementation that refreshes only on publish (constitution §8).
