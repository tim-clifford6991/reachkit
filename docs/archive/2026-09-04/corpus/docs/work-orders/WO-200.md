## Goal
Add the claim-verdict column, define the one normalised list hash, and implement the check that matches the customer's recorded words first and a paraphrase second — and that says `unrun` rather than `passed` when it could not run.

## File plan
| File | New/Modify | Change |
|---|---|---|
| `supabase/migrations/20260901093000_drafts_claims.sql` | NEW | Adds `claim_check jsonb` to `drafts`, holding the last `ClaimVerdict` including the `listHash` the verdict was reached against, and the partial index `(site_id) where claim_check->>'state' <> 'passed'`. **No `outstanding` column, no `recheck_due` flag, no queue table, and no version column on `sites`** (BP-043 decision 2) — their absence is what makes the guard underivable from anything stale. |
| `src/lib/generate/claims/hash.ts` | NEW | `listHash(list: string[]): string` — entries trimmed, case-folded, sorted, joined, SHA-256. One definition, imported by the writer of a verdict and by the reader of the guard, so the two can never disagree (rule 2.4). |
| `src/lib/generate/claims/check.ts` | NEW | `ClaimVerdict` and `claimCheck` verbatim from BP-043's public interface. Normalised substring match over the list runs first and short-circuits; the nano `claim-check` call runs only where that finds nothing, and returns a boolean plus the matched entry's index. The string carried in a `failed` verdict is the customer's own recorded entry, read from their list — never model output (REQ-093 c1). An empty list passes at zero cost with the hash of the empty list. An `llm()` result that is `unmeasured`, or a cap hit, yields `state: 'unrun'` with its reason and never `passed`. |
| `tests/generate/claims/hash.test.ts` | NEW | Reordering, re-casing and re-spacing the list gives one hash; adding an entry changes it; the empty list has a stable hash. |
| `tests/generate/claims/check.test.ts` | NEW | A literal match fails with the customer's own entry as `matchedEntry` and makes no model call (asserted with a stub); a paraphrase with no literal match fails via the nano pass and still names the customer's entry, not the model's words; an empty list passes with the empty-list hash and makes no model call; an `unmeasured` model result yields `unrun` with `llm_unavailable`; a cap hit yields `unrun` with `cap_hit`; every verdict carries the hash of the list it was reached against. |

```ts
export type ClaimVerdict =
  | { state: 'passed';  listHash: string; at: Date }
  | { state: 'failed';  listHash: string; at: Date; matchedEntry: string }
  | { state: 'unrun';   reason: 'llm_unavailable' | 'cap_hit'; at: Date }

/** String/semantic match (BUILD.md §8 hard rule 4). Deterministic normalised
 *  match first; the nano pass runs only where that finds nothing, so an empty
 *  list and an obvious match both cost zero. */
export function claimCheck(c: CostContext, a: {
  text: string; list: string[]
}): Promise<ClaimVerdict>

/** The normalised hash of a site's list. One definition, used by the writer of
 *  a verdict and by the reader of the guard. */
export function listHash(list: string[]): string
```

## Steps
1. Write both test files first and run them; both must fail on a missing module and a missing column.
2. Write the migration, then `hash.ts`, then `check.ts`.
3. The nano schema admits a boolean and an index into the list — nothing else. The entry named to the customer is then read from their own list by that index, which is how a model's words cannot reach them (BP-043 decision 3).
4. `unrun` is a state, not an error and not a pass. ADR-070 point 6: "We could not check" is never "it passed".
5. Log the verdict state and a hash prefix only. Never the draft text and never a list entry — BP-043's observability line calls the list the customer's most sensitive field.
6. Run the tests. Then mutate: return `passed` on an `unmeasured` model result and confirm the `unrun` cases fail; drop the deterministic pass and confirm the literal-match case makes a model call it should not.

## Test plan

| Acceptance criterion (verbatim from REQ) | Test |
|---|---|
| **REQ-053 c1** Given the customer has recorded claims the product must never make, when a draft is generated, then it is checked against that list before it can be queued for review, and a draft matches when it states a recorded claim either in the recorded words or in a paraphrase of them. | `check.test.ts › a recorded claim in the recorded words fails` and `… a paraphrase of a recorded claim fails via the nano pass`; `hash.test.ts › one list, one hash` (the before-queuing half is WO-196's and WO-199's) |
| **REQ-053 c2** Given a generated draft that matches the list, when the check fails, then the draft is not queued for review and the item follows the recovery path in criterion 3, which bounds how often it may be regenerated. | `check.test.ts › a failed verdict names the customer's own recorded entry` — the not-queued half is WO-196's battery and WO-199's pipeline; the recovery path is WO-202's |

**Discriminates (mutation check, constitution §8).**
- Returning `passed` for an unrun check makes both `unrun` cases fail — and would let a forbidden claim publish on a bad vendor day, which is the harm REQ-053 exists to prevent.
- Naming the model's returned string instead of the customer's entry makes `… names the customer's own recorded entry` fail, and is how model output would reach a customer (REQ-093 c1).
- Normalising the hash differently in the writer and the reader is impossible while both import `listHash`; deleting that shared import and inlining one of them makes `hash.test.ts` pass and WO-201's guard tests fail, which is where the divergence would be caught.
