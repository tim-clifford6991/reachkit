# WO-086 — bandRivalSize — three bands from two counts, monotone and reachable at every customer count

- Branch: wo/WO-086-band-rival-size
- Estimate: ≤1 day

## Goal
Implement `src/lib/market/sizing/band.ts` — a pure, total function from a rival's ranked count
and the customer's own to one of three internal handles, with all three assignable at every
customer count including zero.

## Context an implementer needs
No source code exists on disk; both paths below are NEW.

**Handles here; words in `BAND_LABELS`** — BP-052 decision 4, recorded in **ADR-001**. This
module writes no customer-facing string. `RivalSizeBand` is `'near' | 'middle' | 'far'` and
nothing in this file maps a handle to a word: BP-019 owns `BAND_LABELS` and
`tests/pins.test.ts` (BP-005) asserts the two rendered sets are disjoint.

**The three words now exist, and that changes nothing here.** The owner ruled them on
2026-08-31 and BP-019's `BAND_LABELS.rivalSize` carries them under `band.rivalSize.near`,
`band.rivalSize.middle` and `band.rivalSize.far`; BP-019 decision 6 records that the
disjointness assertion **passes** on them rather than skipping. That releases the *screen*
this engine feeds, not this file. **This work order still may not write any of the three
strings**, and the `band/emits-handles-only` test below is what stops the ruling from being
read as permission to inline them here — a handle-to-word map in `band.ts` would be the
second copy rule 2.4 forbids, and the one BP-019 could no longer move.

**The band is derived, never stored as an independent column** (BP-052 decision 1): moving a
boundary re-renders every past measurement correctly with no migration and no re-measurement.

## Interfaces

**Exposes** — copied exactly from BP-052's `## Public interface`, comment included, because the
comment is the specification:

```ts
// src/lib/market/sizing/band.ts — pure, total, no I/O
export type RivalSizeBand = 'near' | 'middle' | 'far'          // internal handles (ADR-001)
export function bandRivalSize(a: { rivalRanked: number; ownRanked: number }): RivalSizeBand
//  near   : R <= max(RIVAL_SIZE_BANDS.nearFloor,   RIVAL_SIZE_BANDS.nearMultiple   × C)
//  middle : not near and R <= max(RIVAL_SIZE_BANDS.middleFloor, RIVAL_SIZE_BANDS.middleMultiple × C)
//  far    : above that
```

## Steps
1. Implement the two bars exactly as the comment states, reading all four operands from
   `RIVAL_SIZE_BANDS`. No literal `100`, `2`, `500` or `5` appears in this file
   (`structure.md` rule 5: a number that appears in two files is wrong).
2. Return `'near'`, `'middle'` or `'far'` — the function is total over all non-negative
   integers for both arguments and returns on every input, including `ownRanked: 0`.
3. Write **no** string mapping, no label, no export named for a word. Nothing in this file may
   be rendered.
4. Emit nothing: this function is called inside `sizeRivals` (WO-087), which owns the
   observability for the pair of counts and the derived band.
5. Write the tests; watch each fail first.

## Test plan

| 2. "Given a tracked rival whose size has been measured, when its band is recorded, then it carries exactly one of three bands, ordered by measured size and named in this requirement by the internal handles `near`, `middle` and `far`: `near`, where the rival appears in no more than the greater of 100 searches and twice the customer's own measured count — a rival roughly the customer's own size; `middle`, where it is not `near` and appears in no more than the greater of 500 searches and five times the customer's own count; and `far`, where it appears in more than that. Of any two rivals measured against the same customer count, the larger never carries a band ordered nearer than the smaller." | `tests/market/sizing/band.test.ts › band/two-bars-at-the-stated-counts` — a table over `(rivalRanked, ownRanked)` boundary pairs read from `RIVAL_SIZE_BANDS`: at `C = 0`, R = nearFloor ⇒ `near`, nearFloor+1 ⇒ `middle`, middleFloor ⇒ `middle`, middleFloor+1 ⇒ `far`; at `C = 1000`, R = 2000 ⇒ `near`, 2001 ⇒ `middle`, 5000 ⇒ `middle`, 5001 ⇒ `far`. `band/is-monotone` — a property test over `ownRanked` in 0…10,000 and pairs `R1 < R2`: the band of `R2` is never ordered nearer than the band of `R1`, under `near < middle < far`. |
| 8. "Given a customer who appears in no searches at all, when their tracked rivals are banded, then each still receives one of the three bands; and at every measured customer count, zero included, all three bands remain reachable — no customer's own count makes `near`, `middle` or `far` impossible to assign." | `tests/market/sizing/band.test.ts › band/all-three-reachable-at-every-C` — a property test over every `ownRanked` in 0…10,000: there exists an `R` yielding each of the three bands (the floors carry the expression at `C = 0`, and at every `C > 0` the multipliers differ, so the two bars never coincide). `band/zero-customer-count-is-not-special` — at `ownRanked: 0` the function returns normally for R = 0, 1, 100, 101, 500, 501 and 10,000, and throws on none. |
