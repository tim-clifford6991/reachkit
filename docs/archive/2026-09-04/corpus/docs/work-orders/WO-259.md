## Blocked-by — BP-039 decision 4 against BP-045's `PageRecord`
> Raised 2026-09-02 by the planner (rule 2.3: a conflict is an edge and a state,
> not a file). **The file plan below is complete and executable the moment one
> line of one blueprint changes; it is held because the input it needs does not
> exist on the type the blueprint says to compute it from.**

BP-039 decision 4 fixes the mechanism in terms: *"`WayThrough` is a two-arm
union computed from `PageRecord` alone, with three named grounds for refusal and
no fourth. `readDay` stays a pure read."* Its `## Error & edge behavior` repeats
it: *"every way through is offered or refused from `PageRecord`, which is stored
data."*

**BP-045's `PageRecord` carries none of the three facts a WordPress address is
formed from.** Its members are `draftId`, `state`, `opportunityId`,
`targetQuery`, `measuredAt`, `mode`, `address`, `unpublishOutcome` and
`verification`. There is no destination kind, no site base URL and no post id:
`WordPressConfig.baseUrl` lives in `destinations.config`, sealed by BP-058 and
holding the application password beside it, and `remoteId` — BP-048's
`WordPressDelivery.remoteId`, "the WordPress post id" — is stored on
`publications` and is described in BP-045 as *"Opaque to us; the post/page id at
the destination. Never rendered."*

Three things follow, and each of them is the same block:

1. `wayInsideTheirWordPress` cannot form an address from `PageRecord`.
2. It cannot decide `no_admin_address` either — that ground is *"no address
   inside that WordPress can be formed for that post"*, and a type that carries
   neither a base URL nor a post id cannot answer it.
3. It cannot tell a WordPress page from a hosted one, so it cannot return the
   `null` BP-039 requires *"at a destination ReachKit serves, where the criterion
   asks for no second way"* — and an absent second way and a refused one are
   different things the panel must render differently (WO-168).

**What would clear it**, and it is one edit: `PageRecord` gains what the panel
needs to read — the destination kind, the site's base URL and the post id, or a
single member already reduced to them. That is the architect's, not this
planner's: constitution §4 places type members and module boundaries with the
architect, and BP-045's `record/` is the node ADR-085 Decision 5 designates as
*"one place to read a page's observed state"*, which is exactly the shape of
this need. Two things argue for putting them there rather than letting this
module read `destinations.config` itself: `destinations.config` holds the
customer's application password, and a surface that reads it to get a base URL
is a credential in a render path; and BP-039's own boundary says this node
*"stores nothing and decides nothing about publishing"*.

**What is not blocked by it.** WO-258 — the union and the first way — is not
held and does not depend on this. WO-166 and WO-168 carry the second way as a
value they pass through and render, and are held for a different reason of their
own.

## Goal
Form, for a page ReachKit delivered to the customer's own WordPress, the one
address inside that WordPress that opens that post there — from what ReachKit
recorded at delivery and never from the customer's credential or a request —
and refuse it where no such address can be formed.

## File plan
| File | New/Modify | Change |
|---|---|---|
| `src/app/(account)/app/calendar/wordpress-way.ts` | NEW | `wayInsideTheirWordPress(record: PageRecord): WayThrough \| null` — pure, synchronous, **no import of `fetch`, of BP-006's `safeFetch`, or of anything under `src/lib/egress/**`**, and no read of `destinations.config`. Four arms in one fixed precedence: (1) the page was not delivered to a WordPress destination → `null`, the criterion asks for no second way at a destination ReachKit serves, and an absent way is not a refused one; (2) the base URL or the post id is missing for that post → refused, `because: 'no_admin_address'` — REQ-043 criterion 12's third ground in terms; (3) `record.state === 'unpublished'` → refused, `because: 'unpublished_by_us'`; (4) otherwise → `{ offered: true, href }`. **`page_not_found` is not a ground here**: criterion 12 scopes that ground to *"no page at the public address"*, and what the one check found at a public address says nothing about whether a post is in the customer's own admin. |
| `src/app/(account)/app/calendar/wordpress-way.ts` | (same file) | The address template, chosen under rule 1.1 and derived in `## Steps` step 3: `` `${baseUrl.replace(/\/+$/, '')}/wp-admin/post.php?post=${encodeURIComponent(postId)}&action=edit` ``. It is built from stored values only, is never interpolated with anything a customer typed into ReachKit, and carries no credential, no token and no query parameter of ReachKit's own. **It promises nothing about what opens there** — the customer arrives under whichever WordPress user they are signed in as, and REQ-043's non-goal places what they may do to the post with them and not with ReachKit. |
| `tests/app/calendar/wordpress-way.test.ts` | NEW | A WordPress page with both facts recorded returns an offered way whose `href` is exactly the template above, asserted against a literal expected string rather than against the template re-computed in the test; a base URL with a trailing slash produces exactly one slash before `wp-admin`; a post id is percent-encoded; a hosted page returns `null` and **not** a refusal; a WordPress page missing either fact is refused with `no_admin_address`; an unpublished WordPress page is refused with `unpublished_by_us`; a WordPress page whose one check recorded `page_not_found` is **still offered** — the public address's absence is not the admin address's; a WordPress page whose check recorded `could_not_confirm` is offered; every refusal carries a key that is in `OWNER_OWED`, and no returned value carries a sentence. |
| `tests/app/calendar/wordpress-way-safety.test.ts` | NEW | Three assertions the address must not violate. (a) The returned `href` never contains the application password, the username, or any substring of `destinations.config` — asserted against a fixture whose config values are distinctive sentinels, and by a source-level assertion that no file under `src/app/(account)/app/calendar/**` imports BP-058's `withConfig` or reads `destinations.config`. (b) The module makes no request when called, with the network stubbed to throw. (c) The `href` is built only from stored values: a fixture whose recorded base URL is a `javascript:` scheme is refused rather than rendered, so a stored value that is not an `http`/`https` origin cannot become an anchor's target. |

## Interfaces
**Consumes** (verbatim from WO-258's `## Interfaces`):
```ts
export type WayThrough =
  | { offered: true;  href: string }
  | { offered: false; because: 'unpublished_by_us' | 'page_not_found' | 'no_admin_address'
      copy: CopyKey }
export const REFUSAL_COPY: Readonly<Record<'unpublished_by_us' | 'page_not_found' | 'no_admin_address', CopyKey>>
```
and, verbatim from BP-048's `## Public interface`, the two recorded facts this
address is formed from — quoted here to show that both are things ReachKit
already has, and neither is a credential:
```ts
export interface WordPressConfig {          // the shape stored in destinations.config, sealed by BP-058
  baseUrl: string                           // the customer's site root; the REST root is derived, never stored twice
  username: string
  applicationPassword: string               // present only in memory, only inside one call
}

export type WordPressDelivery = DeliveryResult & {
  liveUrl: string
  madeLive: true
  remoteId: string                          // the WordPress post id
  seoWritten: readonly SeoPlugin[]
  stampApplied: boolean
  deliveredAt: Date
}
```
> **This work order reads neither of those two shapes directly** — see
> `## Blocked-by`. It reads `PageRecord`, and the two facts must reach it there.
> They are quoted so the architect's edit is a matter of moving two values, not
> of deciding what they are.

**Exposes**:
```ts
/** REQ-043 criterion 12's second way: an address inside the customer's own
 *  WordPress that opens that post there rather than at its public address,
 *  offered separately from the first way and never as a substitute for it.
 *  `null` at a destination ReachKit serves, where the criterion asks for no
 *  second way — which is not the same as a refusal and must not render alike.
 *  Pure and synchronous; it makes no request, this call or any call. */
export function wayInsideTheirWordPress(record: PageRecord): WayThrough | null
```

## Steps
1. Write both test files first and run them; both must fail on a missing module
   (§8, "Watch it fail first").
2. Implement the four arms in the precedence above. Write arm (1) — the `null` —
   before any other, so that a hosted page can never fall through into a
   refusal: telling a customer with no WordPress that a way into their WordPress
   leads nowhere is a sentence about a thing they do not have.
3. **The address template is a parameter chosen here under rule 1.1, and this is
   its derivation.** REQ-043 criterion 12 asks for "an address inside their own
   WordPress [that] opens that post there rather than at its public address".
   WordPress's post editor is the only address inside an install that opens one
   named post for whoever is signed in, and it is reached at
   `wp-admin/post.php?post=<id>&action=edit`. The two values it needs —
   `WordPressConfig.baseUrl` and `WordPressDelivery.remoteId` — are exactly the
   two REQ-043's own `rests-on` row names as "what it recorded at delivery".
   The `action=edit` parameter is part of the editor's address and is **not** a
   promise of editability: what the address opens depends on the WordPress user
   the customer is signed in as, which REQ-043's non-goal places with them.
   *Cost of reversing:* one template string, one expected literal in one test,
   and — if an install serves its admin elsewhere — a 404 inside the customer's
   own site rather than anything ReachKit can observe, which is why the
   assumption is a `rests-on` row and not a silent line of code.
4. Percent-encode the post id and normalise exactly one trailing slash off the
   base URL. Assert the result against a literal expected string in the test,
   never against the template re-computed there — a test that rebuilds the
   template asserts that the code equals itself.
5. Refuse any recorded base URL whose scheme is not `http` or `https`. The value
   is stored data rather than customer input to this surface, but it becomes an
   anchor's target on a page ReachKit renders, and `no_admin_address` is the
   ground already available for "no address inside that WordPress can be formed".
6. Run the tests. Then mutate, three ways: return a refusal for a hosted page
   instead of `null` and confirm the hosted case fails; add `page_not_found` as a
   ground here and confirm the still-offered case fails — the public address's
   absence says nothing about the customer's own admin; and interpolate the
   username into the address and confirm the sentinel assertion fails.

**Discriminates (mutation check, constitution §8).**
- **Returning a refusal for a hosted page instead of `null`** fails the hosted
  case and nothing else. The two render differently by design (WO-168) and the
  mutation puts a sentence about a WordPress they do not have in front of a
  customer who only ever used the hosted blog.
- **Adding `page_not_found` as a ground here** looks like consistency with
  WO-258 and fails the still-offered case. Criterion 12 scopes that ground to the
  *public* address, and the one check at 24 hours never looked inside the
  customer's admin — refusing on it would state, from an observation of one
  address, a fact about a different one.
- **Reading `destinations.config` to get the base URL** — the obvious way to
  unblock this work order without an architect — fails the sentinel and
  source-level assertions in `wordpress-way-safety.test.ts`. It puts the
  customer's application password one property access away from a render path.
- **Rebuilding the template inside the test** instead of asserting a literal
  makes every address assertion vacuous: it would survive any change to the
  template at all, which is the one thing these tests exist to hold.

## Out of scope
- **The `WayThrough` union, `REFUSAL_COPY` and the first way through** —
  WO-258's. This work order imports them and declares neither.
- **`DayDetail`, `readDay` and the panel** — WO-166 and WO-168. Offering the two
  ways separately, and rendering a refusal in place of a way rather than as an
  omission, are theirs.
- **Adding the two recorded facts to `PageRecord`** — the architect's; see
  `## Blocked-by`. This work order changes no file under `src/lib/publish/`.
- **Anything the customer does once they are inside their own WordPress**, and
  any promise that the post is still there or still editable. The address is
  formed from what ReachKit recorded at delivery; ReachKit has not looked at that
  post since, and REQ-043's non-goal places what happens there with the customer.
- **Any fetch of either address, now or ever**, including a probe of the admin
  address before offering it.
- **REQ-060 criterion 6's one place** — the list in the customer's own WordPress
  that brings every post ReachKit created there up together, which ADR-083's
  stamp answers and `WORDPRESS_STAMP_SLUG` names. That is a *bulk* address for a
  whole site; this is a *per-post* address, and the two answer different
  criteria. Neither substitutes for the other and this work order reads no stamp.
- Every customer-visible string. The `no_admin_address` key is WO-258's and its
  sentence is the owner's; this work order mints none.
- `src/lib/config/constants.ts` and `tests/pins.test.ts` — BP-005's alone
  (`structure.md` rules 4 and 5). The address template is a single template
  string in one module with one caller, not a number appearing in two files
  (rule 5); if a second module ever forms it, it moves to BP-005 by that rule.

## Rollback
