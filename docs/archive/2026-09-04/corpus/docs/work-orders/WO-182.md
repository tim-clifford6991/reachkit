## Goal
Implement the two bars, the three-band assignment, and the coercion that stops an unmeasured or capped ranked count from ever satisfying a bar — with `qualifies` and `bandWinnability` shaped so that a per-customer threshold has no argument to arrive through.

```ts
  | { kind: 'measured';   value: T; at: Date }

```

**Exposes** (verbatim from the blueprint):
```ts
/** Pure. Takes no site id, no options and no configuration, so criterion 13
 *  ("the threshold applied is identical for both") holds by construction:
 *  there is no argument through which a per-customer threshold could arrive. */
export function qualifyingBar(ownRanked: number): number      // max(500, 5 * ownRanked)
export function winnableBar(ownRanked: number): number        // max(100, 2 * ownRanked)
export function qualifies(a: { top10RankedCounts: Measured<number>[]; ownRanked: number }): boolean
export function bandWinnability(a: { top10RankedCounts: Measured<number>[]; ownRanked: number }): Winnability
```

## Steps
1. Write all three test files first and run them: every one must fail on a missing module.
2. Create `bars.ts`. **Import `WINNABILITY` from `src/lib/config/constants.ts` and declare no number in this file.** The four are REQ-047 c9's and c10's own (`the greater of 500 searches and five times`, `the greater of 100 searches and twice`) and BP-005 has held them since it was cut, as `WINNABILITY`; BP-040's public interface says so in the same block that declares the two bars. Declaring them again here — the shape a previous cut of this work order carried, as `QUALIFYING_FLOOR`/`WINNABLE_FLOOR` — is the second copy of a pin `structure.md` rule 5 forbids, and it is invisible: both copies read 500 and 100 on the day they are written. Cost of reversing a retune: one edit to `constants.ts` and one to `tests/pins.test.ts`, both BP-005's — nothing here, and nothing stored. `bars.test.ts`'s property sweep fails immediately if `WINNABILITY.nearFloor` is raised to 500, which is the guard BP-040's error-and-edge section names.
3. Create `band.ts`. The `Measured` kind check comes first, so an `unmeasured` count cannot reach a numeric comparison at all.
4. Create `counts.ts`. `qualifies` takes no cap argument by design (that is what makes c13 structural), so the cap coercion happens here, before the argument is built.
5. Run the tests. Then mutate: make `unmeasured` satisfy a bar and confirm the c9 test fails; drop the `rowCap` coercion and confirm the capped-count test fails; add `siteId?: string` to `qualifies`' parameter and confirm `tsc --noEmit` fails.

**Discriminates (mutation check, constitution §8).**
- Deleting the `Measured`-kind guard in `band.ts` makes the all-unmeasured test pass a bar and fails the c9 test — the test asserts the rejection, not merely the acceptance.
- Raising `WINNABILITY.nearFloor` to 500 in `constants.ts` makes the strict-inequality property fail for every `ownRanked` under 250, which is exactly the change REQ-047's second `rests-on` says would make the Reach band unreachable. It fails **only** while the bars read the pin: re-declaring the four numbers locally makes this mutation pass silently, which is why the file plan bans a local copy and `bars.test.ts` asserts the bars against `WINNABILITY`'s own members.
- Adding an optional member to either parameter object breaks `shape.test.ts`'s `Equals` assertion under `tsc --noEmit`; a test that only called the functions would survive that mutation, which is why the compile-time assertion is the test of record for c13.
