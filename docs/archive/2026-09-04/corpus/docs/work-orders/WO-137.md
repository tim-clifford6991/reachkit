# WO-137 — The account card and the email change — the new address proves itself before the old one stops working

- Branch: wo/WO-137-email-change
- Estimate: ≤1 day

## Goal
Move an account's sign-in address safely: hold the change pending until the new
address redeems its link, then switch, end the other sessions and write once to
the old address — and let the customer see, cancel or replace the pending change
until it lapses.

## File plan
> **Every path below is NEW except `links.ts`.** No `src/` exists; `links.ts` is
> created by WO-136 and modified here, which is why these two work orders are
> sequential and not parallel. Anchored to `registry/structure.md` and BP-061's
> `code:` glob `src/lib/account/session/**`. Provisional against a repo with no
> code.

| File | New/Modify | Change |
|---|---|---|
| `src/lib/account/session/email-change.ts` | NEW | Exports `accountCard`, `beginEmailChange` and `cancelEmailChange` with BP-061's signatures verbatim. `beginEmailChange` writes **only** the three pending columns and issues an `email_change` link to the new address; `users.email` is not touched. The in-use check reads `users.email` and `users.pending_email` together **through `dbAdmin()`**, so a soft-deleted account inside its 30-day window still refuses (BP-061's error behavior; ADR-051 point 5 — "the row is present but hidden"). Validity is a syntactic check plus a deliverability attempt: no MX probe, no disposable-domain list. `cancelEmailChange` clears all three columns atomically and spends any live `email_change` token. `accountCard` returns `noteKeys` verbatim and **never** returns an invoice address (REQ-076 c2). |
| `src/lib/account/session/links.ts` | MODIFY | Add the `email_change` completion branch to `redeemLink`'s existing transaction: set `users.email` to `pending_email`, clear the three pending columns, mark every unspent token for that user spent, end all other sessions for that user, create a session at the new address, and send one `account` mail to the **old** address. The change stands even if that mail fails, and the failure is raised (BP-061: "reverting an address the customer has already proved would lock them out of the account they just moved"). No other line of `links.ts` changes. |
| `tests/account/session/email-change.test.ts` | NEW | Begin writes only the pending columns and leaves `users.email` intact; the old address still signs in while a change is pending; `in_use` for an existing account, for a pending address held by another customer, and for a soft-deleted account's address; `invalid` for a syntactically bad address; both refusals send no link and change nothing; cancel clears the pending state and leaves the account unchanged; a change not redeemed within `EMAIL_CHANGE_TTL_H` lapses and the account is unchanged; `accountCard` returns the pending address and its expiry, and returns no invoice address on any path. |
| `tests/account/session/email-change-complete.test.ts` | NEW | Redemption switches the address; **only** the new address can sign in afterwards and the old one cannot; every other session for that user is ended; exactly one `account` mail goes to the **old** address; a failing mail leaves the change standing and raises. The mutation case: deleting the other-sessions termination fails `› every other session is ended`. |

## Interfaces
Exposes (verbatim from BP-061's `## Public interface`):
```ts
export function accountCard(userId: string): Promise<{
  name: string | null
  email: string
  pending: { email: string; expiresAt: Date } | null
  noteKeys: readonly ['account.magic_link_note', 'account.invoices_go_to_billing']
}>

export function beginEmailChange(userId: string, next: string): Promise<
  | { ok: true; expiresAt: Date }
  | { ok: false; reason: 'in_use';  lineKey: 'account.email_in_use' }
  | { ok: false; reason: 'invalid'; lineKey: 'account.email_invalid' }
>

export function cancelEmailChange(userId: string): Promise<void>
```
Consumes: `issueLink` and `redeemLink` (WO-136, BP-061's signatures);
`sendEmail` (BP-016) with `'account': { occasionsFrom: 'REQ-024, REQ-074, REQ-076, REQ-077, REQ-079', stoppable: false }`;
`dbAdmin()` (BP-002); BP-005's `EMAIL_CHANGE_TTL_H: 24`.

## Rollback
Delete `email-change.ts` and both test files, and revert the one branch added to
`links.ts`. Addresses already changed stay changed — the customer proved the new
one, and reverting it would be the lock-out this requirement exists to prevent.
