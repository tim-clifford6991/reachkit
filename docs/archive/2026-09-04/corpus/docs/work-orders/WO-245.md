# WO-245 — `POST /api/drafts/{id}/{approve|veto|skip}` — the three transport adapters over the publishing machine

- Branch: wo/WO-245-api-draft-actions
- Estimate: ≤1 day

## Goal
Turn the three actions a customer takes on a draft into exactly three calls to
BP-045's `transition`, so that what may follow an approval, a veto or a skip is
the state machine's answer and never a route's.

## Provenance of this file plan
**This repository holds no `src/`.** Every path is NEW under BP-001's glob
`src/app/api/**`, which decision 1 fixes as this container's "without exception".
BP-001's delegation table names the target: "BP-046's publishable predicate and
BP-045's `transition`", behind it REQ-045 and REQ-057. WO-169 lists these three
routes in its own out-of-scope as "the publishing node's and … deliberately not
globbed by BP-044" — that reading is superseded by BP-001 decision 1 and by the
delegation table, which put every `src/app/api/**` file here; reported with this
block's return. Nothing under `src/lib/publish/**` is touched either way.

## File plan
| File | New/Modify | Change |
|---|---|---|
| `src/app/api/drafts/[id]/approve/route.ts` | NEW | The `POST` adapter, wrapped in WO-004's `adapter()`. Session plus draft ownership, then one call: `transition(id, 'approved', { kind: 'customer', userId })`. Maps `{ ok: true; state }` to 200 with the state, and `{ ok: false; refused; failedGuard?; state }` to 409 with the refusal's copy key and the unchanged state. Reads no veto window, computes no publish time and calls no publish. |
| `src/app/api/drafts/[id]/veto/route.ts` | NEW | The same shape, calling `transition(id, 'skipped', { kind: 'customer', userId }, 'veto')`. REQ-056 criterion 3 makes veto and skip one destination state; the two routes differ only in the `reason` they record, which is what keeps the customer's two distinct actions distinguishable in history without adding a state. |
| `src/app/api/drafts/[id]/skip/route.ts` | NEW | The same shape, calling `transition(id, 'skipped', { kind: 'customer', userId }, 'skip')`. |
| `src/app/api/drafts/[id]/_action.ts` | NEW | The one shared body of the three: session, ownership, one `transition` call, one response mapping. Each route file is three lines over it. It is **transport only** — it holds no guard, no state name of its own beyond the target it is passed, and imports `src/lib/publish/machine` and `src/lib/account/session` and nothing else. Three sibling files calling one local helper is not "logic in an adapter"; three copies of the same twelve lines would be. |
| `tests/app/drafts/actions.test.ts` | NEW | The suites below. |

## Interfaces

Consumes (verbatim from BP-045 `## Public interface`):
```ts
export type State =
  | 'planned' | 'generating' | 'in_review' | 'approved' | 'publishing'
  | 'published' | 'skipped' | 'failed' | 'needs_attention' | 'unpublished'

export type Actor =
  | { kind: 'customer'; userId: string }
  | { kind: 'system'; job: 'draft/generate' | 'publish/execute' | 'publish/verify' }

export type Refusal = 'not_a_transition' | 'guard'

export function transition(
  draftId: string, to: State, by: Actor, reason?: string
): Promise<
  | { ok: true; state: State }
  | { ok: false; refused: Refusal; failedGuard?: GuardId; state: State }
>
```
Consumes (verbatim from BP-061 `## Public interface`):
```ts
export function currentSession(): Promise<{ userId: string; siteId: string } | null>
```
Exposes (verbatim from BP-001 `## Public interface`):
```
  POST /api/drafts/{id}/{approve|veto|skip}
```
`becomesPublishable` is **consumed by `transition`'s guards, not by these
routes**: BP-045 lists `publishable_and_due` and `customer_told` among the guards
on `approved → publishing` and names BP-046 as their source. A route that called
the predicate itself would be the second decision point REQ-057 criterion 2's
"under this rule and no other" forbids, so none of these four files imports it.

## Steps
1. Write the failing suites first, the "an approval does not publish" case first
   of all.
2. Write `_action.ts`: read the session (none → the sign-in response), read the
   draft's `siteId` and refuse where it is not the session's, call `transition`
   with the target and actor passed in, and map the two arms.
3. Write the three route files over it, each supplying its target state and its
   `reason`.
4. Map `{ ok: false }`: `refused: 'not_a_transition'` and `refused: 'guard'` get
   distinct copy keys, and the response carries `state` unchanged — REQ-056
   criterion 2's "any other attempted change is refused with the page's state
   unchanged" is the machine's, and this is the transport not hiding it.
5. Emit WO-004's log line with the draft id and the outcome; never the body,
   never the draft's text.

| Acceptance criterion (verbatim from REQ) | Test |

| REQ-045 c4 — "Given a draft awaiting review, when the customer reads it, then they are told what will happen if they do nothing, and can approve, edit or veto without leaving the view." | `draft-actions/routes · three actions, each one call` — each of the three routes exists, accepts `POST` only, and calls `transition` exactly once with its own target and `{ kind: 'customer', userId }`; each returns without a redirect, so the view the customer is in is never left. The telling ("what will happen if they do nothing") is WO-169's `doNothing` and the controls are WO-172's; this is the half that makes the actions reachable from that view. |
| REQ-057 c2 — "Given a page in review, when it publishes, then it publishes under this rule and no other: a page becomes publishable when its veto window has expired or it was explicitly approved, and no edit is unsaved and no claim re-check is outstanding (REQ-053 criterion 5, which fixes when one stands outstanding on a draft and how it clears); it publishes at the first publish time at or after it becomes publishable, and never before." | `draft-actions/approve · approving is not publishing` — a successful approval returns `state: 'approved'` and is asserted to make no call that publishes: no `publish`, no `transition(_, 'publishing', _)`, no destination adapter, no job enqueue, asserted by spy across the module surface. And `draft-actions/approve · the predicate is not reachable from a route` — a source assertion that none of the four files resolves an import into `src/lib/publish/publishable/**`, so "publishable" is decided once, inside the machine's guards. Removing the guard call from `transition` is BP-046's mutation; short-circuiting it from a route is this one. |
| REQ-057 c3 — "Given copilot mode, when the veto window expires without an explicit approval, then expiry does not make the page publishable — only an explicit approval does — so the page does not publish and remains in review." | `draft-actions/approve · a refusal leaves the state where it was` — where `transition` refuses, the response carries `refused` and the returned `state` equals the state before the call, and the route performs no second attempt and no fallback transition. The mode itself is never read here: a source assertion that no file names `copilot`, `autopilot` or a veto window, so the two modes cannot diverge at the transport. |

  rendering criteria (1, 2, 3) and its edit criteria (5 to 11) are theirs and
  WO-170's; criterion 4's "can approve … or veto without leaving the view" is
  the only half these routes discharge, and criterion 12's copy-out is WO-171's.
- Any written sentence: these routes return copy keys.

## Rollback
Delete the five files. No customer action can reach the machine, which leaves
every draft in review until its window governs it — a behaviour REQ-057
criterion 3 already defines, so nothing is left in an undefined state.
