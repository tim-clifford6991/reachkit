# WO-111 — captureLead() — one insert, confirmed only after it commits

- Branch: wo/WO-111-capture-lead

- Estimate: ≤1 day

## Goal
Accept an address, write one `leads` row carrying the scan's domain, and fail
closed — refusing in writing and confirming nothing — when the store will not take
it.

## Provisional against an empty repo
**No `src/` exists.** Both files NEW, inside BP-029's `src/lib/mail/leads/**`
glob.

Reuse check (rule 7.2): no lead capture exists in the index or on disk.
`dbAdmin()` (BP-002) is the server-only client this WO consumes — `leads` is
RLS default-deny and a visitor holds no session, so the insert runs server-side
through the admin client from BP-001's thin route adapter, never from a browser.

## Read ADR-041 before adding a suppression check here
Capture does **not** consult `email_suppressions`. A suppressed address that
submits the control for a different domain still gets that domain's page —
REQ-010 c3 against c11 — and the mechanism that makes it so is the register row
`stoppable: false`, not a branch here. Adding one "for safety" is the third of
ADR-041's three honest-looking fixes.

## File plan
| File | New/Modify | Change |
|---|---|---|
| `src/lib/mail/leads/capture.ts` | NEW | `captureLead()` verbatim from BP-029's signature. Validates the address's **form** only, then one insert into `leads` carrying `scan_id`, lowercased `email`, and `domain` read from the scan (BP-029 decision 1: written at capture, thereafter read-only), with `sequence_state` null and `first_page_state` `pending`. Returns `{ captured: true, leadId }` only after the row commits. Any store failure returns `{ captured: false, reason: 'unavailable' }`; a malformed address returns `{ captured: false, reason: 'invalid-address' }` and writes nothing. Enqueues nothing and calls no model — writing and sending happen in the job (BP-029 decision 3). |
| `tests/mail/leads/capture.test.ts` | NEW | The two refusal reasons, the commit-then-confirm order, the domain write, and the negative property that nothing is enqueued. |

## Interfaces
**Exposes** (verbatim from BP-029 `## Public interface`):
```ts
// src/lib/mail/leads/capture.ts
/** Criterion 1's control accepts an address and nothing else. Criterion 3's
 *  delivery is enqueued, never awaited: the visitor's confirmation states the
 *  address was accepted, which is the only thing true at that moment. */
export function captureLead(a: {
  scanId: string
  email: string
}): Promise<
  | { captured: true; leadId: string }
  | { captured: false; reason: 'invalid-address' | 'unavailable' }>   // REQ-003 c10
```
**Consumes**: `dbAdmin()` (BP-002); the `leads` schema (WO-109);
`firstPageOffer()` (WO-110) only to read the scan's domain and to refuse a
capture for a scan with no offer.

## Steps
1. Write `capture.test.ts` first and watch it fail.
2. Implement form validation, then the insert, then the return. In that order:
   the confirmation is the last statement in the function, so no code path can
   confirm before the commit.
3. Assert the module's dependency set contains no queue, no `llm()`, and no
   `generateDraft` import (BP-029 NFR budget: capture is "one insert; p95 under
   300 ms").
4. Mutation check: move the return above the insert's await and confirm the
   fail-closed test fails; add an `email_suppressions` read and confirm the
   ADR-041 dependency assertion fails.
