# WO-054 — The score and its band — `factorsOf`, `presenceOf`, `computeScore`, `bandOf`

- Branch: wo/WO-054-score-bands
- Estimate: ≤1 day

## Goal
Ship `BUILD.md` §5's arithmetic over `Measured` values and the four band handles,
such that a single unmeasured factor yields an unmeasured score with no band, no
estimate and no interpolation — the property ADR-021 exists to protect.

## File plan

> Every path below is **NEW**. Verified 2026-08-31: this repo carries no `src/`.
> Placement per `structure.md`; provisional against a repo with no code.

| File | New/Modify | Change |
|---|---|---|
| `src/lib/measure/score.ts` | NEW | `ScoreFactorName`, `ScoreFactors`, `presenceOf`, `factorsOf`, `computeScore`. All arithmetic runs through WO-052's `combine`, so no branch can reach a raw number from an `unmeasured` arm. `computeScore` takes exactly one parameter and no flag (ADR-021 decision 3). Floors: Answerability and Presence are floored at 1, and a floor applies only to a `measured` or `zero` arm. |
| `src/lib/measure/bands.ts` | NEW | `BandHandle` and `bandOf(score: number): BandHandle`, reading the four boundaries from BP-005's `SCORE_BAND_BOUNDS` — `{ invisible: 0, 'hard-to-find': 25, findable: 50, dominant: 75 }`, imported, never written here (`structure.md` rule 5, and BP-024's own comment on `bandOf`). **No numeric literal 0, 25, 50 or 75 appears in this file.** No band word appears in it either; the words are BP-019's `SCORE_BANDS`. |

## Interfaces

Consumes: WO-052's `Measured<T>`, `combine`, `mapMeasured`, `worseReason`;
BP-010's `Drivers` (`src/lib/measure/index.ts`, another node's file — the four
measured quantities `foundations`, `answerability`, `searchPresence`,
`aiPresence`, each a `Measured<number>`); BP-005's `SCORE_BAND_BOUNDS`.

Exposes (verbatim from BP-024 `## Public interface`, `src/lib/measure/score.ts`
and `bands.ts`):

```ts
/** The three the score is composed of, and the three the report shows beside it
 *  (REQ-004 c2, `BUILD.md` §4.1's "three driver mini-bars"). `Presence` is the
 *  geometric mean of BP-010's `searchPresence` and `aiPresence`, floored at 1
 *  (`BUILD.md` §5) — those two are sub-measures, not shown factors. */
export type ScoreFactorName = 'foundations' | 'answerability' | 'presence'
export type ScoreFactors = Readonly<Record<ScoreFactorName, Measured<number>>>

export function presenceOf(d: Pick<Drivers, 'searchPresence' | 'aiPresence'>): Measured<number>
export function factorsOf(d: Drivers): ScoreFactors
export function computeScore(f: ScoreFactors): Measured<{ score: number; band: BandHandle }>
export type BandHandle = 'invisible' | 'hard-to-find' | 'findable' | 'dominant'
export function bandOf(score: number): BandHandle   // thresholds are BP-005's SCORE_BAND_BOUNDS
```

The arithmetic, verbatim from `BUILD.md` §5: `Presence = max(1, √(SearchPresence
× AIPresence))`; `Score = round( ∛(Foundations × Answerability × Presence) )`;
`Bands: 0–24 Invisible · 25–49 Hard to find · 50–74 Findable · 75–100 Dominant`.

## Steps
1. Write the failing suites first, ADR-021's three prohibitions included.
2. Declare `ScoreFactorName`, `ScoreFactors`, `BandHandle`.
3. Implement `bandOf` over `SCORE_BAND_BOUNDS`, descending through its four
   lower bounds, with a total switch and no default arm that could swallow an
   out-of-range value; assert the input range at the boundary instead. The pin is
   the only source of a threshold: a source assertion in the suite fails on any
   numeric literal in `bands.ts` other than the range guard's own 0 and 100.
4. Implement `presenceOf` with `combine([searchPresence, aiPresence], …)` and the
   floor of 1 applied inside the combining function, so it can only ever apply to
   a value that exists.
5. Implement `factorsOf`: `foundations` and `answerability` pass through from
   `Drivers` (answerability floored at 1), `presence` is `presenceOf`.
6. Implement `computeScore` with `combine([foundations, answerability, presence],
   …)`. Take no second parameter. Do not export a partial variant, an `options`
   object, or a `force` flag — ADR-021 decision 3.
7. Add each ADR-021 test with a failure message naming `ADR-021` (that ADR's
   consequence: "each names this ADR in its failure message").
