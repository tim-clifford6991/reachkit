## Goal
Implement `rankScore` and `rankOpen` so the calendar fills empty future days from open supply in the ranking's order, with `unblock` unranked and a `not-yet` target unqueueable.

## File plan
| File | New/Modify | Change |
|---|---|---|
| `src/lib/opportunities/rank/score.ts` | NEW | `rankScore` — `demand x intent x (1 - effort) x fit` with `demand = min(1, log10(volume + 1) / 5)` (an `unmeasured` volume gives `demand = 0`, never a default), `intent = intentWeight(a.query, a.profile) / 3` — **BP-011's exported classifier, called with the required `Profile` this argument object now carries, never a local re-classification** (BP-011 decision 2, rule 2.4) — `effort` from BP-005's `EFFORT_BY_TYPE`, `fit` from BP-005's `FIT_WEIGHT` (`not-yet` is 0, so a `not-yet` target cannot be ranked above anything even if a caller passes one). **Exposes** (verbatim from the blueprint):
```ts
// ---- ranking (BUILD.md §7: demand x intent x (1-effort) x fit) --------------
export interface Ranked { opportunityId: string; score: number }
/** `profile` is required because the intent term is BP-011's
 *  `intentWeight(keyword, p)`, whose second parameter is not optional and whose
 *  node explicitly rejects a second classifier (BP-011 decision 2). There is no
 *  arm of this function that ranks without a profile, and no default profile:
 *  ranking a search whose intent cannot be classified against the site it was
 *  selected for would be a second classification (rule 2.4). `rankOpen` loads
 *  the site's profile once per call and passes it to every row. */
export function rankScore(a: {
  volume: Measured<number>; query: string; type: OpportunityType
  fit: Winnability; profile: Profile
}): number
export function rankOpen(siteId: string): Promise<Ranked[]>   // computed, never stored
```

**Where `rankOpen` reads the profile, and the one thing it must not do.** BP-040
says only that it "loads the site's profile once per call". Two blueprints
disagree about where that profile is: BP-025's data-model delta says the scan
blob holds it (`report.market = { profile, suggestions, totalVolume }`), and
BP-012's `StoredReport` — the declared shape of that blob, added specifically so
consumers stop inventing reader interfaces — declares `market:
Measured<SuggestionRow[]>` and no profile field anywhere. Read the second
`rests-on` row above before starting. The implementer's rule is fixed and has no
third option:

- If the `StoredReport` on disk exposes the site's `Profile` when this work
  order starts, `rankOpen` reads it from there through BP-012's
  `readCurrentReport`, once, before the loop.
- If it does not, the implementer **stops and logs `failed — next: the
  StoredReport / report.market disagreement between BP-012 and BP-025, reported
  by the planner 2026-08-31`**. They do not call `deriveProfile` (a vendor call
  inside a read path, and a second derivation), do not widen `StoredReport`
  (BP-012's file, not this node's), and do not construct a partial `Profile`
  from what the blob does carry — a fabricated drop set silently changes which
  searches score zero.

## Steps
1. Write both test files first and run them; both must fail on a missing module.
2. Implement `score.ts` against the signature in the Exposes block above, copied verbatim — `profile: Profile` is a required member and nothing in this file classifies intent itself. Importing `intentWeight` from BP-011 is the whole of the intent term; a `switch` on keyword shape anywhere in `src/lib/opportunities/` is the second classifier BP-011 decision 2 rejects.
3. Implement `open.ts` as a single indexed read plus one profile load plus an in-process sort; assert both counts in the test so neither a per-row lookup nor a per-row profile load can creep in. If the profile is not readable, take the stop condition under Interfaces — do not improvise one.
4. Mutate: give `not-yet` a non-zero fit weight and confirm the c10 ordering test fails.
5. Mutate: ignore `a.profile` inside `rankScore` and pass a constant profile to `intentWeight`; confirm the two-profile fixture test fails. A test that only checked ordering within one profile would survive this, which is why that fixture exists.

**Discriminates (mutation check, constitution §8).**
- Setting `FIT_WEIGHT['not-yet']` above 0 makes a `not-yet` target sortable above a `reach` target and fails `score.test.ts`.
- Deleting the `family <> 'fix'` predicate in `rankOpen` makes `open.test.ts › no unblock row appears` fail.
- Replacing `intentWeight` with a locally written classifier leaves every single-profile ordering test passing — which is why `score.test.ts` scores one query against two `Profile` fixtures whose `brandTokens` differ: a local classifier that ignores the profile returns the same weight for both and fails. This is the test of record for BP-011 decision 2 at this seam.
