# WO-207 — The transition table — ten states, fifteen edges, two terminal, eight named guards, as frozen data

- Branch: wo/WO-207-transition-table

## Goal
Ship `STATES`, `TRANSITIONS`, `TERMINAL`, `Refusal`, `GuardId` and `GUARDS` as frozen data, and the property tests that pin them member by member to REQ-056 criteria 1, 2 and 3.

## Interfaces

**Consumes**

- `State` from `src/lib/publish/types.ts` (WO-206).

**Exposes** — copied exactly from BP-045's `## Public interface`:

```ts
// src/lib/publish/machine/index.ts
export const STATES: readonly State[]                                   // exactly ten
export const TRANSITIONS: readonly (readonly [State, State])[]          // exactly fifteen
export const TERMINAL: readonly State[]                                 // ['skipped','unpublished']

export type Refusal = 'not_a_transition' | 'guard'
export type GuardId =
  | 'draft_passed_hard_rules'      // needs_attention → publishing
  | 'never_entered_review'         // needs_attention → generating
  | 'customer_initiated'           // needs_attention → generating
  | 'publishable_and_due'          // approved → publishing, failed → publishing (BP-046)
  | 'customer_told'                // approved → publishing — REQ-057 c8, via BP-046
  | 'publishing_switch_on'         // every edge whose target is 'publishing'
  | 'within_ceilings'              // every edge whose target is 'publishing'
  | 'destination_working'          // every edge whose target is 'publishing'

export const GUARDS: Readonly<Record<string, readonly GuardId[]>>  // keyed 'from→to'
```

The names above are BP-045's and are the public contract. This work order puts
them in `machine/table.ts` and WO-209 re-exports them from `machine/index.ts`
alongside `transition()`, so the import path BP-045 declares is the one every
consumer uses. Splitting the data from the function is a file-plan choice (rule
1.1): the table must be assertable without a database, and `transition()` needs
one. Cost of reversing: merge two files.

## Steps
1. Transcribe the fifteen edges from REQ-056 criterion 2, in the order the criterion lists them, into `TRANSITIONS`. Do not derive them, do not sort them, do not generate them.
2. Transcribe the ten states from REQ-056 criterion 1 into `STATES`.
3. Set `TERMINAL = ['skipped','unpublished']` and assert it is exactly the set of states that are the source of no edge — a derived check, not a second list.
4. Populate `GUARDS`: `needs_attention→publishing` ⇒ `[draft_passed_hard_rules, publishing_switch_on, within_ceilings, destination_working]`; `needs_attention→generating` ⇒ `[never_entered_review, customer_initiated]`; `approved→publishing` and `failed→publishing` ⇒ `[publishable_and_due, customer_told, publishing_switch_on, within_ceilings, destination_working]`. Every other key is absent, meaning no guard.
5. Freeze every export.
6. Write the property tests and watch them fail against an empty table before the table is filled (constitution §8).

## Test plan

Each criterion below is inherited verbatim from the requirement named in the
row, reflowed onto one line and otherwise unaltered.

| Acceptance criterion (verbatim from REQ) | Test |
|---|---|
| **REQ-056 c1** — Given a page in the pipeline, when it is inspected at any moment, then it is in exactly one of `planned`, `generating`, `in_review`, `approved`, `publishing`, `published`, `skipped`, `failed`, `needs_attention` or `unpublished`, and no other state exists. | `tests/publish/machine/table.test.ts` › "STATES is exactly REQ-056 criterion 1's ten" — asserts membership and length against the criterion quoted in the test file. |
| **REQ-056 c2** — Given a page in any state, when its state changes, then the change is one of these fifteen and no other, and any other attempted change is refused with the page's state unchanged: `planned`→`generating`, `planned`→`skipped`, `generating`→`in_review`, `generating`→`needs_attention` (any generation that produced no draft fit for review, whatever stopped it — a generation hard rule for the second time, REQ-053 criterion 3, or a step that failed, REQ-092 criterion 1 — so no failure leaves a page resting in `generating`), `in_review`→`approved`, `in_review`→`skipped` (a draft held by a failed claim re-check leaves review by one of these two and by no other, REQ-053 criterion 5), `approved`→`publishing`, `publishing`→`published`, `publishing`→`failed`, `failed`→`publishing`, `failed`→`needs_attention`, `needs_attention`→`publishing` (open only to a page holding a draft that passed every generation hard rule, so a draft one of those rules stopped is never published by starting an attempt), `needs_attention`→`generating` (open only to a page whose draft never entered review, and only when the customer starts it, so REQ-053 criterion 3's bound on automatic regeneration is never raised), `needs_attention`→`skipped`, `published`→`unpublished`. | `tests/publish/machine/table.test.ts` › "TRANSITIONS is exactly REQ-056 criterion 2's fifteen" — member by member against the quoted clause, plus "no sixteenth edge" and "no duplicate edge". |
| **REQ-056 c3** — Given a page in `planned`, `in_review` or `needs_attention`, when the customer skips, vetoes or discards it, then it moves to `skipped` and never publishes. `skipped` and `unpublished` are the only states from which no further change is possible, so a page the customer stopped or took down is never returned to a destination by any later attempt, and no page — whichever route brought it to `needs_attention` — is left in a state it has no way out of. | `tests/publish/machine/table.test.ts` › "skipped and unpublished are the source of no edge" and › "every non-terminal state has at least one exit" — the second stated as a property over TRANSITIONS so a future edit to the table cannot strand a state. |
