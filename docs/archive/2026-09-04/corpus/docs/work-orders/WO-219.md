# WO-219 — nextPublishTimeAtOrAfter() — the publish hour in the customer's own zone, including the two days a year it is ambiguous

- Branch: wo/WO-219-publish-clock
- Estimate: ≤1 day

## Goal
Ship the one resolution of "the next publish time", in the customer's stated zone, with the spring-forward and autumn-back cases each given one stated answer.

## File plan

> This repository carries no `src/`, no `tests/`, no `supabase/` and no
> `package.json` (verified 2026-08-31). **Every path below is NEW** — none was
> verified to exist, because none can. Placement is anchored to
> `sdlc-factory/docs/registry/structure.md` and to this work order's blueprint
> `code:` globs, and is provisional against a repo with no code: if the
> implementer finds a file already present at one of these paths, they stop and
> log `failed` naming the drift rather than merging into it.

| File | New/Modify | Change |
|---|---|---|
| `src/lib/publish/settings/clock.ts` | NEW | `nextPublishTimeAtOrAfter(instant, s)`. Resolves `s.publishTime` in `s.timezone` and returns the first such instant at or after `instant`. **No code path falls back to the server's zone.** A publish time that does not exist on a spring-forward day resolves to the first instant after the gap; a time that occurs twice on an autumn-back day resolves to the first of the two — both chosen in BP-057's error-and-edge section under rule 1.1, both asserted against a fixed zone. |
| `tests/publish/settings/clock.test.ts` | NEW | Fixtures at a fixed zone and a fixed clock: an ordinary day; the instant exactly at the publish time (returns that instant, not the next day); the spring-forward gap; the autumn-back repetition; a zone east and a zone west of UTC give different instants for the same wall time; a settings object with an empty zone throws rather than defaulting. |

## Interfaces

**Consumes**

- `PublishingSettings` — `src/lib/publish/settings/settings.ts` (WO-218).
- The runtime's IANA zone database. No second zone source and no server-zone fallback.

**Exposes** — copied exactly from BP-057's `## Public interface`:

```ts
// src/lib/publish/settings/clock.ts
export function nextPublishTimeAtOrAfter(instant: Date, s: PublishingSettings): Date
```

This is the one implementation of "when does the next page go out" at the level
of the hour. BP-046's `becomesPublishable` calls it for its `at` (WO-215); BP-001
composes the calendar's next publication from it together with BP-045's due-work
and ceiling state, and BP-057 states plainly that a second implementation "would
be the second copy that disagrees" (rule 7.2). BP-045's ceilings compute
*calendar day and week boundaries* in the same zone, which is a different
question and is deliberately not this function — see WO-211's interface note.

## Steps
1. Create `settings/clock.ts` with the one exported function.
2. Resolve the wall time in `s.timezone`; return the first matching instant at or after `instant`, inclusive at the boundary.
3. Handle the spring-forward gap by returning the first instant after it, and the autumn-back repetition by returning the first of the two. Both are stated choices, not accidents — put the reason in a comment citing BP-057.
4. Throw on a missing or unresolvable zone. Never default.
5. Write the two DST fixtures first and watch them fail against a naive UTC-offset implementation (constitution §8).
