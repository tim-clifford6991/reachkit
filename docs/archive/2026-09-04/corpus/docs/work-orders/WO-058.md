# WO-058 — `claimFreeScanSlot` — the single consumption point, in one transaction

- Branch: wo/WO-058-admission-claim
- Estimate: ≤1 day

## Goal
Make starting a free scan a single transaction that re-evaluates the same
admission order and inserts the `scans` row that *is* the in-flight record, so
two simultaneous submissions can only ever resolve to one scan.

## Interfaces

Consumes: WO-057's `Admission`, `NetworkKey`, and the six-step order it
implements; WO-051's `CanonicalDomain`; WO-056's `network_hash` and
`from_incomplete_rescan` columns; BP-002's `dbAdmin()`.

Exposes (verbatim from BP-023 `## Public interface`, `src/lib/scan/admission.ts`):

```ts
/** The consuming form. One transaction: re-evaluates the same order, inserts the
 *  `scans` row that *is* the in-flight record, and returns its id — so two
 *  simultaneous submissions cannot both pass. */
export function claimFreeScanSlot(a: {
  domain: CanonicalDomain; network: NetworkKey
  fromIncompleteRescan: boolean          // REQ-001 c14's once-only bound
}): Promise<{ claimed: true; scanId: string } | { claimed: false; refusal: Admission }>
```

## Steps
1. Write the failing suites first, the concurrency one included.
2. Extract WO-057's six steps into an internal, transaction-aware evaluator that
   both entry points call, so the order exists once in the file (rule 2.4).
3. Implement `claimFreeScanSlot` as one serialisable transaction: evaluate the
   order, and on `admit` insert the `scans` row and return its id. The in-flight
   bound is resolved by the `status = 'running'` predicate inside the same
   transaction — not by an application-held lock (BP-023's NFR budget).
4. Set `from_incomplete_rescan` from the parameter at insert time, and never
   anywhere else.
5. On refusal insert nothing: a refused scan produces no `scans` row at all
   (BP-023, "so it 'produces no report of its own'").
6. Confirm the fail-open handler from WO-057 still wraps the non-removal steps
   inside the transaction, and that a serialisation failure retries the
   transaction rather than admitting a second scan.

### Deviation review (constitution rule 4.2) — the implementer's three flags

**1. A migration in place of a literal client-driven transaction — independently verified, legitimate.**
- **(a) Cannot be done as a literal transaction from this client, confirmed.**
  `src/lib/db/index.ts` (BP-002's own public interface) declares exactly
  `db()` and `dbAdmin()`, both `createClient<Database>(...)` —
  `@supabase/supabase-js` PostgREST clients. PostgREST is stateless HTTP:
  each `.from(...)` call is one request and one implicit server-side
  transaction: there is no client-side `BEGIN`/`COMMIT` spanning two
  separate `.from(...)` round trips through this client, and neither
  `.rpc()` (a stored procedure — a migration function body) nor a raw `pg`
  connection is in this WO's file plan or reachable from `dbAdmin()`'s own
  declared surface. Confirmed by reading the actual client construction,
  not taken on the comment's word.
- **(b) The partial unique index enforces the claimed property, confirmed
  by reading the SQL.** `create unique index
  idx_scans_one_running_per_network on scans (network_hash) where status =
  'running' and network_hash is not null;` — a unique index scoped to rows
  where `status = 'running'`, so Postgres refuses a second `running` row
  for the same `network_hash` atomically, regardless of what evaluated in
  application code beforehand, and stops constraining a network the moment
  its row leaves `running` (finishes or fails), which is exactly the
  transient in-flight bound BP-023 describes. `network_hash is not null`
  correctly excludes paid-tier rows (`network_hash` is `null` there, and
  Postgres never treats two `null`s as equal for uniqueness) without
  depending on `status='running'` never being a paid-tier value.
- **(c) The concurrency test genuinely proves it — run independently, not
  just read.** N=2 and N=20 against the live substrate (real PostgreSQL 18
  + PostgREST at `127.0.0.1:3001`, real `@supabase/supabase-js`, an async
  `curl`-based loopback fetch so requests actually overlap): 3/3 isolated
  runs, exactly 1 `claimed: true` and n−1 `in_flight` refusals, exactly one
  `running` row in the database, every time. Mutation-verified in both
  directions above (index removed → fails; conflict-detection disabled →
  fails). **This is the most consequential deviation and it holds**: the
  mutual-exclusion property BP-023's NFR budget names ("concurrent claims
  from one network resolve to one `running` row... not by a lock the
  application holds") is delivered, atomically, by the database constraint
  — a stronger guarantee in one respect than a client-driven serialisable
  transaction would even need, since it holds regardless of the calling
  transaction's isolation level (there is none) and survives any future
  caller that reaches this table directly.
