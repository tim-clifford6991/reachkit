# WO-244 — `GET /api/export` — the signed-in download, never withheld on subscription state

- Branch: wo/WO-244-api-export
- Estimate: ≤1 day

## Goal
Stream BP-062's archive to a signed-in customer on the strength of their session
alone, and turn its one failure arm into one written line rather than a partial
download.

## Provenance of this file plan
**This repository holds no `src/`.** Both paths are NEW under BP-001's glob
`src/app/api/**` (decision 1). BP-001's delegation table names the target:
"BP-062's `exportEverything`", behind it REQ-078. WO-004 named this adapter as
one it does not cut.

## File plan
| File | New/Modify | Change |
|---|---|---|
| `src/app/api/export/route.ts` | NEW | The `GET` adapter, wrapped in WO-004's `adapter()`. Reads `currentSession()`; with none, returns the sign-in response WO-003's middleware would have produced and says nothing about whether an account or a payment exists. With a session, calls `exportEverything(session.siteId)` and, on `{ ok: true }`, streams `archive` with the `filename` and a `Content-Disposition` attachment header; on `{ ok: false }`, returns `lineKey` — `'export.failed'` — with **no body bytes at all**. Imports `src/lib/account/export` and `src/lib/account/session` and nothing else; **imports nothing under `src/lib/account/billing/`**, and calls no access gate. |
| `tests/app/export/route.test.ts` | NEW | The suites below, including the two source assertions that carry criterion 2. |

## Interfaces

Consumes (verbatim from BP-062 `## Public interface`):
```ts
/** REQ-078 criteria 2 and 3. Streams a zip. Never consults subscription state. */
export function exportEverything(siteId: string): Promise<
  | { ok: true; archive: ReadableStream<Uint8Array>; filename: string; pages: number }
  | { ok: false; reason: ExportFailure; lineKey: 'export.failed' }
>
export type ExportFailure = 'asset_unreadable' | 'record_unreadable' | 'timeout' | 'internal'
```
Consumes (verbatim from BP-061 `## Public interface`):
```ts
export function currentSession(): Promise<{ userId: string; siteId: string } | null>
```
Exposes (verbatim from BP-001 `## Public interface`):
```
  GET  /api/export                      signed-in download
```

## Steps
1. Write the failing suites first, the "a lapsed customer still downloads" case
   among them.
2. Read the session. No session → the sign-in response, carrying no statement
   about the account's or the payment's existence (BP-001: "A signed-out request
   to `/setup` or `/app` asks for an address and says nothing about whether an
   account or a payment exists").
3. Call `exportEverything(session.siteId)`. Pass nothing else — there is no
   parameter on it that could scope the archive, which is how criterion 3's
   "every page ReachKit wrote for them" stays this route's non-decision.
4. On `{ ok: true }`, stream. On `{ ok: false }`, return `lineKey` and end the
   response with no archive bytes written, so a truncated zip can never be what
   the customer receives.
5. Add the two source assertions in step 6 of the test plan and watch them fail
   first by adding an `hasActiveAccess` import.

## Test plan

> Criteria are copied verbatim from `requirements/REQ-078.md`; line breaks are
> normalised to fit the table and no word is changed. Criteria 1, 3 and 4 —
> the Settings count, the archive's contents and a page file's fields — are
> BP-062's and the Settings surface's; the two below are this transport's.

| Acceptance criterion (verbatim from REQ) | Test |
|---|---|
| REQ-078 c2 — "Given a customer whose subscription is active, cancelled, or past its paid-through date, when they sign in and request an export, then it downloads to them directly and is never withheld on account of subscription state; a lapsed customer reaches it by the sign-in link REQ-076 criterion 5 keeps working." | `export-route/access · three subscription states, one behaviour` — the route streams for a customer whose `plan_status` is `active`, one whose is `canceled`, and one whose `paid_through` is in the past; all three responses are byte-identical in status, headers and stream. And `export-route/access · the gate is unreachable from here` — a source assertion that `route.ts` resolves no import into `src/lib/account/billing/**` and names neither `hasActiveAccess` nor `paid_through` nor `plan_status`; adding either import fails the test **and** the lint fence WO-001 adds from BP-062 decision 1 and ADR-050. Two independent checks, because "the ordinary customer is active" makes this the defect no fixture finds by accident (BP-062 decision 1: "A future reviewer adding 'signed in AND active' to an authorisation helper would break it invisibly"). |
| REQ-078 c5 — "Given an export cannot be produced, when the customer requests one, then they are told so in one written line and are not given a partial archive presented as complete." | `export-route/failure · a line, never a truncated zip` — for each of the four `ExportFailure` reasons, the response carries `lineKey` and a zero-length body, no `Content-Disposition` attachment header and no zip magic bytes; and a fixture where the failure is raised after the first chunk would have been written asserts that no chunk was written, because the route waits for the resolved arm before streaming (BP-062 decision 2: "resolve every record and every asset, then stream"). |

## Out of scope
- The archive, the manifest, `contentSummary` and everything under
  `src/lib/account/export/**` — BP-062's, another block's.
- The Settings "Your content" panel and its count (REQ-078 criterion 1) — the
  Settings surface's.
- The sign-in link itself (REQ-076 criterion 5) — BP-061's.
- Any written sentence: this route returns `lineKey` and nothing else.
- `src/middleware.ts` — WO-003 owns the allow-list, and `/api/export` is an
  account path that middleware denies by default.

## Rollback
Delete both files. The archive builder stays and is unreachable, which withholds
the export from everyone equally rather than from a subset — the safe direction.
