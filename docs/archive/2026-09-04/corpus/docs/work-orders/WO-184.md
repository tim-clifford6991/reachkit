## Goal
Derive the Write-family candidates — and only candidates measured evidence produced — each carrying its evidence, its acceptance test and its winnability band.

## File plan
| File | New/Modify | Change |
|---|---|---|
| `src/lib/opportunities/derive/candidate.ts` | NEW | The internal candidate type shared by the three family modules: `export type Candidate = Omit<Opportunity, 'id' | 'status' | 'createdAt'>`, plus `DerivationResult = { candidates: Candidate[]; assessed: number; rejected: RejectionCount }`. Internal names, not part of BP-040's public interface. |
| `src/lib/opportunities/derive/write.ts` | NEW | `writeCandidates(a: { siteId; scanId; report: StoredReport; ownRanked: Measured<number> }): DerivationResult`. Deterministic, no model call, no network. Produces: `answer_page` where a question's `AnswerCell` is `answered`, `namesCustomer` is false and some cited domain is not the customer's — acceptance `{ form: 'named_on', question }`; `keyword_page` where a selected search's top ten holds no url on the customer's domain — acceptance `{ form: 'top20', query }`; `comparison_page` where such a search's keyword carries a rival brand token from `report.rivals` — acceptance `{ form: 'top20', query }`. Every candidate carries `Evidence` of `family: 'write'` with the query, its `Measured` volume and the rival page (domain, url, position) that shows the gap. Winnability comes from WO-182 over the top ten's ranked counts, each first passed through `rankedCountFrom`; a candidate failing `qualifies` is not produced and increments `rejected.not_yet`, and a top ten with no measured count increments `rejected.unmeasured_top10`. |
| `tests/opportunities/derive/write.test.ts` | NEW | Fixture reports: a question rivals are cited on and the customer is not yields exactly one `answer_page` with that question as its acceptance; a search whose top ten holds the customer's own url yields no `keyword_page`; a top ten of all-`unmeasured` ranked counts yields nothing and increments `unmeasured_top10`; a top ten whose smallest count is above `qualifyingBar` yields nothing and increments `not_yet`; every produced candidate's evidence values are identical objects to the report's, with the report's dates. |

## Steps
1. Write `write.test.ts` first, with hand-built report fixtures, and run it: it must fail on a missing module.
2. Create `candidate.ts`, then `write.ts`.
3. Rule 1.1 parameter record — the type assignment. `answer_page`, `keyword_page` and `comparison_page` are assigned from measured signals that exist in the blob (an answer cell that cites a rival and does not name the customer; an absent own-domain url in a top ten; a rival brand token recorded in `report.rivals`). `format_page` is **not** derived here: no measured signal in the report states a page format, and inventing one would be the composed value REQ-093 c4 and REQ-047 c2 both forbid. It arises only where WO-186's `opportunity-typing` call refines an already-derived candidate's type within the closed enum, which is the one thing BP-040 permits a model to do. Cost of reversing: adding a deterministic `format_page` rule is a new branch here and a new fixture; nothing stored changes.
4. Copy every evidence value out of the report at construction — the value and its date — rather than holding a reference to be read later (BP-040: "Evidence is copied at creation, never referenced").
5. Run the tests. Then mutate: let an all-`unmeasured` top ten qualify, and confirm the `unmeasured_top10` test fails.

## Test plan
> Watch it fail first (constitution §8): every test below is written and
> run against the absent implementation before the implementation exists.

| Acceptance criterion (verbatim from REQ) | Test |
|---|---|
| **REQ-047 c1** Given a completed scan, when opportunities are derived, then each is of exactly one kind from a fixed set of eight — four that propose writing a new page (answering a question rivals own, a search the customer is absent from, a comparison, a page format the customer lacks), three that propose improving a page the customer already has (expand it, make it answerable, refresh it), and one that asks the customer to remove an access barrier — and an opportunity of any other kind cannot be stored. | `write.test.ts › each produced candidate is one of the four write types` — the storage half is WO-181's schema test |
| **REQ-047 c2** Given an opportunity, when it is stored, then it carries the measured evidence that produced it: for the four that propose writing a new page, the search, its volume, and the rival page or position that shows the gap; for the three that propose improving a page the customer already has, the search, its volume, the page of theirs it names, and the measurement on that page that shows the shortfall — its own position, its thinness, or its staleness — with no rival required; for the one that asks the customer to remove an access barrier, the barrier found and the page of theirs it was found on. Every one of those values is one the product measured and stored, never one it composed (REQ-093 criterion 4). | `write.test.ts › evidence carries the search, its volume and the rival page or position` and `… every evidence value is the report's own stored value with its date` |
| **REQ-047 c6** Given an opportunity is created, when it is stored, then it carries an acceptance test in exactly one of three forms: the target reaching the top 20 for a named search, the customer being named in the answer to a named question, or a named access barrier being cleared. | `write.test.ts › an answer_page carries named_on and a keyword_page carries top20` |
| **REQ-047 c9** Given a candidate target for a new page, when it is assessed, then it qualifies only if at least one domain currently in its top ten ranks for no more than the greater of 500 searches and five times the customer's own measured count. | `write.test.ts › a top ten whose smallest measured count is above the bar yields no candidate and counts not_yet` |
| **REQ-047 c11** Given a customer who ranks for nothing, when targets are assessed, then qualifying targets are still produced. | `write.test.ts › a report for a customer at ownRanked zero still yields write candidates` |

**Discriminates (mutation check, constitution §8).**
- Deleting the `qualifies` call produces candidates for the above-bar fixture and fails the c9 test.
- Replacing a copied evidence value with a lookup by id leaves the shape tests passing but fails `… every evidence value is the report's own stored value with its date`, which asserts the date travelled with the value.
- Removing the `namesCustomer` condition yields an `answer_page` for a question the customer is already named on — the fixture asserts zero candidates for that case.
