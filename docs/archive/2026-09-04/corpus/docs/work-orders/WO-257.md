# WO-257 — `nextForDay`

- Branch: wo/WO-257-next-for-day
- Estimate: ≤1 day

## Goal
Answer, for one site, which single opportunity the next day of the calendar is
filled from — the head of the ranked open set, loaded whole — and answer `null`
when there is none, so that no surface has to invent one.

## Provenance of this file plan
**This repository holds no `src/`.** Both paths are NEW. `src/lib/opportunities/`
is BP-013's row in `structure.md` ("The opportunity engine — the eight types,
their evidence, their acceptance tests, winnability banding, ranking, supply
depth and weekly verdicts") and BP-013's `code:` globs are
`src/lib/opportunities/**`, `supabase/migrations/*_opportunities*.sql` and
`tests/opportunities/**`. `next.ts` and `tests/opportunities/next.test.ts` are
claimed by no leaf: BP-040's `code:` names `derive/**`, `winnability/**`,
`rank/**` and `types.ts`; BP-041's is `supply/**`; BP-051's is `verdicts/**`.
So both fall to the component under `structure.md` rule 2.

**Reuse check (rule 7.2).** `capabilities.md` has **no row** for `nextForDay`,
and no work order authors it. It is declared in BP-013's `## Public interface`
("`export function nextForDay(siteId: string): Promise<Opportunity | null>
// ranked order; never invents; never an `unblock`"), constrained in BP-013
decision 2 and in BP-040's error behaviour, and **consumed** by WO-164, whose
file-plan row for `src/app/(account)/app/calendar/month.ts` reads "Requests fill
from BP-013's `nextForDay`; **it creates nothing**" and whose `## Interfaces`
consumes `nextForDay()`. Nothing else in the corpus names it. This work order
creates the capability and registers it; the ordering it reads is BP-040's
`rankOpen` and is not re-implemented here.

**Status.** Left `status: draft` — written and not self-certified in the same
pass. A later audit sets the status against §3's gate list.

## File plan
| File | New/Modify | Change |
|---|---|---|
| `src/lib/opportunities/next.ts` | **NEW** | `nextForDay`, verbatim from BP-013's `## Public interface`. Two steps and no third: call `rankOpen(siteId)`; if it is empty return `null`, otherwise load the head's `opportunities` row by id and return it whole as an `Opportunity`. It applies **no** filter of its own — the `fix` family and every `unblock` are already excluded by `rankOpen` (second `rests-on` row), and a second filter here would be a second statement of the same predicate (rule 2.4). It **creates nothing**: no draft, no opportunity, no queue entry, no write of any kind, asserted at source. It stores no rank (BP-040 decision 4: "no `rank` column. `rankOpen` computes from stored evidence at read time"). It takes no date and no count: one site, one opportunity or none. |
| `tests/opportunities/next.test.ts` | **NEW** | The head-of-order, exclusion, empty and no-write suites named in the test plan. |

## Steps
1. Write `tests/opportunities/next.test.ts` first and run it; every case must
   fail on a missing module (constitution §8, "Watch it fail first").
2. Implement `nextForDay` as `rankOpen` → head → one row load. Return `null` on
   an empty ranking; do not fall back to an unranked query, a most-recent row or
   any other second source.
3. Assert at source that the file issues no `insert`, no `update` and no
   `delete`, and that it contains no `family`, `type` or `status` comparison —
   every exclusion is `rankOpen`'s.
4. Mutate to prove the suite discriminates: (a) return the tail instead of the
   head and confirm the ranked-order row fails; (b) fall back to any open row
   when the ranking is empty and confirm the empty row fails; (c) add a local
   `family !== 'fix'` filter and confirm the no-second-predicate source
   assertion fails.
