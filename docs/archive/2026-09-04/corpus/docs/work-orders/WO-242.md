# WO-242 — `POST /api/lead` — the transport adapter over lead capture

- Branch: wo/WO-242-api-lead
- Estimate: ≤1 day

## Goal
Accept an email address and a scan id, hand them to BP-029's `captureLead`, and
map its two arms to a response — a transport adapter with no lead logic of its
own.

## Provenance of this file plan
**This repository holds no `src/`.** Both paths are NEW. `POST /api/lead` is on
BP-001's public route list and is anchored by this container's glob
`src/app/api/**`: BP-001 decision 1 fixes that "every file under
`src/app/api/**` is BP-001's. Each is a transport-only adapter — read the
request, call one exported function on the owning component, map the result to a
response." BP-001's delegation table names the target: "BP-029's lead capture and
sequence start", behind it REQ-010. WO-004 named this adapter as one it does not
cut; this is that work order.

## File plan
| File | New/Modify | Change |
|---|---|---|
| `src/app/api/lead/route.ts` | NEW | The `POST` adapter, wrapped in WO-004's `adapter()`. Reads exactly two fields from the body — `scanId` and `email` — and nothing else; calls `captureLead({ scanId, email })`; maps `{ captured: true }` to 202 with the acceptance copy key and `{ captured: false, reason }` to 4xx/503 with the key for that reason. Imports `src/lib/mail/leads/capture` and no other engine module (`structure.md` rule 1). Holds no address validation of its own beyond what the body parse requires, no mail call, no sequence start, no clock and no database access. |
| `tests/app/lead/route.test.ts` | NEW | The suites below. |

## Interfaces

Consumes (verbatim from BP-029 `## Public interface`):
```ts
// src/lib/mail/leads/capture.ts
/** Criterion 1's control accepts an address and nothing else. Criterion 3's
 *  delivery is enqueued, never awaited: the visitor's confirmation states the
 *  address was accepted, which is the only thing true at that moment. */
export function captureLead(a: {
  scanId: string
  email: string
}): Promise<
  | { captured: true; leadId: string }
  | { captured: false; reason: 'invalid-address' | 'unavailable' }>   // REQ-003 c10
```
Consumes (from WO-004, `src/app/api/_adapter.ts`):
```ts
export function adapter<T>(h: (req: Request) => Promise<T>): (req: Request) => Promise<Response>
```
Exposes (verbatim from BP-001 `## Public interface`):
```
  POST /api/lead                        email for the finished page
```

## Steps
1. Write the failing suites first.
2. Write the handler: parse the body to `{ scanId, email }` with a schema that
   **rejects any additional property**, call `captureLead`, switch totally over
   its two arms.
3. Map arms to responses: `captured: true` → 202 plus the acceptance copy key;
   `reason: 'invalid-address'` → 400 plus that key; `reason: 'unavailable'` →
   503 plus that key. Every response body carries a `CopyKey`, never a sentence
   and never a vendor payload (BP-001: "a vendor error payload never reaches a
   response body").
4. Confirm the emitted log line is WO-004's four fields plus the scan id, and
   that the address is not among them.
