# WO-140 — The erasure migrations — the promised purge date, the tombstone's comment, the publishing switch, and danger_tickets

- Branch: wo/WO-140-erasure-migrations
- Estimate: ≤1 day

## Goal
Add the erasure column BP-063's data-model delta names that WO-267 has not
already added — `purge_due_at`; `deleted_at` exists from WO-267's
`supabase/migrations/00000000000002_rls.sql` — plus the publishing switch and
the ticket table, and assert, in the applied schema, that `deleted_at` is
present and that no foreign key from `users` or `sites` carries a cascade.

## File plan
> **Every path below is NEW.** This repository carries no `supabase/`. Anchored to
> `registry/structure.md` rule 3a (`*_users_erasure_*` and `*_sites_erasure_*`
> inside BP-017's) and BP-063's `code:` globs. Provisional against a repo with no
> code.
>
> **Read ADR-051 before writing these files.** Its warning is aimed exactly here:
> "Read this before adding a cascade delete, before 'finishing' the delete path,
> and before adding `deleted_at is null` to a query."

| File | New/Modify | Change |
|---|---|---|
| `supabase/migrations/<ts>_users_erasure_columns.sql` | NEW | `alter table users add column purge_due_at timestamptz null`, **stored rather than computed** so a change to `ERASURE_DAYS` cannot retroactively move an existing customer's promised date (BP-063 decision 4). An index on `purge_due_at` for the due-work query. **No `deleted_at` here:** the tombstone column already exists — WO-267's `supabase/migrations/00000000000002_rls.sql` adds `users.deleted_at timestamptz` as the precondition of ADR-051's `deleted_at is null` policy condition (WO-267, third `rests-on` row), and a second `add column` fails the apply. This migration adds the `comment on column users.deleted_at` carrying ADR-051's ruling in one line — that this is a tombstone, that unreachability is the row policy's job, and that no cascade may be added — because BP-063 owns every rule about the column even though it no longer creates it. |
| `supabase/migrations/<ts>_users_erasure_tickets.sql` | NEW | `create table danger_tickets (ticket text primary key, site_id uuid not null references sites(id), action text not null check (action in ('unpublish_all','delete_account')), created_at timestamptz not null default now(), taken_at timestamptz null, spent_at timestamptz null, expires_at timestamptz not null)`. The foreign key carries **no** `on delete cascade`; the row is removed by the purge (BP-063: "The `danger_tickets` row and its archive are themselves purged with the account"). |
| `supabase/migrations/<ts>_sites_erasure_columns.sql` | NEW | `alter table sites add column publishing_enabled boolean not null default true` — REQ-070 c1's "whether pages publish at all". Nothing in BP-063's module ever sets it true (decision 2). |
| `tests/account/lifecycle/schema.test.ts` | NEW | `purge_due_at`, `publishing_enabled` and the table exist with the stated types, nullability and defaults; `users.deleted_at` is **present** — asserted as presence, never created here, because WO-267's `00000000000002_rls.sql` adds it; the `deleted_at` comment is present and non-empty; **the ADR-051 point 7 assertion**: a query over the applied schema finds **no** foreign key referencing `users` or `sites` with `on delete cascade`, anywhere in the database — the test names ADR-051 in its failure message. |

## Out of scope
- Creating `users.deleted_at` — WO-267's `00000000000002_rls.sql`, in build (W1).
- The RLS condition that hides a tombstoned account's rows from `db()` — that is
  **BP-002's**, per ADR-051 point 3, and it is the single point of failure for the
  whole guarantee. This work order does not write it and must not.
- Stamping any of these columns — WO-142, WO-143 and WO-144.
- Every other `users` and `sites` sub-token — WO-116, WO-120, WO-124, WO-129,
  WO-130, WO-135.

## Rollback
Drop `purge_due_at`, the switch, the table and the `deleted_at` comment in a
follow-up migration. `deleted_at` itself is not this order's to drop — it is
WO-267's — and dropping it anywhere in an environment holding tombstoned accounts
makes those accounts reachable again, the opposite of what REQ-079 c7 promises:
purge them first or do not roll back.
