## Goal
Implement the four model steps and the grounding read that produce a draft's Markdown, its rendered text and its grounded fact — each step reporting a step failure rather than a rule failure when it cannot run.

## File plan
| File | New/Modify | Change |
|---|---|---|
| `src/lib/generate/pipeline/grounding.ts` | NEW | `readGroundingFact(a: { domain: string; pages: string[] }): Promise<{ fact: GroundedFact; fetchedToday: string } | { failed: 'no_fact' }>` — one `safeFetch` of a page on the customer's own live site, and the passage copied word for word from the content fetched that day. No fallback: nothing here reads the report, a rival's page or the model's knowledge (REQ-050's non-goal). The same fact may ground more than one draft; c1 does not require a different one each time. |
| `src/lib/generate/pipeline/steps.ts` | NEW | `PipelineStep` verbatim from BP-042, and one function per model step — `brief`, `outline`, `draft`, `answerability` — each taking the `CostContext` and `DraftPromptInputs`, calling `llm()` at its own call site with a parsed schema, and returning `Measured<T>`. Also `renderOf(markdown: string): string`, the one place Markdown becomes the words a reader meets, so `rendered` and `markdown` are never confused by two different derivations. Each step re-checks `capHit()` before it runs. |
| `tests/generate/pipeline/grounding.test.ts` | NEW | A live page yielding a passage produces a `GroundedFact` whose passage occurs verbatim in the fetched content; a fetch that returns nothing yields `{ failed: 'no_fact' }` and never a fact drawn from the report; the fetch goes through `safeFetch` (asserted with a stub) and no other outbound call is made. |
| `tests/generate/pipeline/steps.test.ts` | NEW | Each step passes the `DraftPromptInputs` object it was given, unchanged and with no extra key, to its `llm()` call site (stubbed); an `unmeasured` result from any step is returned as that step's failure and never as a rule failure; `capHit()` true before a step stops it; `renderOf` strips Markdown syntax and leaves the reader's words. |

## Steps
1. Write both test files first and run them; both must fail on a missing module.
2. Implement `grounding.ts`. It has no fallback branch — the absence of one is the enforcement of REQ-050's non-goal, and the test asserts that a failed fetch produces no fact rather than a report-derived one.
3. Implement `steps.ts`. Every step's `input` is the `DraftPromptInputs` object itself, so the closed struct is the only thing a prompt can carry (WO-197's property is preserved by not spreading extra keys in).
4. An `unmeasured` result from `llm()` is a step failure. It does not populate a rule failure list and does not increment `hard_rule_attempts` (ADR-070 point 5); this module returns the step and lets WO-199 route it.
5. Log per-step cost and duration only. Never the prompt, the voice text, the draft body or the grounded passage (BP-042's observability line).
6. Run the tests. Then mutate: add a summary of the customer's past drafts to a prompt input and confirm `steps.test.ts › each step passes the struct unchanged and with no extra key` fails.

## Test plan

| Acceptance criterion (verbatim from REQ) | Test |
|---|---|
| **REQ-050 c1** Given a draft is generated, when it is queued for review, then it carries at least one statement of fact drawn from a page on the customer's own live site, stored with that page's URL, the date it was read and the passage it was drawn from copied word for word from the content fetched that day; the passage is kept unchanged from then on, so the statement can still be read against it after the customer's own page has moved on. | `grounding.test.ts › the passage occurs word for word in the content fetched that day` and `… a failed fetch yields no fact rather than one drawn from the report` |
| **REQ-055 c1** Given the customer has written a voice description, when a draft is generated, then the generation request carries that description in full and unaltered. | `steps.test.ts › each step passes the DraftPromptInputs object it was given, unchanged` — the request carries the description in full and unaltered |
| **REQ-055 c4** Given any number of edited or published pages, when a draft is generated, then the only inputs shaping its voice are that description and the page's own evidence; no profile, summary or embedding derived from the customer's edits, drafts or publishing history is stored or sent. | `steps.test.ts › no step adds a key to the prompt input` — no derived profile, summary or embedding is sent, because none is built and none can be attached |

**Discriminates (mutation check, constitution §8).**
- Adding a fallback that grounds in the report leaves the happy path green and fails `… a failed fetch yields no fact`.
- Spreading additional context into a prompt input fails the no-extra-key assertion — the mutation REQ-055 c4 is most exposed to, since it looks like a quality improvement.
- Treating an `unmeasured` step result as a rule failure fails `… returned as that step's failure and never as a rule failure`, and would spend the one automatic regeneration (ADR-070 point 5).
