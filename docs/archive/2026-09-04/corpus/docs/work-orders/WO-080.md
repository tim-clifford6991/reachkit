# WO-080 — checkCoherence and coherenceThreshold — a three-valued verdict against a rescaling threshold

- Branch: wo/WO-080-coherence-check
- Estimate: ≤1 day

## Goal
Implement `src/lib/market/coherence/check.ts` so a report's market is judged coherent,
incoherent, or unjudgeable — against a threshold that is a share of what was measured, never
an absolute count, and never the whole number measured.

**Risk: high — seam: a customer-visible verdict.** `checkCoherence` produces one of three arms a customer is shown in writing, and its third arm is REQ-094's promise that a report which measured fewer than three searches *says it cannot judge* rather than judging. A threshold test that survives deletion of the threshold publishes a coherence judgement on evidence the product promised it would not judge on, and nothing on the screen would look wrong. Mutation-tested (doctrine 0.13.2, rule 2b).

## Context an implementer needs
No source code exists on disk; both paths below are NEW. The arithmetic is
`max(2, ceil(n / 4))` with both operands pinned in BP-005 (`minAppearances: 2`,
`shareDivisor: 4`) — BP-028 decision 1: "The threshold is a pinned expression, not a pinned
number." BUILD §6.7 step 5's literal "no domain appears in ≥3 of the 12 top-10s" is the
value of that expression at n = 12 only; REQ-006 criterion 1 makes a market that yields
fewer than twelve a legal *complete* result, so the denominator is variable.

The parent/leaf divergence this WO recorded is **resolved**. When it was cut, BP-011's
`## Public interface` declared the two failing arms bare (`{ verdict: 'incoherent' }`,
`{ verdict: 'unjudgeable' }`) while BP-028's declared them carrying `threshold`/`best` and
`measuredCount`, and this WO implemented BP-028's. BP-011 was corrected in-file on 2026-08-31
and now carries the same three-arm shape, with the reason written beside it: "This section
declared a bare three-arm union at approval; BP-028, the leaf cut from REQ-094, ships the
shape below, and one symbol in `src/lib/market/coherence/check.ts` cannot carry two." Parent
and leaf now read alike; the shape implemented is unchanged.

## Interfaces
**Consumes**: `SerpResult` (BP-008), `registrableDomain` (WO-077 — one domain
normalisation in the product, not two), `COHERENCE` from `src/lib/config/constants.ts` (BP-005).

**Exposes** — copied exactly from BP-028's `## Public interface`:

```ts
// src/lib/market/coherence/check.ts
export type CoherenceVerdict =
  | { verdict: 'coherent' }
  | { verdict: 'incoherent'; threshold: number; best: number }
  | { verdict: 'unjudgeable'; measuredCount: number }
export function checkCoherence(a: { serps: SerpResult[]; measuredCount: number }): CoherenceVerdict
/** max(2, ceil(n / 4)) — a share of what was measured, never an absolute count. */
export function coherenceThreshold(measuredCount: number): number
```

## Steps
1. `coherenceThreshold(n)` = `Math.max(COHERENCE.minAppearances, Math.ceil(n / COHERENCE.shareDivisor))`.
   Neither `2` nor `4` appears as a literal in this file (`structure.md` rule 5).
2. `checkCoherence`: where `measuredCount < COHERENCE.minMeasuredSearches`, return
   `{ verdict: 'unjudgeable', measuredCount }` **before** counting anything — with fewer than
   three measured top-tens no domain can reach the threshold whatever they contain, so a
   coherent and an incoherent market would produce the identical result.
3. Otherwise count, per registrable domain, in how many of the supplied SERPs' top tens it
   appears (once per SERP). `best` = the highest such count, `0` where no domain appears.
4. `best >= coherenceThreshold(measuredCount)` ⇒ `{ verdict: 'coherent' }`. Otherwise
   `{ verdict: 'incoherent', threshold, best }`.
5. Emit the observability fields BP-028 names: verdict, threshold, best appearance count.
6. Write the tests; watch each fail first.

## Test plan
| Acceptance criterion (verbatim from REQ-094) | Test |

That threshold is three where twelve searches were measured, and is never the whole number measured, so the same share of the market is asked for at every denominator (REQ-006 criterion 1). ### Ruling on the `SerpResult` `rests-on` row (row 2, disposition on entry: `open`)

**My own independent verification**, not inherited from the implementer's claim: I wrote a fresh probe file (`src/lib/market/coherence/__validator_probe__.ts`, written, `tsc --noEmit`'d, then deleted — no trace left in the tree) that imports BP-008's canonical `SerpResult` (now landed on this branch under WO-023, `src/lib/vendors/dataforseo/types.ts`) and passes a `readonly SerpResult[]` value directly into `checkCoherence`, and separately assigns one canonical `SerpResult` value to a variable typed as `check.ts`'s local, narrower `SerpResult`. Both compile clean with **no cast**, confirming the WO's own claim: any real, canonical `SerpResult` structurally satisfies the local interface. I also confirmed `src/lib/market/` still exposes no neutral re-export of `SerpResult` anywhere (`grep -rln "export.*SerpResult" src/lib/market/` returns only `check.ts` itself), so the workaround's premise — no neutral re-export exists yet — still holds.

**My ruling, as asked**: this is **not** a rule 2.4/7.1 violation, and not a duplicate requiring refusal. Reasoning:
- Rule 7.1 ("two implementations of one capability is a `blocked-by`") targets *implementations* — parsing logic, I/O, derivation. `check.ts`'s local `interface SerpResult { organic: readonly { domain: string }[] }` implements nothing: it declares no parsing, no defaults, no derivation, and reads only the two fields (`organic`, `domain`) `checkCoherence` actually touches (BP-028 step 3 — organic top-ten only, never `ai_overview`). It is a structural projection of BP-008's type, not a second implementation of the capability that produces a `SerpResult`.
- Rule 2.4 ("one claim, one home") is about a *fact* being restated in two artifacts and diverging. A structural TypeScript interface used only as a parameter constraint states no independent fact about what a SERP result *is*; if BP-008's canonical shape ever narrows a field this local type depends on, the mismatch surfaces as a compile error at the real call site the day these two modules are actually wired together (out of this WO's scope) — it does not silently drift, because TypeScript checks structural compatibility at every call site, not just at declaration.
- The alternative BP-028 doesn't offer here — importing the canonical type — is foreclosed by this WO's *own* approved test plan (`check/is-pure`'s textual ban on any import, including type-only, from `src/lib/vendors/`), not by anything the implementer chose. Whether that purity boundary should admit type-only imports is a legitimate question for a future architect pass, but it is a different question from whether *this* WO's workaround is sound, and it does not retroactively make the current file non-compliant with its own approved plan.
- Precedent: the row itself correctly identifies this as the same shape of cross-node tension ADR-095 already resolved once (`report.market`/`coherence`), which supports treating it as a known, tolerable pattern rather than a new violation.

**Disposition: confirmed.** The claim — a sound, minimal, structural narrowing exists, is compile-verified compatible with BP-008's now-landed canonical type, no neutral re-export yet exists, and it was correctly flagged once (rule 4.2) rather than decided unilaterally — is true as observed, independently, by this build. I am not overriding the architect's standing invitation to add a neutral re-export later (a genuinely available, low-cost improvement, noted below as a non-blocking gap) — I am ruling, as asked, that the current state is not itself a defect requiring refusal.
