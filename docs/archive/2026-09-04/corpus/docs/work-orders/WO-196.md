## Goal
Compose the ten hard rules into one battery that reports every failure it found, and expose the near-duplicate cause a rejected day may carry.

## File plan
| File | New/Modify | Change |
|---|---|---|
| `src/lib/generate/rules/index.ts` | NEW | `runHardRules` exactly as BP-042 declares it. Runs the nine deterministic arms from WO-192 to WO-195 and the tenth by calling BP-043's `claimCheck`; returns `{ passed: true }` or `{ passed: false, failed: RuleFailure[] }` with every rule that failed, not the first. A `ClaimVerdict` of `unrun` is **not** a rule failure: it is returned to the caller as a step failure (ADR-070 point 5), so it never populates `failed`. Deterministic order is `HARD_RULES`' order, so a failure list is comparable across runs. |
| `src/lib/generate/pipeline/rejection.ts` | NEW | `rejectionCause(draftId)` — reads `drafts.rule_failures` and returns `{ kind: 'near_duplicate', duplicateOf: { ref, title } }` where the last battery run failed on `near_duplicate`, and null otherwise. A handle plus stored values; no sentence is composed here. |
| `tests/generate/rules/battery.test.ts` | NEW | A draft failing three rules reports all three, in `HARD_RULES` order; a draft failing none returns `{ passed: true }`; an `unrun` claim verdict does not appear in `failed` and is surfaced as a step failure; the battery calls BP-043's `claimCheck` rather than matching the list itself (asserted with a stub that records the call). |
| `tests/generate/pipeline/rejection.test.ts` | NEW | A draft whose last run failed `near_duplicate` yields the duplicated page's ref and title; a draft that failed another rule yields null; the return carries no string that is not a stored value. |

## Steps
1. Write both test files first and run them; both must fail on a missing module.
2. Implement `rules/index.ts`. Every arm is called; the battery does not short-circuit on the first failure, because REQ-050 c14's cause and BP-042's observability both need to know which rules failed.
3. Handle the `unrun` verdict explicitly and separately — ADR-070 point 5: "An unrun check is a step failure, not a rule failure", and merging the two would spend the customer's one automatic regeneration on a condition regeneration cannot fix. The battery therefore returns the step failure to its caller rather than adding it to `failed`.
4. Implement `pipeline/rejection.ts` as a read of `rule_failures` — the column WO-191 created so c14's cause survives the run that produced it.
5. Run the tests. Then mutate: fold `unrun` into `failed` and confirm the battery test's `unrun` case fails; short-circuit on the first failure and confirm the three-failure case fails.

| **REQ-053 c1** Given the customer has recorded claims the product must never make, when a draft is generated, then it is checked against that list before it can be queued for review, and a draft matches when it states a recorded claim either in the recorded words or in a paraphrase of them. | `battery.test.ts › the do_not_claim arm calls BP-043's claimCheck` — the check happens before anything can be queued, and no second matcher exists in this node |

**Discriminates (mutation check, constitution §8).**
- Short-circuiting on the first failure makes the three-failure case report one, which is how a second rule's cause silently disappears from `rule_failures`.
- Treating `unrun` as a rule failure makes the battery test's `unrun` case fail — and in production would burn the one automatic regeneration on a vendor outage (ADR-070's cost-of-reversing paragraph).
- Re-implementing the list match here rather than calling `claimCheck` leaves every verdict identical and fails the stub-call assertion, which is the only test that can see the duplicate capability rule 7.1 forbids.
