# WO-092 — changeMarkers, domainHistory and weeksMeasured — the dates every series breaks at

- Branch: wo/WO-092-change-markers
- Estimate: ≤1 day

## Goal
Implement `src/lib/market/changes/markers.ts` so every series, chart, verdict and week count
can be broken at the dates the answers changed — derived from the sequence of stored scans,
with no change-log table anywhere.

## Context an implementer needs
No source code exists on disk; both paths below are NEW.

**Read `sdlc-factory/docs/decisions/ADR-030.md`.** Point 5: "Change markers for charts, series,
week counts and verdicts (`changeMarkers`, `domainHistory`) are derived from the sequence of
stored scans, which already carries the domain and the category each one measured against."
Every historical number stays interpretable because the answer it was measured against is
stored on its own scan and is never overwritten by the current declared answer.

**This module reads `scans` through BP-002's `db()` and never imports `src/lib/scan/`**
(BP-056 decision 4). Unlike BP-034's setup card, the rows are **not** pushed in by an adapter:
`changeMarkers` needs a *sequence* of scans over a date range, and pushing that query into
`src/app/` would be engine logic in a route handler, which `structure.md` rule 1 forbids. Two
nodes therefore read `scans` — BP-012 for the current-report pointer, this node for the
historical sequence — and BP-056 decision 4 records that these are different questions, not two
implementations of one capability.

**Bounded by BP-056 decision 3**: across a change, a headline number carries its goal (REQ-041
criterion 4, unchanged and not this module's); every other affected number carries the change
marker this module supplies and **no** change figure. Nothing is invented to stand in for a
goal REQ-041 does not define.

## Interfaces
**Consumes**: `db()` (BP-002) and `ChangeKind` from `./declared` (WO-089).

**Exposes** — copied exactly from BP-056's `## Public interface`, the trailing comment included:

```ts
// src/lib/market/changes/markers.ts
export interface ChangeMarker { kind: ChangeKind; on: Date }
export function changeMarkers(a: { siteId: string; from: Date; to: Date }): Promise<ChangeMarker[]>
export function domainHistory(siteId: string): Promise<{ domain: string; firstMeasuredAt: Date }[]>
export function weeksMeasured(siteId: string): Promise<number>   // counts from the current domain's first measurement
```

## Steps
1. `changeMarkers({ siteId, from, to })`: read the site's scans in the window, ordered by
   measurement date ascending, projecting the measurement date, `scans.domain`,
   `report.market.category` and `report.rivals`. Emit one `ChangeMarker` at each scan whose
   answer differs from the immediately preceding scan's — `kind: 'domain'`, `'category'` or
   `'rivals'`, `on` that scan's measurement date. A scan may produce more than one marker.
   Compare rivals as a **set**, so a reordering is not a change.
2. The first scan in a site's whole history produces no marker: there is nothing before it to
   have changed from. Where the window's first scan is not the site's first, compare against
   the last scan before `from` so a change at the window boundary is not lost.
3. `domainHistory(siteId)`: one entry per distinct domain in measurement order, each carrying
   `firstMeasuredAt` — the date that domain was first measured. This is the value BP-013's
   `judgePublished` consumes to return `'not_judgeable'` with reason `'domain_changed'`; this
   module states nothing about a verdict itself.
4. `weeksMeasured(siteId)`: count from the **current domain's** first measurement — the last
   entry of `domainHistory` — to the latest completed scan, in whole weeks. A site whose domain
   changed last week counts from last week, not from the account's creation.
5. Query, do not scan-and-filter in memory beyond the adjacent-pair comparison: BP-056's
   `## NFR budget` requires `changeMarkers` over a year of scans to be one indexed query.
6. Emit no state of its own.
7. Write the tests; watch each fail first.

Window correctness: `markers/compares-across-the-window-boundary` — a change occurring at the
window's first scan is emitted, because the query compares against the last scan before `from`;
and `markers/first-scan-ever-emits-nothing`.

No-change-log guard, from **ADR-030** point 5: `markers/derived-from-scans-only` — the module's
queries reference only the `scans` table and no table named `site_changes`; this WO's diff adds
no file under `supabase/migrations/`.

Cycle guard, from BP-056 decision 4: `markers/no-scan-import` — `markers.ts` reaches no module
under `src/lib/scan/`, type-only imports included.

Discrimination: emitting a marker for the first scan in history, counting weeks from the
account's first scan instead of the current domain's, or comparing rival lists by order, must
each fail a named test above.
