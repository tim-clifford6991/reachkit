# WO-265 — publish_capable — the one probe result on the destinations row that is a health input

- Branch: wo/WO-265-destinations-publish-capable

## Goal
Add `publish_capable boolean null` to the `destinations` topic and widen `health_reason`'s constraint to admit `cannot_publish`, so BP-058 can record what the last probe found and derive the destination's state from it.

## Interfaces

**Consumes**

- `db()` / `dbAdmin()` and the migration runner — BP-002, WO-011.
- The `destinations` table and the columns WO-223 created — `health`, `health_reason`, `health_changed_at`, `broken_mail_sent_at`, `last_checked_at`, `deleted_at`, and the partial unique index.

**Exposes** — copied exactly from BP-058's `## Data model delta`:

```sql
-- BP-058 "## Data model delta", on the `destinations` topic:
--   publish_capable boolean null
--       ADR-084 Decision 3, ADR-086 Decision 1. Whether this WordPress
--       credential can publish and not merely create (BP-048's `canPublish`),
--       written at connect and refreshed at each health check. `null` for
--       `hosted` and before the first check. It **is** a health input, and it is
--       the one thing on this row that is: a `false` here makes the destination
--       `error`/`cannot_publish` and holds the queue. Kept as its own column
--       rather than folded into `health_reason` because the reason is what the
--       last check *concluded* and this is what the last probe *found*; the
--       first is derived from the second and from DNS and credential outcomes
--       together.
--   health_reason: the eighth member, `cannot_publish` (ADR-086 Decision 1).
--       `health` stays 'ok' | 'expired' | 'error' — BUILD.md §10's enum,
--       unchanged and not widened.
```

**Three values, not two, and the nullability is load-bearing.** `null` means
*this question does not apply, or has not been asked yet* — a `hosted`
destination, or a WordPress destination before its first check. `false` means
*asked, and the answer was no*, which holds the customer's queue. Collapsing them
with `not null default false` would put **every** destination into
`error`/`cannot_publish` at the moment it is created, before any probe has run:
a customer connecting a working WordPress site would be told their account cannot
publish, and a hosted site would be told the same about a question that does not
apply to it. The nullability assertion in the file plan is what catches that, and
it is the sort of default a migration author adds for tidiness.

**A separate column, not a fold into `health_reason`** (BP-058's data-model
delta, in terms): the reason is what the last check **concluded**, and this is
what the last probe **found**. The first is derived from the second together with
the DNS and credential outcomes. Folding them would mean the probe's raw answer
could not be read back without re-deriving it from a conclusion that also
encodes two other checks.

**`health` is not widened, and the test asserts it directly.** ADR-086 Decision 1
and BP-058 decision 2 both reject a fourth `DestinationHealth` member: it changes
a column `BUILD.md` §10 specifies and makes REQ-074 criterion 1's three
customer-read states a mapping every surface has to know. The occasion costs a
reason, a copy key and an action — and nothing in the enum. Asserting the refusal
of a fourth value here means a later widening fails at the schema rather than
quietly reaching the surfaces.

**This column is the one probe result on this row that is a health input, and
`stamp_capable` is deliberately not.** BP-058's data-model delta says so: a site
that will not take the findability term still publishes, and holding its queue
over a findability attribute is a promise no requirement makes. `stamp_capable`
is ADR-083's and is **not added by this migration** — see `## Out of scope`.

## Steps
1. Read **ADR-086** Decision 1 and BP-058 decision 2's "fourth occasion" note before writing the file.
2. Write the migration adding `publish_capable boolean null` — **nullable, no default**.
3. Widen the `health_reason` check constraint to the eight members, adding `cannot_publish`. Change nothing else about it.
4. **Do not touch the `health` enum.** Add a SQL comment saying why, naming ADR-086 Decision 1 and BP-058 decision 2, so the next reader of the schema meets the reason before the temptation.
5. Add a SQL comment on `publish_capable` naming ADR-084 Decision 3 and ADR-086 Decision 1 and stating that `null` is "not applicable or not yet asked" and is not `false`.
6. Write `capability_schema.test.ts` against a freshly migrated database and watch the nullability and no-default assertions fail before the migration lands (constitution §8).
7. Mutate, and confirm each fails: make the column `not null default false` (the nullability and default rows fail); widen `health` to four members (the enum row fails); narrow `health_reason` back to seven (the reason row fails).
