# WO-112 — Address-wide suppression and the opt-out token

- Branch: wo/WO-112-suppress-optout

- Estimate: ≤1 day

## Goal
Stop every running and waiting sequence for an address, block every future one,
and give a stranger exactly one capability — a signed, unexpiring, idempotent
token that suppresses the address it was signed for.

## Provisional against an empty repo
**No `src/` exists.** All files NEW, inside BP-029's `src/lib/mail/leads/**`
glob.

Reuse check (rule 7.2): `registry/capabilities.md` row "Address-wide
suppression — `src/lib/mail/leads/` — BP-029 — `suppressAddress()` ·
`applyOptOutToken()` — consumers BP-001 (opt-out), BP-017". Nothing exists. The
`unsubscribeTokenFor()` family (WO-108, BP-059) is **not** reused: ADR-042 fixes
two token formats over two subjects, permanently.

## Read ADR-042 before touching this file
`suppressAddress()` never writes `users.notify`. This store is keyed by an email
address and reaches `stoppable: 'opt-out'` kinds only. Merging it with the
per-kind toggles removes a paying customer's magic-link sign-in mail, silently,
discovered only when they cannot get back in.

An unverifiable token returns `{ error: 'invalid' }` and writes nothing. |

## Interfaces
**Exposes** (verbatim from BP-029 `## Public interface`):
```ts
/** BP-016's declared entry point, realised here. Ends every running and every
 *  waiting sequence for the address and blocks every future one. Never touches
 *  users.notify — that is BP-059's, and ADR-042 states why the two must not
 *  become one. */
export function suppressAddress(email: string, cause: 'opt_out' | 'subscribed'): Promise<void>

// src/lib/mail/leads/optout.ts
export function optOutTokenFor(email: string): string                 // signed, no expiry
export function applyOptOutToken(token: string): Promise<
  | { email: string }
  | { error: 'invalid' }>                                             // idempotent
```
Plus, chosen under rule 1.1: `isSuppressed(email: string): Promise<boolean>` —
the read side of the same store. Derivation: BP-053's seam "consults BP-029's
suppressions … immediately before the vendor call" and BP-029's error section has
`scheduleSequence` "refuse an address present in `email_suppressions`"; both need
a read, and neither node names one. One exported read beats two ad-hoc queries in
two modules. Cost of reversing: inline the query at both call sites.

**Consumes**: `dbAdmin()` (BP-002); the `email_suppressions` and `leads` schema
(WO-109); BP-005's opt-out signing secret.
