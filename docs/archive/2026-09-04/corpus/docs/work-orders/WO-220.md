# WO-220 — Saving a settings change — the four re-deadline rules, and the telling it re-opens

- Branch: wo/WO-220-settings-apply
- Estimate: ≤1 day

## Goal
Ship `newVetoDeadline` — REQ-073 criterion 4's four rules as one pure function — and `savePublishingSettings`, which applies it to every draft not yet published in one transaction and re-opens the telling for every draft whose governing pair changed.

## File plan

> `package.json` (verified 2026-08-31). **Every path below is NEW** — none was
> verified to exist, because none can. Placement is anchored to
> `sdlc-factory/docs/registry/structure.md` and to this work order's blueprint
> `code:` globs, and is provisional against a repo with no code: if the

| File | New/Modify | Change |
|---|---|---|
| `src/lib/publish/settings/apply.ts` | NEW | `newVetoDeadline` as one pure function of the whole situation, with no I/O. The four rules, in BP-057's own order: (1) a draft not yet published is in scope, including one already in review, and a `published`, `skipped` or `unpublished` draft is untouched; (2) a window already running is never shortened — the result is never earlier than `currentDeadline`; (3) a draft in review whose window is lengthened keeps `max(currentDeadline, enteredReviewAt + nextVetoHours)`; (4) a draft in review whose window already expired **under Copilot** restarts at `changedAt + nextVetoHours`. Rule 4 is scoped to `in_review`: a draft already in `approved` reached it through an approval and a settings change does not revoke it. |
| `src/lib/publish/settings/settings.ts` | MODIFY | Add `savePublishingSettings` — the **only** writer of `sites.mode` in the product. Validates the patch whole; writes the four values; maps `newVetoDeadline` over the drafts not yet published for the site; clears `drafts.told` for every draft whose `GoverningPair` changed and returns them in `applied.retellOwed`; all in one transaction so a change is never half-applied across drafts. **Sends no mail** (BP-057 decision 3). |
| `tests/publish/settings/apply.test.ts` | NEW | Every limb of `newVetoDeadline` at its boundary, as pure fixtures with no clock and no database: in-scope and out-of-scope states; a shortening change on a running window; a lengthening change on a draft in review; the Copilot-expired restart; an `approved` draft is untouched by rule 4. |
| `tests/publish/settings/save.test.ts` | NEW | The save is one transaction and is never half-applied; an invalid patch writes nothing; a pair change clears `told` and returns the draft in `retellOwed`; a saved change sends no mail; a change that alters neither whether nor when a draft publishes clears no telling. |

export function newVetoDeadline(a: {
  state: State

**A settings change clears the telling rather than sending one** (BP-057 decision
3). BP-046 owns what is said (WO-216) and BP-045's `customer_told` guard owns the
holding (WO-209), so a settings change can delay a publication and can never
cause one the customer was not told about. A customer stepping the window from 1
to 2 to 3 days sends no mail at all.

## Steps
1. Create `settings/apply.ts` with `newVetoDeadline` as a pure function. No clock read, no database read — every limb testable at its boundary.
2. Implement the four rules in BP-057's stated order and scope rule 4 to `in_review` only.
3. Add `savePublishingSettings` to `settings.ts`. Refuse an invalid patch whole before writing anything.
4. Map `newVetoDeadline` over the drafts not yet published for the site, inside one transaction with the four-value write.
5. Clear `drafts.told` for every draft whose `GoverningPair` changed and return those ids in `applied.retellOwed`. Send nothing.
6. Write the Copilot-restart limb's test first and watch it fail against an implementation that lets a switch to Autopilot publish a held draft immediately (constitution §8) — that limb is the one protecting the interval.
