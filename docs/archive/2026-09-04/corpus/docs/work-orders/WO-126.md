# WO-126 — provisionFromPayment — one account, one site, one running subscription, two idempotency keys

- Branch: wo/WO-126-provision-from-payment
- Estimate: ≤1 day

## Goal
Turn one verified completed payment into exactly one account, one site and one
running subscription, get the sign-in link out inside 60 seconds, and take the
right branch when the same payment or the same address arrives twice.

## File plan
> **Every path below is NEW.** No `src/` exists. Anchored to
> `registry/structure.md` and BP-032's `code:` glob
> `src/lib/account/provisioning/**`. Provisional against a repo with no code.

| File | New/Modify | Change |
|---|---|---|
| `src/lib/account/provisioning/provision.ts` | NEW | Exports `provisionFromPayment(sessionId)` with BP-032's signature verbatim. Order, exactly as BP-032 fixes it — "provision, then issue the link, then queue the deep pass": (1) call `recordCheckoutFacts(sessionId)` (WO-119); (2) insert `users` + `sites` in one transaction, with `sites.domain` and `sites.provisioned_from_scan_id` taken from `purchaseContext(sessionId)` (WO-123) and `paid_through` set to the subscription's first period end (BP-060's column, added by WO-129 and `not null`; BP-060's data-model delta assigns provisioning as its first writer — "Set at provisioning to the first period end" — so this cross-node write is the architect's design, not drift); (3) `issueLink({ userId, to: email, purpose: 'sign_in' })` (WO-136); (4) queue the deep pass through BP-003 **without awaiting it**. |
| `src/lib/account/provisioning/duplicates.ts` | NEW | The two conflict branches. A conflict on `checkout_session_id` returns `{ created: false, duplicate: 'replay' }` and sends no mail and queues no deep pass. A conflict on `lower(email)` runs BP-032's fixed order: cancel the newly created Stripe subscription, then send one `account` mail naming one way to reach a person, send no sign-in link, queue no deep pass. Cancelling is not optional (BP-032 decision 3). |
| `src/lib/account/provisioning/lead-conversion.ts` | NEW | Calls `suppressAddress(email, 'subscribed')` (BP-016) and the `leads` owner's conversion stamp through its exported seam. Writes no `leads` row — `leads` is not this node's migration topic (BP-032, error & edge behavior). |
| `tests/account/provisioning/provision.test.ts` | NEW | The happy path with a fixed clock: one `users` row, one `sites` row, one link issued, the deep pass queued after the link and never awaited, the whole path inside 60 s of the charge. Ordering asserted by call sequence, not by duration alone. |
| `tests/account/provisioning/duplicates.test.ts` | NEW | Replay: two deliveries of one session leave one account, one site, one subscription, one link, one deep pass — and the second returns `duplicate: 'replay'` with **no** mail. Second purchase: a new session from an address that already has an account leaves exactly one account, one site and **one running subscription** (the second is cancelled, asserted against the Stripe stub), sends exactly one `account` mail and no sign-in link, and queues no deep pass. A mutation case: deleting the cancel call fails `› exactly one running subscription remains`. |
| `tests/account/provisioning/lead-conversion.test.ts` | NEW | Provisioning suppresses the address and stamps the lead through the exported seams, and writes no `leads` row directly (asserted by table-level write capture). |
