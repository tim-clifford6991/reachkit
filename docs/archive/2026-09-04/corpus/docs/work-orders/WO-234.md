# WO-234 — verifyLive() — one fetch, three outcomes, and four Measured<boolean> in the one arm that has them

- Branch: wo/WO-234-verify-live
- Estimate: ≤1 day

## Goal
Ship `verifyLive()`: fetch the page's own live address **once, ever**, 24 hours after it published, and record exactly one of REQ-062 criterion 4's three outcomes — the four `Measured<boolean>` checks where the page answered, that no page was found, or that the check could not be confirmed — with the four checks produced in the `found` arm and in no other.

```ts
// src/lib/publish/verify/verify.ts
export type CheckId = 'reachable' | 'indexable' | 'sitemap' | 'aiReadable'

/** `VerifyChecks`, `VerifyOutcome`, `NotConfirmed` and `VerifyDisposition` are
 *  **declared in BP-045's `src/lib/publish/types.ts`** and re-exported here, so
 *  every caller's spelling is what it reads below. They live in the leaf because
 *  BP-045's `record/` must name the recorded outcome for REQ-062 criterion 7 and
 *  `types.ts` imports nothing — declaring them here would make BP-045 → BP-049 →
 *  BP-045 a node cycle and a build failure (BP-045 decisions 6 and 9). The
 *  behaviour behind every arm is this node's. */
export type { VerifyChecks, VerifyOutcome, NotConfirmed, VerifyDisposition } from '../types'

/** REQ-062 criterion 4's three outcomes of the one check, as three arms.
 *  **ADR-085 (landmine).** `checkedAt` is on every arm because criterion 4 and
 *  criterion 7 both require the date on every one of them. There is no fourth
 *  arm and no "pending": a check that has not run yet is a `VerifyDisposition`,
 *  not an outcome. */
export type VerifyOutcome =
  | { outcome: 'found';              checks: VerifyChecks; checkedAt: Date }
  | { outcome: 'page_not_found';     status: 404 | 410;    checkedAt: Date }
  | { outcome: 'could_not_confirm';  why: NotConfirmed;    checkedAt: Date }

export function verifyLive(publicationId: string): Promise<VerifyOutcome>
```

**One fetch, three outcomes, never a fourth — ADR-085 (landmine).** A 404 or a
410 **and no other answer** is `page_not_found`. **Any** other answer — no HTTP
answer at all, a 5xx, a redirect away from the page, or a document that is not
the page ReachKit published — is `could_not_confirm`. The mapping is WO-261's and
is a **whitelist of two statuses, never a blacklist of failures**: a blacklist
admits an unclassified answer into `page_not_found` by default, and the default
arm must be the one that asserts nothing.

**Neither of those two arms produces the four checks, states a failure of the
page, or names a cause.** REQ-062 criterion 4 forbids all three in terms. In
particular, **`could_not_confirm` must never be folded into `reachable: false`**:
that turns ReachKit's own network problem into an accusation against the
customer's page. It reads as tidying up an obviously incomplete union and it
passes every test that would exist without the two arm-separation rows in the
file plan.

**Neither is retried, rescheduled or repeated.** That is `dueNow`'s
(WO-232) and this module adds nothing: `verifyLive` runs once per publication and
returns. A retry here is the single most likely wrong change anyone will make to
this node and ADR-085's warning block leads with it.

**`reachable` is `true` in every `found` result, and is not deleted for it.**
Every way a page could be unreachable now lands in criterion 4's third outcome,
so the arm that produces the four checks is only ever reached by a 200 carrying
our page. The check therefore has one value in production and reads exactly like
a field nobody needs. It is kept because REQ-062 criteria 1, 2 and 3 promise the
customer **four** outcomes with their dates, and because criterion 3 requires all
four to state that they have not been checked yet in the 24 hours before the
check runs — a promise a three-outcome surface cannot keep. Same shape as
ADR-084's `made_live_by_us`: a constant field that is load-bearing for a
rendered promise. **Deleting it is a surface change, not a cleanup.**

**The user agent is our own token.** BP-049 states it plainly: it is permitted
because the robots document BP-047 serves blocks no general crawler (REQ-059
criterion 4), **it is not one of the six named AI agents, and impersonating one
of them would be a false statement to a server we are measuring.** `VERIFY.userAgent`
is a pin in BP-005 and a test asserts it matches none of `AI_CRAWLERS`.

**The four outcomes are `Measured<boolean>`, not booleans** (BP-049 decision 1).
`boolean | null` reads as false in every language the surface will pass through,
and the reason a check did not run would be lost. Nothing anywhere defaults a
`Measured<boolean>` to `false`.

## Steps
1. Create `verify/verify.ts` with the block above verbatim, re-exporting the four shapes from `../types` rather than declaring them.
2. Make **one** `safeFetch` GET of `live_url` and hand the answer straight to WO-261's `classify`. **Write no status mapping in this file** — assert its absence in test, so the whitelist stays in one place.
3. On `page_not_found` and on `could_not_confirm`, record the arm and return. Produce no checks, name no cause, and make neither of the other two fetches: they exist to decide checks those arms do not produce.
4. On `found`, run the remaining three checks. Check both the header and the meta tag for indexability. Fetch the sitemap the site publishes — BP-047's for a hosted page, `/{sitemap_index,sitemap}.xml` plus whatever `robots.txt` names otherwise.
5. Run the `aiReadable` evaluation over the same document, with no script execution of any kind and with `VERIFY.userAgent`. Never send one of the six named AI agent strings.
6. Record a `SiteCondition` only from an answer the site gave. Where the sitemap or robots document did not answer or could not be parsed, leave that one check `unmeasured` for this page alone, write no condition, and suppress nothing for any later page. **Any suppression keyed on "could not be reached" is wrong twice over** — that case moved to criterion 4's third outcome, and criterion 6 may not fire on a non-answer at all.
7. Write `publications.verify` as the serialised `VerifyOutcome` — the **discriminant stored**, so a reader cannot obtain the four outcomes without having gone through the arm that produces them. Write nothing on a job failure.
8. Write the two arm-separation tests first and watch them fail against (a) an implementation that maps any non-2xx to `page_not_found` and (b) one that records `could_not_confirm` as `reachable: false`. Both are the merges ADR-085 exists to stop and both read as tidier code (constitution §8).

## Out of scope
- Repairing anything. A failed check produces no retry, no republish and no transition (REQ-062's non-goal). The customer reads it.
- **Classifying the answer.** The two-status whitelist and the identity test are WO-261's `answer.ts`. This module fetches and records; it maps nothing.
- **Storing and reading back a site's condition** — WO-262's `site.ts`.
- Re-verifying — WO-232's `dueNow` selects only `verify is null`. **Adding a retry, a backoff or a "pending" render for `could_not_confirm` is forbidden, not merely out of scope** (ADR-085 Decision 3; REQ-062's non-goal).
- Rendering the four outcomes — BP-019's `renderMeasured` and BP-039/BP-001's surface. Handing the recorded outcome to a surface with the page's state is BP-045's page record, WO-263.
- **What the two not-measured outcomes do downstream.** `page_not_found` stops the page being shown as live (REQ-060 c2) and is a terminal not-judgeable cause; `could_not_confirm` does neither and the page goes on being judged with the outcome shown beside the verdict. Those consequences are BP-051's, BP-039's and BP-045's, and **ADR-085 Decision 4's table is where they are stated**. This module records the arm and nothing more.
- The message — WO-235.
- Traffic, ranking or conversion analytics — REQ-062's non-goal; the weekly verdict is REQ-063's.
