# WO-282 — The report screen — the route, the total view switch, the verdict strip, the one notice, the one control, and the removal address

- Branch: wo/WO-282-report-screen
- Estimate: ≤1 day
- Preview: sdlc-factory/docs/design/previews/WO-282.html
- Signed-off: 2026-09-04 — v1

## Goal
Serve the one public report address end to end: resolve it, 308 a non-canonical form, render exactly one arm of the closed union — including the removed arm and the removal address every report names — mark every response `noindex`, and never answer with a blank page, a 404 or an unhandled error.

**Risk: normal.** It moves no money, reads no session (its middleware entry is on BP-001's public allow-list), calls back to no third party and publishes to no customer domain. Its criteria are rendering and response-header assertions a plain test discriminates directly — a deleted `noindex` header fails a presence assertion outright rather than surviving it — and the silent half of the removal promise, the state precedence, is WO-280's, which is `risk: high`. `ui: yes` already routes this order through rule 7.3's preview gate and the UI-fit pass (doctrine 0.13.2, rule 2b).

## Consolidation (rule 2.6)
WO-069 is a total switch over `AddressState` whose `report` arm is WO-068 and
whose `removed` arm is WO-067; WO-068's `## Rollback` reads "WO-069's switch is
the only consumer and does not exist yet"; WO-067 exists so "WO-068 and WO-069
can consume them without re-deriving anything", in its own words. None of the
three can state its stop condition — every arm renders, exactly one control, one
removal address — without citing the other two. One order, one journey step:
JN-001 steps 3 and 4, the screen a stranger lands on.

**A `draft` order brought forward.** WO-067 carried `status: draft` because the
removal address is an owner-owed string with no value in the corpus. That is the
owner's standing posture for this wave — an order that needs customer-visible
strings renders keys and the keys stay owner-owed (WO-070's pattern) — not an
unmet gate, so the row is carried as an open `rests-on` and the replacement is
self-certified below.

**The problem-card and DIY-method modules are slots here (rule 1.1).** WO-068
carried `depends-on: WO-066` and filled `BUILD.md` §4.1 modules 3 and 4 directly.
WO-066 is REQ-009's and JN-001 step 8's, outside this wave (rule 7.4), so those
two modules become named, absent-safe slots exactly as modules 2, 5 and 6 already
were in WO-068's own plan. Cost of reversing: two slot props and the `depends-on`
edge.

## Steps

**WO-067's steps** (renumbered; order within the block unchanged):

1. Produce the preview artifact at the path in the display bullets above and hold
   in draft until it is signed off (rule 7.3).
2. Write the failing suites first.
3. Implement `RemovalAddressLine` over one address key and one framing key. The
   address is resolved by `copy()` and is never concatenated, templated from a
   domain, or read from `env`.
4. Implement `RemovedView` reusing `RemovalAddressLine`, so one key serves both
   surfaces and the address on the removal line and the address on a report can
   never differ.
5. Render no control on `RemovedView`: no re-scan, no retry, no landing field,
   no form.
6. Add the product-wide no-writer assertion: `domain_blocks` is written by no
   file under `src/`.

**WO-068's steps** (renumbered; order within the block unchanged):

7. Produce the preview artifact at the path in the display bullets above and hold
   in draft until it is signed off (rule 7.3).
8. Write the failing suites first.
9. Render the verdict strip from the stored `Verdict`: `scoreAndBand` through
   `renderMeasured`, the band word from `SCORE_BANDS[handle]`, and the one line
   from `LIMITING_LINES` where `limiting.kind === 'factor'`. The three factors
   each named and each rendered through `renderMeasured`. On the `unmeasured`
   arm render the dash, render no band element at all, and render the one line
   naming every missing factor with its reason's key.
10. Render `notice` as a total switch over `AddressNotice | null` — at most one
   line, ever.
11. Render `control` as a total switch over `AddressControl` — `none` renders
   nothing; every other arm renders exactly one control.
12. Render the modules in order, omitting a slot that is absent and rendering a
   section that `sectionOutcome` reports `present: false` as absent with one
   written line naming it — never an empty card and never a spinner.
13. Render the copy-link control, whose value is the canonical address and which
   carries no token and no expiry.
14. Render `RemovalAddressLine` at the foot of every report.

**WO-069's steps** (renumbered; order within the block unchanged):

15. Produce the preview artifact at the path in the display bullets above and hold
   in draft until it is signed off (rule 7.3).
16. Write the failing suites first.
17. Implement the route: network key, `canonicalRedirect` → 308, else
   `resolveAddress` → view switch.
18. Set `noindex` as a meta tag and as an `X-Robots-Tag` header on every response
   of this route, including the redirect, the removal line, the malformed line,
   the refusal, the cooldown and the progress shell. Read `decisions/ADR-002.md`
   before touching this: the `noindex` policy and the absent sitemap are that
   decision's, and this node implements them.
19. Implement the switch as a total `switch` over `AddressState.kind` with a
   `never` default, so a new arm fails the build.
20. Implement the `starting` arm: render the progress shell server-side, and post
   `/api/scan` from the client on first frame. Nothing is posted during server
   render.
21. Implement the progress swap: subscribe to `/api/scan/{scanId}/progress`, and
   on the `ending` event replace the progress view with the report without a
   reload.
22. Set no CDN cache header on this route: the `refused` and `scanning` arms
   depend on the visitor, so the render is not shared.
