# WO-151 — The release latch: four triggers, one monotonic write, no scheduled job

- Branch: wo/WO-151-release-latch
- Estimate: ≤1 day

## Goal
Release the founder into the app exactly once — on completion, degradation,
failure, or at ten minutes from `setup_completed_at` — with a latch no caller
can clear and no scheduled job can miss.

## File plan
> Every path below is **NEW** (no `src/` on disk, checked 2026-08-31). Placement
> follows `structure.md` and BP-036's `code:` globs; provisional.

| File | New/Modify | Change |
|---|---|---|
| `src/lib/scan/deep/release.ts` | NEW | `ReleaseReason`, `releaseToApp()` and `isReleased()`. The latch is a single-row conditional update (`set … where setup_released_at is null`); a zero-row result means somebody else latched first. `isReleased` latches `deadline` on the read path when `now - setup_completed_at >= 10 min`. It consults no opportunity count. |
| `tests/scan/deep/release.test.ts` | NEW | Idempotency and monotonicity, the four reasons, the read-path deadline latch, and the never-again property. |

## Interfaces
Consumes: `sites.setup_completed_at` (BP-033's delta on the `sites` topic),
`db()` (BP-002), the deep pass's end status (WO-150's `runDeepPass`), and the
10-minute deadline pin (BP-005).

Exposes (verbatim from BP-036 `## Public interface`):
```ts
export type ReleaseReason = 'completed' | 'degraded' | 'failed' | 'deadline'

/** The latch. Monotonic and idempotent: the first writer wins and no caller
 *  can clear it. REQ-029 criterion 5's "the wait is over for that founder for
 *  good" is this function's only postcondition. */
export function releaseToApp(a: { siteId: string; reason: ReleaseReason }):
  Promise<{ releasedAt: Date; reason: ReleaseReason }>

export function isReleased(siteId: string):
  Promise<{ released: false; deadlineAt: Date } | { released: true; at: Date; reason: ReleaseReason }>
```

## Steps
1. Write the failing tests first.
2. Implement `releaseToApp` as the conditional update; on zero rows, read the
   existing latch and return it — the first writer's reason stands.
3. Implement `isReleased`: if `setup_released_at` is set, return it; else if
   `now - setup_completed_at >= 10 min`, latch `deadline` and return it; else
   return `{ released: false, deadlineAt }`.
4. Latch `failed` immediately on an outright failure rather than waiting out the
   ten minutes (criterion 5: "fails outright, **or** has not ended").
5. Assert there is **no** scheduled job in this path (BP-036 decision 1) — the
   test asserts the release happens for a site whose pass never reported and
   whose next read is a week later.
6. Assert the release consults no opportunity count: a site with zero
   opportunities releases identically (criterion 4's structural half).
7. Mutation check: make the update unconditional and confirm the
   "first writer wins" test fails.
