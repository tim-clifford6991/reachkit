# WO-274 — tests/db/migration-naming.test.ts's directory-enumeration case asserts membership, not an exact two-file snapshot

- Branch: wo/WO-274-migration-naming-enumeration
- Estimate: ≤1 day (well under; one assertion in one existing file)

## Goal
Replace the exact-equality directory listing in
`tests/db/migration-naming.test.ts`'s `"finds the two migrations this work
order writes"` case with a membership check, so the case keeps proving
WO-267's baseline and RLS migrations are present without failing every time
any other order correctly adds a new, correctly-named migration file under
its own topic token.

## Provenance
`tests/db/migration-naming.test.ts` is WO-267's file, `tests/db/**` is
BP-002's by `structure.md` rule 4's `code:` glob (`supabase/**` ·
`src/lib/db/**` → BP-002, `structure.md` line 24: "every other migration
file is owned by the node whose topic or sub-token it carries" — the test
itself is the registry check, and the registry check is BP-002's). No
other order's file plan claims this file (`grep -rn
"tests/db/migration-naming.test.ts" sdlc-factory/docs/work-orders/*.md`
returns only WO-267's plan and mentions in WO-272's provenance/log/report,
none of which claim it as their own file to modify) — reuse check clear
(rule 7.2).

**Why this is its own order, not a merge into the order that found it
(rule 2.6's merge test).** WO-272 (BP-017) discovered the brittleness as a
side effect of correctly adding two new `users`/`sites`-topic migrations —
its own validator report (`## TST-006`) names the defect and explicitly
routes the fix to the planner rather than to its own implementer, because
`tests/db/**` is outside WO-272's file plan and outside BP-017's ownership
(rule 7.1). This order's goal and stop condition are stated entirely in
terms of `tests/db/migration-naming.test.ts`'s own behavior — "the case
must keep passing for the two migrations it names as more, correctly-named,
migrations are added" — and are true and checkable with zero reference to
WO-272, WO-272's columns, or BP-017: the fix is exercised here with a
synthetic third fixture file, not with WO-272's own migrations. WO-272 is
cited above only as *how the defect was found*, not as a fact this order's
stop condition needs. That is the distinction the merge test turns on, so
this is its own order, cut under BP-002 where the file is owned (rule
7.1) rather than admitted into WO-272's file plan, which would hand one
capability — the migration-naming registry check — two owners (BP-002's
WO-267 and BP-017's WO-272), exactly what rule 7.1 forbids.
