# WO-237 — The WordPress adapter — one create call that publishes live, at most one post, and the marker that makes it so

- Branch: wo/WO-237-wordpress-adapter
- Estimate: ≤1 day

## Goal
Ship `wordpressAdapter`: publish the page live into the customer's own WordPress in a single create call, search for our marker before creating so a lost answer never produces a second post, report the permalink the site came back with, and never write into a post ReachKit did not itself make live.

> verified to exist, because none can. Placement is anchored to

export interface WordPressConfig {          // the shape stored in destinations.config, sealed by BP-058

   *  REQ-060 criterion 1 upheld a criterion that has since inverted. */
  liveUrl: string
  madeLive: true                            // ADR-084 Decision 4: true for every row
                                            // this adapter writes. It looks like a
                                            // constant and is the discriminator
                                            // REQ-056 c16's second outcome rests on.
  remoteId: string                          // the WordPress post id
  seoWritten: readonly SeoPlugin[]          // possibly empty — criterion 4's case
  stampApplied: boolean                     // ADR-083. `false` is a delivered page
                                            // whose site would not take the term:
                                            // criterion 6 is unmet for it and
                                            // REQ-079 c6's mail has no place to
                                            // name — stated, never inferred

**One call, live, and the two-step is forbidden rather than merely unnecessary**
(**ADR-084** Decision 1). The one-call shape is not a performance choice. A
two-step opens a window in which a post exists in the customer's site as a draft
ReachKit meant to publish, and **a crash inside that window re-creates by
accident exactly the population the owner's ruling removes** — while ADR-080's
marker search, which answers "is this the post for draft X?", would then have to
also answer "and did we finish?", the second job ADR-083 Decision 3 forbids
loading onto a mark. The test asserts a request *count*, not a request *shape*,
because a second write added later would otherwise read as a harmless follow-up.

**`madeLive: true` and `liveUrl: string` are narrowed by type, and the narrowing
has inverted.** Until 2026-09-01 this adapter narrowed them the other way, and
that narrowing upheld REQ-060 criterion 1's promise that a WordPress post "is
never made live by us". **That criterion has inverted** (REQ-060 c1 now: "it is
publicly readable on their site from the moment the delivery completes"), so the
old narrowing upheld a promise that no longer exists. Widening `madeLive` back to
`boolean` is not a simplification: it is what would let a later edit report a
delivery as published with nothing live behind it.

**`servesPublicly: true`, `hostedByUs: false` — and this adapter is the reason
they are two fields.** They had the same value at every destination that existed
until 2026-09-01. `servesPublicly: true` is what puts `live_url` on the row,
which is what puts `verify_due_at` on it (WO-213), which is what makes BP-049
verify this page at 24 hours and BP-051 judge it weekly — **all by rules that
already read the address and were not edited** (ADR-084 Decision 2).
`hostedByUs: false` is what keeps REQ-056 criterion 15's `removed` arm hosted-only:
without the split, the obvious reading of `servesPublicly === true` here is "so
we can remove it", and `unpublish` would reach for a delete call against a site
ReachKit does not own. Merging them back fails one of the two assertions in the
file plan and nothing else in the corpus.

**The waiting-in-WordPress line is retired, not repurposed.**
`publish.wordpress.awaitingYou` described a page waiting for the customer to
publish it, which no page does any more; REQ-056 criterion 6's second arm was
deleted from the requirement on 2026-09-01. A retired key given a new meaning is
the plausible-but-wrong address rule 5.3 exists against.
`publish.wordpress.namedForRemoval` is **kept, minted and unreached** for the
opposite reason (ADR-084 Decision 4) — WO-239's.

**The marker is the second half of the at-most-once guarantee — ADR-080.** The
unique index on `(draft_id, destination_id)` protects a table in our database; it
cannot see inside a customer's WordPress. The case REQ-056 criterion 5 names
explicitly — "a retry of an attempt whose outcome was never confirmed" — is
precisely the case where we called the destination, it created the post, and we
lost the answer. **Neither the marker nor the publication row may be cleaned up.**
Changing the marker's shape is a migration of somebody else's site and requires a
fallback that finds the old shape first (ADR-080 decision 5).

**`unpublish` is WO-239's, and it has four WordPress arms whose populations have
inverted.** `returned_to_draft` is now every WordPress unpublish that reaches the
site; `named_for_removal` is the arm with no members. Which arm is taken is read
from `publications.made_live_by_us`, never from a re-read of the customer's site.
This file binds the member and implements none of it.

## Steps
1. Read **ADR-084** in full — its warning block first — then ADR-080, then ADR-086 Decision 5. Every simplification this file invites is one of those files' landmines and none of them makes a happy-path test fail.
2. Create `adapter.ts` with the block above verbatim, plus `servesPublicly: true` and `hostedByUs: false`.
3. Implement `deliver`: search for the marker first and return the existing post on a hit; otherwise make **one** create request carrying `status: 'publish'`, the SEO fields (WO-238) and the stamp, and write the marker in that same request.
4. **Assert the created post's status.** A response whose post status is not `publish` is `credentials_invalid`, non-retryable, through `errors.ts` — never a successful delivery. This is the arm that catches the case BP-058's probe missed by one health-check interval, and it is why no post is ever reported as published with a draft behind it.
5. Take `liveUrl` from the create response's permalink. **Do not compute it, do not derive it from the slug**, and do not fall back to a computed value if the field is absent — an absent permalink is an unclassifiable response and BP-048 decision 3 makes that non-retryable.
6. Write the SEO fields by calling WO-238's `seo.ts`. A write that fails while the delivery succeeded is reported as a not-written outcome on `seoWritten`, **never as a failed publish** — the page is in their site, and saying otherwise would be false.
7. Bind `unpublish: unpublishWordPress` from `./unpublish` (WO-239). Write no unpublish logic in this file and no read of `made_live_by_us`.
8. Implement `health` as one authenticated read of the REST index, mapped through `errors.ts`.
9. Write the "one create request, and no second write to that post" count assertion first, and the "a retry after a lost answer creates no second post" test, and watch both fail — the first against a two-step implementation, the second with the marker search removed. Those are the mutation checks §8 requires.
10. **Stop condition — the stamp.** ADR-083's `post_tag` term must be assigned **in the create call and never afterwards** (REQ-060 criterion 6 forbids a later write into their site), and `WORDPRESS_STAMP_SLUG`'s value and the term's display name are **owner-owed customer-visible strings** that no artifact in this corpus mints. **No work order cuts the stamp** (fourth `rests-on`). An implementer reaching this step therefore **stops and logs `failed — next: the stamp work order, and the owner's ruling on `WORDPRESS_STAMP_SLUG`** rather than inventing a slug or shipping `stampApplied: false` as a placeholder — ADR-083 Decision 4 makes `false` a *real outcome* ("a delivered page whose site would not take the term"), so writing it where no attempt was made is a false statement about the customer's site.

## Rollback
Delete both files. WO-225 imports `wordpressAdapter`; revert this only before it, or `adapterFor` loses one arm of a closed union. Note that reverting after any post has been delivered leaves markers in customers' sites with no code that reads them — which is safe (they are inert) but re-arms the duplicate if a later attempt runs. **It also leaves live pages on customers' own domains that no ReachKit surface any longer accounts for** — a heavier consequence than before 2026-09-01, when a reverted delivery left only a draft.
