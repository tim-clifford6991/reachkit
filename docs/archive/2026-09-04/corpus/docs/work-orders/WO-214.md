# WO-214 — Retry at most three times, withheld while the switch is off — and unpublish()

- Branch: wo/WO-214-publish-retry-unpublish
- Estimate: ≤1 day

## Goal
Ship the retry policy — retryable reasons only, at most three, backed off, withheld while publishing is off — and `unpublish()`, available for as long as the page is published.

## File plan

> `package.json` (verified 2026-08-31). **Every path below is NEW** — none was
> verified to exist, because none can. Placement is anchored to
> `sdlc-factory/docs/registry/structure.md` and to this work order's blueprint
> `code:` globs, and is provisional against a repo with no code: if the
> implementer finds a file already present at one of these paths, they stop and
> log `failed` naming the drift rather than merging into it.

| File | New/Modify | Change |
|---|---|---|
| `src/lib/publish/attempt/retry.ts` | NEW | The policy as one pure decision plus its scheduler. A `failed` page schedules a retry only while `reason ∈ RETRYABLE` and `attempt_no < 3`; otherwise `failed → needs_attention` is taken in the same invocation, so no page rests in `failed` with neither a retry due nor that move made. While the switch is off the retry is **withheld and the page held in `failed`** — the one legitimate rest — and becomes due again on resume. Backoff from BP-005's `PUBLISH_RETRY_BACKOFF_MIN` (`[5, 30, 180]`), never a literal here. |
| `src/lib/publish/attempt/unpublish.ts` | NEW | `unpublish()`, **returning BP-045's `UnpublishResult` — the five-arm closed union.** Calls `adapterFor(kind).unpublish(pub, cfg)`, sets `publications.unpublished_at`, **records the arm it got back in `publications.unpublish_outcome`** (WO-208's column, ADR-082 Decision 6 carried forward by ADR-084 Decision 4), takes `published → unpublished` through `transition()`, and **returns the adapter's outcome unchanged** — it neither re-derives the arm nor collapses the five into fewer. Available for as long as the page is `published`. **No publication row is deleted** (ADR-080 decision 2). **One edge, five outcomes, and the edge is the same in all five** — including `unreachable`, which is `ok: true` and takes the edge and sets `unpublished_at` exactly as the other four do (BP-045: reading it as a failure and holding the page in `published` would leave the customer's stop un-taken, which is the one thing REQ-056 c16 promises in every branch). **Which family of arms applies is the adapter's, and the adapter reads `hostedByUs` — never `servesPublicly`, which is now `true` at both destinations** (ADR-084 Decision 2). **This function branches on neither**: it is handed the `Publication`, hands it to the adapter, and stores what comes back, so the discriminator is consulted in exactly one place. |
| `tests/publish/attempt/retry.test.ts` | NEW | Each of the nine `FailureReason` members is retried or not according to `RETRYABLE`; the third failure moves to `needs_attention`; no page is left in `failed` with neither a scheduled retry nor that move; with the switch off a due retry is withheld and the page stays in `failed`, and becomes due again on resume. |
| `tests/publish/attempt/unpublish.test.ts` | NEW | `unpublish` is offered for every `published` page and at any time; it sets `unpublished_at` and deletes no row; a subsequent publish attempt against the unpublished page creates no post; on a hosted destination the outcome is `removed`. **Pass-through, asserted five ways:** a stub adapter returning each of `removed`, `returned_to_draft`, `named_for_removal`, `already_gone` and `unreachable` produces exactly that outcome from `unpublish()`, each is written to `publications.unpublish_outcome` unchanged, and `published → unpublished` and `unpublished_at` are identical in all five — the state change does not vary by arm. **`unreachable` is the row that discriminates the `ok: true` reading**: an implementation that treats it as a failure and holds the page in `published` passes every other row here. **`named_for_removal` is the row that would silently disappear if the union were narrowed to today's reachable population**, and it uses a stub adapter precisely because no production adapter can return it since ADR-084 inverted which arm is empty. **A source assertion that this file reads neither `made_live_by_us` nor `hostedByUs` nor `servesPublicly`** — the branch belongs to exactly one place and this is not it. |

**Exposes** — copied exactly from BP-045's `## Public interface`:

```ts
/** ADR-082, carried forward **unchanged in shape** by ADR-084 Decision 4: five
 *  outcomes, never a boolean and no longer three. Each of REQ-056 c16's four
 *  WordPress outcomes has its own written line on the page's record, and
 *  collapsing any pair makes one of those lines unrenderable. `unreachable` is
 *  `ok: true` on purpose: the page did reach `unpublished` and the product did
 *  stop treating it as live — what failed is the write into a site we do not
 *  own, and that is the outcome, not a failure of the action. */
export type UnpublishResult =
  | { ok: true;  outcome: 'removed' }             // hosted — REQ-056 c15, 410 at BP-047
  | { ok: true;  outcome: 'returned_to_draft' }   // WordPress, made live by us — c16 outcome 1
  | { ok: true;  outcome: 'named_for_removal' }   // WordPress, never made live, post still there — c16 outcome 2
  | { ok: true;  outcome: 'already_gone' }        // WordPress, post no longer in their site — c16 outcome 3
  | { ok: true;  outcome: 'unreachable'; retryOffered: true }
                                                  // WordPress, site not reached, nothing written — c16 outcome 4
  | { ok: false; reason: FailureReason }

export function unpublish(a: { draftId: string; by: Actor }): Promise<UnpublishResult>
```

`UnpublishResult` is declared in `src/lib/publish/types.ts` (WO-206) and is
consumed here, not re-declared.

**The liveness branch reads `hostedByUs`, and it is not this function's branch.**
BP-045: "Which family of arms applies is read from `hostedByUs` (**ADR-084
Decision 2**), never from `servesPublicly`, which is now true at both
destinations." Until 2026-09-01 the two were one boolean; they now differ at
WordPress, and reading the merged field would either stop verifying live
customer pages or point `unpublish` at a delete call against a site ReachKit does
not own. This function reads neither: it passes the `Publication` to the adapter
and stores what comes back, which is why the source assertion in the test row is
part of the plan rather than a review comment.

**`named_for_removal` is now the arm with no members, and `returned_to_draft` is
the ordinary one — the ends have swapped.** ADR-082's warning block told a
future reader to protect `returned_to_draft`; ADR-084 Decision 4 records that
**that warning now points at the wrong arm**. Read ADR-084's warning block
before removing either.

## Steps
1. Create `attempt/retry.ts` with the decision as a pure function of `(reason, attemptNo, switchOn)` and a thin scheduler over it, so every limb is testable without a clock.
2. Read `PUBLISH_RETRY_BACKOFF_MIN` (`[5, 30, 180]`) from BP-005's `src/lib/config/constants.ts`. Do not add it here and do not inline the numbers: `src/lib/config/**` is BP-005's under structure.md, and a number in two files is wrong (rule 5). If the pin is absent when the implementer starts, they stop and log `failed — next: wait on BP-005's pins work order`.
3. Create `attempt/unpublish.ts`. Set `unpublished_at`; write the arm to `unpublish_outcome`; delete nothing. Return the adapter's `UnpublishResult` unchanged: no `switch` in this file maps an outcome to a boolean, to a message, or to a different state edge, and **`unreachable` takes the same edge as the other four**. Read ADR-084's warning block first — `named_for_removal` has no members in production since the ruling of 2026-09-01, and a `default:` arm that folded it into `returned_to_draft` would break nothing here and no test but the five-arm pass-through above.
4. Write the "no page rests in failed without a retry due or the move made" property test first and watch it fail against an implementation that only retries (constitution §8).

## Out of scope
- What the WordPress adapter does inside the customer's site on unpublish — **BP-048, WO-239**, which owns all four WordPress arms. This work order calls the adapter and does nothing with which arm it took beyond returning it and storing it.
- Reading `publications.made_live_by_us`, `hostedByUs` or `servesPublicly`. The adapter is handed the `Publication` and reads what it needs (BP-045); this function branches on none of them.
- **`retryUnpublishWrite`** — BP-045 declares it in `attempt/` for REQ-056 c16's fourth outcome, and **no work order in this corpus cuts it.** It is not folded in here: it takes no transition, evaluates no guard and rewrites a stored outcome, which is a different contract from this function's, and cutting it was outside this pass's allocation. Reported rather than absorbed (rule 4.2).
- Republishing an unpublished page or restoring a skipped one — REQ-056 criteria 3 and 5 forbid it and the table has no such edge.
- The job schedule that invokes the retry — BP-003's `publish/execute`.

## Rollback
Delete the four files. `publish()` stands without a retry policy, which is a degraded but not incorrect state: a failed page simply rests in `failed`, which is why the property test above exists.
