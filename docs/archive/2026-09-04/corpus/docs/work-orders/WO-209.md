# WO-209 — transition() — the only mover of state, with named guards and an append-only record

- Branch: wo/WO-209-transition-fn
- Estimate: ≤1 day

## Goal
Ship `transition()`: refuse any move that is not one of the fifteen with the state unchanged, evaluate the named guards for the move that is, and append the transition record.

## File plan

> This repository carries no `src/`, no `tests/`, no `supabase/` and no
> `package.json` (verified 2026-08-31). **Every path below is NEW** — none was
> verified to exist, because none can. Placement is anchored to
> `sdlc-factory/docs/registry/structure.md` and to this work order's blueprint
> `code:` globs, and is provisional against a repo with no code: if the
> implementer finds a file already present at one of these paths, they stop and
> log `failed` naming the drift rather than merging into it.

| File | New/Modify | Change |
|---|---|---|
| `src/lib/publish/machine/guards.ts` | NEW | One function per `GuardId`, each named for the id. `draft_passed_hard_rules` calls BP-014's `runHardRules` result on the draft row; `never_entered_review` reads `drafts.transitions` for an `in_review` target; `customer_initiated` is `by.kind === 'customer'`; `publishable_and_due` calls BP-046's `becomesPublishable` (WO-215); `customer_told` calls BP-046's `toldCurrentPair` (WO-216); `publishing_switch_on` calls WO-210's `isPublishingOn`; `within_ceilings` calls WO-211's `ceilingRoom`; `destination_working` reads the site's live `destinations` row and is true only when `deleted_at is null` and `health = 'ok'`. |
| `src/lib/publish/machine/index.ts` | NEW | `transition()`, plus the re-export of WO-207's `STATES`, `TRANSITIONS`, `TERMINAL`, `Refusal`, `GuardId` and `GUARDS` so BP-045's declared import path holds. Order: membership check against `TRANSITIONS` first (a non-member returns `{ok:false, refused:'not_a_transition'}` and writes nothing at all), then each `GuardId` in `GUARDS['from→to']` in list order, returning `{ok:false, refused:'guard', failedGuard}` on the first failure with the state unchanged, then the update and the append. | `tests/publish/machine/transition.test.ts` | NEW | Every non-member move is refused with the row unchanged and no record appended; each guarded edge is refused by each of its guards in turn with `failedGuard` naming it; `needs_attention → generating` is refused for a system actor and for a draft that entered review; the transition record is append-only and never rewritten. |

**Exposes** — copied exactly from BP-045's `## Public interface`:

```ts
export function transition(
  draftId: string, to: State, by: Actor, reason?: string
): Promise<
  | { ok: true; state: State }
  | { ok: false; refused: Refusal; failedGuard?: GuardId; state: State }
>
```

## Steps
1. Create `machine/guards.ts` with one exported function per `GuardId`, each taking the loaded draft row and the `Actor` and returning a boolean. No guard reads a setting it does not own; each delegates to the node that owns it.
2. Create `machine/index.ts` with `transition()` in the order above and the re-exports.
3. Append `{from,to,actor,reason,at}` to `drafts.transitions` in the same statement that sets the state, so a state that moved without a record is impossible.
4. Emit the one structured log line. Assert in test that no field of it can hold a credential or a vendor string.
5. Write the refusal tests first and watch them fail against a stub that always transitions (constitution §8).

| Acceptance criterion (verbatim from REQ) | Test |
|---|---|
| **REQ-056 c2** — Given a page in any state, when its state changes, then the change is one of these fifteen and no other, and any other attempted change is refused with the page's state unchanged: `planned`→`generating`, `planned`→`skipped`, `generating`→`in_review`, `generating`→`needs_attention` (any generation that produced no draft fit for review, whatever stopped it — a generation hard rule for the second time, REQ-053 criterion 3, or a step that failed, REQ-092 criterion 1 — so no failure leaves a page resting in `generating`), `in_review`→`approved`, `in_review`→`skipped` (a draft held by a failed claim re-check leaves review by one of these two and by no other, REQ-053 criterion 5), `approved`→`publishing`, `publishing`→`published`, `publishing`→`failed`, `failed`→`publishing`, `failed`→`needs_attention`, `needs_attention`→`publishing` (open only to a page holding a draft that passed every generation hard rule, so a draft one of those rules stopped is never published by starting an attempt), `needs_attention`→`generating` (open only to a page whose draft never entered review, and only when the customer starts it, so REQ-053 criterion 3's bound on automatic regeneration is never raised), `needs_attention`→`skipped`, `published`→`unpublished`. | `tests/publish/machine/transition.test.ts` › "every move outside the fifteen is refused with the state unchanged" — drives all 100 ordered pairs, asserts the 85 non-members return `not_a_transition`, the row is untouched and `drafts.transitions` gained no entry. |
| **REQ-056 c3** — Given a page in `planned`, `in_review` or `needs_attention`, when the customer skips, vetoes or discards it, then it moves to `skipped` and never publishes. `skipped` and `unpublished` are the only states from which no further change is possible, so a page the customer stopped or took down is never returned to a destination by any later attempt, and no page — whichever route brought it to `needs_attention` — is left in a state it has no way out of. | `tests/publish/machine/transition.test.ts` › "no move leaves skipped or unpublished" — every outbound pair from each terminal state is refused, so a page the customer stopped is never returned to a destination by any later attempt. |
| **REQ-056 c4** — Given a page in `publishing`, when the attempt fails, then it becomes `failed` with a written reason and is retried automatically only while that reason is one a repeated attempt could clear, and at most three times; when no such retry is due — because the reason needs the customer, or because the third retry failed — it moves to `needs_attention`, where no further automatic attempt is made and the customer can start one. No page rests in `failed` without either a further attempt scheduled or that move already made — except while publishing is switched off, when a retry that was due is withheld and the page is held rather than moved (criterion 11), and becomes due again when publishing resumes. | `tests/publish/machine/transition.test.ts` › "needs_attention → publishing requires draft_passed_hard_rules" — the guard refusal names the failed guard rather than moving the page. |
| **REQ-057 c8** — Given a draft in review, when the pair of publishing mode and veto window governing it changes (REQ-073 criterion 4) so that what the customer was last told about whether and when it publishes has stopped being true, then before it publishes they are told again which pair now governs it and, under that pair, either the exact date and time it will publish unless they act or that it will not publish until they approve it — on criterion 1's terms where the new pair leaves them an interval in which to act, and on criterion 7's where it leaves none. No page publishes on a pair the customer was never told about, and no page publishes at all without their having been told, on the pair it actually publishes under, either the interval they have to stop it or that no interval exists. | `tests/publish/machine/transition.test.ts` › "approved → publishing is refused when customer_told fails" — the page is held in `approved`, not moved and not skipped. |
