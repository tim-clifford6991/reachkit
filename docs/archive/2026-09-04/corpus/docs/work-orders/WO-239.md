# WO-239 — The WordPress unpublish — four outcomes, one stored discriminator, and the arm that is empty now

- Branch: wo/WO-239-wordpress-unpublish
- Estimate: ≤1 day

> This repository carries no `src/`, no `tests/`, no `supabase/` and no
> `package.json` (verified 2026-09-02). **Every path below is NEW** — none was
> verified to exist, because none can. Placement is anchored to
> `sdlc-factory/docs/registry/structure.md` and to BP-048's `code:` globs
> (`src/lib/publish/destinations/wordpress/**`, `tests/publish/destinations/wordpress/**`),
> and is provisional against a repo with no code: if the implementer finds a
> file already present at one of these paths, they stop and log `failed` naming
> the drift rather than merging into it.

> **Read ADR-084's warning block in full before writing a line of this file, and
> ADR-082 after it.** This is the fourth BP-048 work order — the one deliberately
> never cut while BP-048 carried `blocked-by: [REQ-079]`. One of its four arms
> has no members in production and will read as dead code against a passing
> suite. **Since 2026-09-01 that arm is `named_for_removal`, not
> `returned_to_draft`** — the ends have swapped, and ADR-082's warning block,
> which a reader might reach first, now names the wrong one. The tests below are
> what make deleting either fail loudly.

## Goal
Ship the WordPress adapter's `unpublish`: a page ReachKit made live is returned
to draft in the customer's own site by one write of one field; a page it never
made live is named for the customer and not touched; a post that is no longer
there and a site that could not be reached are their own outcomes; and which of
the four happens is read from `publications.made_live_by_us` and from what the
call itself finds, never from a re-read of the site to decide the arm.

## File plan

| `src/lib/publish/destinations/wordpress/unpublish.ts` | NEW | `unpublishWordPress(pub: Publication, cfg: DestinationConfig): Promise<UnpublishResult>` — the whole of ADR-082's ruling for this destination, as carried forward by ADR-084 Decision 4, and nothing else. Reads `pub.madeLiveByUs` (the `publications.made_live_by_us` column WO-208 creates, carried on the `Publication` WO-206 declares). **`true` → one `POST` through WO-236's client setting that post's status to `draft`, and nothing else** — no other field is read, edited or reordered — then `{ ok: true, outcome: 'returned_to_draft' }`. **This is now the ordinary outcome and reaches every WordPress unpublish that reaches the site.** **`false`, post present → `{ ok: true, outcome: 'named_for_removal' }` with zero outbound writes**: not the post status, not a tag, not a comment, not a removal of the marker and not a removal of the stamp (ADR-080 decision 5, ADR-083 decision 3). **This arm is now empty in production and stays specified, tested and unreachable.** **Post no longer in the site → `{ ok: true, outcome: 'already_gone' }`** — nothing was written and nothing is theirs to remove; it applies whichever way `made_live_by_us` reads, because there is nothing left to return either way. **Site could not be reached → `{ ok: true, outcome: 'unreachable', retryOffered: true }`** — nothing was written, the post may still be live there, and it is `ok: true` because the customer's stop was taken and the page is `unpublished`; what did not happen is the write into a site we do not own. module table names four (`adapter.ts`, `client.ts`, `seo.ts`, `errors.ts`) and
places `unpublish` among `adapter.ts`'s members. Splitting it out is a file-plan
choice under rule 1.1: it keeps this work order and WO-237 off a shared file so

## Interfaces

**Consumes**

```ts
// BP-045 · src/lib/publish/types.ts (WO-206) — declared in the leaf
/** ADR-082, carried forward **unchanged in shape** by ADR-084 Decision 4: five
 *  outcomes, never a boolean and no longer three. REQ-056 c16 names four things
 *  that can happen inside a customer's own WordPress and each of the four has
 *  its own written line on the page's record. */
export type UnpublishResult =
  | { ok: true;  outcome: 'removed' }             // hosted — REQ-056 c15, 410 at BP-047
  | { ok: true;  outcome: 'returned_to_draft' }   // WordPress, made live by us — c16 outcome 1
  | { ok: true;  outcome: 'named_for_removal' }   // WordPress, never made live, post still there — c16 outcome 2
  | { ok: true;  outcome: 'already_gone' }        // WordPress, post no longer in their site — c16 outcome 3
  | { ok: true;  outcome: 'unreachable'; retryOffered: true }
                                                  // WordPress, site not reached, nothing written — c16 outcome 4
  | { ok: false; reason: FailureReason }

export type FailureReason =
  | 'network' | 'timeout' | 'destination_unavailable' | 'rate_limited'
  | 'credentials_expired' | 'credentials_invalid' | 'dns_not_pointed'
  | 'destination_rejected' | 'no_destination'

// BP-045 · the member this module implements, quoted from `DestinationAdapter`:
  /** Whether the hosted `removed` arm or a WordPress arm is taken is read from
   *  `hostedByUs` (ADR-084 Decision 2), and which WordPress arm is read from
   *  `publications.made_live_by_us` — never from a re-read of the destination.
   *  Whether the post is still there, and whether the site answered at all, are

  unpublish(pub: Publication, cfg: DestinationConfig): Promise<UnpublishResult>
```

**Exposes**

```ts
// src/lib/publish/destinations/wordpress/unpublish.ts
export function unpublishWordPress(
  pub: Publication, cfg: DestinationConfig
): Promise<UnpublishResult>
```

**The discriminator is a stored fact, and there are exactly two things that must
never be substituted for it** (ADR-082 Decision 2, carried forward by ADR-084
Decision 4 — both substitutions read as the obvious implementation):

- **Not `pub.liveUrl != null`, and the reason has changed sign.** ADR-081
  rejected this predicate because BP-048 left `live_url` null for *every*
  WordPress delivery, so it classified every WordPress page as never-live and
  quietly reduced "unpublish everything" to "touch nothing". **Since ADR-084
  `live_url` is non-null for every WordPress row**, so the same predicate now
  classifies every WordPress page as **made-live-by-us** — and would write into a
  post a future draft-delivery option had left alone. Same substitution,
  opposite failure, both wrong.
- **Not a re-read of the post's status at unpublish time.** A customer who
  published our draft themselves is not a page ReachKit made live, and writing
  into a post the customer chose to publish is the harm REQ-060's non-goals and
  REQ-056 criterion 16 name. The stored fact is about what *we* did; the site's
  state is about what *they* did.

Neither `servesPublicly` nor `hostedByUs` is the discriminator between these four
arms either. `hostedByUs` chooses the *family* — the hosted `removed` arm against
this module's four — and it is read one level up, in BP-045 and on the adapter
(ADR-084 Decision 2); `made_live_by_us` chooses between outcomes 1 and 2 inside
the family. Reading `servesPublicly` here would now be actively wrong: it is
`true` at both destinations.

**The empty arm has swapped ends, and it is now `named_for_removal`.** Until
2026-09-01, REQ-060 criterion 1 promised a WordPress post was never made live by
us, so `made_live_by_us` was `false` on every WordPress publication and
`returned_to_draft` was the arm with no members. **That criterion has inverted.**
This adapter now sets `status: 'publish'` on every create and `made_live_by_us`
is `true` on every publication it writes, so `returned_to_draft` is the ordinary
outcome and **`named_for_removal` is the arm with no members**. It is kept for
exactly the reason ADR-082 kept the other one: it is the outcome REQ-056
criterion 16 promises, held open against a page ReachKit created but did not make
live, and the analyst deliberately did not narrow the criterion to today's
population. Its copy key is kept minted and unreached beside it — a deleted key
is how an empty arm becomes unrenderable and therefore deletable next. **Deleting
it looks like a cleanup with a passing suite; the mutation rows in the test plan
are what stop that.**

**`already_gone` and `named_for_removal` are not the same arm and must not
merge.** `named_for_removal` tells the customer "removing the post is theirs to
do"; `already_gone` tells them "nothing is theirs to remove". A customer sent to
delete a post that is not there was told the wrong one. ADR-082 Decision 3b
withdraws the mapping ADR-081 made between them, and `already_gone` applies
whichever way `made_live_by_us` reads.

**`unreachable` is `ok: true` on purpose.** REQ-056 criterion 16's opening binds
all four outcomes alike — the product stops treating the page as one of their
live pages — so this arm takes the `published → unpublished` edge and sets
`unpublished_at` exactly as the other three do (WO-214). What failed is the write
into a site we do not own, and that is the outcome, not a failure of the action.
Reading it as `ok: false` would leave the customer's stop un-taken, which is the
one thing criterion 16 promises in every branch.

## Steps
1. Read **ADR-084**'s warning block in full, then ADR-082, then ADR-080 decision
   5. Every simplification this module invites is one of those files' landmines,
   and none of them makes a happy-path test fail.
2. Write `tests/publish/destinations/wordpress/unpublish.test.ts` first, every
   row, and run it: every row must fail on a missing module (constitution §8,
   watch it fail first).
3. Implement the `made_live_by_us = true` arm as exactly one `POST` setting
   `status: 'draft'` on `pub.remoteId`, through WO-236's client. Send no other
   field. Do not delete the marker, do not touch a tag, do not remove the stamp,
   do not add a comment (ADR-080 decision 5 and ADR-083 decision 3: a cleanup
   that strips either mark while returning the post to draft is the same
   landmine).
4. Implement the `made_live_by_us = false` arm as an early return with **no
   client call at all**. The zero-egress assertion is the test of REQ-056
   criterion 16's second outcome; write the arm so the egress seam is not merely
   unused but unreachable — the client is not imported into that path.
5. Take `already_gone` and `unreachable` from `errors.ts`'s mapping (WO-236) and
   write no second mapping here. `already_gone` applies whichever way
   `made_live_by_us` reads.
6. Return `unreachable` as `{ ok: true, outcome: 'unreachable', retryOffered: true }`.
   It is not a failure and must not be mapped to one.
7. Mutate, and confirm each fails:
   - replace `pub.madeLiveByUs` with `pub.liveUrl != null` — the never-live
     fixture then takes `returned_to_draft` and **writes into a post ReachKit
     did not make live**, failing the c16 zero-egress row;
   - delete the `named_for_removal` branch and let both populations fall through
     to `returned_to_draft` — the never-live fixture fails;
   - merge `already_gone` into `named_for_removal` — the already-gone fixture
     fails;
   - map `unreachable` to `{ ok: false }` — the unreachable row fails.

**Discriminates (mutation check, constitution §8).**
- **Deleting the `named_for_removal` branch** — the change ADR-084's warning
  block is now written against — leaves every production-shaped test green,
  because no production path produces a `made_live_by_us = false` row. It fails
  the REQ-056 c16 zero-egress row and the disagreeing-fixture row, both of which
  construct that row directly. Together with WO-206's type-level exhaustiveness
  test (deleting the arm from `UnpublishResult` stops the type-check), the arm
  cannot be removed silently at either level: WO-206 pins that the arm *exists*,
  this work order pins that it is *taken*, and neither alone is sufficient.
- **Substituting `live_url != null` for `made_live_by_us`** passes every row
  whose two fields agree and fails the two whose fields disagree — and now fails
  them by writing into somebody else's post rather than by declining to.
- **Merging `already_gone` into `named_for_removal`** sends a customer to delete
  a post that is not there, and fails the already-gone row alone.
- **Mapping `unreachable` to `{ ok: false }`** leaves the customer's stop
  un-taken and fails the unreachable row alone.
- **Calling the client on the never-live arm** — even a harmless GET — fails the
  c16 zero-egress assertion.

## Rollback
Delete both files. `adapter.ts` (WO-237) binds `unpublish: unpublishWordPress`
from this module, so reverting this work order leaves `wordpressAdapter` short
of one `DestinationAdapter` member and the type-check fails — which is the
correct behaviour: it is a build failure rather than an adapter that silently
does nothing when a customer asks for their pages back. Revert this only
together with WO-237, or before it lands. Nothing is stored and no migration is
involved; no request is made to any customer's site by either arm's absence.
**Since 2026-09-01 the stakes of that absence are higher**: the pages a customer
would be asking back are live on their own public domain, not drafts.
