# WO-216 — The telling — what the customer is told, when the pair changes, and the one mail that cannot be suppressed

- Branch: wo/WO-216-telling
- Estimate: ≤1 day

## Goal
Ship `tellingFor`, `toldCurrentPair`, `recordTold` and `isUnsuppressible` — the occasion, the payload contract and the record of what was said, including what the telling says about a page bound for the customer's own site — so a page whose telling is owed is held rather than published.

```ts
// src/lib/publish/publishable/telling.ts
/** REQ-057 criterion 9. What the telling says about the destination, composed
 *  **at the moment the mail is composed** and never read from `drafts.told`
 *  (decision 5). Present only for a page bound for the customer's own site —
 *  decided from `hostedByUs === false` on the adapter (ADR-084 Decision 2),
 *  never from `kind === 'wordpress'`; `null` at a destination ReachKit serves,
 *  which criterion 9 does not speak about. */
export type DestinationClause =
  | { says: 'goes_live_there'; site: string
      copy: 'mail.draftReady.dest.goesLiveThen'        // with an interval (c1, c8)
          | 'mail.draftReady.dest.goesLiveAtOnce'      // zero window (c7)
          | 'mail.draftReady.dest.goesLiveOnApproval' } // copilot (c1, c8)
  /** ReachKit already reads that site as one it cannot publish to (REQ-060
   *  criterion 7, BP-058's `cannot_publish`). The telling says the page cannot
   *  go live there as things stand and what must change. It **does not**
   *  suppress the date criteria 1, 7 and 8 have it name, and does not suppress
   *  the stop action; it only stops the telling asserting the page goes live
   *  there then, or that approving it will make it live. One key, whichever kind
   *  the telling is. */
  | { says: 'cannot_go_live_there'; site: string; copy: 'mail.draftReady.dest.cannotPublish' }

export type Telling =
  | { kind: 'interval';     publishesAt: Date; stopAction: VetoLink; destination: DestinationClause | null
                                                                     copy: 'mail.draftReady.autopilotWindow' }
  | { kind: 'no_interval';  publishesAt: Date;                        destination: DestinationClause | null
                                                                     copy: 'mail.draftReady.autopilotZero' }
  | { kind: 'approval_only';                                          destination: DestinationClause | null
                                                                     copy: 'mail.draftReady.copilot' }

export interface GoverningPair {          // the pair REQ-057 criterion 8 tracks
  mode: 'autopilot' | 'copilot'
  vetoHours: number                       // 0..168, BP-057
  publishTime: string                     // 'HH:mm', in `timezone`
  timezone: string                        // IANA
}

/** **Asynchronous since 2026-09-01** (decision 5): criterion 9's third arm binds
 *  on what ReachKit reads "at the moment that telling is sent", so this reads
 *  BP-058's `ensureFreshHealth` for the page's destination. Every other input is
 *  still a pure function of `DraftView`. */
export function tellingFor(d: DraftView): Promise<Telling>
export function toldCurrentPair(d: DraftView):
  | { told: true }
  | { told: false; owed: Telling; because: 'never_told' | 'pair_changed' }
export function recordTold(draftId: string, t: Telling, pair: GoverningPair): Promise<void>

/** True only for `kind: 'no_interval'`: this telling is the whole of the telling. */
export function isUnsuppressible(t: Telling): boolean
```

**The clause is composed at send time and is not part of the pair.** BP-046
decision 5 rejects the three alternatives explicitly: a fourth `Telling` kind
duplicates three arms and would duplicate them again at the next window setting;
computing the clause at generation time is a stale second copy of a fact that
can change in the hours before the mail is composed (rule 2.4); and putting
destination health into `GoverningPair` makes every health flap a `pair_changed`
and holds pages on a precondition criterion 8 never names. **What holds a page
against a broken destination is BP-045's `destination_working` guard, which
already exists** — not this module.

**The cannot-publish arm suppresses nothing else, and four assertions hold that.**
Criterion 9's third arm changes one clause of the sentence and not the three
behaviours around it: the date criteria 1, 7 and 8 have the telling name is still
named, the stop action is still offered, and criterion 7's zero-window mail is
still unsuppressible and still carries no unsubscribe link. The negative
assertions are in the file plan because the natural implementation of "the page
cannot go live there" is to stop naming a date — and nothing else in the corpus
would catch it.

**`hostedByUs === false`, never `kind === 'wordpress'`.** Criterion 9 speaks
about "a page bound for the customer's own site rather than a destination
ReachKit serves". Since ADR-084 `servesPublicly` is true at both destinations and
can no longer answer that question. The two are coextensive today, which is
exactly why a kind check would pass every test — write the stated rule and assert
it against a hypothetical third kind.

**The zero-window telling is sent before the claim commits** (BP-046 decision
2): send, then `recordTold`, then claim. A send failure fails the `customer_told`
guard and holds the page rather than publishing it untold. That ordering is
enforced in WO-212's claim; this work order supplies the predicate the guard
reads and the payload the sender needs.

**No unsubscribe link on the zero-window mail** (BP-046 decision 3, REQ-057
criterion 7's own words: "because no link would stop it"). Adding one will look
like a compliance fix and is not one. The `sendEmail` call carries
`suppressible: false, unsubscribeLink: false`.

## Steps
1. Create `publishable/telling.ts` with the block above verbatim.
2. Derive the `Telling` **kind** from the `GoverningPair` alone: autopilot with `vetoHours > 0` ⇒ `interval`; autopilot with `vetoHours === 0` ⇒ `no_interval`; copilot at any window ⇒ `approval_only`. Nothing about the destination enters this.
3. Compose `DestinationClause` separately, at the moment the telling is composed. Read the adapter's `hostedByUs`: `true` ⇒ `destination: null`. `false` ⇒ call `ensureFreshHealth` for that destination; `error`/`cannot_publish` ⇒ `cannot_go_live_there`, anything else ⇒ `goes_live_there` with the key matching the telling's kind. **Do not test `kind === 'wordpress'` anywhere in this file** — assert its absence in test.
4. Implement `toldCurrentPair` as one comparison against `drafts.told.pair`, over the four `GoverningPair` fields **and no fifth**. The clause is stored in `drafts.told` as sent but is not compared: a health flap must not re-open the telling obligation.
5. Implement `recordTold` as one write of `{pair, kind, publishesAt, sentAt}`.
6. Name the seven copy keys and write **no string**. The cannot-publish line in particular is owner-owed and unminted (ADR-086 Decision 3, ADR-084's Open questions), and it may never be written from a held-pages count. Assert in test that no fixture in this module contains a sentence.
7. Write the pair-change tests first and watch "a page whose telling is owed is held" fail against an implementation that publishes and then tells (constitution §8).
8. Write the four suppression-negative assertions on the cannot-publish arm before implementing it, and watch them fail against the natural implementation that stops naming a date when the destination cannot publish.

## Out of scope
- Sending anything. BP-016's `sendEmail()` sends; this module returns the occasion and payload.
- Writing any customer-visible sentence. This work order creates copy **keys** and the tests that assert them; the strings are the owner's (constitution §1). The cannot-publish line is owner-owed and named in ADR-084's and ADR-086's Open questions; nothing here mints it.
- Clearing `drafts.told` on a settings change — that write is BP-057's (WO-220).
- The veto link itself — WO-217 supplies `VetoLink`; this module carries it on the `interval` kind.
- **Everything about the destination except reading its health at compose time.** The `publish_capable` column is WO-265's, the `cannot_publish` reason and the `reconnect_other_account` action are WO-266's, the `canPublish` probe is WO-264's, and the delivery's `credentials_invalid` failure is WO-236's and WO-237's. This module reads one `DestinationView` and attaches one clause.
- **Holding a page against a destination that cannot publish.** That is BP-045's `destination_working` guard (WO-212), and BP-046 decision 5 is explicit that it is the right instrument and already exists. Widening `GoverningPair` to carry health would hold pages on a flap and is rejected there.
- Renaming anything. BP-046's status-grounds addendum records a rename it says was not made in this pass; this work order and BP-046's `## Public interface` both already spell the function `isUnsuppressible`, so there is nothing to rename here — reported, not acted on.
