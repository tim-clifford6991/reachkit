# WO-012 — domain_blocks — the table with no writer anywhere in the product

- Branch: wo/WO-012-domainblocks
- Estimate: ≤1 day

## Goal
Create the one table that binds a removal to a *domain* rather than to a scan,
and enforce in the schema that no application code can write to it.

## Provenance of this file plan
**This repository holds no `supabase/`.** Both paths are NEW, anchored to
BP-002's `code:` glob `supabase/migrations/*_domainblocks*.sql`.

## File plan
| File | New/Modify | Change |
|---|---|---|
| `supabase/migrations/00000000000003_domainblocks.sql` | NEW | `domain_blocks` — id, domain (unique, lowercased), blocked_at, and the operator note field the written request is recorded against. RLS enabled; a select policy for the server path only and **no insert, update or delete policy at all**, so the table has no writer reachable through `db()`. Writing a row is a manual operator action through the service role, which is what "no writer anywhere in the product" means. |
| `tests/db/domainblocks.test.ts` | NEW | The tests below. |

## Interfaces
Consumes: the schema and the policy conventions WO-009 and WO-010 applied.
Exposes: no code interface. The reader is BP-022's report address resolution,
outside this block.

## Steps
1. Write the migration with the unique lowercased domain key.
2. Write the select-only policy set.
3. Write the tests; watch the "no writer" test fail first by adding an insert
   policy, then remove it.

## Test plan
> **Criterion source: the blueprint, not a requirement.** BP-002 carries
> `satisfies: []`. REQ-002's promise — that a domain's owner can have the report
> removed on written request — is discharged at the report address by BP-022,
> which renders the removal line; this table is what makes the removal outlive
> any one scan. The criterion is cited, not inherited.

| Acceptance criterion (source quoted) | Test |
|---|---|
| BP-002 data-model delta: "REQ-002 criterion 3 removes a report for a **domain**, permanently and across every future scan; a scan-scoped column cannot bind a scan that does not exist yet." | `tests/db/domainblocks.test.ts` — inserting a block for a domain with no `scans` row succeeds through the service role, and the block is found by domain alone. |
| `structure.md` rule 3: "`*_domainblocks*.sql` (REQ-002's table has no writer anywhere in the product, so no feature node can own it)" | Same file — asserts the table has no insert, update or delete policy, and that no file under `src/` writes to it. Adding an insert policy fails it. |
| BP-002 decision 1: "a `removed_at` column on `scans` — rejected, REQ-002 criterion 3 must refuse a scan for a domain that has no scan row" | Same file — asserts `scans` carries no `removed_at`, so the rejected alternative cannot reappear silently. |
| BP-002 error behaviour: "RLS is default-deny" | Same file — an anon-key select returns zero rows. |

  criterion 1 requires the report to name — BP-022 and BP-019; the address itself
  is a customer-visible string the owner still owes (BP-005 decision 3).
- Any operator tooling for recording a written request.
