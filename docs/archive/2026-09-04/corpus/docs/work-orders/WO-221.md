# WO-221 — The setup cards — working defaults already chosen, and the DNS record or a written line, never a blank

- Branch: wo/WO-221-setup-cards
- Estimate: ≤1 day

## Goal
Ship `setupCards()`: the two cards' data with autopilot and the hosted blog pre-selected, each option carrying its own copy key, and the DNS record where the site address is known or a stated pending shape where it is not.

> verified to exist, because none can. Placement is anchored to
> `sdlc-factory/docs/registry/structure.md` and to this work order's blueprint
> `code:` globs, and is provisional against a repo with no code: if the
> implementer finds a file already present at one of these paths, they stop and
> log `failed` naming the drift rather than merging into it.

| File | New/Modify | Change |
|---|---|---|
| `src/lib/publish/setup/cards.ts` | NEW | `ModeOption`, `DestinationOption`, `setupCards`. Autopilot is `preselected: true` and copilot `false`; hosted is `preselected: true` and wordpress `false`. **Both defaults are data on the card, not a fallback applied when a field is missing**, so a submit carrying no explicit choice records the value the founder was shown. `dns` is present only for `hosted` and has exactly two shapes — BP-058's `DnsRecord`, or `{pending: 'no_domain_yet', copy: 'setup.destination.dnsPending'}`. There is no third shape, so no surface can render a blank, a dash or a placeholder where a value would sit. Each option carries a copy **key**; this module writes no sentence. |

## Interfaces

**Consumes**

- `dnsRecordFor(siteId): Promise<DnsRecord | { pending: 'no_domain_yet' }>` — BP-058, `src/lib/publish/destinations/hosted/` (WO-228).
- `copy()` and the `CopyKey` registry — BP-019. The four keys `setup.mode.autopilot`, `setup.mode.copilot`, `setup.destination.hosted`, `setup.destination.wordpress` and the fifth `setup.destination.dnsPending` are named here; the sentences are the owner's.
- `env` (the pinned edge hostname the CNAME points at) — BP-005, via BP-058's `dnsRecordFor`. Never a string in a card.

**Exposes** — copied exactly from BP-035's `## Public interface`:

```ts
// src/lib/publish/setup/cards.ts
export interface ModeOption {
  mode: 'autopilot' | 'copilot'
  preselected: boolean                       // autopilot true, copilot false
  copy: 'setup.mode.autopilot' | 'setup.mode.copilot'
}
export interface DestinationOption {
  kind: 'hosted' | 'wordpress'
  preselected: boolean                       // hosted true, wordpress false
  copy: 'setup.destination.hosted' | 'setup.destination.wordpress'
  /** Present only for `hosted`. `pending` is criterion 2's written line, never a blank. */
  dns?: DnsRecord | { pending: 'no_domain_yet'; copy: 'setup.destination.dnsPending' }
}
export function setupCards(siteId: string): Promise<{
  mode: readonly ModeOption[]
  destination: readonly DestinationOption[]
}>
```

**The setup cards carry copy keys and no logic** (BP-035 decision 1). Do not call
BP-057's `explainPair` here: at setup there is nothing to compute, and calling it
would put a Settings sentence on a setup card and make one key's wording
answerable to two screens. The strings are the owner's and the two surfaces may
word them differently.

This module **renders nothing** — `/setup` is BP-001's surface and calls this as
a thin adapter (structure.md rule 1). That is why this work order is `ui: no`.

## Steps
1. Create `setup/cards.ts` with the block above verbatim.
2. Return both mode options and both destination options every time, with the pre-selection as data on the option.
3. Call `dnsRecordFor(siteId)` and map its two results onto the two `dns` shapes. Add no third shape and no nullable.
4. Assert zero outbound network calls by stubbing BP-006's egress seam to throw. `setupCards` runs no health check.
5. Write the "no blank, dash or placeholder" test first and watch it fail against an implementation returning `dns: null` (constitution §8).
