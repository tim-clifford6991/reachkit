# WO-264 — canPublish() — can this credential publish, not merely create, and it is not the stamp probe

- Branch: wo/WO-264-wordpress-can-publish
- Estimate: ≤1 day

## Goal
Ship `canPublish(cfg)` on the WordPress adapter: one authenticated read that answers whether this credential may publish and not merely create, called by BP-058 at connect and at each health check, never by this node on a schedule of its own, and never proved by creating a post.

| File | New/Modify | Change |
|---|---|---|
| `src/lib/publish/destinations/wordpress/adapter.ts` | MODIFY | Add `canPublish(cfg: WordPressConfig): Promise<boolean>`, exported beside the adapter as BP-048's `## Public interface` places it. **One authenticated read** through WO-236's client — the credential's own capabilities as the REST API reports them — mapped to a boolean. **It never creates a post to find out**: a health check makes no write to a customer's site (BP-058), and proving publish capability by publishing is the one implementation that would put a post in a customer's site as a side effect of a health check. `false` is not an error and throws nothing: it is an answer BP-058 turns into a destination state (WO-266). A read that itself fails is **not** `false` — it maps through `errors.ts` like any other failure, because "we could not ask" is not "the answer is no". |
| `tests/publish/destinations/wordpress/capability.test.ts` | NEW | A credential the REST API reports as able to publish returns `true`; one reported as able to create but not publish returns `false`. **The zero-write row:** the egress seam is stubbed to throw on any non-GET, and `canPublish` is asserted to make **no write of any kind** — no post, no draft, no meta, no term. **The not-an-error row:** `false` returns normally and throws nothing, and a **transport failure or a 5xx returns neither `true` nor `false`** but maps through `errors.ts` — asserted separately, because an implementation that catches everything and returns `false` would mark a working destination as unable to publish and hold its queue on a network blip. **The two-probes row:** `canPublish` and `canStamp` are asserted to be two functions with two call sites and no shared implementation — a fixture site that can publish and cannot stamp returns `true`/`false`, and one that can stamp and cannot publish returns `false`/`true`, so neither answer can be derived from the other. |

## Interfaces

**Consumes**

- `WordPressConfig` — declared in `adapter.ts` alongside the adapter (BP-048, WO-237).
- The authenticated REST calls and the error mapping — `wordpress/client.ts` and `wordpress/errors.ts` (WO-236). Every outbound call goes through them and therefore through BP-006's `safeFetch`.

**Exposes** — copied exactly from BP-048's `## Public interface`:

```ts
/** REQ-060 criterion 7 and **ADR-084 Decision 3**. Can this credential *publish*,
 *  not merely create? WordPress's default role map gives `edit_posts` to
 *  Contributor and `publish_posts` only from Author upward, so an application
 *  password from a Contributor-level user can create a post and have WordPress
 *  quietly hold it at `draft` whatever the request asked for — the one route by
 *  which the owner's ruling could produce, unnoticed, exactly the outcome it
 *  abolishes: a page ReachKit reports as published sitting invisible in a drafts
 *  folder. Probed by BP-058 at connect and at each health check, never by this
 *  node on a schedule of its own; `false` makes the destination **failing** with
 *  reason `cannot_publish` (**ADR-086** Decision 1) and holds the queue there,
 *  rather than being discovered by a customer whose page went nowhere.
 *
 *  It is a **separate probe from `canStamp` and must stay one.** A site can
 *  publish and refuse the term, and a site can take the term and refuse to
 *  publish; they gate different things (one holds the queue, one only costs
 *  REQ-060 c6's list), and merging them either blocks publishing over a
 *  findability attribute or publishes into a site that cannot publish. */
export function canPublish(cfg: WordPressConfig): Promise<boolean>
```

**This probe is the only thing standing between the owner's ruling and a silently
drafted post — ADR-084 Decision 3.** The ruling of 2026-09-01 abolishes the
population of pages that sit in a customer's drafts folder. WordPress's default
role map is the one route by which that population could come back **unnoticed**:
a Contributor-level application password creates the post, WordPress holds it at
`draft` regardless of `status: 'publish'`, and ReachKit reports a page as
published that nobody can read. Left unhandled it is not a visible failure — it is
a success message over an invisible page.

**It never creates a post to find out.** BP-058 states that health checks make no
write to a customer's site, and the two capability probes are reads for that
reason: `canPublish` asks what the credential *may* do, and never proves it by
doing it. An implementation that creates a probe post and deletes it would leave
a post in a customer's site whenever the delete failed, and would do so on the
*read path*, since `ensureFreshHealth` runs in-line when a customer opens a
screen.

**`false` is an answer; a failed read is not.** They must not collapse. `false`
puts the destination in `error`/`cannot_publish`, holds its queue and offers the
customer a remedy that costs them a new WordPress user (WO-266). A transport
failure means ReachKit could not ask, and mapping it to `false` would hold a
working customer's publishing on a network blip while telling them their account
lacks a permission it has. The two rows in the file plan are what keep them apart.

**Two probes, not one, and the merge is the temptation** (BP-048 decision 4).
`canStamp` (ADR-083) and `canPublish` (ADR-084) look like one question —
"what can this credential do?" — and returning a capability set would invite one
caller to gate on the wrong member. They gate different things: `canPublish`
false **holds the queue**; `canStamp` false is a **working destination** that
publishes normally and only loses REQ-060 criterion 6's list. Merging them either
blocks a customer's publishing over a findability attribute or publishes into a
site that cannot publish.

**This is the first of two guards, not the only one.** The probe can be stale by
one health-check interval, so BP-048's create call also asserts the status of the
post it got back and fails `credentials_invalid` where it is not `publish`
(WO-236, WO-237, ADR-086 Decision 5). Relying on the probe alone leaves the race
between a role change and the next health check unspecified and the page in
`publishing`; relying on the delivery alone means the customer discovers the
problem by a page that went nowhere. Both, and BP-048 decision 4 says why.

## Steps
1. Read **ADR-084** Decision 3 and **ADR-086** in full, then BP-048 decision 4.
2. Add `canPublish` to `adapter.ts`, exported as BP-048 places it. One authenticated read through WO-236's client.
3. **Make no write of any kind.** Do not create a post, not even one you intend to delete. Assert the absence in test with a seam that throws on any non-GET.
4. Return `false` for a credential the API reports as unable to publish. Do not throw and do not treat it as an error.
5. Map a read that fails through `errors.ts`. **Do not catch it into `false`** — write the two paths separately and assert them separately.
6. Keep it a separate function from `canStamp` with no shared implementation, and write the two-probes fixture pair before implementing either.
7. Write the zero-write assertion and the failed-read assertion first and watch each fail — the first against a probe that creates and deletes a post, the second against a `try/catch` returning `false` (constitution §8).

## Out of scope
- **The destination state, its reason, its line and its action.** `publish_capable`, `cannot_publish`, `reconnect_other_account` and `publishCapability()` are BP-058's — WO-265 and WO-266. This work order answers a question; it stores nothing and renders nothing.
- **Calling this probe on any schedule.** BP-058 calls it at connect and at each health check (WO-266). This node never calls it on a schedule of its own — BP-048 says so in terms.
- The create call and its status assertion — WO-237. The `credentials_invalid` mapping — WO-236. This probe is the first guard; those are the second.
- **`canStamp` and everything else of ADR-083's** — the `post_tag` term, `stamp_capable`, `stampApplied` and `WORDPRESS_STAMP_SLUG`. **Cut by no work order anywhere in this corpus** (verified 2026-09-02 by grep over all 245 work orders); recorded here and in WO-237's fourth `rests-on` rather than absorbed, because it is ADR-083's pass and not this one's. This work order's two-probes fixture pair references `canStamp` as a stub, and its implementation is not this file's.
- Every customer-visible string. ADR-084's and ADR-086's Open questions record the cannot-publish line and the `reconnect_other_account` label as **owner-owed**; this probe returns a boolean.
- Holding the queue. BP-045's `destination_working` guard does that, from the health state WO-266 writes.

## Rollback
Revert the `adapter.ts` addition and delete the test file. WO-266 imports `canPublish`; revert this only before it, or `publishCapability` has nothing to call. Reverting leaves the delivery-time status assertion (WO-237) as the only guard — a degraded but not incorrect state: no post is ever reported as published with a draft behind it, but the customer discovers the problem by a page that failed rather than by a destination that reads as failing before it was attempted.
