# WO-131 — hasActiveAccess — the paid-through date alone (ADR-050)

- Branch: wo/WO-131-has-active-access
- Estimate: ≤1 day

## Goal
Ship the product's single access gate as one expression over one column, with the
three tests that each fail if a second term is ever added to it.

## File plan
> **Every path below is NEW.** No `src/` exists. Anchored to
> `registry/structure.md` and BP-060's `code:` glob `src/lib/account/billing/**`.
> Provisional against a repo with no code.
>
> **Read ADR-050 in full before touching `gate.ts`.** Its own warning: "The
> obvious improvement — 'and the subscription is actually active' — is the bug."
> The clause is one line to add and its effect is invisible in every test that
> uses an active subscription.

| File | New/Modify | Change |
|---|---|---|
| `src/lib/account/billing/gate.ts` | NEW | Exports `hasActiveAccess(siteId)` with BP-060's signature verbatim. The body is `users.paid_through > now()`, resolved through `sites.user_id`, and nothing else — no `plan_status`, no `cancelled_at`, no `deleted_at`, no Stripe call. One indexed read; p95 ≤ 10 ms. This is the only implementation of the gate in the repository (ADR-050 point 3). |
| `tests/account/billing/gate.test.ts` | NEW | ADR-050 point 4's three cases, each written so it fails if the clause is added: a cancelled subscription with a future `paid_through` **has** access; a `past_due` subscription with a future `paid_through` **has** access; a subscription Stripe still calls `active` with a past `paid_through` does **not**. Plus the mutation case: deleting the gate must fail all three. Plus a fixed-clock boundary at exactly `paid_through`. |
| `tests/account/billing/single-gate.test.ts` | NEW | ADR-050 point 3, made enforceable: a source-level assertion over `src/jobs/**`, `src/lib/scan/**`, `src/lib/publish/**` and `src/lib/account/lifecycle/**` that no file computes a predicate over `paid_through`, `plan_status` or `cancelled_at` of its own — each either imports `hasActiveAccess` or has no access predicate at all. A second predicate is the rule 7.1 violation ADR-050 names as most likely to appear here. **This test stays, and is not replaced by the lint rule.** BP-001 decision 2 (2026-08-31) adds the *lintable half* of ADR-050 point 3 to `eslint.config.mjs` — an import fence: nothing outside `src/lib/account/billing/**` may import `users.paid_through`'s reader or re-derive access from `plan_status`. A fence catches an import; it cannot catch "computes no access predicate of their own", which is a behavioural invariant and not a lexical one. BP-001's own words: "The test stays ADR-050's; the import fence is this file's." Deleting this test on the grounds that the lint rule covers it would leave a check that looks like it holds and does not. |
| `tests/account/billing/lapsed-sign-in.test.ts` | NEW | REQ-076 c5's structural guarantee: `src/lib/account/provisioning/magic-link.ts` imports nothing from `src/lib/account/billing/**`, and a customer whose `paid_through` has passed is still sent a link and can still sign in. BP-060: "`requestMagicLink` (BP-032) does not consult this node, by design and by test." |

## Interfaces

```ts
/** REQ-076 criterion 8 — THE access gate. See ADR-050 before changing this. */

```
Consumes: `db()` (BP-002).

## Steps
1. Write `tests/account/billing/gate.test.ts`'s three cases and watch all three
   fail.
2. Write `gate.ts` as one expression.
3. Write the single-gate source assertion.
4. Write the lapsed-sign-in test (it depends on WO-127 having landed; where it
   has not, the import-absence half stands alone).
5. Run the mutation check: delete `gate.ts`'s body and confirm all three
   discriminating cases fail.
