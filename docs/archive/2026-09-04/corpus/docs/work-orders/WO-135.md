# WO-135 — users identity columns and the auth_links table — the pending change, and the hashed token

- Branch: wo/WO-135-users-identity-migration
- Estimate: ≤1 day

## Goal
Add the name and the three pending-email columns, the partial unique index that
stops two customers racing onto one address, and the `auth_links` table every
sign-in reads — all under the `users_identity` sub-token.

## File plan
> **Every path below is NEW.** This repository carries no `supabase/`. Anchored to
> `registry/structure.md` rule 3a (`*_users_identity_*` inside BP-017's
> `*_users*`) and to BP-061's `code:` globs. Provisional against a repo with no
> code.
>
> **Filename derivation (rule 1.1).** `auth_links` is a new table and
> `structure.md` rule 3's closed topic list has no `auth_links` topic; BP-061's
> `code:` admits exactly one migration glob, `*_users_identity_*.sql`. The table
> therefore lands in a file under that sub-token, named
> `<ts>_users_identity_links.sql`. `links` is a descriptive suffix, not a second
> sub-token from rule 3a's list, so it does not trip rule 3a's "a filename
> carrying two sub-tokens is a lint failure". Reversal cost: renaming an applied
> migration is not done, so this is fixed at creation — which is why it is written
> down here rather than left to the implementer.

| File | New/Modify | Change |
|---|---|---|
| `supabase/migrations/<ts>_users_identity_columns.sql` | NEW | `alter table users add column name text null`, `pending_email citext null`, `pending_email_token_hash text null`, `pending_email_sent_at timestamptz null`. `create unique index users_pending_email_key on users (lower(pending_email)) where pending_email is not null`. No cascade (ADR-051 point 2). |
| `supabase/migrations/<ts>_users_identity_links.sql` | NEW | `create table auth_links (token_hash text primary key, user_id uuid not null references users(id), purpose text not null check (purpose in ('sign_in','email_change')), sent_to citext not null, expires_at timestamptz not null, spent_at timestamptz null)`. The foreign key carries **no** `on delete cascade` (ADR-051 point 2) — a tombstoned account's links are removed by the purge, not by a cascade. A partial unique index on `(user_id, purpose) where spent_at is null` enforces BP-061's "at most one live token per `(user_id, purpose)`". No column stores a token in plaintext, and a test asserts the table has no such column. |
| `tests/account/session/schema.test.ts` | NEW | The four `users` columns exist with the stated types and nullability; two rows cannot hold the same `pending_email` in different cases; `auth_links` exists with exactly the six columns named and no seventh; the one-live-token index refuses a second unspent row for one `(user_id, purpose)`; neither file introduces an `on delete cascade`. |

## Out of scope
- Issuing, hashing or redeeming a token — WO-136.
- The account card and the email-change state machine — WO-137.
- Every other `users` sub-token: `*_users_billing_*` (WO-116),
  `*_users_provisioning_*` (WO-124), `*_users_subscription_*` (WO-129),
  `*_users_erasure_*` (WO-140).
- The RLS policy that hides a tombstoned account's rows — BP-002's, per ADR-051
  point 3.

## Rollback
Drop the index, the four columns and the table in a follow-up migration. Dropping
`auth_links` in a live environment invalidates every outstanding sign-in link,
which is the only credential this product has — do it only with no links in
flight.
