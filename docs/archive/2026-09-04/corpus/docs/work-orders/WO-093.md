# WO-093 — No contact ever reaches a rival — the import-graph assertion that makes criterion 17 a build failure

- Branch: wo/WO-093-no-contact-guard
- Estimate: ≤1 day

## Goal
Implement the standing assertion BP-056 requires for REQ-071 criterion 17: no export in the
market engine takes or returns a contact address, and no import path from
`src/lib/market/**` reaches `src/lib/mail/**` — so a violation is a build failure rather than
a review finding.

## Context an implementer needs
No source code exists on disk; the path below is NEW.

BP-056's `## Error & edge behavior` states it as a property of the module graph: "**No contact
ever reaches a rival.** No export here takes or returns an address, and no import path from
`src/lib/market/**` reaches `src/lib/mail/**` — asserted as an import-graph test, so criterion
17 is a build failure rather than a review finding."

This work order writes a **test only** — no production file. It lives in
`tests/market/changes/` under BP-056's own glob (`structure.md` rule 4).

**Discrimination is the whole point of this WO** (constitution §8: "A test that survives
deletion of its feature is vacuous"). A test that merely observes today's import graph passes
trivially, since almost nothing exists yet. The test must therefore be written as a checker
applied to a supplied root, and exercised against a **fixture tree** that does contain a
forbidden import, so it is proven to fail when a violation exists — today and at every later
size of the codebase.

## File plan
| File | New/Modify | Change |
|---|---|---|
| `tests/market/changes/no-contact.test.ts` | **NEW** | A reusable checker — given a root directory, resolve every import edge transitively from every file under it and return any path reaching a forbidden target — plus (a) its application to `src/lib/market/**`, and (b) its application to two hand-built fixture trees, one clean and one containing a forbidden import, proving the checker discriminates. |
| `tests/market/changes/fixtures/no-contact/clean/**` | **NEW** | A three-file fixture tree with no forbidden import. |
| `tests/market/changes/fixtures/no-contact/violating/**` | **NEW** | The same three files, one of which imports a stub standing for `src/lib/mail/`. |

No file under `src/` is created or modified by this work order.

## Interfaces
**Consumes**: nothing from the product. The checker reads the repository's own module graph
(TypeScript's resolver over the project's `tsconfig`, so type-only imports are included —
a type-only edge is still an edge in the dependency graph this criterion is about).

**Exposes**: nothing. This WO adds no export to `src/`.

## Steps
1. Write the checker: given a root glob and a set of forbidden target globs, resolve every
   import specifier — value and type-only alike — transitively, and return the list of
   `(file → … → forbidden target)` paths found, with each hop named so a failure message points
   at the edge to delete.
2. Apply it with root `src/lib/market/**` and forbidden targets `src/lib/mail/**`. Assert the
   result is empty.
3. Assert, over the same root, that no exported function signature in `src/lib/market/**` names
   a parameter or a return field matching `/email|mailto|recipient|contactAddress/i` — the
   "no export here takes or returns an address" half of the clause, which the import graph alone
   does not cover.
4. Build the two fixture trees and assert the checker returns empty for the clean one and
   exactly one named path for the violating one. This is the mutation proof: it fails if the
   checker is stubbed out, regardless of what `src/lib/market/**` currently contains.
5. Where `src/lib/market/**` does not yet exist (this repository has no `src/`), the checker
   must **fail** rather than pass vacuously: assert the root resolves to at least one file, so
   the day the module is deleted or renamed the guard reports it instead of going green.
6. Write the tests; watch the violating fixture fail the clean assertion first.
