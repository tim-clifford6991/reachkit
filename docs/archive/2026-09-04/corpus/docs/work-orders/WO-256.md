# WO-256 — `runScan` — the one scan pipeline, tier as a parameter

- Branch: wo/WO-256-run-scan
- Estimate: ≤1 day

## Goal
Run the one measurement pipeline at whichever tier it was asked for — six named
stages, in order, under the tier's spend cap and (on the free path) the
90-second deadline — and end it in exactly one stored report or in a failure
that leaves the previous report untouched.

## Provenance of this file plan
**This repository holds no `src/` and no `supabase/`.** All four paths are NEW.
`src/lib/scan/` is BP-012's row in `structure.md` ("The one scan pipeline — tier
is a parameter — plus free-path admission control, the time and spend ceilings,
degradation, and the stored report blob") and its `code:` globs are
`src/lib/scan/**`, `supabase/migrations/*_scans*.sql` and `tests/scan/**`.
`run.ts`, `tests/scan/run/**` and a `scans_stage` sub-token file are claimed by
no leaf: BP-023's `code:` names `domain.ts`, `admission.ts`, `stages.ts`,
`ceilings.ts`, `*_scans_freepath*.sql` and `tests/scan/free/**`; BP-036's is
`src/lib/scan/deep/**`; BP-050's is `src/lib/scan/weekly/**`.

**Reuse check (rule 7.2).** `capabilities.md`'s row "The one scan pipeline, tier
as a parameter · `src/lib/scan/` · BP-012 · `runScan()` · consumers BP-001,
BP-003" names this seam and **no work order authors it**. Nine work orders name
`runScan` and every one is a caller or an out-of-scope note — WO-015 ("Calls
`runScan()` once and records the outcome. Holds no scan logic"), WO-150

(`runScan({ correctionOf })`), WO-046, WO-058, WO-060, WO-080, WO-082. No

> **Three sequencing facts this file fixes, each recorded rather than assumed.**
>
> 1. **Stage emission against call order.** `measureDomain` is one call and
>    produces the datasets of stages 1, 2 and 4 (`reading_your_site`,
>    `reading_access_rules`, `checking_your_presence`), while stage 3
>    (`reading_your_market`) consumes its home text. The stream therefore emits
>    stages 1 and 2 `done` on `measureDomain`'s return, runs the market chain
>    under stage 3, and emits stage 4 `done` immediately after — from
>    `drivers.searchPresence`, which `measureDomain` already produced. `STAGES`
>    order is preserved exactly; what moved is when a completed stage is
>    reported, not what it reports. Reversal: split `measureDomain` into a read
>    half and a presence half — a change to BP-010's declared signature, which is
>    why it is not taken here.
> 2. **`aiPresence`.** Filled at the `scoring` stage from `aiPresenceOf` over the
>    SERPs stage 5 bought (fourth `rests-on` row). Nothing is re-bought.
> 3. **Opportunities.** `deriveOpportunities` requires a `siteId: string`, and a
>    free scan has none (`scans.site_id null for free`, WO-009). The pipeline
>    calls it when and only when `siteId` was given. The free path's "first page
>    worth writing" is BP-029's, reached after the report, and is not this
>    pipeline's.

## Steps
1. Write both test files first and run them; every case must fail on a missing
   module (constitution §8, "Watch it fail first").
2. Write the migration and its two columns.
3. Build the frozen per-tier parameter table first, so that every later step
   reads a looked-up value and no step can be written as a tier comparison.
4. Implement acquisition: `parseDomain`; on the free tier adopt the running row
   (third `rests-on` row) and refuse with `status: 'failed'` if there is none;
   otherwise insert. Where `correctionOf` is given, carry it to
   `storeCurrentReport` as `supersedesScanId` and consume no second allowance —
   BP-012: "A market correction runs inside the scan it corrects: same spend
   ceiling, no second allowance consumed."
5. Open `withCostContext` with the tier's cap name. Wrap the body in
   `withFreeBounds` where the tier's parameters say the report deadline applies —
   the free tier only. The deep pass is **released** at ten minutes rather than
   stopped (BP-012 `## NFR budget`: "Deep pass: live, released at 10 minutes
   whatever its state"; that release is BP-036's `releaseToApp`, not a ceiling
   here), and the weekly pass runs on the standard queue; for both, the spend cap
   re-checked between stages is the whole of the bound.
6. Run the six stages in `STAGES` order, writing `stage` on entry and
   `stage_done` on exit, and calling `stopNow()`/`capHit()` between every pair.
   A stage that is cut off writes no `stage_done` and contributes its section as
   `unmeasured / not_attempted`.
7. Build the `Record<ScanInput, InputOutcome>` for `verdictOf` from what each
   stage actually returned — one entry per member of BP-024's closed
   seven-member union, none defaulted.
8. Assemble, derive opportunities where a `siteId` was given, store, return.
9. Mutate to prove the suite discriminates: (a) branch a battery on `tier` and
   confirm the tier row fails; (b) let a cut-off stage contribute a 0 instead of
   `not_attempted` and confirm the ceiling row fails; (c) insert a new row on the
   free tier instead of adopting and confirm the never-two-rows row fails.
