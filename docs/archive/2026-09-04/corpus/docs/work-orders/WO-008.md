# WO-008 — Supabase project config and the migration naming convention check

- Branch: wo/WO-008-supabase-config
- Estimate: ≤1 day

## Goal
Stand up the local Supabase project and make `structure.md`'s closed topic-token
list executable, so a migration whose name carries no assigned token fails a
check rather than a review.

## Provenance of this file plan
**This repository holds no `supabase/`.** Every path is NEW, anchored to
`structure.md`'s row for `supabase/**` and to BP-002's `code:` globs.

## File plan
| File | New/Modify | Change |
|---|---|---|
| `supabase/config.toml` | NEW | Local project config: Postgres version, the auth block with magic-link (email OTP) enabled and password sign-in disabled — `BUILD.md` §1, "Supabase (Postgres, RLS default-deny, magic-link auth)" — and the migrations directory. No secrets; keys come from `env` (WO-005). |
| `src/lib/db/topics.ts` | NEW | The closed topic list and the open sub-token list as data, transcribed from `structure.md` rule 3 and 3a: topics `users · sites · scans · fetches · opportunities · drafts · publications · destinations · leads · suppressions`, plus `domainblocks`, `baseline` and `rls` as BP-002's own; sub-tokens `users_provisioning`, `users_subscription`, `users_identity`, `users_erasure`, `sites_provisioning`, `sites_hosting`, `sites_erasure`, `scans_freepath`, `scans_verdict`, `opportunities_core`, `opportunities_supply`, `opportunities_verdicts`, `drafts_core`, `drafts_claims`. Each entry carries its owning BP id. |
| `tests/db/migration-naming.test.ts` | NEW | Reads every file in `supabase/migrations/` and asserts its name carries exactly one assigned topic token or one sub-token of an assigned topic; a name carrying none, or two, fails. |

## Interfaces
Exposes:
```ts
// src/lib/db/topics.ts
export const MIGRATION_TOPICS: readonly { token: string; owner: string }[]
export const MIGRATION_SUBTOKENS: readonly { token: string; parent: string; owner: string }[]
export function topicOf(filename: string): { token: string; owner: string } | null
```
Consumes: nothing.

## Steps
1. `supabase init`; edit `config.toml` for magic-link auth.
2. Write `topics.ts` from `structure.md` rule 3 and 3a, one entry per token.
3. Write the naming test with fixture filenames: a valid `*_baseline*.sql`, a
   valid sub-token `*_users_erasure_*.sql`, an unassigned `*_widgets*.sql` and an
   ambiguous two-token name. Watch the unassigned case fail before the check
   exists.
