# WO-153 — The waiting screen and the progress endpoint: which step, never how long

- Branch: wo/WO-153-waiting-screen
- Estimate: ≤1 day
- Preview: sdlc-factory/docs/design/previews/WO-153.html
- Signed-off: <date>

## Goal
Render `/setup/waiting` — the running step in written words, refreshed at least
every 30 seconds, with nothing about time anywhere on it — and serve
`progressStream` from the one progress endpoint, with the three redirects the
release latch decides.

## File plan
> Every path below is **NEW** (no `src/` on disk, checked 2026-08-31). These two
> paths sit inside BP-001's boundary and are governed by BP-036 as
> transport-only adapters (BP-036 decision 4, structure.md rule 1 and its scope
> table). Provisional against a repo with no code.

| File | New/Modify | Change |
|---|---|---|
| `src/app/(account)/setup/waiting/page.tsx` | NEW | Server component. Reads `isReleased`; released → redirect `/app`; no submitted setup → redirect `/setup`; otherwise renders the waiting frame with the current stage's written line. |
| `src/app/(account)/setup/waiting/Waiting.tsx` | NEW | Client component subscribing to the progress endpoint. Renders the stage's copy key and a motion affordance that shows the pass is still running; renders **no** elapsed, estimate, countdown, clock or percentage — the frame carries none. On `running: false` it navigates to `/app`. |
| `src/app/api/setup/progress/route.ts` | NEW | SSE adapter over `progressStream(siteId)`; `siteId` from the session. Performs no vendor call, no measurement and no write other than the deadline latch `isReleased` performs. Closes at 11 minutes. |
| `tests/app/waiting/page.test.tsx` | NEW | Redirect matrix, the written-step render, the no-time assertion. |
| `tests/app/waiting/progress-route.test.ts` | NEW | Stream shape, session-scoped `siteId`, close at 11 minutes. |

## Interfaces
Consumes (verbatim from BP-036 `## Public interface`):
```ts
export interface ProgressFrame { stage: DeepStage; running: true; heartbeatAt: Date }
export type ProgressEvent = ProgressFrame | { running: false; reason: ReleaseReason }
export function progressStream(siteId: string): AsyncIterable<ProgressEvent>

export function isReleased(siteId: string):
  Promise<{ released: false; deadlineAt: Date } | { released: true; at: Date; reason: ReleaseReason }>
```
and `readSetupState` (BP-033, WO-146), `copy()` (BP-019), registered components
and tokens only (BP-018).

Exposes: the two routes above. No new engine interface.

## Steps
1. **Precondition (rule 7.3):** signed preview. As of 2026-08-31
   `docs/design/tokens.md` is `Status: ready` and `components.md` registers 24
   components, every row `proposed` and reaching `approved` only when a preview
   carrying it is signed off. **One gap blocks this screen's preview and not the
   others:** `components.md` §4 row 4 records that no registered component
   renders motion without a number — `Progress` is determinate only, and REQ-003
   c1 forbids "an unlabelled spinner or an indeterminate bar alone" — and offers
   `Steps` (whose every step label is required, which the deep pass's named
   stages supply) as the likely answer. That resolution is the design-guardian's
   and the architect's, not this WO's; the motion affordance in `Waiting.tsx`
   below is whichever component the signed preview names, and no new one is
   minted here.
2. Write the failing tests first.
3. Implement the redirects: released → `/app`; unreleased and inside the window
   → render; setup not submitted → `/setup`; past the window `/app` never
   redirects back here.
4. Render the stage line from a copy key per `DeepStage`. The client must not
   compute elapsed time from `heartbeatAt`; it uses it only to detect staleness.
5. Assert the rendered DOM contains no duration, estimate, countdown, clock or
   percentage — a string-scan test over the rendered output plus a props test on
   the component.
6. Mutation check: render `heartbeatAt` as an elapsed counter and confirm the
   no-time test fails.

## Test plan
| Acceptance criterion (verbatim from REQ-029) | Test |
|---|---|
| 1. Given the founder has submitted setup, when they are on the progress screen while the deep pass is running — whether they stayed on it or came back to it within the window criterion 6 sets — then they see which step is under way in written words rather than a bare spinner, the step named is the step actually running, the screen shows them at least once every 30 seconds that the pass is still running, and nothing on the screen states how long the pass has taken or has left: no duration, no estimate, no countdown, no clock and no percentage of time. | `tests/app/waiting/page.test.tsx › the running step renders as written words, not a bare spinner, and matches the frame's stage`, `(same file) › a re-entry within the window renders the current stage`, `tests/app/waiting/progress-route.test.ts › the stream delivers a frame at least every 15 s`, `tests/app/waiting/page.test.tsx › the rendered output contains no duration, estimate, countdown, clock or percentage` |
| 2. Given the deep pass completes, when it ends, then the founder is taken into the app without any further action from them. | `tests/app/waiting/page.test.tsx › a running:false event navigates to /app with no customer action` |
| 6. Given a founder who has submitted setup, when they return — signing in minutes or weeks later (REQ-024 criterion 4, "returned to where they left off"; REQ-025 criterion 4, "not asked the three decisions again") — then they land in the app itself, with no re-run of the pass, and where their pass degraded, failed or did not complete, the one written sentence criteria 3 and 5 promise is on the screen they arrive at rather than having been shown only at the moment of release; they are shown the progress screen only while their own pass is still running and fewer than the 10 minutes of criterion 5 have passed since they submitted setup, and past that point they land in the app whatever state the pass is in. | `tests/app/waiting/page.test.tsx › a released founder requesting /setup/waiting is redirected to /app and no pass is re-run`, `(same file) › a founder past ten minutes is redirected to /app whatever the pass state`, `(same file) › a founder who never submitted setup is redirected to /setup, never a blank wait` |
