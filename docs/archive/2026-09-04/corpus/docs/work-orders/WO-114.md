# WO-114 — scheduleSequence and advanceSequences — sweep, then release, then send

- Branch: wo/WO-114-nurture-sequence

- Estimate: ≤1 day

## Goal
Run at most one sequence per address at a time, in the order the pages were
delivered, dropping any that has waited more than seven days, and send at most
three touches per domain.

## Provisional against an empty repo
**No `src/` exists.** All files NEW, inside BP-029's `src/lib/mail/leads/**`
glob.

Reuse check (rule 7.2): `registry/capabilities.md` row "Bounded per-domain
follow-up sequencing — `src/lib/mail/leads/` — BP-029 (seam declared by BP-016) —
`scheduleSequence()` · `advanceSequences()` — consumers BP-003". Nothing exists.
This WO consumes `sendEmail()` (WO-106), `buildNurture()` (WO-113),
`isSuppressed()` (WO-112) and the schema (WO-109), and re-implements none.

**Pins are BP-005's and imported, never redeclared** (`structure.md` rule 5;
BP-029 says so in its own words): `NURTURE_TOUCH_HOURS = [24, 72, 168]`,
`NURTURE_MAX_TOUCHES = 3`, `SEQUENCE_START_DEADLINE_DAYS = 7`. Each is asserted in
`tests/pins.test.ts`, which is BP-005's file and which this WO does not touch. A
literal `24`, `72`, `168`, `3` or `7` anywhere in this module is a defect.

## Read ADR-041 before "fixing" a lead who received no follow-ups
Two of the three landmines are this file's:
1. **A waiting sequence past its deadline is dropped forever.** The sweep runs
   **before** the release step, on **every** invocation, so the terminal state is
   reached even on a run that releases nothing. There is no code path from
   `dropped` to `running`. Releasing them "because they only missed their slot" is
   one line and breaks the 14-day bound REQ-010 c12 states.
2. **A re-delivery starts nothing.** `scheduleSequence` inserts nothing when the
   unique index (WO-109) already holds a sequence for `(lower(email), domain)`.
   The second `leads` row keeps a null `sequence_state` forever. It reads as a
   lost enqueue and is not one.
The 14-day guarantee is **arithmetic over two pins**, not a separate check: 7 days
of waiting plus a last touch at 168 hours. Do not add a third check that could
disagree with them.

## File plan
| File | New/Modify | Change |
|---|---|---|
| `src/lib/mail/leads/sequence.ts` | NEW | `scheduleSequence()` — refuses outright for an address in `email_suppressions` (`isSuppressed`, WO-112), otherwise inserts `sequence_state = 'waiting'` with `page_delivered_at = deliveredAt`; a unique violation from WO-109's index is swallowed as success-with-no-effect, not retried and not raised. `advanceSequences(now)` — in this order and no other: **(1) sweep** every `waiting` row whose `page_delivered_at + SEQUENCE_START_DEADLINE_DAYS < now` to `dropped`, stamping `dropped_at`; **(2) release** for each address with no `running` sequence the oldest surviving `waiting` row by `page_delivered_at`, setting `running`, `sequence_started_at = now`, `touch_count = 0`, `next_touch_at = now + NURTURE_TOUCH_HOURS[0]`, and skipping any suppressed address; **(3) send** every `running` row whose `next_touch_at <= now`, calling `sendEmail` with `buildNurture` at touch `touch_count + 1`, then advancing `touch_count` and setting `next_touch_at` from `NURTURE_TOUCH_HOURS[touch_count]` or `finished` at `NURTURE_MAX_TOUCHES`. ## Interfaces
**Exposes** (verbatim from BP-029 `## Public interface`):
```ts
// src/lib/mail/leads/sequence.ts — criteria 9 to 13
/** BP-016's declared entry point, realised here. Keyed by (lower(email), domain):
 *  a second delivery of the same domain's page to the same address starts
 *  nothing (criterion 13). Starts nothing at all for a suppressed address
 *  (criterion 11's last limb). */
export function scheduleSequence(a: { email: string; domain: string; deliveredAt: Date }): Promise<void>

/** The lead/nurture job body (BP-003). Sweeps first, then releases, then sends:
 *  a waiting sequence past its own deadline is dropped even on an invocation
 *  that releases nothing, so the stored state is never a lie about what is due. */
export function advanceSequences(now: Date): Promise<{
  dropped: number; released: number; sent: number
}>
```

## Steps
1. Write both test files first and watch them fail.
2. `scheduleSequence` first — it is the only writer of `sequence_state = 'waiting'`.
3. `advanceSequences` as three named internal steps called in a fixed order from
   one function, so the order is visible in one place and a reviewer can see the
   sweep precede the release.
4. Log lead id, domain, state transition, touch index, drop reason and suppression
   outcome; never an address in clear text (BP-029 NFR budget). Every `dropped`
   row's log line names REQ-010 c12 and ADR-041, per that ADR's consequences.
5. Mutation checks: (a) move the sweep after the release and confirm the
   deadline test fails on an invocation that releases nothing; (b) delete the
   `NURTURE_MAX_TOUCHES` stop and confirm a fourth touch is sent and the c9 test
   fails; (c) release a `dropped` row and confirm the 14-day bound test fails.

## Out of scope
- The `lead/nurture` job trigger and its schedule — BP-003's, which "calls
  `advanceSequences()` and holds no logic of its own" (BP-029).
- Delivering the first page (WO-115). A sequence is only ever scheduled from a
  delivery that already happened.
- Suppression writes and the opt-out token (WO-112).
- Any customer-visible string (REQ-093 c1); the nurture copy keys are WO-113's.
- Any change to the touch cadence, the deadline or the cap — those are BP-005
  pins, and changing one is a change to `tests/pins.test.ts` and to ADR-041.

## Rollback
Delete `src/lib/mail/leads/sequence.ts` and its two tests. WO-109's schema stands;
rows already in `running` stop advancing, which is a halt, not a violation — no
mail is sent that should not be.
