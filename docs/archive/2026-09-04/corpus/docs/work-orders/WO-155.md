# WO-155 — The app frame: three destinations, one tuple, publishing state on every screen

- Branch: wo/WO-155-app-frame
- Estimate: ≤1 day
- Preview: sdlc-factory/docs/design/previews/WO-155.html
- Signed-off: <date>

## Goal
Render the frame every app screen sits inside — the domain block, exactly three
destinations from one tuple with the Calendar's waiting count, and the
publishing mode with its next time or its one line — at every breakpoint.

## File plan
> Every path below is **NEW** (no `src/` on disk, checked 2026-08-31). Placement
> follows `structure.md` and BP-037's `code:` globs. The `_shell` prefix keeps
> the folder out of the route table so the shell can never become a fourth
> destination. Provisional against a repo with no code.

| File | New/Modify | Change |
|---|---|---|
| `src/app/(account)/app/layout.tsx` | NEW | `AppLayout` — reads `readShell`, renders the domain block, the sidebar (or tab bar) and the publishing card around `children`. |
| `src/app/(account)/app/page.tsx` | NEW | The `/app` redirect to Overview. One redirect exists in the product and it is this one. |
| `src/app/(account)/app/_shell/destinations.ts` | NEW | `DESTINATIONS` and `Destination` — one readonly tuple consumed by both renderers. |
| `src/app/(account)/app/_shell/SidebarNav.tsx` | NEW | Desktop nav mapping over `DESTINATIONS`; renders the Calendar count only when `waiting > 0`. |
| `src/app/(account)/app/_shell/TabBar.tsx` | NEW | Narrow-viewport nav mapping over the **same** tuple; the domain block and publishing state collapse into its header rather than disappearing. |
| `src/app/(account)/app/_shell/DomainBlock.tsx` | NEW | Domain, week count or the not-measured line, and the measurement **date** rendered in `sites.time_zone` — never the weekday word (BP-037 decision 4). |
| `src/app/(account)/app/_shell/PublishingCard.tsx` | NEW | Mode plus next publish time in the customer's zone, or the one line for the resolved `NoPublishReason`. |
| `tests/app/shell/frame.test.tsx` | NEW | Destination count at both breakpoints, the count's presence/absence, the publishing line, the date-not-weekday render. |

## Interfaces
Consumes (verbatim from BP-037 `## Public interface`):
```ts
export interface ShellModel {
  domain: string
  weeks: WeekCount
  waiting: number                          // 0 renders no count at all (criterion 2)
  publishing:
    | { mode: 'autopilot' | 'copilot'; next: Date }
    | { mode: 'autopilot' | 'copilot'; next: null; because: NoPublishReason }
}
export function readShell(siteId: string): Promise<ShellModel>
```
and `copy()` / `stoppedWorkStatement` (BP-019), `Sidebar` and the registered
component set (BP-018), `releaseNotice()` (BP-036, WO-152) for the sentence that
travels with a released founder.

Exposes (verbatim from BP-037 `## Public interface`):
```ts
export default function AppLayout(p: { children: React.ReactNode }): JSX.Element

/** REQ-040 criterion 1 made structural. Exactly three, one tuple, consumed by
 *  both the sidebar and the mobile tab bar — so a fourth cannot appear on one
 *  breakpoint only, and cannot appear at all without a type change. */
export const DESTINATIONS = ['overview', 'calendar', 'settings'] as const
export type Destination = (typeof DESTINATIONS)[number]
```

## Steps
1. **Precondition (rule 7.3):** signed preview. As of 2026-08-31
   `docs/design/tokens.md` is `Status: ready` and `components.md` registers 24
   components including `Sidebar` and `Tabs` — every row `proposed`, reaching
   `approved` only when a preview carrying it is signed off. **`TabBar` is not
   one of the 24:** `components.md` §4 row 5 records it as an open boundary
   call — a shell-local composition over the registered `Tabs` needs no row, and
   a `TabBar` needing custom CSS would be a sixth custom surface `BUILD.md` §2.2
   does not admit. Build `TabBar.tsx` as a composition over `Tabs` with no
   custom CSS, or stop and raise it: minting a sixth custom surface here is the
   one thing this step forbids.
2. Write the failing tests first.
3. Declare `DESTINATIONS` once and map over it in both renderers; a route added
   under `/app` with no entry is unreachable by navigation, which is the safe
   failure (BP-037 decision 1).
4. Render every date and time in `sites.time_zone`; the domain block renders the
   measurement **date**, not `BUILD.md` §4.4's specimen weekday word.
5. Render `releaseNotice`'s sentence in the frame so it is on every screen the
   founder arrives at (REQ-029 criterion 6's placement, satisfied here).
6. Mutation check: add a fourth entry to one renderer's list only — the test
   that both breakpoints render the same tuple must fail.

## Test plan
| Acceptance criterion (verbatim from REQ-040) | Test |
|---|---|
| 1. Given a signed-in customer on any app screen, when they look at the navigation, then exactly three destinations are offered — Overview, Calendar and Settings — and no fourth destination is offered anywhere in the app. | `tests/app/shell/frame.test.tsx › exactly three destinations render, from the one tuple, on every app screen` |
| 2. Given items in the calendar are waiting on the customer, when they look at the navigation, then the Calendar destination shows how many are waiting; when none are, it shows no count. | `tests/app/shell/frame.test.tsx › the Calendar item shows the waiting count when non-zero and renders no count at zero` |
| 3. Given a customer on any app screen, when they look at the navigation, then the current publishing mode is shown together with the date and time of the next scheduled publish, in the customer's timezone. | `tests/app/shell/frame.test.tsx › mode and next publish time render in sites.time_zone on every app screen` |
| 4. Given no publish is scheduled — publishing is paused, nothing is approved, no page is planned, or ReachKit itself stopped the work — when the customer looks at the navigation, then in place of a time it carries one written line naming which of those is the case; where it was ReachKit that stopped, that line "names ReachKit's stop as the reason no publish is scheduled" (REQ-092 criterion 7) and never one of the other three. | `tests/app/shell/frame.test.tsx › with next null, exactly one line renders for the resolved reason, and the reachkit_stopped line is BP-019's stopped-work statement naming no internal cause` |
| 5. Given a viewport too narrow for the sidebar, when the customer opens any app screen, then the same three destinations remain reachable. | `tests/app/shell/frame.test.tsx › the tab bar renders the same three destinations, and the domain block and publishing state collapse into its header rather than disappearing` |
| 6. Given a site with at least one completed weekly measurement, when the customer looks at any app screen, then it states the domain being measured and how many weeks of measurement the site has, counted from the first weekly measurement of that domain — and where the customer has changed the domain, the count starts again at the first measurement of the new domain (REQ-071 criterion 13). That number is never larger than the number of weeks in which the site was measured: a week that ran and measured something advances it, a week that produced no measurement at all — one REQ-065 criterion 3 states "has not been measured" — does not. | `tests/app/shell/frame.test.tsx › the domain block renders the domain and the counted weeks, with the measurement date in the customer's zone and never a weekday word` |
| 7. Given the domain has no weekly measurement yet, whether because none has ever completed or because the customer changed the domain, when the customer looks at any app screen, then no week count is stated and in its place the domain block carries one written line saying this domain has not been measured yet and naming the date its first measurement is due. | `tests/app/shell/frame.test.tsx › kind 'none' renders no number and one line carrying firstDueOn` |

## Out of scope

- Every screen's content: Overview, Calendar, Settings, the draft view.
- Sidebar dimensions, sticky behaviour, the accent dot and chip styling —
  design system (REQ-040's non-goals).
- Any customer-visible string; keys only.
