# WO-113 — The three lead-directed templates — first-page, first-page-unavailable, nurture

- Branch: wo/WO-113-lead-templates
- Estimate: ≤1 day
- Preview: sdlc-factory/docs/design/previews/WO-113.html
- Signed-off: (pending — design-guardian)

## Goal
Declare the block list of each of the three mails a lead may receive, so that
every one of them carries a working opt-out and none of them can hold a
conditional, a formatter or a sentence of its own.

## Provisional against an empty repo
**No `src/` exists.** All files NEW. The three directories are named explicitly
in BP-029's `code:` globs — `src/lib/mail/templates/first-page/**`,
`src/lib/mail/templates/first-page-unavailable/**`,
`src/lib/mail/templates/nurture/**` — and ADR-040 point 1 fixes the directory name
as the `MailKind` string. **No node globs `src/lib/mail/templates/**`**, so this
WO creates three directories and touches no fourth; the other six kinds' template
directories belong to sibling blueprints outside this block.

Reuse check (rule 7.2): no template exists in `registry/capabilities.md` or on
disk. This WO consumes the block vocabulary (WO-101), both renderers by way of
`composeMail` (WO-102, WO-103), `firstPageOffer()` (WO-110) and
`optOutTokenFor()` (WO-112). It re-implements none of them: ADR-040 point 3 is
explicit that "A template holds no shell, no formatter and no vendor knowledge".

## Read ADR-041 before removing the opt-out from the first-page mail
`first-page` and `first-page-unavailable` are `stoppable: false` — suppression
never blocks their send — **and they still carry the opt-out link**. BP-029:
"`stoppable: false` governs whether suppression blocks the send, not whether the
mail carries a way to stop what comes next; the page has already been asked for,
and the opt-out in it stops the follow-up, not the page." REQ-010 c11 says "any of
these emails", with no exception.

## Interfaces
**Consumes** (verbatim from BP-053 `## Public interface`):
```ts
export type MailBlock =
  | { block: 'heading';   text: CopyKey; vars?: CopyVars }
  | { block: 'paragraph'; text: CopyKey; vars?: CopyVars }
  | { block: 'stat';      label: CopyKey; value: Measured<number>
                          format: 'integer' | 'delta' | 'perMonth'
                          note?: CopyKey }                        // travels with its value or not at all
  | { block: 'list';      label: CopyKey; items: Measured<readonly ListRow[]>; emptyLine: CopyKey }
  | { block: 'verdicts';  label: CopyKey; items: Measured<readonly VerdictRow[]>; emptyLine: CopyKey }
  | { block: 'action';    label: CopyKey; href: string }
  | { block: 'notice';    text: CopyKey; vars?: CopyVars }
  | { block: 'pageBody';  pageTitle: string; written: boolean; markdown: string }
```
and `optOutTokenFor(email: string): string` (WO-112, verbatim from BP-029).

**Exposes** (chosen under rule 1.1 — neither BP-029 nor ADR-040 names a
template's function; ADR-040 fixes only the directory):
```ts
export function buildFirstPage(a: { … }): { subject: CopyKey; blocks: readonly MailBlock[]; optOut: { href: string } }
export function buildFirstPageUnavailable(a: { causeLine: CopyKey; email: string }): { subject: CopyKey; blocks: readonly MailBlock[]; optOut: { href: string } }
export function buildNurture(a: { touch: 1 | 2 | 3; … }): { subject: CopyKey; blocks: readonly MailBlock[]; optOut: { href: string } }
```
Derivation for the **required** (not optional) `optOut` in the return type: REQ-010
c11 says "any of these emails" carries a working opt-out, and BP-029 lists all
five lead-directed mails. Making `optOut` a required field of what a lead template
returns makes a lead mail without one unrepresentable, which is the same
structural move BP-053 decision 1 makes for the omission rule. The alternative —
each caller remembering to pass it — is the "asked to" failure BP-053 decision 1
rejects in so many words. Cost of reversing: make the field optional and move the
obligation to three call sites.

Derivation for `causeLine: CopyKey` rather than `cause: FirstPageFailure`: the
exhaustive `Record<FirstPageFailure, CopyKey>` map lives in `giveaway.ts` (WO-115)
where `FirstPageFailure` is declared, because BP-029 needs the **same** map read
by BP-001 to render the cause in place on the report. Passing the resolved key
here keeps the template free of the union and keeps this WO free of a dependency
cycle with WO-115.

## Out of scope
- Every customer-visible sentence. This WO creates `CopyKey` **references** and
  the tests that assert a key resolves; every string is BP-019's registry and the
  owner's (REQ-093 c1; constitution §1, "Customer-visible strings"). That includes
  criterion 4's first-of-N line, criterion 7's per-cause lines, the locale
  disclosure, and all three nurture subjects.
- The other six template directories (sibling blueprints, ADR-040 point 2).
- Deciding when each template is used (WO-114, WO-115).
- Writing the page (BP-014).
