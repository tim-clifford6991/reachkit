# WO-243 — `POST /api/report/{domain}/correct` — the transport adapter over the one market correction

- Branch: wo/WO-243-api-correct
- Estimate: ≤1 day

## Goal
Turn a submitted category correction into one call to the correction state
machine and, where it advances, one re-measurement inside the scan it corrects —
with no decision of this route's own about whether a correction is available.

## Provenance of this file plan
**This repository holds no `src/`.** Both paths are NEW under BP-001's glob
`src/app/api/**`, which decision 1 fixes as this container's "without exception".
BP-001's delegation table names the target: "BP-028's
`correctionOffer`/`nextCorrectionState`, then BP-012's
`runScan({ correctionOf })`", behind it REQ-094. WO-004 named this adapter as one
it does not cut.

## File plan
| File | New/Modify | Change |
|---|---|---|
| `src/app/api/report/[domain]/correct/route.ts` | NEW | The `POST` adapter, wrapped in WO-004's `adapter()`. Parses the `{domain}` segment with WO-051's `parseDomain` and refuses a segment that does not parse; reads exactly one body field, the corrected category, as an opaque string; asks `correctionOffer({ report, now })` whether one is on offer and refuses with that arm's `because` where it is not; asks `nextCorrectionState({ current, event: 'submitted' })` and, on `{ next }`, calls `runScan({ domain, tier: 'free', correctionOf: scanId })`; on `{ refused }` returns that refusal by key. Holds no state table of its own, no threshold, no allowance arithmetic and no SQL. |
| `tests/app/correction/route.test.ts` | NEW | The suites below. |

## Interfaces

Consumes (verbatim from BP-028 `## Public interface`):
```ts
export type CorrectionOffer =
  | { offered: true;  as: 'first' | 'retry' }
  | { offered: false; because: 'used' | 'exhausted' | 'in_progress' | 'report_too_old' | 'domain_removed' }
export function correctionOffer(a: { report: ReportFacts; now: Date }): CorrectionOffer

export type CorrectionState =
  | 'none' | 'running' | 'failed_once' | 'running_retry' | 'used' | 'exhausted'
export type CorrectionEvent =
  | 'submitted' | 'refused_before_run' | 'produced_report' | 'produced_no_report'
export function nextCorrectionState(a: { current: CorrectionState; event: CorrectionEvent }):
  { next: CorrectionState } | { refused: 'already_running' | 'already_used' }
```
Consumes (verbatim from BP-012 `## Public interface`):
```ts
export function runScan(a: {
  domain: string; siteId?: string; tier: Tier
  correctionOf?: string          // a market correction re-measures inside the scan it corrects
}): Promise<{ scanId: string; status: 'done' | 'degraded' | 'failed' }>
```
Also consumes: WO-051's `parseDomain`/`CanonicalDomain`, and WO-004's
`adapter()`.
Exposes (verbatim from BP-001 `## Public interface`):
```
  POST /api/report/{domain}/correct     one market correction per free scan
```

## Steps
1. Write the failing suites first.
2. Parse the segment with `parseDomain`; a segment that does not parse is a 400
   with the malformed key and no call to anything downstream.
3. Call `correctionOffer` **before** `nextCorrectionState`. Where
   `{ offered: false }`, return that `because` by key and call neither the state
   machine nor `runScan` — nothing is spent by a refusal this route makes.
4. Call `nextCorrectionState({ current, event: 'submitted' })`. On
   `{ refused: 'already_running' }` return that key — REQ-094 criterion 5's
   "refused in writing as a correction already under way rather than as one
   already used" is a distinct key from `already_used`, and the two are never
   collapsed here. On `{ refused: 'already_used' }` return that key.
5. On `{ next }`, call `runScan({ domain, tier: 'free', correctionOf: scanId })`
   and return the running scan's id. Pass no spend ceiling, no deadline and no
   allowance flag: BP-012 fixes that a correction "runs inside the scan it
   corrects: same spend ceiling, no second allowance consumed", and this route
   passes `correctionOf` and nothing else that could change it.
6. Emit WO-004's one log line carrying the scan id; never the category, never a
   payload.

## Test plan

> Criteria are copied verbatim from `requirements/REQ-094.md`; line breaks are
> normalised to fit the table and no word is changed. Criteria 1, 2, 4 and 6 are
> the report surface's and BP-028's rendering and state work and are not
> inherited here; the three below are the ones this transport discharges.

| Acceptance criterion (verbatim from REQ) | Test |
|---|---|
| REQ-094 c3 — "Given a reader who submits a corrected category, when the correction is accepted, then the market set, the questions, and every figure measured from them — the AI answers, the Google presence, and the drivers and score that rest on those — are measured again against the corrected category and the report re-renders from them, while what the scan read from the domain's own pages is not re-read and does not change. That re-measurement is the free scan it corrects still measuring: it spends no further scan allowance and opens no second spend ceiling (REQ-003 criteria 6 and 11), and its own wait is bounded as any scan's wait is, timed from the moment the correction was accepted (REQ-003 criteria 1, 2 and 5) — the time the reader took to decide counts against no bound. The corrected report is one scan's report throughout, carrying one measurement date, the moment that scan's measurement finished; every figure under that date comes from that one scan and none from another (REQ-004 criterion 12), and the figures carried forward unchanged from the domain's own pages were read less than 7 days before the correction started (criterion 1)." | `correct-route/accepted · one runScan, correctionOf set, nothing else passed` — an accepted correction calls `runScan` exactly once with `correctionOf` equal to the report's scan id and with no fourth argument, no ceiling override and no allowance parameter; a source assertion that the route never calls `claimFreeScanSlot` or `admitFreeScan`, so no allowance can be consumed from here. What is re-derived and what is carried forward is `CORRECTION_SCOPE`'s and is asserted in BP-028's suite. |
| REQ-094 c5 — "Given a report whose one correction has been accepted and has produced a corrected report, when any visitor opens it, then no correction control is offered, one written line says a free scan allows one correction and that this one has been used, and the corrected report stays readable. Given a correction already running for that report, when a second is submitted, then it is refused in writing as a correction already under way rather than as one already used, and whoever was refused is left where the running correction leaves them: the corrected report if it produced one (criterion 4), or the control still available if it did not (criterion 7)." | `correct-route/refusal · running and used are two different refusals` — a submission against `running` or `running_retry` returns the `already_running` key; one against `used` or `exhausted` returns the `already_used` key; the two keys are asserted distinct and neither response starts a scan. A mutation collapsing them into one key fails, and it is the mutation the criterion's own sentence exists to forbid. |
| REQ-094 c7 — "… Given a correction refused before it ran, because free scanning is paused or switched off or a scan is already running for that network (REQ-003 criteria 7 and 8), when the reader is told which limit was met, then neither attempt has been used and the control still stands: nothing was measured and nothing was spent. A correction whose re-measurement stopped early does produce the stored report — incomplete, on REQ-003 criterion 11's terms — and that correction has been used." | `correct-route/refused-before-run · nothing is spent` — for each `correctionOffer` `because` arm and for a refusal raised inside `runScan`'s admission, the route is asserted to leave the correction state untouched: `nextCorrectionState` is either not called or called with `event: 'refused_before_run'`, never with `'submitted'` recorded as spent, and the response carries the limit's own key. Asserted by spy over the state machine, so an adapter that "helpfully" advances the state fails. |

## Out of scope
- The state table itself, `correctionOffer`'s age and coherence rules, and
  `CORRECTION_SCOPE` — BP-028's, another block's.
- The re-measurement, its ceilings and the stored corrected report — BP-012's.
- The correction control, the coherence line and the category on the report's
  face — the report surface's (REQ-094 criteria 1 and 2), another node's.
- Validating or normalising the submitted category — BP-028's; see `rests-on`.
- Any written sentence: this route returns copy keys.

## Rollback

work order; the stored report and its category are untouched.
