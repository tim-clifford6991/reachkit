# WO-073 — The one intent classifier: classifyIntent, intentWeight, passesRelevanceGuard, stemKey

- Branch: wo/WO-073-intent-classifier
- Estimate: ≤1 day

## Goal
Implement the four deterministic, model-free predicates `select.ts` and the opportunity
engine both read — intent classification, its weight, the relevance guard and the
near-duplicate key — so there is exactly one classification of a search in the product.

## Context an implementer needs
No source code exists on disk; both paths below are NEW. This file is the **single owner**
of intent classification: `sdlc-factory/docs/registry/capabilities.md` lists
"Deterministic selection of the twelve searches, and the one intent classifier ·
`src/lib/market/questions/` · BP-025 (seam declared by BP-011) · `selectTwelve()` ·
`classifyIntent()` · `intentWeight()` · consumers BP-012, BP-040". BP-040 (the
opportunity ranking) imports these; it does not mint a second classifier, and a second
one is a rule 7.1 conflict, not a judgement call.

Rule 7.2 reuse check performed: the capability index has exactly one row for intent
classification and it names this module; grep over the repository finds no
implementation, because the repository carries no `src/` at all. This WO therefore
**creates** the capability, and its index row already exists naming BP-025.

```ts
// src/lib/market/questions/select.ts — step 3. Deterministic; takes no CostContext.
export type Intent = 'decision' | 'solution' | 'problem' | 'informational'
export function classifyIntent(keyword: string, p: Profile): Intent | 'own_brand'
/** The one intent classifier's weight, exported because BP-040's ranking uses
 *  the same classification the twelve were selected by — one classification in
 *  the product, not two (rule 2.4; BP-011 decision 2). Returns
 *  `SELECTION.intentWeights[intent]` (3 decision · 3 solution · 2 problem ·
 *  1 informational) and 0 for `own_brand`, which is dropped. The second
 *  parameter is required: the own-brand drop set and the relevance vocabulary
 *  are the profile's, so there is no one-argument form. */
export function intentWeight(keyword: string, p: Profile): number
export function stemKey(keyword: string): string          // near-duplicate collapse key
export function passesRelevanceGuard(keyword: string, p: Profile): boolean
```

## The parent/leaf divergence this WO recorded is resolved
When this WO was cut, BP-025's `## Public interface` omitted `intentWeight` while BP-011's
declared it as `intentWeight(query, p)` with an `'own-brand'` arm, and this WO implemented
the leaf's spellings on the strength of `structure.md` and `capabilities.md`. **BP-011
decision 2's "Two corrections, 2026-08-31" settled it in the blueprints' favour of the
leaf**: `intentWeight` is declared in BP-025's own interface (quoted above verbatim,
comment included), the parameter is `keyword`, and the extra member is `'own_brand'`. BP-011
was corrected in-file to the same spellings, so parent and leaf now read alike and there is
one symbol with one spelling. Nothing in this WO's plan changed as a result; the choice it
recorded became the declaration.

The same correction notes that BP-040 decision 3 previously called `intentWeight(query) / 3`
with **one** argument. A one-argument form is the second classifier BP-011 decision 2 rejects
— the own-brand drop set is the profile's — and BP-040 now carries a `profile` on `rankScore`.
This WO exports the two-argument form only; an implementer adds no one-argument overload for
BP-040's convenience.

## Steps
1. Create `select.ts` with the five symbols above. No import of `CostContext`, no clock,
   no I/O, no model call — BP-025 decision 1 makes this a property of the module, and
   WO-074's determinism test asserts it.
2. `classifyIntent(keyword, p)`: return `'own_brand'` when the keyword contains any of
   `p.brandTokens` (token match after `stemKey`-style normalisation, not substring — a
   brand token must not swallow an unrelated word that contains it). Otherwise classify by
   keyword shape into `decision`, `solution`, `problem`, `informational`, deterministically
   and with a total function: every keyword lands in exactly one arm. Keep the shape
   patterns in one exported-for-test constant table in this file so a change is one edit.
3. `intentWeight(keyword, p)`: `classifyIntent` then look the weight up in
   `SELECTION.intentWeights`. `'own_brand'` returns `0` — BP-025's comment "0 for `own_brand`,
   which is dropped" — so a caller that ranks by weight drops it without a second branch. The
   second parameter is required; export no one-argument form.
4. `passesRelevanceGuard(keyword, p)`: true when the keyword shares at least one content
   token with `p.vocabulary` after the same normalisation. The support set is the profile's;
   this function invents no vocabulary of its own.
5. `stemKey(keyword)`: lower-case, strip punctuation, drop stop-words, singularise plural
   content tokens, sort the remaining tokens, join with a single space. Two keywords
   differing only in plural form, word order, punctuation or stop-words produce the same key.
6. Write the tests; watch each fail first.

## Test plan
| Acceptance criterion (verbatim from REQ-006) | Test |
|---|---|
| 12. "Given the set of questions the report measured, when it renders, then no two of them derive from searches that differ only in plural form, word order, punctuation or stop-words — each question stands for a different search." — the key this criterion is enforced by; the collapse itself is WO-074's. | `tests/market/questions/intent.test.ts › stemKey/collapses-the-four-differences` — a table of pairs differing only in (a) plural form, (b) word order, (c) punctuation, (d) a stop-word produces an equal key in all four cases; a pair differing in a content token produces different keys. |
| 13. "Given any of the 12 questions, when it renders, then the search shown beside it (criterion 9) is the search that question was selected from, and how the question is worded never changes which search it stands for: a differently worded question is still the same measured search, and no question stands for a search the report did not measure." — *contributing arm only*: the classification that drives selection is model-free, so no wording step can reach it. | `tests/market/questions/intent.test.ts › classifyIntent/is-pure-and-model-free` — the module's import graph contains no path to `src/lib/llm/` and no path to `src/lib/vendors/`, asserted over the resolved imports of `select.ts`; and `classifyIntent` called twice with identical arguments returns an identical value. |

Discrimination: replacing `intentWeight`'s table lookup with a literal, or making
`classifyIntent` non-total (a keyword returning `undefined`), must fail a named test.

Additional interface-contract tests:
- `classifyIntent/own-brand-is-token-not-substring`.
- `classifyIntent/is-total` — a property test over a generated keyword corpus: every input
  returns one of the five members.
- `intentWeight/reads-the-pin` — the four weights equal `SELECTION.intentWeights`, read
  from `constants.ts` rather than restated in the test.
- `intentWeight/own-brand-weighs-zero` — a keyword `classifyIntent` calls `'own_brand'`
  weighs `0`, so ranking drops it with no second branch.
- `intentWeight/is-the-signature-BP-025-declares` — a type-level assertion that the exported
  symbol is `(keyword: string, p: Profile) => number`: the parameter is required and no
  one-argument overload exists (BP-011 decision 2's correction (c)).
- `passesRelevanceGuard/empty-vocabulary-passes-nothing`.
