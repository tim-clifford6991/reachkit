The report screen — the route, the total view switch, the verdict strip, the one notice, the one control, and the removal address

WO-282. Serves /scan/{domain} end to end: resolves it, 308s a non-canonical form, renders exactly one arm of a closed union — including the removed arm and the removal address every report names — marks every response noindex, and never answers with a blank page, a 404 or an unhandled error (BP-022 ## Responsibility, REQ-001 c5).

Drawn ahead of the code — the point of this dispatch. Unlike WO-070's sheet, this one precedes implementation: three implementers are building this screen's own dependencies (src/lib/egress/, src/lib/costs/, src/lib/presentation/generated/) in parallel worktrees right now, and none of WO-282's own files exist in this repo yet (checked: no src/app/(public)/scan/, no src/lib/presentation/, no src/lib/measure/). Every element below cites a WO-282 file-plan line, a BP-022/BP-024 clause, or a REQ criterion — never a file on disk.

1 · The route — not a pixel of its own

BP-022 ## Error & edge behavior, verbatim: “Every response from /scan/{domain} — report, removal line, malformed line, refusal, cooldown, progress — carries noindex as both a meta tag and an X-Robots-Tag header, and no sitemap the product publishes names a report address” (REQ-001 c8). A non-canonical written form 308s to the one canonical address (REQ-001 c2) before any of §2–7 below ever renders. No route in this node reads a session, sets a cookie, or renders a gate (REQ-001 c6, c10). Nothing here is drawn twice: it is a header and a status code, not a screen — the same shape WO-070's §4 took for the no-JS transport.

2 · Malformed — one written line, the landing field

REQ-001 c4, verbatim: “one written line names what is wrong with it and the visitor is offered the landing field — never a blank page, an unhandled error, or a scan.” DomainProblem (src/lib/scan/domain.ts) is the one union both this arm and WO-070's landing page classify against — confirmed by reading that file directly. This arm reuses WO-070's five landing.problem.* keys rather than minting five new ones: same union, same wording obligation, rule 2.4's “one claim, one home.” They are no longer owner-owed — WO-070 shipped them 2026-09-04 — so the line below is the owner's real, ruled string, not a bracket.

The other four DomainProblem handles render the same way, each its own already-filled landing.problem.* line. Not redrawn four more times — same mechanism.

3 · Removed — nobody, ever, until the address asks again

REQ-002 c3, verbatim: “…it shows the removed report to nobody and starts no scan for anyone, on that visit or any later one, and in its place one written line says the report was removed at the domain owner's request and names the address criterion 1 names — until a request to that same address asks for that domain to be scannable again.” REQ-001 c18 forbids any route back: no re-scan, no retry, no form. Served HTTP 200, never 404 or 410 (BP-022, “a removed address serves its line with HTTP 200”).

7a · Verdict strip — measured

REQ-004 c1, verbatim: “…the first module shows a single score on a 0–100 scale, its band as one of the four written words — Invisible, Hard to find, Findable, Dominant — the domain measured, and the date it was measured.” REQ-004 c2: “one written line beside it names the one driver… whose measurement holds the score down the most — and names it without stating that driver's value, its weight, or how the score is put together. No driver's own value is shown anywhere.” The owner's 2026-09-03 design ruling — mono numerals, --r-box 14px, a labelled specimen, the bare score with band — bears on this screen directly (unlike WO-070's, where all four were not applicable): the score is mono with tabular-nums; the strip is a Card at --r-box 14px; the score is never shown unlabelled — domain and date always ride beside it, so it is never a bare specimen number; and it renders bare with its band and nothing else — no bar, no chip, no chart.

10 · Registry / token audit

Five components.md §1 rows drawn, all already approved: Card (verdict strip, module slots), Badge (the band word), Alert (notice arms, refused, cooldown, module-absent lines), Btn (controls, copy-link), Steps (named scan stages). No new component and no new token are proposed. Confirmed against §2's own custom-surface list and §3's chart inventory: this screen needs neither — the verdict strip is a Card composition, not a chart, and REQ-004's own non-goals forbid the driver bars that would have been the closest thing to one. Every colour, radius, spacing and type value in this file traces to a named token in the :root block; grep of this file for a raw hex or px outside that block returns nothing.

ReportView, RemovedView and the address view switch itself are screen compositions, not registry rows — components.md §4's own closing note names both ReportView and RemovedView explicitly as compositions that "must not become any."

11 · Design-guardian verdict (duty 2)

PASS, with one gap reported and not blocking. One primary action per screen: checked per arm in the header comment and confirmed by enumeration in §7g (copy-link coexists with, and is distinct from, the control union's own single-or-none rule). Data-driven layout: every module and slot renders from Verdict/AddressState fields, no hardcoded per-domain content anywhere. No long generated text: every string is a bracket, a transcribed literal, or a data value; nothing here is invented prose. Only registered components: confirmed in §10, five rows, all approved, no widening needed. Tokens by name only: confirmed, one :root block, no raw value elsewhere in the file. Loading/empty/error states: §4 (loading), §7b/§7e (the closest analogues to empty), §5/§6/§7c (error) — all present. The one gap: §7c/§7d/§7f's copy keys have no name anywhere in the corpus yet (§7's boxed note) — reported, not fixed here, and not a reason to withhold this sheet, on the same footing WO-070's eight owner-owed keys stood on before they were filled.
