# ADR-040 — One directory per mail kind — the register is the partition of `src/lib/mail`

- Date: 2026-08-31

## Context
`structure.md` gives `src/lib/mail/**` to BP-016 as one module and says a module
may hold several BP nodes. It then fixes two rules those nodes must both keep:
one owner per path with no overlaps (rule 2), and — through rule 5.6 of the
constitution — a `code:` glob per blueprint from which `file → blueprint` is
derived.

The mail module is the one module in this repository whose feature nodes are cut
from **nine different requirements**, several of them concurrently. Each of those
nodes owns a template: `first-page`, `first-page-unavailable` and `nurture`
(REQ-010), `draft-ready` (REQ-057), `published` (REQ-062), `weekly` (REQ-063 and
REQ-065), `magic-link` (REQ-024, REQ-077), `setup-reminder` (REQ-025) and
`account` (REQ-024, REQ-074, REQ-076, REQ-077, REQ-079). Nothing in the module
map says where a template lives, so the obvious layout — one flat
`src/lib/mail/templates/` directory of files named after their kinds — is what
each node would independently reach for.

That layout cannot be globbed without collision. A node that writes
`src/lib/mail/templates/**` claims every sibling's template; a node that writes
`src/lib/mail/templates/weekly.ts` claims a single file and loses the
partial-render helpers, fixtures and plain-text variants that will sit beside it
within a week. Either way `file → blueprint` starts returning the wrong node, and
it does so silently: a wrong address that reads plausibly is exactly what rule
5.3 exists to prevent, and rule 5.6's derived console has no way to notice.

No single blueprint owns this. BP-016 owns the module but its interface is
written and its `code:` globs the whole of it; each feature node owns one kind
and cannot bind the others; and the nodes are being cut in parallel, so the first
one to guess sets a convention the rest inherit without ever having read it.

## Decision
**A mail kind's template is a directory named for that kind:
`src/lib/mail/templates/<kind>/`, owned by the BP node that owns that kind's
occasions. The register, `MAIL_KINDS`, is the partition: one row, one directory,
one owning node.**

Concretely:

1. `MailKind` and the directory name are the same string. A directory with no
   register row, or a register row with no directory, fails BP-053's register
   test.
2. A feature node's `code:` globs `src/lib/mail/templates/<kind>/**` once per
   kind it owns, and nothing broader. No node globs
   `src/lib/mail/templates/**`.
3. Everything true of *every* mail — the shell, the block model and its
   renderer, the register itself, the send seam and the vendor call — is
   BP-053's, at `src/lib/mail/{send.ts,kinds.ts,blocks/**,shell/**,vendor/**}`.
   A template holds no shell, no formatter and no vendor knowledge.
4. Everything true of *some* leads or *some* customers — sequencing, capture,
   suppression, preferences — is a named subdirectory of the owning node
   (`leads/`, `notifications/`), never a file at the module root.
5. Tests mirror it: `tests/mail/<area>/**` belongs to whoever owns
   `src/lib/mail/<area>/`.

## Alternatives considered
1. **A `## Decisions` entry inside BP-053** — rejected. BP-053 owns the register
   but not the templates, and the nodes that need this rule most are the ones
   that will never open BP-053: a sibling cut from REQ-062 reads its own
   requirement, its parent BP-016, and the module map. Rule 2.2's file test is
   "spans nodes no single blueprint owns", and this spans nine feature nodes plus
   their component.
2. **A row in `structure.md`** — rejected as out of reach rather than as wrong.
   The map is a single file being read by eight architects concurrently and its
   grain is the module, not the module's interior. A sub-module partition
   recorded there would also make every future kind a change to the one file
   every node depends on.
3. **A flat `templates/` directory globbed by BP-016 alone, with feature nodes
   owning no template files** — rejected: it makes BP-016 the owner of every
   customer-visible mail body, which puts nine requirements' content behind one
   node and hides each mail's data-model and copy dependencies from the node that
   specified them. It is the same bottleneck BP-002's second decision rejected
   for migrations, for the same reason.
4. **Kind-per-file with a naming convention (`templates/weekly.*`)** — rejected:
   a glob over a filename stem cannot hold a directory of fixtures, and the first
   template to need a second file either breaks its own glob or widens it into
   its neighbour's.

## Consequences
- Nine directories, each with exactly one owner, and a `code:` glob per node that
  cannot collide with a sibling's by construction rather than by review.
- Adding a mail kind is: one register row, one directory, one owning node — three
  changes that fail loudly if any is missing (decision point 1).
- The `file → blueprint` derivation of rule 5.6 stays correct inside the one
  module where nine nodes share a parent.
- Cost of reversing: low today, when no file exists; high the moment templates
  land, because a flattening is a path move that invalidates every mail node's
  `code:` glob at once and leaves the derived console pointing at nodes that no
  longer govern the files it names.
