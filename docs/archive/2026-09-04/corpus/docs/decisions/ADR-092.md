# ADR-092 — LANDMINE — the publishing subsystem's six leaves are one strongly connected component, and the edges are true: the cycle is broken at file granularity, never by deleting a `depends-on`

- Date: 2026-09-02

## Context

`skills/blueprint-writing/SKILL.md` says, in four words: *detect and forbid
circular BP dependencies.* Detection, run over the corpus on 2026-09-02, returns
one strongly connected component of **six nodes** —

```
BP-045  Ten states, fifteen transitions, no duplicate post, instant stop
BP-046  Approval, the veto window, and when a page becomes publishable
BP-047  The hosted serving edge
BP-048  The customer's own WordPress
BP-057  Publishing settings
BP-058  A broken destination is a state the customer can fix
```

— and **six mutual pairs** inside it: BP-045↔BP-046, BP-045↔BP-057,
BP-045↔BP-058, BP-046↔BP-057, BP-047↔BP-058, BP-048↔BP-058. Every leaf of
BP-015 is in it. Nothing else in the corpus's sixty-three nodes has a cycle of
any length.

This was disclosed once before, on 2026-09-01, as a triangle (BP-045 ↔ BP-058
with BP-046 → BP-058 closing it) and declined on the grounds that at file
granularity the imports are acyclic and splitting the module is restructuring
with no user-visible value. That disclosure was correct in its reasoning and
**wrong in its extent**: the component is twice the size it described, so the
reasoning has to be recorded where a future reader will find it before acting,
not left in a status paragraph on one node.

The reason a reader will act is that every plausible cleanup is wrong in a way
that does not show up in a test:

- **Deleting the edges** makes the graph read acyclic in one commit and destroys
  true information. `BP-045 depends-on BP-046` is there because
  `machine/`'s `publishable_and_due` and `customer_told` guards call into
  `publishable/`; `BP-046 depends-on BP-045` is there because `publishable/`
  names `DraftView` and `State`. Both are facts. A graph that says otherwise is
  the authored index rule 5.1 warns about, arrived at by hand.
- **Splitting `src/lib/publish/`** into two modules to make the direction
  one-way puts the ten-state machine and the thing that decides when a page
  enters `publishing` on opposite sides of a boundary that no requirement draws.
  REQ-056, REQ-057, REQ-060, REQ-062, REQ-073 and REQ-074 all speak about one
  page moving through one lifecycle.
- **Adding a seventh "shared" node** for the types is the same move as declaring
  them in a leaf, with one more BP-### and one more owner to keep in step.

`structure.md` rule 6 — the rule that is actually enforced — says *a cycle
between `src/lib/` modules is a build failure*. Its subject is the module. Five
of these six nodes are leaves of **one** module, `src/lib/publish/`, so rule 6
has nothing to say about the edges between them: a `depends-on` between sibling
leaves of one component is not a module dependency. The sixth, BP-047, is not in
`src/lib/` at all, and its pair with BP-058 is the one edge in the component
that rule 6 does forbid outright. That pair is broken here; the other five are
kept and argued.

## Decision

**1. The node-level component stands. No `depends-on` edge in it is deleted to
make the graph read clean.** `depends-on` at BP granularity records *this node's
contract names that node's*. It is not an import direction and was never
promised to be a partial order. The corpus already relies on this: BP-045's
`types.ts` exists precisely so that BP-046, BP-048, BP-049 and BP-058 can name
`State`, `DraftView`, `Publication`, `DestinationAdapter`, `FailureReason` and
`VerifyDisposition` without the file-level cycle — an arrangement that leaves
the *node* edges mutual by construction and is the right answer anyway (BP-045
decisions 6 and 9).

**2. The enforced invariant is at directory granularity inside
`src/lib/publish/`,** and it is the one thing a reviewer or a lint rule checks:

| Level | Directory | Owner |
|---|---|---|
| 0 | `types.ts` | BP-045 |
| 1 | `settings/` · `switch/` · `ceilings/` · `destinations/config/` | BP-057 · BP-045 · BP-045 · BP-058 |
| 2 | `destinations/wordpress/` · `destinations/hosted/` | BP-048 · BP-058 |
| 3 | `destinations/health/` | BP-058 |
| 4 | `destinations/index.ts` (the registry) | BP-058 |
| 5 | `publishable/` · `verify/` | BP-046 · BP-049 |
| 6 | `machine/` | BP-045 |
| 7 | `attempt/` · `record/` | BP-045 |
| 8 | `index.ts` (the barrel) | BP-015 |

**A file at level *n* imports only from levels strictly below it, and level 0
imports nothing under `src/lib/publish/` and nothing under `src/app/`.** That is
what makes the subsystem compile, and it is a property of files, which is where
compilation happens. Level 0's emptiness is the load-bearing row: it is what
lets levels 5 and 7 point at each other's *nodes* without pointing at each
other's *files*.

The order is not invented here; it is read off imports the nodes and their work
orders already declare, and it is now the rule rather than the observation:
`types.ts` imports nothing (BP-045 module table, decisions 6 and 9);
`destinations/wordpress/` receives its decrypted config from `config/` for the
duration of one call (BP-058 module table); `health/` probes through BP-048's
`canStamp` and `canPublish` (BP-058's `stampCapability`, `publishCapability`);
the registry returns the adapters and reads the publishing switch and nothing
else under `src/lib/publish/` (WO-216 `## Interfaces`); `publishable/` calls
`ensureFreshHealth` at compose time (BP-046 decision 5, ADR-086 Decision 4);
`machine/`'s guards call `becomesPublishable` and read health, ceilings and the
switch (BP-045 `GUARDS`); `attempt/` drives `transition()`. **A new import that
runs upward is a build failure, not a review comment** — `structure.md` rule 6's
sentence, applied one level down from the module.

**3. `tags` moves out of `src/app/(hosted)/` into `src/lib/publish/types.ts`,
and BP-047 leaves BP-058's `depends-on`.** BP-047 declared the two hosted
cache-tag builders and BP-045 and BP-058 were specified to invalidate the tags
"by name". Neither reading of "by name" is legal. An import is `src/lib →
src/app`, which rule 6 forbids in terms. A re-typed string literal is a second
home for a key (rule 2.4) whose copies diverge silently on the first rename —
and the symptom of divergence is a customer's page staying stale at their own
domain after they take it down, which no unit test on either side would catch.
The builders are declared in the leaf that imports nothing and re-exported
unchanged from `resolve-host.ts`, so every caller's spelling is the one it
already was. This removes BP-047↔BP-058 and forestalls a BP-045→BP-047 edge that
was never declared but was specified in prose.

**4. Five mutual pairs remain, and each is intra-module and intended.** They are
recorded here once so no later pass re-derives them:

| Pair | Why it is mutual |
|---|---|
| BP-045 ↔ BP-046 | the machine's guards call `becomesPublishable`/`isUnsuppressible`; `publishable/` names `DraftView`, `State` (level 0) |
| BP-045 ↔ BP-057 | ceilings and resume order read the publish time and zone; `settings/apply.ts` rewrites `veto_deadline` on drafts the machine owns |
| BP-045 ↔ BP-058 | the `destination_working` guard reads health; `destinations/` reads the publishing switch in `switch/` and names `DestinationAdapter` (level 0) |
| BP-046 ↔ BP-057 | the telling's governing pair is the settings pair; saving settings clears `drafts.told` |
| BP-048 ↔ BP-058 | the WordPress adapter receives its decrypted config from `config/`; the registry returns the adapter |

**5. A node added under BP-015 joins this component and that is not a defect.**
The question to ask of a new leaf is never *does it close a cycle in
`depends-on`* — it will — but *which level of Decision 2's table does its
directory sit at, and does every import it declares go downward*.

## Alternatives considered

1. **Split `src/lib/publish/` so the node graph is a DAG** — rejected. It draws
   a boundary no requirement draws through one page's lifecycle, it is a
   top-level-adjacent restructuring with no user-visible value (rule 2.2a), and
   it does not even work: the machine and the publishable predicate would still
   need each other's types, so the split would produce two modules with a
   module-level cycle, which is the failure rule 6 actually forbids.
2. **Delete the "weaker" direction of each pair so the graph reads acyclic** —
   rejected, and this is the cleanup this file exists to stop. It is a five-line
   diff, it makes the derived graph look better, and it is a lie: the edges
   record contracts that exist. Worse, it is silent — the console has no way to
   notice a true edge that was removed, so the next reader trusts a graph that
   under-reports the coupling in the most coupled module in the product.
3. **A seventh BP node owning `src/lib/publish/types.ts`** — rejected. It moves
   the mutual edges rather than removing them (every leaf would then depend on
   it and BP-045 would still depend on BP-046 and BP-058), and it gives a file
   with no behaviour an owner, a status and a work order of its own. The leaf
   already has an owner: the node that specifies the state machine those types
   describe.
4. **Say nothing and keep the disclosure in BP-045's status paragraph** —
   rejected under rule 2.2's own file test: the subject spans six nodes and no
   one of them owns it (BP-045 cannot bind BP-047 or BP-057), and it amends how
   `structure.md` rule 6 is read. It is also the landmine case the skill puts
   above that test: the counterintuitive choice needs a file whose job is to be
   found before the "fix".
5. **Weaken `depends-on` to mean only import direction, so the edges disappear
   honestly** — rejected. Then nothing in the graph records that the veto window
   and the ceiling are the same page's business, and `/wave` sequencing loses
   the only signal it has for what must be built near what.

## Consequences

- The corpus contains, and will keep containing, one six-node cycle in
  `depends-on`. A conformance run that reports it reports a true fact; the
  answer is this file, not an edit.
- The invariant that can fail a build is Decision 2's table, and it is checked
  where compilation happens. Until a lint rule exists it is checked by review —
  recorded as this ADR's `rests-on`, `open`.
- BP-047's `depends-on` gains BP-045 and BP-058's loses BP-047; the component
  shrinks from six mutual pairs to five and from six nodes to five plus BP-047
  hanging off it one-way.
- **Cost of reversing:** deleting this file and "fixing" the graph costs one
  afternoon and buys a `depends-on` projection that no longer describes the
  subsystem — recoverable only by re-reading six blueprints. Reversing Decision
  3 costs one declaration and one re-export, and buys back a rule 6 violation.

## Open questions
None. The lint rule's absence is a `rests-on`, not a question — there is no
repository to put it in yet.
