# ADR-011 — LANDMINE — one arbiter decides a place's single account, and ReachKit's own stop outranks every other reason that is also true

- Date: 2026-08-31

> **Read this before making the next-publish line "more accurate", before
> letting a paused account say it is paused while ReachKit is stopped, or before
> moving an empty-state line back next to the component that renders it.** Each
> of those reads like an obvious improvement. Each breaks a promise an approved
> requirement makes.

## Context
Four approved requirements put a line in the same slot on the screen, and no one
of them owns the slot.

- **REQ-091 criterion 2** — a place holding nothing "carries exactly one written
  line", and where a sibling requirement already fixes the wording, "that fixed
  line is the one line".
- **REQ-043 criterion 5** — an empty date "carries exactly one account of itself
  and no second one"; and where an instruction for the customer stands against
  that date, "that instruction is the date's one account while it is
  outstanding".
- **REQ-043 criterion 3** — the exhausted-supply line is reserved: "No date
  emptied by any other cause, whether or not a requirement names that cause,
  ever carries that line."
- **REQ-092 criterion 7** — while ReachKit has stopped its own work, any
  statement of when the next page publishes "names ReachKit's stop as the reason
  no publish is scheduled, and gives no other reason for it, **whether or not
  that other reason is also true of the account at that moment**".

REQ-092's own non-goals hand the reconciliation to a blueprint in as many words:
"Reconciling criterion 7's bar with REQ-040 criterion 4's set of causes belongs
to the blueprint that builds that line." No single blueprint builds all four
lines: BP-021 owns the empty place, BP-054 owns the stop, REQ-040's node owns the
navigation and REQ-043's node owns the calendar day. That is rule 2.2's file test.

**Why the precedence reads as wrong.** Take an account where publishing is
switched off by the customer *and* ReachKit has hit a spend ceiling. Two things
are true. The customer-caused one is more actionable — they can turn publishing
back on — and a developer looking at the navigation line will read "we're showing
them the cap instead of telling them they paused it" as a bug, or at best as an
ordering nobody thought about. Naming both reasons reads as strictly more honest.
Naming the actionable one reads as strictly more useful. The code that produces
the stop-only line looks, from the inside, like a missing `else if`.

**Why it is load-bearing.** REQ-092 exists because an empty day means one thing
to the customer — that nothing in their market was worth publishing — and a day
ReachKit emptied is a false statement about the customer's own market. The
requirement's user story is "I am never told there was nothing worth publishing
when the truth is that we stopped." Naming a second, also-true reason is how the
first one gets buried: a line that says "publishing is paused" while ReachKit is
also stopped tells the customer the absence is theirs to fix, they fix it, and
nothing publishes — because it was never theirs. The criterion's trailing clause
is not loose drafting. It anticipates exactly the "but this other reason is true
too" argument and rules it out in advance.

## Decision
**One arbiter, `account()` in BP-021, returns exactly one line for any place
holding nothing, over a closed `Cause` union with a total, fixed precedence; and
`nextPublishStatement()` in BP-054 ignores every other cause while a stop is
present.**

1. **The precedence, in order:**

   | # | `Cause` tag | Owner of the line | The clause it serves |
   |---|---|---|---|
   | 1 | `reachkit-stopped` | BP-054 | REQ-092 c1, c7 |
   | 2 | `customer-instruction` | REQ-043 c5's node | REQ-043 c5, REQ-047 c5 |
   | 3 | `named` | the requirement naming the cause | REQ-043 c4 |
   | 4 | `unrecognised` | BP-021 | REQ-043 c4 ("or any cause whatever") |
   | 5 | `supply-exhausted` | BP-021 | REQ-043 c3 |
   | 6 | `no-presence-yet` | BP-021 | REQ-091 c2 |

2. **`unrecognised` outranks `supply-exhausted`, and that is the point.**
   REQ-043 criterion 3 reserves the "nothing worth publishing" line to genuinely
   exhausted supply and forbids any other cause from inheriting it. Making
   `supply-exhausted` reachable only from an explicit `supply-exhausted` cause,
   with an `unrecognised` arm sitting above it, means a cause nobody classified
   falls to a line that says a cause emptied the date — never to the line that
   says the market offered nothing. The safe default is the honest one, not the
   reassuring one.

3. **`no-presence-yet` is last.** Cold start is the baseline account, not a
   competing one: it is what a place says when nothing else emptied it.

4. **The stop outranks the customer's outstanding instruction — and carries it.**
   REQ-043 criterion 5 says an outstanding instruction is the date's one account.
   REQ-092 criterion 1 says a stopped day must say ReachKit did not do the work.
   Both hold, because REQ-092 criterion 2 already requires the stop statement to
   say "whether anything is needed from them". So the instruction is not dropped:
   it is carried inside the stop statement's `needs` arm. `dayAccount()` **rejects**
   the pair where a stop is arbitrated over an outstanding instruction while
   `stop.needs.kind === 'nothing'` — an assertion, not a silent merge, because a
   silent merge is how the instruction disappears.

5. **`nextPublishStatement()` ignores `otherwise` entirely when `stop` is
   non-null.** Not "prefers"; ignores. The other causes are not consulted, not
   appended, not shown as secondary text, and not logged to the customer. This is
   REQ-092 criterion 7's trailing clause implemented literally.

6. **A new cause is an edit to `account.ts`.** The `Cause` union is closed and
   `CAUSE_PRECEDENCE` sits beside it, so adding a cause puts the author in front
   of the ordering. An open extension registry would let a cause be registered
   without ever meeting the order — and an unordered set cannot satisfy "exactly
   one account".

## Alternatives considered
1. **Name every true reason** — rejected. It is the reading that feels most
   honest and it is the one REQ-092 criterion 7 names and forbids, because a
   second reason buries the first and hands the customer a fix that will not
   work.
2. **Name the most actionable reason first** — rejected on the same clause, and
   worse: while ReachKit is stopped, the actionable reason is not actionable.
   The customer acts, nothing publishes, and the product has taught them that its
   account of itself is unreliable.
3. **Let each surface decide its own precedence** — rejected. Four requirements
   put lines in one slot; four independent decisions produce two accounts on one
   date the first time two causes coincide, which REQ-043 criterion 5 forbids and
   which no test written against a single requirement would catch.
4. **Fall back to the exhausted-supply line for an unclassified cause** —
   rejected, and it is the tempting default because "nothing worth publishing" is
   the friendliest sentence available. REQ-043 criterion 3 forbids exactly this
   inheritance.
5. **A `## Decisions` entry inside BP-054** — rejected under rule 2.2's file
   test and the blueprint skill's landmine rule. The subject spans BP-021 (the
   arbiter), BP-054 (the stop), REQ-040's node (the navigation line) and
   REQ-043's node (the day line), no one of which owns it; and it is precisely a
   decision that "reads as wrong but is load-bearing", where the reversal would
   look like a cleanup.

## Consequences
- Every empty place in the product gets its line from one function. A second
  account on one date is not a bug to find; it is a call that does not exist.
- The navigation, the footer autopilot card and any mail stating what publishes
  next all render through `nextPublishStatement()`. While a stop is present they
  say the same thing, because they call the same function with the same argument.
- A customer with publishing switched off *and* ReachKit stopped is told about
  the stop only. When the stop clears, the paused line appears. This will be
  reported as a bug at least once. It is not one.
- The precedence table is the only place the ordering exists. Moving it, or
  duplicating it into a surface, re-opens every failure above.
- **Cost of reversing:** trivial in code — reorder an array, add an `else if`, or
  concatenate a second line — and that cheapness is the danger. What reversal
  actually costs is REQ-092's user story: the customer told there was nothing
  worth publishing, or told to fix something that was never theirs. Anyone who
  finds this precedence and thinks "this is a bug" should read this file first,
  which is the entire reason it is a file.
