# ADR-030 — LANDMINE — the declared answer and the measured answer are two different facts, and a pending change is their difference

- Date: 2026-08-31

> **Read this before adding `sites.pending_category`, a `site_changes` table, or
> any "apply this change later" queue.** Every one of those reads like the
> obvious way to build a delayed edit. Each one creates a second source of truth
> for a fact the product already stores twice for good reason, and breaks a
> promise three requirements make.

## Context
Three answers decide what every number in ReachKit is a measurement of: the
domain, the market category and the rival set. Each is settled at setup (REQ-026),
each is changeable in Settings (REQ-071), and each change is **effective only at
the first weekly re-measurement that begins after the moment of the save** (REQ-071
criteria 7, 8 and 9; REQ-065 criterion 1).

That delay is the whole difficulty. Between the save and the pass, the product
must simultaneously:

- show the customer the answer they just saved, and the date it takes effect
  (REQ-071 criteria 1, 6 and 11);
- show every number measured under the *old* answer, unchanged and dated
  (criterion 10);
- generate no page from an opportunity derived under the answer being replaced,
  with one line naming which change is holding it (criterion 11);
- never present anything measured under the old answer as the new answer's, and
  never present the difference across the change as movement (criteria 12 and 13);
- and, from the pass onward, use the new answer for everything.

The obvious design is a pending-change record: `sites.pending_category`,
`pending_domain`, `pending_effective_from`, or a `site_changes` table the pass
drains. Every engineer who meets this requirement will reach for it, and nothing
in BUILD names it as forbidden — BUILD does not describe the change path at all
beyond §4.7's one Settings line.

**Two facts already exist, and they already answer every clause above.** The
*declared* answer lives on `sites` — it is what setup wrote (BP-034) and what a
save changes (BP-056). The *measured* answer lives on the scan that produced the
current report: `scans.domain`, `report.market.category`, `report.rivals`, all
carrying that scan's own measurement date (BUILD §10, one report blob per scan;
BP-012's `is_current` pointer makes exactly one of them current per site). The
product stores both because they answer different questions — "what are we
measuring against from now on" and "what was this number measured against" — and
REQ-004 criterion 12 already forbids a report carrying figures from two scans.

## Decision
**There is no pending-change record. A save writes the declared answer
immediately, and a pending change is computed as the difference between the
declared answers on `sites` and the measured answers on the current scan.**

1. `saveDomain` / `saveCategory` / `saveRivals` (BP-056) write `sites.domain`,
   `sites.category`, `sites.competitors` at once. Nothing else is written.
2. A pass reads the declared answers **at the moment it begins** — which is
   precisely REQ-071's "the first weekly re-measurement that begins after the
   moment of the save", with no scheduling arithmetic and no queue to drain.
3. `pendingChanges({ declared, measured, now, timezone })` returns one entry per
   answer where the two differ, each carrying the date the next pass begins. That
   set drives the Settings pending line, the generation hold and the resume date.
4. The moment the pass completes, the new scan is current, `measured` equals
   `declared`, and `pendingChanges` returns `[]`. The pending state clears itself
   with no transition to run and no row to delete.
5. Change markers for charts, series, week counts and verdicts (`changeMarkers`,
   `domainHistory`) are derived from the sequence of stored scans, which already
   carries the domain and the category each one measured against.

## Alternatives considered
1. **`sites.pending_*` columns plus `pending_effective_from`, applied by the
   pass** — rejected. It creates a second home for a fact `sites` already holds
   (rule 2.4), and the two diverge on every path that is not the happy one: a pass
   that fails after applying, a second save before the first is applied, a
   customer who changes back. It also needs its own migration on the `sites` topic
   token and its own back-fill semantics for accounts that predate it. Worst, the
   clearing step is a write that can fail, so "pending forever" becomes a
   reachable state — where in the decision above, pending is not a state at all.
2. **A `site_changes` append-only table the pass drains** — rejected for the same
   reasons plus one: BUILD §10 admits a tenth table only when "a rendered surface
   that reads it" is specified first, and no surface reads a change log. Everything
   the customer is shown about a change (the pending line, the date, the marker on
   a chart) is derivable from the two facts already stored.
3. **Do not write the save at all until the pass runs; hold it in the form** —
   rejected, it loses the customer's save on a reload and makes criterion 6's
   promise ("the date that line names at the moment the customer saves is the date
   the change is effective on") unkeepable, because there would be no saved moment.
4. **Write the save and also re-measure immediately** — rejected outright by
   REQ-065's non-goal and REQ-071 criteria 7 to 9: measurement on demand is exactly
   what makes week-on-week movement incomparable, which is the harm the delay
   exists to prevent.
5. **Record this inside BP-056's `## Decisions`** — rejected under rule 2.2's file
   test and the skill's landmine rule. The invariant binds five nodes — BP-034
   writes the declared answers, BP-056 changes them, BP-025 and BP-026 re-derive
   from them, BP-012 reads them when a pass begins — and no one of them owns it. A
   contributor adding `pending_category` would most likely be working in BP-002's
   migration directory or on the Settings surface, and would find nothing in
   BP-056 telling them the absence was deliberate.

## Consequences
- **Nothing to migrate, nothing to clear, nothing to reconcile.** Pending is a
  computation, so it cannot get stuck, cannot be applied twice and cannot survive
  the pass that resolves it.
- **The Settings card shows the declared answer**, not the measured one, with the
  pending line beside it whenever they differ (BP-056 `## Decisions` 2). Anyone who
  "fixes" that card to show the measured value hides the customer's own save from
  them, which is how a correction gets made twice.
- **Every historical number stays interpretable** because the answer it was
  measured against is stored on its own scan, not overwritten by the current
  declared answer. This is what makes criteria 12 and 13 — never present the
  difference across a change as movement — derivable rather than bolted on.
- **A save during a running pass is resolved by the database, not by us**: the pass
  reads the row, so the write that lands first wins, and BP-056 recomputes the
  effective date after the write rather than before it.
- **Cost of reversing: low in code, and that cheapness is the danger.** Adding
  `pending_*` columns is one migration and one branch. The true cost is a second
  source of truth for the three facts the entire product's numbers are measured
  against, a reachable "pending forever" state, and the quiet loss of REQ-071
  criteria 10, 12 and 13, none of which fails loudly when it breaks — a chart
  simply stops naming the day the domain changed. Anyone who finds the missing
  pending table and thinks "this is an oversight" should read this file first,
  which is the entire reason it is a file.
