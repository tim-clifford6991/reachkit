# ADR-096 — LANDMINE — `UnmeasuredReason` stays two-membered: a schema-parse failure is `undeterminable`, and `unparseable` lives only in the log

- Date: 2026-09-04

> **Read this before adding `'unparseable'` to `UnmeasuredReason` to make
> `src/lib/llm/index.ts` agree with BP-009's prose.** It is a one-word edit to
> a union, it makes a documented mismatch go away, and it reads as a tidy-up.
> It is not one. That third member costs a customer-visible sentence only the
> owner may write, and a stored reason value older readers cannot classify.

## Context

`UnmeasuredReason` is the closed union carried by the `unmeasured` arm of
`Measured<T>` — the trichotomy REQ-004 makes a customer promise. BP-024
`## Public interface` declares it, verbatim:

```ts
export type UnmeasuredReason = 'undeterminable' | 'not_attempted'
```

BP-010 `## Public interface` declares the same two members inline, with each
one annotated to the criterion it exists for — `'undeterminable' = REQ-004
criterion 6 (nothing returned / unreadable / no answer)`, `'not_attempted' =
REQ-004 criterion 9 (90s ceiling or spend ceiling)`. It ships at
`src/lib/measure/measured.ts` (WO-277, `done`).

BP-009 `## Error & edge behavior` disagreed with both. Until this decision it
read: "A response that does not parse against the schema is `unmeasured` with
reason **`unparseable`**" — naming a member of `UnmeasuredReason` that neither
blueprint declares and no code has ever had. WO-026's implementer hit the gap
building the seam, mapped a parse failure to `undeterminable`, and raised it
rather than widening a type outside its file plan (rule 7.1). WO-026's
validator confirmed the mismatch by direct read and refused to rule on which
artifact moves. This is that ruling.

**Why widening reads as the obvious fix.**

1. The prose says `unparseable` and the code says `undeterminable`. One of
   them is wrong, and the shipped code is the thing you can run — so the
   blueprint looks like the authority and the union looks like the bug.
2. `unparseable` is a genuinely more precise description of what happened: the
   model answered, and the answer did not fit the schema. Collapsing it into
   "could not determine" throws information away, which is the shape of a
   defect, not a design.
3. The word already exists in the codebase — `ParseOutcome` in
   `src/lib/llm/index.ts` has an `"unparseable"` member — so adding it to
   `UnmeasuredReason` looks like making two neighbouring types agree rather
   than adding anything.
4. It is one word in one union, in a file that already lists two.

**Why it is load-bearing.**

- **Each member of `UnmeasuredReason` is an owner-owed customer sentence.**
  BP-019's `renderMeasured` takes `unmeasuredLine: CopyKey` and its own
  comment says the key "differs by reason: undeterminable vs not_attempted".
  BP-020 decision 3 names the keys it resolves to — `unmeasured.undeterminable`
  (`fixedBy: "REQ-004 c6"`) and `unmeasured.not-attempted`
  (`fixedBy: "REQ-004 c9"`) — and marks both **owner-owed**, landing empty in
  `OWNER_OWED` with `copy()` throwing until the owner writes them. A third
  member is therefore a third owner-owed sentence, and a customer-visible
  string is the owner's under constitution §1's decision-rights table. A
  widening committed as a cleanup either escalates silently to the owner or,
  worse, gets a sentence written for it by whoever did the widening.
- **Each member is bound to a requirement criterion, and there is no third
  criterion.** REQ-004 criterion 6 covers "nothing returned / unreadable / no
  answer" and criterion 9 covers the ceilings. BP-024 `## Data model delta`
  spells criterion 6's scope out: "could not tell whether it exists: nothing
  returned, **unreadable**, or a data source did not answer". A model response
  that does not parse is unreadable output from a data source. It is already
  inside criterion 6; it is not a third thing the requirement forgot.
- **The reader cannot act on the distinction.** BP-027's blocked-readers table
  gives each unmeasured reason its own row, its own line and its own fix
  affordance (`unknown` — no lines). "We could not read the model's answer" and
  "we could not determine it" resolve to the same non-action by the same
  reader. The precision in point 2 above is real and is entirely diagnostic.
- **The union is stored, not just rendered.** `Measured` values are written to
  `scans.drivers jsonb` and into the versioned `scans.report jsonb` blob
  (BP-010 `## Data model delta`; BP-012's `StoredReport`). A third reason value
  starts appearing in stored blobs the moment it ships, and every reader of an
  older or newer blob must classify it. That is a data migration wearing a
  one-word diff.
- **`worseReason` has an ordering that a third member silently joins.** BP-024
  decision 3 fixes `undeterminable` above `not_attempted` so a composite factor
  carries the worse reason. A third member added without touching
  `worseReason` gets an undefined rank, and `combine` picks a reason by
  accident — the failure is invisible, because every arm still type-checks.

No single blueprint owns the span. BP-024 declares the union, BP-010 declares
it again in its own interface, BP-009 is where the wrong prose lived, BP-019
renders it, BP-020 holds the copy keys, BP-027 tabulates the rows. The
"cleanup" would most naturally be done in BP-024's file by someone who has
never read BP-020 — which is precisely rule 2.2's file test, and the reason
this is a file.

## Decision

1. **`UnmeasuredReason` stays `'undeterminable' | 'not_attempted'`.** Two
   members, one per REQ-004 criterion. Adding a third is a requirement change
   and an owner copy ruling, never a type edit.
2. **A schema-parse failure at the `llm()` seam is `unmeasured` with reason
   `undeterminable`** — REQ-004 criterion 6's "unreadable", which BP-024's own
   words already cover. Model unavailability resolves there too.
   `not_attempted` stays reserved for the case BP-024 and ADR-021 define it
   for: a ceiling stopping the call before it was attempted.
3. **`unparseable` survives where it is useful and harmless: the log.** It is a
   member of `ParseOutcome` in `src/lib/llm/index.ts` and reaches the log record
   BP-009's `## NFR budget` already specifies — "call site, tier, tokens in and
   out, cost, duration, **parse outcome**". The diagnostic distinction is kept
   in observability, where an operator can act on it, and kept out of the
   trichotomy, where a customer cannot.
4. **BP-009's prose was the wrong artifact and it moves.** Its
   `## Error & edge behavior` is amended to state `undeterminable` as the
   returned reason and `unparseable` as the log's parse outcome, citing this
   file. One claim, one home (rule 2.4): the reason vocabulary is stated at
   BP-024 and cited everywhere else.
5. **The word `unparseable` in other blueprints is left alone where it is not
   naming an `UnmeasuredReason`.** BP-008 ("a vendor error, a timeout or an
   unparseable payload returns `unmeasured` with its reason"), BP-025 and
   BP-049 describe the *condition*, not the member, and reading them against
   clause 2 gives the right answer already.

## Alternatives considered

1. **Widen `UnmeasuredReason` to three members and correct the code** —
   rejected. It is the move this file exists to stop: a third owner-owed
   customer sentence (BP-020 decision 3) chosen by whoever did the widening, a
   third stored reason value in two `jsonb` columns, and an unranked member in
   `worseReason` (BP-024 decision 3) — for a distinction no reader of the
   report can act on differently.
2. **Leave both artifacts as they are and let the mismatch stand** — rejected.
   BP-009's prose names a member of a type that does not have it; WO-026's own
   `## Test plan` quotes that prose as an acceptance criterion. A criterion
   that cannot be satisfied as written is how a test gets rewritten to match
   the code instead of the promise.
3. **Introduce a second, seam-local reason type and map it at the boundary** —
   rejected as ceremony. That is what `ParseOutcome` already is, and clause 3
   keeps it; giving it a second life as a public type would create the two
   vocabularies rule 2.4 forbids.
4. **Record this as a `## Decisions` entry inside BP-024** — rejected under
   rule 2.2's file test. The load-bearing part of the argument lives in BP-020
   (owner-owed copy) and BP-019 (the render seam), which BP-024 does not own,
   and the tempting reversal would be performed in BP-024's own file by
   someone who never opens theirs.

## Consequences

- `src/lib/llm/index.ts` is correct as shipped and needs no change. WO-026's
  second-listed open row is dispositioned `confirmed` against this file.
- BP-009's `## Error & edge behavior` and WO-026's `## Test plan` row 1 now
  quote a reason the type actually has. The test itself is unchanged: it
  asserts `unmeasured` after exactly two attempts with no coercion, which is
  the behaviour either wording demands.
- Any future call site that wants the parse/unavailability distinction reads
  the log, not the value.
- **Cost of reversing:** one word in one union, which is the danger. The true
  cost is a REQ-004 amendment, an owner-written customer sentence, a
  `worseReason` rank, and every stored `scans.drivers` and `scans.report` blob
  written before and after the change disagreeing about how many reasons exist.
  Anyone who finds `undeterminable` where the word `unparseable` would read
  better should read this file before editing the union.
