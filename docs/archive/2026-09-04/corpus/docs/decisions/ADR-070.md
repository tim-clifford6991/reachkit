# ADR-070 — LANDMINE — one automatic regeneration, and a draft that has entered review is never regenerated at all

- Date: 2026-08-31

> **Read this before adding a retry to the generation pipeline, before wiring
> `needs_attention → generating` to a job, and before unifying the two places a
> claim check can fail.** Each of those reads as an obvious reliability or
> tidiness improvement. Each breaks a promise the corpus makes.

## Context
Three rules about regeneration live in three requirements and are enforced in
three nodes, and read alone each of the three looks arbitrary.

**REQ-053 c3** — a draft stopped by any generation hard rule "is regenerated once
and no more; if the regenerated draft is stopped by any of those rules again, the
item comes to rest in the state REQ-056 defines for an item needing the
customer's attention". `BUILD.md` §8 hard rule 4 states the same shape:
"failure = regenerate, twice = needs-attention".

**REQ-056 c2** makes `needs_attention → generating` a legal edge — but only "to a
page whose draft never entered review, and only when the customer starts it, so
REQ-053 criterion 3's bound on automatic regeneration is never raised". So the
edge exists and must not be driven by anything but a person.

**REQ-053 c5** — a page held by a *failed re-check* against a changed
do-not-claim list "is never regenerated — criterion 3's path reaches only a draft
stopped before it entered review — and it goes to its destination only if a
re-check later passes, or never, if the customer stops it".

Put together, three things are true that no single file says:

1. The bound of one is a bound on **automatic** regeneration, not on the item's
   lifetime. A third, fourth or tenth generation is legal — each started by the
   customer, from `needs_attention`.
2. The same rule (`do_not_claim`) has two failure paths that must never be
   merged: failing **before** review regenerates once; failing **after** review
   never regenerates at all.
3. A step that did not run is not a rule that failed, and must not consume the
   one automatic regeneration.

**Why each reads as wrong.**

*The edge that no job may use.* An engineer who finds `needs_attention →
generating` in the state machine and no scheduler pointing at it will read a
missing feature. Wiring the nightly `draft/generate` job to sweep
`needs_attention` items is a four-line change that looks like it recovers stuck
work. It silently converts a bounded promise into an unbounded loop: the item
never comes to rest, the day never carries its line (REQ-043 c4), and the
customer is never told anything needs them.

*The two claim-check paths.* A draft that matched the list before review, and a
draft that matched it after review, look identical in the data: same rule, same
matched entry, same `claim_check` verdict shape. Unifying them into one handler
is the archetypal cleanup. But the post-review draft may carry the customer's own
edits — REQ-045 owns them, and REQ-053's non-goal is explicit that "an edit of
their own that fails this check is returned to them". Regenerating it destroys
text a person wrote, with no undo, in service of a rule that only ever bound what
ReachKit generates (REQ-050 c12). The break is silent: the pipeline reports a
successful regeneration.

*The unrun check.* `claimCheck` returning `unrun` because the model was
unavailable or a cap was hit is a failure, and a failure at a rule-shaped call
site. Counting it as a hard-rule stop is a one-character decision in a
`switch`. It would spend the customer's single automatic regeneration on a
condition regenerating cannot fix, and on a bad vendor day it would burn every
customer's allowance before the pipeline had produced anything for a rule to
judge.

None of the three is visible from any one requirement, and each spans BP-042
(the rules), BP-043 (the recovery decision) and BP-015 (the states).

## Decision

1. **`recoveryOutcome` is the single rule, and it is pure.** BP-043 owns it. It
   returns `regenerate_once` when a draft that has not entered review failed a
   hard rule and `drafts.hard_rule_attempts` is 0; `rest` in every other case.
   It performs neither outcome — BP-042 regenerates, BP-015 transitions.
2. **`hard_rule_attempts` counts automatic attempts only.** A customer-started
   regeneration from `needs_attention` resets it to 0. That is what makes "once
   and no more" a bound on the machine rather than on the person, and it is the
   reading REQ-056 c2 states in its own parenthesis.
3. **No scheduler, job, retry or cap-recovery path may take
   `needs_attention → generating`.** The edge is reachable from a customer action
   and from nothing else. BP-015's implementation must make that structural — the
   transition's guard takes an actor, and the only admissible actor is the
   customer.
4. **A draft that has entered review is never regenerated, whatever stopped it.**
   REQ-053 c5's held page leaves review by `in_review → approved` (once a
   re-check passes against the text as it then stands) or `in_review → skipped`,
   and by no other edge. `recoveryOutcome` returns `rest` for it because
   `enteredReview` is true, so the rule that protects the customer's edits is the
   same rule that bounds the machine, not a second one someone can forget.
5. **An unrun check is a step failure, not a rule failure.** `ClaimVerdict.state
   === 'unrun'`, an `unmeasured` result from `llm()`, a grounding fetch that
   returned nothing, and `capHit()` all take REQ-092 c1's route
   (`generating → needs_attention`) with `reason: 'step_failed'`. They do not
   populate `failed`, do not increment `hard_rule_attempts`, and never reach
   `recoveryOutcome`.
6. **Fail closed, always.** A draft whose claim check could not run is not queued
   and is not handed to a destination. "We could not check" is never "it passed".

## Alternatives considered
1. **Record all of this inside BP-043's `## Decisions`** — rejected under rule
   2.2's file test. Points 3 and 4 are obligations on BP-015's state machine and
   point 5 is an obligation on BP-042's pipeline; a reader arriving at either
   node to add a retry would find nothing in BP-043 telling them a constraint
   exists. The subject spans three nodes and no one of them owns it.
2. **Let a job retry `needs_attention` items with a small cap (say three)** —
   rejected. It is not a smaller version of the promise; it is a different one.
   REQ-053 c3 makes the resting state a thing the customer is told about
   (REQ-043 c4's line), and a job that clears items before they are read deletes
   the telling, not just the wait.
3. **Unify the pre-review and post-review claim failures behind one handler with
   a flag** — rejected. A flag is what gets dropped in the refactor that follows.
   The two paths differ in whether customer-written text exists, which is a
   difference of kind; `enteredReview` is an input to a pure function precisely
   so the distinction survives every later edit to the pipeline.
4. **Treat an unrun check as a hard-rule failure "to be safe"** — rejected. It is
   not safer: it fails closed either way, and the only difference is that it
   spends the regeneration allowance on a condition regeneration cannot clear.
   Failing closed is point 6; spending the allowance is a separate and wrong
   choice.
5. **Count all regenerations, customer-started included, against the bound** —
   rejected. It would leave an item the customer wants retried with no way out
   of `needs_attention`, which REQ-056 c3 forbids in terms ("no page … is left in
   a state it has no way out of").

## Consequences
- The generation path has exactly one automatic retry, and every other recovery
  is something a person chose. That is a worse-looking reliability number and a
  better product: nothing loops, and every stop is a line the customer reads.
- BP-015's `needs_attention → generating` guard carries an actor, which is an
  extra parameter on one transition and the only enforcement of point 3.
- `hard_rule_attempts` resetting on a customer-started attempt means the column
  is not an audit trail of generations. If an audit trail is ever wanted it is a
  new fact with a new home, not a change to this counter.
- **Cost of reversing:** low in code — a job registration, a merged handler, a
  `switch` arm. That cheapness is the danger. The true cost is an unbounded
  generation loop with no customer telling (point 3), destroyed customer edits
  with no undo (point 4), and a regeneration allowance spent on vendor outages
  (point 5) — none of which fails a test that exists today, because each of them
  produces a *successful-looking* run.
