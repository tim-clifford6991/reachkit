# ADR-020 — One canonical domain key, produced by one parser, used by every domain-keyed row, URL and counter

- Date: 2026-08-31

## Context
A domain is the product's most-used key and the only identifier a free visitor
ever supplies. It appears, in v1, in at least six places owned by five different
blueprints:

| Where | Node | What breaks if the form differs |
|---|---|---|
| `/scan/{domain}` URL segment | BP-022 | two addresses for one domain; REQ-001 criterion 7's copy-link promise ("the same report … for a different person on a different device") no longer holds |
| `scans.domain` and the `unique (domain) where is_current` partial index | BP-012 / BP-002 | two current reports for one domain, which the index exists to make unrepresentable |
| `domain_blocks.domain` | BP-002 | a removal that blocks `example.com` and serves `www.example.com` — REQ-002 criterion 3 says "to nobody" |
| the free-path cooldown and in-flight checks | BP-023 | REQ-003 criterion 7's "if the running scan is of the domain they asked for" becomes a string comparison that is wrong for the same domain typed twice |
| `sites.domain` at setup and on the scanless checkout path | BP-017 | a paying customer's site does not join up with the free scan they converted from, and `BUILD.md` §6.4's "a free scan's data is reused by the paid deep pass" silently misses |
| the `content.{customer-domain}` host key | BP-004 | a hosted page served from a host the product does not recognise as the customer's |

REQ-001 criterion 2 states the customer promise directly: "with or without a
scheme, with or without `www`, with a trailing path, in any letter case … no two
of those forms produce different addresses or different stored reports." REQ-001
criterion 3 states the rejection rule: an empty value, an IP literal, or a
hostname with no public suffix is not a well-formed public domain name — and
"a well-formed domain is accepted here whether or not it resolves".

No blueprint owns this. BP-022 owns one URL, BP-023 owns two counters, BP-002
owns three columns, BP-017 owns one, BP-004 owns a host. Each could parse for
itself, and each parse would be defensible in isolation. The failure they
produce together is silent: nothing errors when `WWW.Example.com` and
`example.com` become two rows, two reports and two removal states. It surfaces
as a domain owner who asked for their report to be removed and finds it still
served at a neighbouring address.

`structure.md` names no module for a domain parser, and `BUILD.md` does not
mention one. The gap is real and it is not any one node's to fill.

## Decision
**One canonical form, produced by one function, `parseDomain`, in
`src/lib/scan/domain.ts` (BP-023), returning a branded `CanonicalDomain`. Every
domain-keyed value in the product is a `CanonicalDomain` or is derived from
one.**

1. **The canonical form.** Lowercase; scheme removed; userinfo, port, path,
   query and fragment removed; a leading `www.` removed; a trailing dot removed;
   internationalised labels converted to punycode (A-labels). What remains is a
   registrable domain plus any remaining subdomain labels.
2. **The rejections**, matching REQ-001 criterion 3's three named cases and two
   the parser cannot avoid: `empty`, `not_a_hostname`, `ip_literal`,
   `no_public_suffix`, `too_long`. Each is a `DomainProblem` handle; the written
   line for each is BP-019's.
3. **DNS is not consulted.** Resolution is a scan outcome (REQ-001 criterion 3),
   and a parser that made a network call would put a third party's outage on the
   landing page's submit path.
4. **The type is branded**, so `CanonicalDomain` is not interchangeable with
   `string`. `runScan`, `admitFreeScan`, `readCurrentReport`, the `domain_blocks`
   read, the `sites.domain` write and the host key all take the branded type;
   the only producer is `parseDomain`.
5. **It lives in `src/lib/scan/`, not `src/app/`.** `src/lib/` may not import
   from `src/app/` (`structure.md` rule 6), and `src/lib/account/` (BP-017) needs
   the parser for the setup and scanless-checkout paths — so an edge-only parser
   would leave BP-017 with a second implementation, which is exactly the
   duplication rule 7.1 forbids.
6. **BP-023 owns the file** because free-scan admission cannot be evaluated
   without the key: removal, cooldown and same-domain in-flight are all
   equality on it. It is exported for every other node named above.
7. **Non-canonical URL forms redirect, they do not render.** BP-022 answers a
   non-canonical `/scan/{segment}` with a 308 to the canonical address, so one
   report has one address in the address bar and in every share of it.

## Alternatives considered
1. **Each node parses for itself** — rejected. Five parsers, five sets of edge
   cases, and the disagreement is silent: nothing fails, rows just stop joining
   up. The specific harm is REQ-002 criterion 3 becoming partial, which is the
   one promise in the corpus made to a person who never asked for the product.
2. **Parse at the HTTP edge only and pass plain strings inward** — rejected.
   `src/lib/account/` and `src/jobs/` both need the parse and neither may import
   from `src/app/`; the engine would be trusting a caller for its primary key.
3. **Store the raw form and normalise in every query** — rejected. It makes the
   partial unique index on `scans.domain` unable to hold "one current report per
   domain", which is BP-012's whole mechanism for REQ-001 criterion 17, and moves
   a correctness property into every `where` clause.
4. **Keep `www.` as part of the key** — rejected against REQ-001 criterion 2's
   explicit "with or without `www`". A site that genuinely differs between the
   apex and `www` is a real thing on the web, and this decision does measure them
   as one; that is the requirement's ruling, not this decision's, and the cost is
   accepted there.
5. **Put the parser in `src/lib/egress/` (BP-006)** — not unreasonable: BP-006
   already refuses IP literals and non-http schemes, and owns `resolvesInDns`.
   Rejected because BP-006's vocabulary is about *reaching* a URL, and the free
   path must accept a domain it can never reach; folding the two would make an
   unreachable domain look like a malformed one, which REQ-001 criterion 3
   separates in so many words.
6. **A `## Decisions` entry inside BP-022** — rejected under rule 2.2's file
   test. The subject is the key shared by six surfaces across five blueprints,
   and the reader most likely to break it is a future implementer of BP-017 or
   BP-004, neither of whom would ever open BP-022.

## Consequences
- One parser, one fixture suite, one place the public-suffix data is loaded.
- The branded type makes the failure a compile error: a plain `string` cannot be
  passed where a domain key is expected, so a new surface that forgot to
  canonicalise does not build.
- `parseDomain` is on the free path's hottest routes (every landing submit, every
  report render). It is pure and local, with the suffix list held in memory.
- **Cost of reversing:** high and mostly invisible. Reversing means the stored
  keys already written under one form no longer match what a new parse produces —
  a data migration over `scans`, `domain_blocks` and `sites`, with the risk that a
  removal record stops matching the domain it removed. Anything that changes the
  canonical form after launch (dropping the `www` rule, keeping the port, changing
  IDN handling) is that same migration, not a code change.
- BP-023's implementation narrows two parameter types in BP-012's published
  `admitFreeScan` signature (`string` → `CanonicalDomain`, `string` →
  `NetworkKey`). That is deliberate and recorded in BP-023's `## Decisions`; the
  librarian should read it as a refinement, not as drift.
