2026-11-08  **A valid, unused sign-in or email-change link takes its holder straight into the app, with no confirm page** (owner C5, #2522: "All magic links, when valid and unused should navigate the user directly into the app without a confirm page"; mechanism by the architect on #2522). This supersedes the 2026-11-06 ruling (#2445) and the line that magic-link mail is for later visits. `/auth/confirm` renders nothing. A `HEAD` answers `204`. A `GET` spends the link only when it is a person's page load: `Sec-Fetch-Mode: navigate` and `Sec-Fetch-Dest: document`, with either `Sec-Fetch-User: ?1` or a valid `__Host-rk_signin_pending` cookie for the link's type; it lands on the link's allowed landing, else `/setup` on a first sign-in, else `/app`. Any other `GET` (a mail scanner, a prefetch, an embedded load, a browser that sends no Fetch Metadata) is sent to `/signin` with the `link=open` marker, which speaks `signin.link_open`, before the token is looked up, so the answer is the same whatever the link is. The dead-link answer is unchanged. Each open is logged with its signal (`fetch-user`, `pending` or `none`); a dead link opened with `pending` counts as a scanner spending it first, and the own-token design is reconsidered only if that rate passes 2% of person-opened links over 30 days. Accepted: a sandbox that fakes user activation still spends a link, and a person can be signed in to an account whose link someone else sent them.
