# ReachKit — operating guardrails

ReachKit is a discoverability engine: a user submits a store/site URL, we scan it, score how findable it is, and hand back a ranked plan of actions. Next.js 16 App Router on Vercel · heavy work in Inngest at `/api/inngest` (`maxDuration=300`) · Supabase (Postgres + RLS + pgvector).

This file is the **rules of engagement** — the invariants and hard rules that must survive edits. It does not restate the architecture; two companion docs do that and must be kept in sync when they change:

- **`docs/REQUIREMENTS.md`** — the LIVING product-requirements doc: what the product is required to do, owner-readable and owner-editable, with the `OPEN(O-n)` push-list of decisions waiting on the owner. Behavior truth lives THERE; this file is the rules for changing it; architecture.md is how it's built. An owner edit to REQUIREMENTS.md is a requirement change — reconcile code to it or raise the conflict.
- **`docs/architecture.md`** — living structural doc (3 Mermaid diagrams: system, scan sequence, billing).
- **`docs/score-calibration.md`** — scoring bands + the open calibration problem.
- **Interactive process/invariant map** — https://claude.ai/code/artifact/e2b1232f-a7fb-4071-9bf4-627740998700 (clickable nodes + the invariant enforcement ledger). ⚠️ STALE SNAPSHOT (pre 2026-07-09): does not reflect the v4 on-site headline, external-cost tracking, or the `/app` nav fix — treat this file + `docs/architecture.md` as authoritative over the artifact; regenerate the artifact when convenient.

## Invariants — do not break these

Each has (or should have) a guard test. Breaking one is a correctness regression, not a style nit. The load-bearing constants these restate (headline version, fixed-basis keys, pillar weights, `MAX_SELECTED`) are pinned by `lib/scan/documented-invariants.test.ts` — a change there is your signal to update this file + `docs/architecture.md` in the SAME commit.

1. **Free↔paid score stability (unified Discoverability Score, v6).** The headline gauge is the **unified Discoverability Score** = `discoverabilityScore(onPageReadiness, searchPresence, keywordsRanked)` = **geometric mean** of two 0–100 drivers: (a) **on-page readiness** — the v4 `headlineScore` (`registryScore` over the FIXED on-site basis `FIXED_BASIS_SIGNAL_KEYS`: the 8 HTML signals title/meta/schema/canonical/headings + content_depth/social_share/media), and (b) **search presence** — the free-tier `searchVisibility.score` (from ONE `ranked_keywords` call), **floored by the v6 findability blend** (below). **All inputs are computed identically on free AND paid**, so the unified number is **identical free↔paid — it never moves on upgrade**. Geometric (not arithmetic) so BOTH must be strong: a flawless page nobody finds (on-page 98 × search 4) reads ~20, not 98 — this is the fix for the "98 in discoverability vs 4 in search visibility" contradiction. `searchPresence` floored at 1 (never a hard 0 that reads as an error). The two drivers are shown as bars beneath the gauge (`score_version 6`, 2026-07-26). Off-site cohort strength (backlinks, marketplace/community/press vs rivals) is STILL the separate **`marketPositionScore`** grade, never in the headline. The trend writers (`verify`/`refresh`/`pulse`) reuse the persisted `report_payload.searchVisibility` (score **and** `keywordsRanked`) via `unifiedHeadline(...)` so the score-over-time line never mixes scales. **v6 findability blend (owner-approved, 2026-07-26):** `searchPresence` is additionally floored by `findabilityFloor(keywordsRanked)` — a scale-invariant log curve (`14·log₁₀(keywordsRanked)`, 0 ranked → 0, 15M → 100) — so `searchEffective = max(searchPresence, findabilityFloor)`. `searchVisibility.score` is the CATEGORY-CLASSIFIED presence; when the frozen classifier can't recover a site's category (x.com; a broken SPA fetch that starves it) it reads ~0, and the geomean then collapsed the WHOLE score to "Invisible" — x.com (15,060,115 ranked keywords) read **4/100**, savvycal (32k) read 7, getapp (120k) read 32: the launch-credibility "one red rule". `keywordsRanked` is a **RAW count from the same `ranked_keywords` call, NOT the frozen classifier** — so the blend is invariant-#1-safe (never touches `classify`/`computeSearchVisibility`) and, because `keywordsRanked` is identical free↔paid, the number STILL never moves on upgrade. A genuinely footprint-less site (0 ranked → floor 0) stays low (reachkit.app, unlaunched → ~9). **Deepen freshness gate (owner rule, 2026-07-24):** the deep pass must ALSO reuse the free scan's persisted `searchVisibility` when the free scan is **≤`FREE_LAYER_MAX_AGE_DAYS`(7) old** — `full-scan.ts` gates the `gatherFreeSearchVisibility` re-fetch behind `shouldReuseFreeLayer(...)` (`lib/scan/free-layer-freshness.ts`). Re-fetching unconditionally was the bug: once the free pass's `ranked_keywords` cache expired (days later), the re-run returned DIFFERENT footprint data, moving the score on upgrade (plausible.io free total 10 → paid 19, same version + same pillars, search presence 1→4) and surfacing it as a false "▲ +N since last scan" (a re-measurement artifact, not a gain). Only a **>7-day-stale** free layer is recomputed — fresh data is honest there even if the score legitimately moves; a same-week upgrade stays perfectly stable. Guards: `registry-score.test.ts` (`unifiedHeadline` stable free↔paid incl. WITH `keywordsRanked`; `discoverabilityScore` geomean; `findabilityFloor` monotonic + saturating) + `score-calibration.corpus.test.ts` (band separation over REAL captured footprints — no false-low for a broadly-ranking site, no false-high for the footprint-less; mutation-proven) + `free-layer-freshness.test.ts` (the 7-day gate, mutation-proven) + `documented-invariants.test.ts` (v6 pin). **History:** v4 (2026-07-09) was the on-site-only headline (stable free↔paid but dishonestly high for invisible-in-search sites); v5 (2026-07-11) folded in search presence as the *second half of the same free-computable pair* (stays free↔paid stable, unlike PR #36's v3 which folded in *paid-only* off-site signals and dropped the score on upgrade, free 74 → paid 66); v6 (2026-07-26) floors search presence by the RAW ranked-keyword footprint so a broadly-ranking site can't read "Invisible" on a classifier miss — same free↔paid stability, closing the false-low half of the "one red rule" (the false-HIGH half — a tidy-but-thin page reading on-page 98, e.g. trustmrr — is a deferred on-page-curve follow-up, NOT in v6). `headlineScore`/`headlineFromRows`/`HEADLINE_SCORE_VERSION=4` are UNCHANGED — they remain the on-page driver; `classify`/`computeSearchVisibility` are UNCHANGED — the frozen classifier.
2. **Cost caps + FULL spend attribution.** *Every* cost-bearing call — LLM or data — must be attributable to a **scan**, and through `users.app_ids` → `scans.app_id` back to a **user**. Nothing spends money anonymously. Two mechanisms, both required:
   - **LLM (Anthropic):** `callModel` writes a `pipeline_runs` row keyed by scanId; `scans.cost_cents` is the rollup. A caller may pass `scanId: null` — it then **inherits the ambient costed step via `currentScanId()`** (`lib/scan/cost-context.ts`), so drafts/synthesis attribute without threading a scanId through ~15 generator signatures. A `pipeline_runs.scan_id = NULL` row means money spent that no scan and no user can be billed for — that's the bug this closes. Guard: `cost-context.scanid.test.ts`.
   - **External (DataForSEO + Tavily):** every cost-bearing caller runs under a cost context (`costedStep` / `costedIntelStep` — guard: `app/api/costed-routes.test.ts`, which pins the exact route list incl. the paid `content-draft` + `distribute/draft`) so spend attributes to a scan row.
   Because BOTH now ride the same context, wrapping a route in `costedStep`/`costedIntelStep` attributes its LLM *and* data spend at once. Caps: LLM/tool side (`ScanBudget`) 60 tool-calls; cents free 20 / full 250 / weekly 120; `BudgetExceededError` on breach. Both heavy cost points (deep scan + competitor-select) bounded to `MAX_SELECTED=5` rivals, de-duped only by per-domain caches. Plus a **per-scan SOFT cap** (free 25¢ / paid 150¢, `EXTERNAL_SCAN_CAP_CENTS_*`) bounds it: on breach `recordExternalCost` flips a flag (**never throws** — degrade, never invent), the pipeline's checkpoints (`externalCapBreached`) skip remaining external enrichment (market pass), and the scan is stamped `external_cap_hit_at` (visible on `/app/diagnostics`). Guards: `cost-context.test.ts` (breach semantics) + `documented-invariants.test.ts` (cap defaults). See `docs/architecture.md` §4.3.
3. **Don't-cache-empties.** Never cache an LLM-failure `[]`; refuse stale blank rows on read-back (`isEmptyDemandIntel` / `buyerInsightsEmpty`). Extended (Task 2b, 2026-07-19 — the cache-poisoning class fix): a cached sheet also carries a **policy version** (`POLICY_SUFFIX_BY_KIND` in `lib/scan/fact-sheets.ts`, stamped onto `fact_sheets.model_version` for policy-gated kinds); a policy bump invalidates every sheet cached under the old policy on read-back, even inside its TTL. Originally introduced as `GROUNDING_POLICY_VERSION` for the `review_themes` kind (`lib/scan/adapters/web-reviews.ts`) — the fix for a stale pre-WS-A sheet (cached 2026-07-16) still being served after the fetch-layer filter tightened. **`review_themes` and `GROUNDING_POLICY_VERSION` were retired M3b (2026-07-23, O-7)** — the mechanism now has one live member, `relevance_verdicts` (`RELEVANCE_JUDGE_VERSION` in `lib/scan/fact-sheet-kind.ts`, Phase B's LLM relevance judge). Guard: `lib/scan/fact-sheets.test.ts`.
4. **Always-insight action floor.** `topUpActions`+`linkSignalKeys` floor the plan to `MIN_ACTIONS` with deterministic fixes; the **market-aware re-floor** re-runs after market signals attach (the earlier floor ran with `market:null`). Floor cards bypass the critic by design.
5. **Per-category floor.** Every active category (a pillar with a weak measured signal) keeps ≥1 surviving safe action after the §11 cap. Enforced in **production** by `ensurePerCategoryFloor` (`lib/scan/action-linking.ts`), wired into `full-scan.ts` at both floor points — not just the eval. Guards: `action-linking.test.ts` + `tests/eval/golden-set.eval.test.ts`.
5a. **Impact honesty.** Every action's `expectedOutcome.delta` (the "+N pts" shown/sorted on) is the model-computed signal shortfall (`pillarWeight × signalWeight × (100−normalised)` over the card's linked signals), NEVER the LLM's free-choice number — `recomputeActionImpacts` overwrites the generated `delta` after signal-linking. `outcomes.observed_delta` stores the REAL post-completion gauge movement (new − prior), not the prediction (`verify.ts`). Guard: `action-linking.test.ts`.
5b. **Paid-intel gate.** Every cost-bearing authenticated route (`/api/app/intel`, `/api/app/intel/stream`, `/api/competitors/select`, `/api/competitors/candidates`) calls `assertPaid` before any gather — the `/app` UI paywall does NOT protect the APIs. Guard: `app/api/entitlement-gates.test.ts` (source tripwire).
6. **Brand-ambiguity: discovery-only.** Competitor gap is built ONLY from the category-validated discovery set (`facts.competitors`). The raw "alternatives" extract may enrich matching names but must NEVER add competitors (acquire.io vs acquire.com class of bug).
7. **§11 algorithm safety.** Outreach cap 5 · divergence 0.92 · 1 action per evidence-host · every card `draftRequiresEdit=true` (no auto-send). `lib/scan/algorithm-safety.ts`.
8. **Abuse rate limit.** 10 scans / IP-hash / hour, 15-min in-flight window; only the IP hash is stored (`lib/scan/abuse.ts`).
9. **Terminal-status resilience.** A pipeline failure must leave a renderable `degraded` partial, never a permanent ACTIVE status.
10. **Deep-pass sentinel is `scans.deepened_at`** — NOT `report_payload` (both tiers write that now).
11. **Grounding honesty — degrade, never invent.** No synthesized field may assert evidence we did not gather. When an input fact sheet is empty, the dependent field is empty/absent and its UI section does not render — never a plausible synthesis. **M3b (2026-07-23, O-7) retired the `review_themes` producer entirely** — reviews are no longer gathered for either tier, so `runSynth` now **UNCONDITIONALLY** wipes `positioningMirror.reviewsValue`/`actualAudience` after every parse (`lib/llm/synth.ts`), independent of any sheet's emptiness; the **renderer** still omits an ungrounded section (`to-results-props.ts` blanks the Positioning Mirror when `actualAudience` is empty). Guard: `lib/scan/grounding.test.ts` (reduced to the unconditional-wipe assertion). The adapter-level SUBJECT-VALIDATION machinery this invariant used to lean on for review evidence (`fetchWebReviews`/`filterSubjectResults`/`parseWebReviewSnippets`/`reviewCountFromSnippets`/`GROUNDING_POLICY_VERSION` in `web-reviews.ts`) was cut in the same change — **but the underlying domain-conflict rule (`referencedDomains`/`dropDomainConflicts`) survives** as a separate, still-live producer's guard: the recent-buzz Tavily NEWS search in `lib/scan/gap/run.ts` is exactly as brand-ambiguous as the old reviews search, and keeps the same "drop a same-brand different-domain hit" rule (weaker than the retired reviews gate — press rarely writes domains and buzz feeds an aggregate count, not rendered quotes). Guard: `web-reviews.test.ts`. **History (pre-M3b, when review_themes still existed):** the adapter SUBJECT-VALIDATED web-review search results (WS-A v3, 2026-07-19 evening — a review result referencing a same-brand different domain was dropped, reachkit.app vs reachkit.ai scan `4093f1c9`; a result hosted ON the subject's own domain was never a review; every kept result required explicit DOMAIN-level subject evidence — a bare brand-NAME match was never attribution). v2's weaker rule — host evidence only when the batch was "contested" — was poisoned LIVE (fact_sheets id 110): review platforms key products by NAME (capterra/p/…/Reachkit), so a batch with no conflicting domain TOKEN read as uncontested and the brand-token fallback cached reachkit.AI's "Features 5/5" as reachkit.app's reviews under a fresh policy stamp. Root shipped violation (scan `6d49d58e`, 2026-07-16): a free scan of the unlaunched reachkit.app produced invented user reviews (*"Users consistently praise ReachKit…"*) and an `actualAudience` rendered under "Your page reads as", on a product whose hero reads *"Every claim grounded in your live page"*. Root cause: Tavily `answer` ingested as review #1 (`web-reviews.ts`) + no empty-sheet guard at synth. Invisible to tests because `FIXTURE_REVIEW_THEMES` always had 4 themes and no fixture took a scenario argument. M3b closes this class permanently for reviews by removing the producer rather than continuing to patch its adapter-layer filter.
12. **The public scan surface is always a free preview.** `app/api/scan/route.ts` (the marketing scan box + the shared-report auto-start — NOT the in-app `/api/app/scan-current`) creates `tier='free'` for **every** viewer, anonymous or authenticated or paid; it never deepens (`resolveProductScan(url, { paid:false })` → no `deepen` plan; no `ensureDeepScan`) and never enrols the URL (`linkScanToUser` removed). Deep scans + product tracking happen **only** via the deliberate `/app/add` and post-checkout provision paths. This is surface-driven, not viewer-driven — the fix for the cardpointers leak (a paid viewer's *preview* ran a 66¢ deep scan + auto-tracked a third-party URL, 2026-07-18). **Paired cost invariant:** every scan step's external soft cap derives from the TIER via the one seam `externalCapCentsFor(step, tier)` (`lib/scan/scan-caps.ts`) — no step hard-codes the full 150¢ cap for a free scan (the collect step used to, so a free scan could overspend its 25¢ ceiling; the sender now stamps `tier` onto the `scan/requested` event). Guards: `app/api/scan/route.tier.test.ts` (paid viewer → `tier='free'`, no deepen/enrol; mutation-proven), `lib/scan/scan-caps.test.ts` (free scan capped at the free ceiling on every step it runs), and the operational `tests/integration/scan-requested-e2e.test.ts` (a free scan runs the lightweight path only — `deepened_at IS NULL`, 0 monitors/actions, cost ≤ free cap; runs every build in CI `eval-integration`). Optional live complement: `pnpm check:live` §6 (opt-in `LIVE_SCAN_SMOKE=1`, real-adapter free-scan reaches `done`).

## Hard rules for working in this repo

- **Fix the CLASS, never the case — and keep the process simple.** (Owner rule, 2026-07-17.) Every change must improve the *process*, not patch the instance that happened to surface. Before fixing, name the class: "what else fails this same way?" — then fix all of it, once. A fix that resolves the reported symptom and leaves its siblings standing is not done, and a fix that adds an edge case to an already-branchy path is a regression even when it works. The user-facing processes (onboarding above all) must stay **straightforward and simple** — one entry point, one path, no special-casing per tier/product/entry. When a fix needs a new special case to work, that is the signal the underlying process is wrong; fix the process. Shipped instances of the anti-pattern this rule exists to stop:
  - `735dbae` "fixed" the dashboard Outreach row by **rewording its dead-end copy** — but the row is structurally unreachable (`headlineScore` filters to `FIXED_BASIS_SIGNAL_KEYS`: 5 SEO + 3 content, **zero outreach**, so `outreach.assessed` is always false). The case (bad copy) was patched; the class (a branch that can never render) survived.
  - The competitor step was made first-app-only (`shouldBlockSetup`'s `appCount <= 1`) so product #2 wouldn't inert product #1 — special-casing the symptom. The class fix was to move the step **per-product into `/app/add`** so the special case disappears entirely.
  - Two upgrade paths drifted until only the anonymous one deepened (`webhook.ts` returns before `provisionCheckoutUser`). One policy, shared, is the fix — the same shape as `resolveProductScan` retiring the `/api/scan` vs `addFirstTrackedProduct` dedupe split.
  - The **public** `/api/scan` route decided a scan's tier from the *viewer's plan* (`viewerIsPaid ? "full" : "free"`) and unconditionally `linkScanToUser`'d — special-casing the surface per auth-state. So a logged-in growth user pasting a third-party URL (cardpointers.com) into the *free* marketing scan box got a 66¢ `tier='full'` DEEP scan silently billed AND the URL auto-enrolled as their tracked product (2026-07-18). The class fix: the public surface is **surface-driven, not viewer-driven** — always `tier='free'`, no deepen, no enrol, for everyone (invariant #12). Deep scans + tracking are `/app/add`/checkout only. No per-auth branch survives.
- **Never pay for data you don't render.** (Owner rule, 2026-07-17.) *"There should never be data that we call from DataForSEO or Tavily or LLMs that is not used for rendering the output. There is no point in wasting money on data that we store and never show to a user."* Every cost-bearing call must terminate in something a user SEES. Before adding one, name the surface that renders it; if you cannot, the call must not exist. Before deleting a render, check whether it orphans a call — then delete the call too. This binds in both directions and applies per-FIELD, not per-call: fetching 50 keywords to render 8, or paying for 8 seed volumes to itemise only the 3 unwon ones, is the same waste at smaller scale. Write-only data is a defect even when it is cheap, because it is spend with no possible payoff — the 7 retired write-only intel tables (`20260708120000_retire_dead_intel_tables.sql`) were this rule applied before it had a name. Corollary: **degrade, never invent** already forbids fabricating what we failed to fetch; this forbids fetching what we never show. Enforced by **G9** — the paid-data ledger (`lib/scan/cache/paid-data-ledger.test.ts`): every cost-bearing `cached*` wrapper must have a live consumer that CALLS it, and a new wrapper without a ledger entry fails (the costed-routes idiom, applied to adapters). Instances found and **closed** by this program: `categoryCapturedSearches` (the score aliased under a "you capture X%" label — deleted, WS1/G1); `categorySeeds` volumes where only the *unwon* seeds reached the page (all phrases now render, WS2/G4); and `cachedDiscoverCompetitors` (a `dc:*` size-banded cohort fetched, cached, rendered nowhere — the prod pipeline uses the closeness-ranked cohort; deleted 2026-07-17, G9). Still open: nothing has swept the *field* level (fetching 50 keywords to render 8 is the same waste at smaller scale) — G9 is per-wrapper, not yet per-field.
- **A rendered number must measure what its label says.** (Plan B §7, 2026-07-17 — the free-scan number-honesty class; one keyword engine.) Every metric that crosses into a component means exactly what its label claims: it is never an **alias** of another metric, never its own **fetch limit** dressed as a total, and a **sampled** number always renders its sample basis. One concept has **one name** product-wide. The strong harness was blind to this — `captureRate = score` and `keywordsRanked = 50` are true-by-construction and passed every gate — so it ships as its own guard family, each **mutation-proven**: **G1** no metric aliases another · **G2** no metric equals its fetch limit (`footprintComplete` is the honesty flag) · **G3** a sample discloses its basis · **G4** `categoryDemand === Σ categoryPhrases` and every phrase renders · **G5** comparative copy ("the weaker half") is conditional · **G6** signal counts are computed, never a literal · **G7** ONE demand vocabulary — the bare phrase "monthly searches" (four different computations, §1.9) is retired from every production demand surface. (**G8** — the external cap fires on a single-RUN overspend — is Phase 7, not landed.) The paired structural fix is **RC1: ONE keyword-brand detector** (`lib/scan/referral/brand-keywords.ts`) shared by the free footprint classifier (`search-visibility.ts`) and the paid keyword-gap filter (`lib/scan/referral/keyword-gap.ts`) — the two forked it and **drifted** (different tokenizers/thresholds classed the same keyword differently). Canonical semantics are **free's**, so the persisted v5 score never moves (invariant #1). Guards: `lib/scan/search-visibility.test.ts` (G1–G4, G6, G7) + `lib/scan/referral/brand-keywords.test.ts` (RC1: both engines route through it, neither may re-fork). **History:** shipped live — `resend.com`'s free report printed the search-presence score twice ("Search presence 81" beside "You capture 81%"), rendered `keywordsRanked = 50` for a domain that ranks for 2,100, and claimed "18 signals" where 9 were measured. **Ratchet (2026-07-18, the SpaceX class):** "category demand" was `Σ(the LLM's category seed phrases)` — for spacex.com the LLM named 2 narrow phrases (`launch services` 8,100 + `commercial space launch` 70 = 8,170), so the headline read "8,170 searches/mo across your category" for a site that ranks **#12 for "space" (368k/mo), #10 for "space launch system" (110k), #4 for "rocket launch" (74k)** — data the SAME scan already had in `categoryRanked`. G4 passed (8,170 == its 2 phrases) because it only checks arithmetic reconciliation, not whether the phrases REPRESENT the category. Fix: `computeCategoryDemand` now MERGES the site's real category rankings (`sv.categoryRanked`, classified from the one `ranked_keywords` call — **no new data call/cost**) with the seed volumes — ONE scale-invariant rule (real rankings dominate for a big site; a 0-ranking site falls back to the seeds, unchanged). Opportunities carry the site's `yourPosition`, so "where you are today" renders "#12" (a real, discoverable near-miss) not a bare "Not winning". **Invariant #1 untouched** — `sv.score` is computed from the classified rows, NOT from these demand fields, so the persisted score never moves (verified: registry-score + v5-parity eval green). Guard: `search-visibility.test.ts` ("merges the REAL category footprint (scale-invariant)", mutation-proven). **Ratchet (2026-07-19, the classification-corpus — the reason this class kept recurring):** G1–G7 checked arithmetic/aliasing on SYNTHETIC or ≤12-row hand-made inputs and **never ran the classifier against a realistic footprint**, so classification errors were invisible by construction — SpaceX AND x.com shipped the same way. x.com: brand `0%` (its brand "x"/"twitter" undetectable), and **"google" (101M/mo), "fox news", "usps" classified as x.com's CATEGORY → rendered as "your biggest untapped opportunity"**; savvycal: its whole footprint of "what time is it in hawaii" timezone lookups became "category" via the generic token **"time"** in its prose. Root: `classify` flipped a whole phrase to category on a **single shared unigram**, and `buildVocab` fed it noisy prose tokens ("google", "time"). Fix: `buildVocab` now drops **generic + mega-brand/entity tokens** (`GENERIC_TOKENS` + `MEGA_BRAND_TOKENS`) from the category vocabulary UNLESS the LLM's own category seeds used them (so "time" defines a time-tracker but not savvycal; "space" defines SpaceX; "google" defines no one), and `classify` sends a keyword that IS a mega-brand off-topic outright. The **ratchet** is a machine-checked calibration corpus: `lib/scan/classification-corpus.test.ts` runs the ONE shared `classifyFootprint` (also used by the live gather — no forked replica) over REAL captured footprints (`lib/scan/fixtures/classification-corpus/*.json`: x.com, savvycal, resend, spacex) and asserts the split every build. A new misleading result → add its domain + the correct expected split; expectations only tighten (never weaken). Mutation-proven (disable the pollutant filter → 5 fail). Invariant #1 holds (classifier runs identically free & paid — v5-parity green). **KNOWN residual:** x.com's `brandPct 0` is NOT fixed here — its brand is unrecoverable because the SPA fetch fed the extract garbage (it thinks x.com is "a browser extension"); that is a fetch-layer fix (Part C), not classification. **G10 (2026-07-19):** a locked-content teaser count derives from the SAME collection its adjacent section renders (never a sibling metric — "Unlock all 0" class); the market ladder's per-tier demand reconciles to its rendered phrases (G4-per-tier). Guards: `results-screen.render.test.tsx` (mutation-proven) + `search-visibility.test.ts`. **The macro rule (2026-07-19 evening):** `classify` now requires EVERY non-generic token of a keyword to be vocabulary-supported — brand match, or a mega-brand bigram-join, or every remaining token individually corroborated by the subject's own vocabulary/LLM seeds — so an entity phrase fails structurally the moment ANY of its tokens lacks support, no blocklist entry needed for the next unlisted case (the shipped "fox news" bug: a legitimized "news" seed let the whole phrase ride on one supported token under the old any-shared-token rule). `MEGA_BRAND_TOKENS` is defense-in-depth only, not the primary mechanism, now that the macro rule forecloses unsupported entities on its own. This class cuts both ways: fixture `seedText` must be capture-accurate (the react-email lesson) — an incomplete seedText starves the classifier of real vocabulary support and flips the subject's OWN sub-brand to a false off-topic, the inverse of the false-category bug this rule exists to stop.
- **Look for what nobody is looking for.** (Owner rule, 2026-07-17.) Do not stop at the reported symptom. Every investigation must actively hunt the angles *not* raised: the sibling path with the same defect, the guard that cannot bite, the metric that is silently garbage, the branch that never runs. Report those findings explicitly even when they are outside the ask — they are usually worth more than the ask. Verify each one against reality (live data, a live render, the DB) before reporting it; an unverified hunch reported as a finding is the dishonesty the rule below forbids. Found this way and invisible from the symptoms: the in-app upgrade never deepening, the magic link silently skipped on a Stripe-ordering race, `deepened_at` scans reporting a 6-day wall clock, the stale-`done` SSE replay.
- **A guard you have not SEEN FAIL is not a guard — verify the effect, never a proxy for it.** This is the generalisation of the two rules below, and it is the failure this repo keeps re-learning. Three shipped instances: `bless:design` certified an AppShell card that said "Progress" for weeks after the live nav became "History" (it re-pins a hash — it verifies *nothing*); the `add-product-policy` tripwire asserted `lib/app/add-product.ts` contains `resolveProductScan` — a file that **defines** it, so the assertion was true by construction and could never catch the drift it existed to catch; the same tripwire's other half was then mutation-proved still vacuous (delete the call, keep the import → passed 3/3). The discipline, non-negotiable:
  - **Check the rendered/actual effect, not the source.** A source match is satisfied by *code*: `active={activeKey === "history"}` "contains" History; an import, comment, type-only reference or dead branch "contains" a symbol. This is why the label-drift gate compares the **prerender**, and why source tripwires must go through `expectCallsSymbol` (`lib/testing/tripwire.ts`), which **refuses** an assertion that is true by construction.
  - **Prove every new guard bites**: break the production code it guards, watch it fail with real output, revert, confirm green.
  - **Verify the mutation actually applied** (`git diff --stat` non-empty) *before* trusting the result. A no-op mutation that "passes" proves nothing — a `replace()` with zero matches printing success is how a vacuous test was certified as sound.
  - Applies to every gate, not just tests: a green check whose instrument you have not verified is an *unverified claim*, and reporting it as evidence is the dishonesty this file's honesty rule forbids.
- **Always live-test against REAL adapters before trusting a change.** Production ships ONE path (no fixtures flag — Phase 8). The injected fixtures (eval + `test:int` + code-review) return canned clean data and MASK real-adapter / LLM-on-mixed-content bugs — the `linear.app=22` SPA-fetch failure was invisible to the fixture suite. Verify by scanning a live site against a real deploy, never the test seam.

After a free-report change: deploy, scan a directory + a 0-ranking new product + a normal SaaS, then headless-render each (`chrome --headless --dump-dom --virtual-time-budget`) and read the actual text. **Never fabricate a number** — the LLM identifies the category (`categorySeeds`), DataForSEO supplies the volumes; when a call flakes, degrade (footprint/zero-state), never invent (the "fomc meeting"/keyword_ideas-expansion lesson). ## Claude Design & UI conventions (read before building any UI)

- **Data-driven, not word-driven (owner rule 2026-07-23, R-1.8).** ReachKit is a data app: show gaps/trends/performance as **the data itself** — bars, gauges, sparklines, deltas, positions, counts (the intel kit's `Gauge`/`Bar`/`Donut`/`KpiRow`/`DataTable`). NEVER a paragraph describing the data; when a surface can show a sentence or a chart/number, it shows the chart/number. Generated text collapses to labels. This is the positive half of R-1.7 (no LLM sentences) — that rule says "no prose"; this one says "show the number/chart instead." Every UI change is mirrored 1:1 in `ds-src` in the same commit.
- **Every number carries its label (owner rule 2026-07-24, R-1.9).** NO number ever renders "hanging loose" — a bare `88`, `66`, `19` with no adjacent word telling the user WHAT it measures. Every rendered metric shows its **name + scale/unit** at a glance (e.g. "Footprint strength 88/100", "1,425 keywords ranked", "Search presence 4/100"), never a naked figure the reader must reverse-engineer. This is the honesty companion to R-1.8: the data-driven rule says *show the number*; this says *and always say what the number is*. Applies to gauges, bars, chips, KPI rows, comparison rows — everywhere a figure appears. Especially: when a surface shows MULTIPLE scores on different scales (the dashboard's Discoverability / Market position / Footprint-strength trio), each must be unambiguously named so they can't be confused for one another (the "what is this 88?" walkthrough finding). Data-driven + always-labelled = a number a first-time viewer can read without a tooltip.
- **Tokens only — never arbitrary Tailwind values or raw hex.** The theme is the single seam: light in `app/globals.css` `@theme`, dark in the `.dark` overrides. Use the semantic tokens — Tailwind classes (`bg-surface`, `text-muted`, `text-accent`) or the CSS vars in inline styles (`var(--c-*)` semantic palette · `var(--color-*)` Tailwind theme · `var(--radius-*)`, `var(--elevation-*)`, `var(--font-*)`). NEVER `bg-[#6e56f7]`, `text-[13px]`, or raw hex — those break light/dark and drift from the system. Score-band colours are `--c-band-*`.
- **Mobile is a machine-checked gate, and inline styles are the trap.** `pnpm test:mobile` fails any route whose content spills a 390/360px screen — the whole app is mobile-clean, keep it that way. Both idioms here (captured HTML strings, and the `--c-*` intel kit) style with **inline `style=`**, which **beats every stylesheet rule** — so a media query silently does NOTHING to an inline `display:grid`/`grid-template-columns`. To make something responsive: (1) prefer an **intrinsic** collapse you can write inline — `repeat(auto-fit, minmax(min(100%, 280px), 1fr))` (the `dashboard-hero.tsx` idiom) needs no media query; (2) when a breakpoint is unavoidable, add a class hook and **move that property OUT of inline into a scoped `<style>`** (the `scan-hero.tsx` `HERO_CSS` idiom) — keep only dynamic/state styles inline; `!important` is acceptable ONLY inside a mobile media query overriding *captured* HTML you can't restructure. Two more repeat offenders: a **flex/grid child needs `minWidth: 0`** or its default `min-width:auto` pins the row to its content's min-content (this alone held the footer at 624px); and **a URL/host has no spaces**, so its min-content is the whole string — it needs `overflow-wrap:anywhere` (or `break-all`) or it forces the page wider than the screen. A half-applied transform looks *worse* than none, so always verify the computed style at the target width, never assume the rule landed.
- **Reuse before you build — the inventory is the map.** What exists, what's active vs archived, and each component's live counterpart is `.design-sync/INVENTORY.md` (25 active atomic components · 20 page templates · a few archived). In the app itself, the two component kits are: **shadcn / Base UI primitives** in `@/components/ui` (`base-nova` style, `@base-ui/react`, lucide icons — command, dialog, tooltip, sonner, skeleton, info-tip) and the **`--c-*` intel kit** `@/components/app/intel/kit.tsx` (`Card`, `HeroCard`, `Badge`, `Gauge`, `Bar`, `Donut`, `KpiRow`, `DataTable`, `Tabs`, `Eyebrow`, `EvidenceLink`, …). Check both before writing anything new.
- **Import paths / conventions** (from `components.json`): `@/components`, ui = `@/components/ui`, utils = `@/lib/utils` (the `cn()` helper = `clsx` + `tailwind-merge` — use it for conditional classes), lib = `@/lib`, hooks = `@/hooks`. shadcn style is **`base-nova`** (Base UI, not Radix); icons are **lucide-react**. Server Components by default (`rsc: true`).
- **Compose from existing primitives before introducing anything new.** A new component must first be attempted as a composition of the `@/components/ui` primitives + the intel kit + existing design-system components. Only add a genuinely new atomic component when no combination works — and when you do, add it to the kit/inventory and (for Claude Design) `.design-sync/ds-src/` + `INVENTORY.md` in the same change. **Claude Design specifics (reality-first):** the DS must reflect what actually SHIPS 1:1. A `ds-src` component is **active** only if its live counterpart is reachable from a real page — every active one carries a resolving `/* @mirrors <live-path> */` tag (primitives use `-`), enforced by `pnpm check:design`. Anything whose live counterpart is dead/unreachable is **archived** (`archived: true` in `layout.mjs`, delete-free — files stay, pane groups under Archive, exempt from mirror enforcement); NEVER `delete_files` to archive. Un-archiving requires giving it a resolving `@mirrors` or the check fails. The build regenerates `_ds_manifest.json` and the `_ds_sync.json` sentinel must be re-armed **last** on upload or the pane looks stale. Full workflow in `.design-sync/NOTES.md` + `INVENTORY.md`.

### Keeping Claude Design and the code in EXACT sync

**Direction of truth: code → Claude Design, never the reverse.** The app is the source of truth. Each `ds-src` component is a hand-authored mirror of a live file (its `@mirrors` target); the Claude Design project is a *rendered copy* built from `ds-src` and uploaded via `/design-sync`. **A change made only in the Claude Design pane is NOT real and is overwritten on the next upload** — use the pane for viewing/sharing/exploration only.

**To change a design for real, edit in Claude Code, then re-sync:**
- **Design language (colours, fonts, radii, spacing):** edit `app/globals.css` (`@theme` + `.dark`) AND `.design-sync/tokens.css` together — one token change propagates to the whole app + DS. `pnpm check:design` fails if the two drift.
- **A component/page's structure or copy:** edit the **live** component first (that's the product), then update its `ds-src` mirror to match, then rebuild + upload. Both in the same change.
- **Then push to the pane:** `node .design-sync/ds-src/build.mjs && node .design-sync/ds-src/layout.mjs`, run `/design-sync` (scoped to the changed `components/<Group>/**` + `_ds_manifest.json`, sentinel `_ds_sync.json` **last**), and `pnpm bless:design`.

**Four layers keep them matching:**
1. **Token/band parity** — `--c-*` in globals.css == `.design-sync/tokens.css`; `--c-band-*` == `SCORE_BANDS`. Hard-fails `check:design`.
2. **Mirror existence** — every active `ds-src` must carry a resolving `@mirrors`. Hard-fails.
3. **Mirror freshness** (movement) — `.design-sync/mirror-lock.json` pins a hash of each mirrored live file at last reconcile. When a live component changes, `check:design` prints `mirror STALE: live X changed since <Component> …` (a WARNING, so it never blocks unrelated work) until you review the DS card, update the `ds-src`, re-upload, and `pnpm bless:design`.
4. **Label drift** (content) — HARD-fails. Every user-visible label in a live component must actually be **RENDERED** by the card(s) mirroring it. Compared against `.design-sync/card-labels.json` (each card's rendered text, distilled from the prerender by `scripts/gen-card-labels.mjs`, committed so CI needs no DS build; each entry carries its `ds-src` hash, so editing a card without rebuilding hard-fails rather than checking a stale artifact). Total unrendered labels are pinned in `.design-sync/label-drift-baseline.json` — **only ever shrinks**. Re-pin with `node scripts/check-design-parity.mjs --pin-drift`.

> ⚠️ **`pnpm bless:design` re-pins a HASH — it verifies NOTHING.** Blessing a card that is *already* divergent certifies that drift as "fresh" forever. Layer 3 only ever answers *"did the live file move since we blessed?"*; it is structurally blind to a mirror that was never accurate. That blindness shipped real drift: the AppShell card said **"Progress"** for weeks after the live nav was renamed **"History"** (WS4), and `check:design` reported OK the whole time — including immediately after a bless. **Layer 4 exists because of that, and a bless cannot silence it** (proven by negative test: rename a live label → `check:design` exits 1; `--bless` does not clear it). Never bless a card you have not actually diffed against its live counterpart.

`@mirrors` proves the file exists; freshness catches "live moved"; **label drift catches "the card never matched"**. Layer 4 is *necessary, not sufficient* — it cannot see layout/structural fidelity, so a card can pass it and still look wrong. Full workflow: `.design-sync/NOTES.md` + `INVENTORY.md`.

## Requirement Intake Protocol (read before designing ANY substantive change)

Every **substantive** requirement gets an intake doc at `docs/superpowers/intakes/YYYY-MM-DD-<slug>.md` (template: `docs/superpowers/templates/requirement-intake.md`) **before design begins** — and its `docs/REQUIREMENTS.md` delta ships in the same PR. The template forces, in order: the verbatim requirement · a restatement with deltas called out · **clarifying questions asked and RECORDED first** (an empty list needs a stated reason) · the **permutation matrix** — tier (free/paid) × auth (anon/authed/owner) × entry surface (public `/scan` · `/app` · checkout/webhook · cron) × data-state (fresh/legacy/empty/pathological/wrong-subject), every touched cell covered or excluded-with-reason, **no blank cells** (the cardpointers leak was one unenumerated cell; the reflect.app crash another; the reachkit.ai reviews a third — every shipped class lived in an unenumerated cell) · acceptance criteria written first (the Acceptance clause's artifact lives here) · the class statement · the rendered-surface ledger.

**Substantive** = adds or alters user-visible behavior, a data contract (`report_payload` shape, DB schema, API response), a cost-bearing call, or tier/auth/entry-surface handling. **Not substantive** (no intake needed): copy tweaks within existing semantics, mechanical/typo fixes, guard-green refactors, test-only or docs-only changes, dependency bumps. When in doubt, it's substantive.

Anything the implementer cannot decide is recorded as an `OPEN(O-n)` row in `docs/REQUIREMENTS.md` §0 — the owner's push-list — and the stated default applies until the owner rules. Never resolve an OPEN item silently.

**Design token source of truth.** App tokens live in `app/globals.css` (`@theme` light + `.dark`). The committed DS mirror is **`.design-sync/tokens.css`** (parity-checked; `layout.mjs` copies it into the gitignored `ds-bundle/tokens/tokens.css` on build — it is no longer re-fetched from the remote project). To change a token: edit `app/globals.css` AND `.design-sync/tokens.css` together, then `pnpm check:design`. Score-band colors change only in `score-bands.ts` → mirror into `globals.css` `--c-band-*` (and thus `.design-sync/tokens.css`). New design-system component → add its `ds-src` file with a `/* @mirrors <live-path> */` tag.

**The Change Protocol.** To change an invariant, a token, or a layer boundary *on purpose*, update all of these **in the same commit**: (1) the source constant / token / rule, (2) its guard/parity check, (3) this file (`CLAUDE.md`), (4) `docs/architecture.md` if structural. CI enforces the mechanical half; this protocol names the human half. New invariant → it gets a guard (test, arch rule, or parity check) *before* merge, and this table is updated. Never delete a check without a documented reason in the commit body.

**Acceptance (corpus-first).** A user-visible change to the report additionally declares its acceptance criteria BEFORE implementation: the observable outcome on the report corpus (`lib/scan/fixtures/report-corpus/`) — a new/updated per-fixture expectation or a new rubric rule (`lib/testing/report-rubric.ts`) — written first, watched fail, then made green by the implementation (TDD at the product level; the discipline that made the classification corpus the one place a failure class actually stopped recurring). A user-visible change with no corpus-expressible outcome states why in the PR body. Fixtures are captured VERBATIM from live scans (`pnpm capture:report <scanId> --archetype=…`), never hand-authored or pruned (the react-email lesson); the corpus and `RUBRIC_RULES` only grow, suppressions only shrink, expectations only tighten. Rationale: every pre-existing gate (G1–G10, invariant #11/#12) was created AFTER a shipped failure that the owner found by reading live renders — the acceptance oracle was human, late, and expensive. This clause moves the oracle to pre-merge: expected outputs exist before the change does.

**The feedback fast path (report-quality feedback → a durable gate, one workflow).** When the owner says a rendered report "feels wrong" — too small, too thin, not credible, cluttered — the durable form is a corpus threshold, not a per-site patch: (1) `pnpm capture:report <scanId> --archetype=…` freezes the offending render verbatim; (2) a rubric rule or per-fixture expectation in `lib/testing/report-rubric.ts` encodes the judgment as a threshold (magnitude R9, terseness R8, honesty R1–R7) and is watched FAIL on that fixture; (3) the implementation makes it green; the corpus only tightens. This is why "these numbers seem too little" (trustmrr, 2026-07-21) became **R9** the same session instead of another token heuristic — the quality dimension had a durable home (the Quality Contract, `docs/REQUIREMENTS.md` §12) so the feedback landed as a machine check, not prose. Prefer this over editing generator heuristics whenever the feedback is about what the RENDER shows.

**The Feedback Protocol.**
1. **User feedback is always made durable.** A correction or preference from the user is recorded where it survives the session: a rule in this file when it's a way of working, an invariant + guard when it's load-bearing behavior, `docs/architecture.md` when it's structural, memory otherwise. "Noted" without a durable write is not taking it on board.
2. **Contradictions are raised, never silently resolved.** When a new instruction conflicts with a documented invariant, hard rule, or protocol here, surface the conflict explicitly — quote the existing rule and the new instruction — and ask which wins before proceeding. Never silently comply (that breaks the ratchet) and never silently ignore (that breaks trust). If the new instruction wins, apply the Change Protocol: rule, guard, and docs updated in the same commit.
